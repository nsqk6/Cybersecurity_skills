## I — 方法论骨架 (Interpretation)

这个能力解决的是：写一个会在后台、cron 或无人值守环境跑的 shell 脚本，如何让"失败可见、结果可信、不会写坏文件、不会烧资源、不会在错误目录以错误身份闯祸"。shell 是解释执行，报错点常常不是出错点，且很多失败是静默的——这决定了可靠性不能靠"跑一遍看着对"，而要靠结构化的纪律。

机制分五组。第一组是调试定位：报错时回看整段结构（`do`/`done`、`fi`、引号配对）而非只盯疑问行；用 `set -n` 过语法、`set -v` 看读入行、`set -x` 看展开后的命令，关闭用 `set +x`（作者特别提示与直觉相反）；取退出码先 `rc=$?` 存下来，别让中间插入的 `echo` 把失败伪装成成功。引号用两条实用规则：含变量默认双引号，需要字面 `$`/反引号/`\` 改单引号，穷举三种引用试错成本低于推理成本。

第二组是输出与完整性：合并多份来源时用 `cat a b 1>merged.out 2>merged.err` 把 stdout/stderr 分离，"错误文件是否为空"这一个判据就能回答"数据齐不齐"；决定合并时记住 shell 从左至右求值，`cmd >file 2>&1`（`2>&1` 在后）才是两类都进文件，`2>&1 >file` 会把错误留在屏幕；给 sort 这类"参数即文件名"的命令写重定向时符号前留空格，避免 `>` 被解析成参数。逻辑未验证前用 `tee out.txt` 边看边存，确认正确再改纯重定向，且同名文件可能被覆盖要留意。

第三组是动作闸门：不可逆动作（rm -r、覆盖、mv）用 `&&` 钉在前一步成功之后（`mv src dst && rm -r src`），失败即短路；用 `|| exit`/`|| 发邮件` 兜底失败分支；多个失败后动作要用 `{ 邮件; exit; }` 组合，否则 shell 只执行最后的 exit。管理/删除类脚本开头放三重守卫：查 `LOGNAME`/身份、查当前目录、查 `$#` 参数个数，全过才进入破坏性主体（但 `$LOGNAME` 可伪造，不能作唯一依据）。

第四组是循环与资源的幂等：轮询/监视循环体内必须 `sleep` 节流，告警分支末尾必须 `exit`，否则条件持续为真会邮件轰炸；跨脚本传递用 LCK 锁文件——生产者建、结束删，消费者 `until [ ! -f LCK ]` 等待，避免读到半成品。临时文件名加进程号 `$$` 后缀（`TMP=/tmp/name.$$`）保证并发不互相覆盖，配 `trap 'rm -f $TMP' EXIT` 在中断/退出时清理。关键处理段（写多文件、改配置）在临界区前 `trap "" 1 2 3 15` 屏蔽信号、退出后 `trap "my_exit" 1 2 3 15` 恢复捕获，防止 Ctrl-C 留下半写入状态；信号 9 无法屏蔽。

第五组是失败记录：把 `logger` 放进捕获信号的退出函数，脚本异常退出就在系统日志留下带用户/进程信息的记录，管理员看日志即可发现失败的后台任务。还有一条独立纪律：用 shell 循环 + expr 做累加时，所有变量必须在循环外初始化（`LOOP=0`），否则 expr 报"需要数值参数"并刷屏，淹没真正结果。

## A1 — 应用示例 (Application Example)

### 示例 1: echo $? 吃掉退出码
- **类型与来源**: 【转述】作者经验，《Linux与unix shell编程指南》第23章 调试脚本
- **问题/输入**: 批量任务脚本里想检查命令是否失败，写成 `cmd; echo $?`，却总是看到 0。
- **方法论的使用**: 原因是 `echo` 本身返回 0，读到的是 echo 的退出码而非 cmd 的。改为 `cmd; rc=$?; echo $rc`——先存再显示。配合 `set -x` 看展开后的命令、`set -n` 先过语法；报错时回看整段结构而非只盯疑问行。
- **结论**: "检查动作本身失效"是批量任务"失败不可见"的主要来源；作者列出的常见错误还有漏写引号、`[: missing ']'`、for 列表漏 `$`、变量大小写不一致（"大多数错误是由于使用变量时大小写保持不一致"）。
- **结果**: 原书为作者经验转述，未给具体数值结果。

### 示例 2: 合并 stdout/stderr 的顺序陷阱
- **类型与来源**: 【例题】《Linux与unix shell编程指南》第5章 5.9
- **问题/输入**: 后台 cleanup 脚本想把所有输出和错误都存档到 cleanup.out。
- **方法论的使用**: 必须写 `cleanup >cleanup.out 2>&1`（`2>&1` 在后）：先把 stdout 指向文件，再让 stderr 跟随当前 stdout（即文件），两者都进文件。若写成 `2>&1 >cleanup.out`，先把 stderr 指向当时的 stdout（屏幕），再把 stdout 转向文件，结果错误仍留屏幕、只有正常输出进文件。
- **结论**: shell 从左至右逐项求值重定向；顺序颠倒导致错误在屏幕一闪而过、"特别是你不在的时候"无法追溯。
- **结果**: 原书给出 `cleanup >cleanup.out 2>&1`、`grep "standard"* > grep.out 2>&1`。

### 示例 3: 磁盘容量监控两次触发两次邮件
- **类型与来源**: 【例题】《Linux与unix shell编程指南》第18章 18.6.1
- **问题/输入**: 一个 until 循环监控 /logs 容量，达到 90% 就发邮件给超级用户。
- **方法论的使用**: 循环体内加 `sleep` 节流避免烧 CPU；告警分支末尾加 `exit`，否则容量持续 >90% 条件保持为真，会不断发邮件。涉及跨脚本时用 LCK 锁文件：生产者结束删 LCK，消费者 `until [ ! -f /tmp/monitor.lck ]` 等待后再处理报表，避免读到半成品。
- **结论**: 无 sleep → 资源耗尽；无 exit → 邮件轰炸；不等 LCK → 处理到不完整数据。
- **结果**: 原书示例为监视 /logs 容量达 90% 发邮件后退出；未提供真实运行数值。

### 示例 4: $$ 唯一临时文件 + trap 清理
- **类型与来源**: 【例题】《Linux与unix shell编程指南》第26章 26.1.2 / 26.3.2
- **问题/输入**: 一个脚本要用 /tmp 下的临时文件存 df/ps 输出，可能被并发调用、可能被 Ctrl-C 中断。
- **方法论的使用**: 定义 `HOLD1=/tmp/hold1.$$`、`HOLD2=/tmp/hold2.$$`（进程号后缀保证并发唯一）；用 `trap 'rm -f $HOLD1 $HOLD2' EXIT` 在正常/异常退出时清理；结束时 `rm /tmp/*.$$` 只删本进程后缀文件。
- **结论**: 用固定临时文件名会被并发实例覆盖、中断后残留；`$$` 只在本进程唯一，跨进程复用同一清理模式会误删（作者明确提醒"该进程号只在当前进程中唯一"）。
- **结果**: 原书示例 HOLD1.$$/HOLD2.$$ 存 df/ps 输出，Ctrl-C 时 trap 清除。

### 示例 5: 三重守卫（合成演练）
- **类型与来源**: 【合成演练】按本卡 E 段规则推演，依据《Linux与unix shell编程指南》第18章 18.3.6/8/12 单元
- **问题/输入**: 要写一个会 `rm -r` 全局文件的管理脚本，担心在错误目录、以错误身份、缺参数时运行。
- **方法论的使用**: 脚本开头依次测 `LOGNAME` 是否为 root、当前目录 `$(pwd)` 是否等于预期、`$#` 是否达到要求；任一不符则打印用法并退出；全过才进入破坏性主体。
- **结论**: 三类检查是把爆炸半径约束在启动前的通用守卫框架；但 `$LOGNAME` 可被伪造，不能作唯一安全依据。
- **结果**: 按规则推演得到带守卫的脚本骨架；原书未提供此具体案例的真实执行结果。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 要写一个在后台/cron/无人值守环境运行的脚本，失败时没人盯着屏幕，需要事后能发现它失败过。
2. 脚本里有删除、覆盖、全局移动这类不可逆动作，需要在启动前约束身份、目录、参数，在执行时用返回码做闸门。
3. 脚本报错但看不出哪错，或者"跑完没输出/静默什么都不做"，需要系统化的调试手段。
4. 脚本要合并多份来源/输出，担心数据不齐或错误混进数据，需要完整性校验。
5. 脚本里有轮询/监视循环，或者要写多文件、改配置的临界区，担心烧 CPU、邮件轰炸、中断写坏文件。
6. 会创建临时文件、可能被并发调用，担心互相覆盖或中断后残留垃圾。

### 语言信号（出现这些就该激活）
- 中文：「脚本跑完没输出」「脚本报错但看不出哪错」「后台脚本的日志怎么没有报错」「合并后数据对不上」「2>&1 放前面行不行」「确认成功再删除」「脚本删文件很危险」「监控脚本一直发邮件」「轮询太耗 CPU」「等另一个脚本写完再读」「临时文件名怎么不冲突」「脚本中断留垃圾」「脚本被中断写坏文件」「别让 Ctrl-C 打断」「脚本循环里数字算不对」
- English: "shell script silently does nothing", "redirect stderr order", "only delete if copy succeeded", "log script failure syslog", "unique temp file pid", "critical section trap", "expr non-numeric argument loop", "script safety guard root args", "merge logs completeness"

### 与相邻能力的区分
- 与 `batch-file-operations` 的区别：相邻卡是命令行上一次性批量操作的现场防护（空跑、备份、传参），本卡把防护固化进脚本结构（守卫、&&/|| 闸门、trap、临时文件）。脚本里的删除动作两者可叠加。
- 与 `text-processing-pipeline` 的区别：相邻卡搭一次性排查管道出结论，本卡是把流程固化成可长期运行的脚本并保证其健壮。
- 与 `host-timeline-forensics` 的区别：两者都涉及 history 与日志，但本卡是"怎么写健壮脚本/怎么记录脚本失败"，相邻卡是"怎么从 history 和日志溯源入侵时间线"。

## E — 可执行步骤 (Execution)

**必需输入**: 脚本要完成的任务与运行方式（前台/后台/cron）；是否含不可逆动作；是否有循环/并发/临时文件；期望的成功与失败判定。缺"运行方式"必须先问——无人值守与交互式对失败可见的要求完全不同。

**交付物与完成标准**: 一份带调试/守卫/闸门/清理结构的脚本 + 一份失败可见性说明（失败会在哪留下记录）；完成标准是人让触发条件持续为真时不会重复告警、中断不会留半写入状态、不可逆动作前有闸门。

1. **调试结构就位**
   - 做什么：语法检查 `sh -n script`；必要时用 `set -v`/`set -x` 跑一遍（关闭用 `set +x`）；取退出码先 `rc=$?`；报错回看整段结构；变量含字符串默认双引号、按需换单引号。
   - 完成标准：能定位报错根因而不仅是报错行；`$?` 不被 echo 吃掉。
   - 判停：变量大小写不一致/漏引号导致空值继续跑 → 先修这些"静默错误"再继续。

2. **输出与完整性设计**
   - 做什么：合并来源用 `1>out 2>err` 分离并判 err 是否为空；要合并存档写 `>file 2>&1`（后）；重定向符号前留空格；逻辑未验证前用 `tee` 边看边存。
   - 完成标准：数据齐不齐有单一判据；错误不会混进数据；落盘前输出经过人工确认。
   - 判停：err 非空 → 先补齐来源再分析；同名文件可能被覆盖 → 先备份。

3. **动作闸门与守卫**
   - 做什么：不可逆动作用 `&&` 接在成功的验证/拷贝之后，用 `|| exit`/`|| 邮件` 兜底，多个失败后动作用 `{ ...; exit; }` 组合；脚本开头放身份/目录/参数三重守卫。
   - 完成标准：失败即短路、守卫全过才进入主体。
   - 判停：守卫不过 → 立即退出，不进破坏性主体；`LOGNAME` 仅作初筛，不能当唯一依据。

4. **循环与幂等**
   - 做什么：轮询循环体加 `sleep`；告警分支末尾 `exit`；跨脚本传递用 LCK 锁文件协调；人为让条件持续为真测试不会重复告警。
   - 完成标准：不烧 CPU、不邮件轰炸、不读半成品。
   - 判停：发现重复告警 → 检查是否漏 `exit`；发现读到半成品 → 补 LCK 等待。

5. **临时文件与临界区**
   - 做什么：临时文件名加 `$$`（`TMP=/tmp/name.$$`），`trap 'rm -f $TMP' EXIT` 清理；临界区前 `trap "" 1 2 3 15` 屏蔽信号、退出后恢复捕获。
   - 完成标准：并发实例互不覆盖、中断不留垃圾、临界区不被打断。
   - 判停：信号 9 无法屏蔽 → 强杀仍会中断临界区，需另设恢复机制；屏蔽范围过大会让用户无法用 Ctrl-C 退出僵死脚本。

6. **失败记录**
   - 做什么：在退出/清理函数里加 `logger`，用 `trap "my_exit" 2 3 15` 让中断也走该函数；用 `-i` 记进程号、`-p` 指定优先级。
   - 完成标准：异常退出能在系统日志留下可追溯记录。
   - 判停：各厂商 logger 语法有差异、消息可能有延迟 → 查手册并留足观察时间。

7. **计数变量初始化（expr 场景）**
   - 做什么：所有参与累加/计数的变量在循环外统一 `VAR=0` 或用 `${VAR:-0}` 兜底。
   - 完成标准：首轮不因空值报错、结果不被错误信息淹没。
   - 判停：expr 刷屏报错 → 先查未初始化变量。

## B — 边界 (Boundary) ★

### 不要用的情况
- 一次性排查、不需要长期维护——转 `text-processing-pipeline` 用管道即可，脚本的结构成本不划算。
- 命令行上一次性批量文件操作——转 `batch-file-operations`。
- 需要真正的并发安全/事务语义——shell 的 trap/锁是弱保证，关键系统应使用专门工具或语言。
- 信号 9（SIGKILL）场景——无法捕获或忽略，本卡的临界区保护失效。

### 已知失败模式
- **echo 吃掉退出码**：《Linux与unix shell编程指南》第23章 "不要使用echo命令后直接加最后状态命令，因为此命令永远为真"，失败被伪装成成功。
- **只看报错行**：同书报错点常是闭合语句时报的，不是真正出错点；必须回看整段结构。
- **重定向顺序颠倒**：同书 5.9 `2>&1 >file` 让错误留屏幕、只有正常输出进文件，"特别是你不在的时候"无法追溯。
- **`>` 紧贴 sort 被当文件名**：同书 5.7.1 对"参数即文件名"的命令，紧贴的 `>` 可能被解析成参数。
- **只用 `;` 分隔**：同书第6章失败后继续删；`cmd1 || echo ok; rm` 中 rm 不受 `||` 约束仍执行，不用 `{ }` 组合则只执行最后的 exit。
- **轮询无 sleep/exit**：同书 18.6 无 sleep 烧 CPU、无 exit 邮件轰炸、不等 LCK 读到半成品报表。
- **固定临时文件名**：同书 26.1 被并发覆盖、中断残留；`$$` 只在本进程唯一。
- **expr 未初始化**：同书 18.7.6 屏幕布满 expr 错误、真正结果被淹没。
- **缺三重守卫**：同书 18.3 在错误目录执行 `rm -r` 波及无关文件；`$LOGNAME` 可伪造。

### 作者与时代的局限
- 基于 2000 年前后的 bash/sh 与 syslog（`/var/adm/messages`），现代系统日志路径多为 `/var/log`；各厂商 logger 语法有差异。
- 示例未涉及 systemd unit、trap 与子 shell 的复杂交互等现代场景。
- "$LOGNAME 作守卫"是作者的"普遍方法"，并非安全强保证，作者自己也未将其作为唯一依据。

### 容易混淆的方法
- `set -n`/`-v`/`-x`：语法检查 / 显示读入行 / 显示展开后命令，用途不同；关闭用 `+` 而非 `-`。
- `>` vs `tee`：确认结果正确前用 tee 边看边存，确认后才用纯重定向覆盖。
- `&&` vs `||`：前者左侧成功才执行右侧（闸门），后者左侧失败才执行（兜底）；多个兜底动作要 `{ }` 组合。
- trap 两种用法：清理（trap 'rm...' EXIT）与临界区屏蔽（trap "" 1 2 3 15），目的不同。

### 授权与合规边界
> 待补充（用户自行填写）
