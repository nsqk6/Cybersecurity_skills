## I — 方法论骨架 (Interpretation)

这个能力解决的是：命令"成功执行"了、退出码是 0、屏幕上也有输出，但结果是错的——该命中的没命中（漏检），不该命中的混进来了（误检）。这类错误比报错危险得多，因为你据此得出"没有此现象"或"有这么多"的结论，而结论建立在错误的匹配之上。它覆盖文本处理里最高发的一类静默失败：字段切分错位、匹配语义选错、正则方言不认、不可见字符干扰、引号被 shell 吃掉、模式太多堆在命令行。

核心机制是把"匹配"当成一个需要双向验证的动作，而不是写完就信。第一原则：**先定期望，再写模式**。写正则前先列 2–3 条应命中样本和 1–2 条应排除样本，把"猜模式"变成"对答案"；正则失败通常静默（返回过多或过少行），没有期望值就无法判断错在哪。第二原则：**确定工具即确定方言**。awk 的 ERE 支持 `+`、`?`，grep/sed 的 BRE 要把 `+` 写成 `\{1,\}`、`?` 写成 `\{0,1\}`；sed 不认 `\d`、`\+` 要转义、分组括号要转义。按 Perl/Python 直觉写进 sed，命令会"成功但什么都没替换"。第三原则：**分清语义**。awk 的 `==` 是整字段等于、`~` 是包含；grep 的裸串匹配会把 484、483 一并命中，精确值要靠 `\>` 词尾锚定或字段边界。第四原则：**让数据自己说话**。两行"看起来一样"却匹配不上时，用 `sed -n l` 把制表符变 `\t`、行尾变 `$`，先看见不可见字符再谈替换。

批量场景另有三条：用正则做 awk 的 FS（`FS="[,:%]"`）一次吃掉多种分隔符，并用 `{print NF}` 抽查字段数稳定；多文件逐文件统计用 FNR（NR 跨文件累加会让阈值失真且不报错），配合 `find -exec {} \;` 让每个文件独立执行；模式数量多时写进文件用 `egrep -f patterns.txt` 装载，可复用可版本化，但要注意清单里本意字面的正则元字符和空白行。shell 层还有一对反向纪律：grep 的模式必须加引号（防 shell 展开），需要 shell 展开的文件名通配符不能加引号；变量字符串默认双引号，穷举三种引号试错成本低于推理成本。最后，只需布尔结果时用 grep 返回码（0=命中）配合 `-s`/`2>/dev/null` 作 if 条件，但要区分"查不到"和"文件不存在"。

## A1 — 应用示例 (Application Example)

### 示例 1: awk 用 == 匹配 "Tennis" 却漏掉 Tennis Racket
- **类型与来源**: 【例题】《Sed & awk 101Hacks》68. Regular Expression Operators
- **问题/输入**: 一份商品清单，想筛出"网球类"商品，其中一条是 `Tennis Racket`。
- **方法论的使用**: 先按语义判断——这里是"包含"而非"精确等于"，应用 `~` 而非 `==`。写成 `$2 ~ "Tennis"` 命中 `Tennis Racket`；若误写 `$2 == "Tennis"` 则结果为空且不报错。
- **结论**: `==` 整字段匹配、`~` 包含匹配；结果为空时先 `print $2` 看实际值，再判断是数据没有还是匹配写错。反向错误同样存在：用 `~` 做精确比对时 `200` 会命中 `2001`。
- **结果**: 原书示例 `$NF ~ /\/bin\/sh/ { n++ } END { print n }` 统计 passwd 里用 sh 的账号数，用计数变量 + END 输出避免空结果被当 0 条。

### 示例 2: sed 里搬用 Python 正则导致"原文照抄"
- **类型与来源**: 【例题】《grep-find-sed-awk》Part 3 "sed" · Capturing groups
- **问题/输入**: 想把电话号 `1234567890` 格式化为 `(123) 456-7890`，从 Python 搬来 `s/(\d{3})(\d{3})(\d{4})/.../`。
- **方法论的使用**: 按方言纪律改写：`\d` → `[0-9]`，`{3}` → `\{3\}`，分组 `(` → `\(`，反向引用 `\1`。正确写法 `s/\([0-9]\{3\}\)\([0-9]\{3\}\)\([0-9]\{4\}\)/(\1) \2-\3/g`。先在 `echo` 小样上验证输出，看到预期再碰文件。
- **结论**: sed 用 BRE，量词和分组必须转义；按直觉写会"成功执行但什么都没替换"，`d` 被当字面字符。若此时已加 `-i`，文件被重写但内容未变、mtime 已改（取证场景会误导时间线）。
- **结果**: 原书给出格式化后的电话号表达式；未转义版本得到"原文照抄"输出。

### 示例 3: grep "48" 把 484/483 也算进来
- **类型与来源**: 【例题】《Linux与unix shell编程指南》第8章 8.1.7 精确匹配
- **问题/输入**: 想统计字段值恰好为 48 的行数，data.f 里还有 484、483。
- **方法论的使用**: 裸 `grep "48" data.f` 会命中所有含 48 的字符串；改用 `grep '48\>'`（词尾锚定）或带上字段后的 `<Tab>` 边界，把"包含"收紧为"等于"，再 `grep -c` 对比前后计数差异。
- **结论**: 子串误命中会把频次、IOC 列表系统性做大；精确抽取靠词尾锚定或字段边界。
- **结果**: 原书示例改用精确匹配后只取纯 48 行。

### 示例 4: 两行"看起来一样"却匹配不上
- **类型与来源**: 【例题】《Sed & awk 101Hacks》32. Print Hidden Characters
- **问题/输入**: 一份文件里某字段有两行肉眼相同，但 awk 取字段时对其中一行总取错。
- **方法论的使用**: `sed -n l file | head` 让隐藏字符显形：制表符变 `\t`、行尾变 `$`。发现其中一行 `$` 之前还有 `\r` 或其他转义字符，说明混入了控制字符；正则 `$` 锚点、`awk` 末字段、`cut` 末字段都会偏。处理后再 `l` 一遍验证。
- **结论**: 数据本身含不可见字符时，先"看见"再谈替换；`diff` 判两文件相同也可能是假象（差异只在行尾不可见字符）。
- **结果**: 原书示例 `sed -n l tabfile.txt` 输出 `fname\tFirst Name$`。

### 示例 5: 几十个 IOC 堆在命令行（合成演练）
- **类型与来源**: 【合成演练】按本卡 E 段规则推演，依据《Linux与unix shell编程指南》第8章 8.5 `egrep -f` 单元
- **问题/输入**: 有 60 个恶意域名 IOC，需要在一份外联日志里一次性匹配。
- **方法论的使用**: 把 60 个域名逐行写入 `patterns.txt`（一行一个），用 `egrep -f patterns.txt out.log` 一次装载；结果留存并与清单对照覆盖率。注意清单里本意字面的点号要转义、不能有空白行（空模式会匹配所有行）。
- **结论**: 模式清单可独立维护、复用、版本化，是从手工命令升级为可重复流程的关键一步。
- **结果**: 按规则推演，输出为命中 IOC 的行；原书未提供此具体案例的真实结果。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 一条 grep/awk/sed 命令跑通了、有输出，但结果明显不对——该有的没有、不该有的混进来，需要定位是语义、方言还是数据本身的问题。
2. 要写一个精确的抽取/统计规则（IOC、日期、IP、账号、状态码），需要保证不漏检也不误检。
3. 一份日志/导出文件字段错位，或者两份"看起来一样"的文件匹配不上，怀疑有不可见字符或混合分隔符。
4. 批量逐文件统计时，结果比单独跑某个文件偏大/偏小，怀疑 NR/FNR 或 xargs 传参方式出了问题。
5. 在脚本里需要判断"某串/某账号在不在"，把它变成自动化条件。

### 语言信号（出现这些就该激活）
- 中文：「sed 替换没生效」「grep 搜不到」「awk 匹配不到」「正则在 awk 能用 sed 不行」「明明一样却匹配不上」「文件里有奇怪的空格」「grep 结果里有相似但不对的项」「批量统计每个文件结果偏大」「变量没被替换」「参数被拆成两个」
- English: "regex works in Python but not sed", "sed invalid reference", "awk condition not matching", "regex dialect differences", "invisible characters in file", "exact match grep", "NR vs FNR", "quoting problem in bash", "grep multiple patterns from file", "check if string exists silent"

### 与相邻能力的区分
- 与 `text-processing-pipeline` 的区别：相邻卡负责"把管道搭出来并出结论"，本卡负责"命令跑通但结果不对"。先搭管道，结果可疑时转本卡排除静默错误，再回去信结论。
- 与 `batch-file-operations` 的区别：本卡解决"单个文本流里的匹配/字段语义"，相邻卡解决"一批文件的传递方式与不可逆操作"。FNR/NR 单元横跨两卡——本卡从"变量选错"角度讲，相邻卡从"xargs 传参方式"角度讲。
- 与 `untrusted-file-inspection` 的区别：本卡在命令行用工具验证匹配，相邻卡在编辑器里检视文件内容/状态。都处理"不可见字符"，但本卡用 `sed -n l` 命令行显形，相邻卡用 vim `-b` 二进制模式检视。

## E — 可执行步骤 (Execution)

**必需输入**: 一段有问题的命令及其输出；或待抽取的目标（IOC/日期/IP/账号）与样本数据；明确是"漏检"（该有没有）还是"误检"（不该有混进）。缺"期望输出"必须先问清——没有基准就无法判断对错。

**交付物与完成标准**: 一条经过小样验证、语义正确、方言匹配的命令 + 一份"应命中/应排除"样本对照；完成标准是对照样本全部符合期望，且能说明每个元字符的作用。

1. **写下期望输出（正/反例）**
   - 做什么：列 2–3 条应命中样本 + 1–2 条应排除样本，作为判定基准。
   - 完成标准：基准明确到"这条该命中、那条不该"。
   - 判停：举不出正反例 → 先补充对目标格式的理解，不要急着写正则。

2. **锁定工具与方言**
   - 做什么：确定用 grep/sed/awk，锁定其正则方言。awk 可用 `+`、`?`；sed/grep 的 BRE 把 `+` 改 `\{1,\}`、`?` 改 `\{0,1\}`，`\d` 改 `[0-9]`，`{n}` 改 `\{n\}`，分组括号转义。
   - 完成标准：表达式里每个量词/分组都符合所选工具的方言。
   - 判停：跨工具复用正则 → 逐工具改写，不要假设方言通用；小样验证不是"执行成功"而是"命中正确"。

3. **确认匹配语义（精确 vs 包含）**
   - 做什么：精确比对用 awk `==`、grep `\>` 词尾锚定或字段边界；包含用 awk `~`、grep 裸串，排除用 `!~`/`grep -v`。结果为空先 `print $字段` 看实际值。
   - 完成标准：统计类判断用计数变量 + END 输出，空结果不被当成 0 条。
   - 判停：结果为空 → 先判断是数据没有还是语义写错，不要直接下"没有此现象"的结论。

4. **设置正确的字段切分**
   - 做什么：多种分隔符用 `awk -F '[,:%]'` 一次覆盖；`{print NF}` 抽查每行字段数是否稳定；字段内含分隔符时按位置取或 `$(NF-n)` 从右取。
   - 完成标准：字段数稳定、切分后语义正确。
   - 判停：字段数忽大忽小 → 说明分隔符出现在数据内部，改用按位置取或从右取。

5. **检查不可见字符（按需）**
   - 做什么：`sed -n l file | head` 显形制表符、行尾 `$`、控制字符；可疑行 `sed -n 'N l'` 单独复核；与"已知正常"文件对照行尾。
   - 完成标准：确认 `$` 紧贴最后可见字符，无混入额外转义字符。
   - 判停：若行尾有 `\r` 等，先统一行尾再谈匹配。

6. **批量场景专项（按需）**
   - 做什么：多文件逐文件统计用 FNR 而非 NR，配 `FILENAME` 标注来源，并抽查某文件结论与单独跑一致；模式多时写 `patterns.txt` 用 `egrep -f` 装载，注意转义与空白行。
   - 完成标准：批量结论与单文件单独跑一致；模式清单覆盖率可核对。
   - 判停：批量结果系统性偏移 → 检查是否用了 NR 或 xargs 把多文件塞进同一 awk 进程。

7. **shell 层引号与布尔化（按需）**
   - 做什么：grep 模式加引号、需 shell 展开的文件名通配符不加引号；变量字符串默认双引号、穷举三种引号；只需布尔结果用 `if grep -qs 'pattern' file`，`-s`/`2>/dev/null` 屏蔽"文件不存在"噪音。
   - 完成标准：区分"查不到"（返回 1）与"文件不存在"（也是非 0，但需另外辨别）。
   - 判停：命令报 "No such file" → 先怀疑文件名误写成参数，不要当"未命中"处理。

## B — 边界 (Boundary) ★

### 不要用的情况
- 数据是二进制或结构化（JSON/Protobuf）——本卡的正则/字段语义建立在行式文本上，需先转文本或换专用解析器。
- 需要模糊相似度、语义匹配——正则只做确定性模式匹配。
- 已经确认工具语义正确、结果可疑只因管道搭错——转 `text-processing-pipeline`。

### 已知失败模式
- **`==` 当包含用**：《Sed & awk 101Hacks》#68 "== looks for a full match"，`$2 == "Tennis"` 匹配不到 `Tennis Racket`，且不报错——漏检型错误比误报更危险。
- **`~` 当精确用**：同书 #68，`200` 会命中 `2001`，前缀相同的值互相污染。
- **sed 方言静默失效**：《grep-find-sed-awk》Part 3 "\d and + not supported in sed regex"，按 Perl 直觉写得到"原文照抄"；若已加 `-i`，mtime 被改但内容未变，取证场景误导时间线。
- **awk 方言差异**：《Linux与unix shell编程指南》9.2.4 `+`、`?` 只适用 awk，用到 grep/sed 的基本正则会零命中不报错。
- **子串误命中**：同书 8.1.7 裸 `grep "48"` 命中 484/483，频次与 IOC 列表被污染。
- **不可见字符干扰**：《Sed & awk 101Hacks》#32 行尾控制字符让 `$` 锚点、awk 末字段、cut 末字段都偏；`diff` 也可能误判两文件相同。
- **NR 跨文件累加**：同书 #61 "NR keeps growing between multiple files"，批量阈值失真不报错，单文件跑一次却是对的，最难发现。
- **grep 引号搞反**：《grep-find-sed-awk》Part 2 模式未引号被 shell 展开、文件名加引号让 grep 找字面 `*.xml`，表现都是"找不到明明存在的东西"。
- **模式文件空白行**：《Linux与unix shell编程指南》8.5 空白行被当空模式匹配所有行；本意字面的正则元字符被当正则解析。

### 作者与时代的局限
- BRE/ERE 方言基于 2000 年前后的 grep/sed/awk，现代 GNU 工具的 `-P`（PCRE）等扩展可缓解部分问题，但作者未覆盖；不同实现（BSD vs GNU）行为有别。
- 示例面向 ASCII 行式文本，UTF-8 多字节、Unicode 正则类在原文语境之外。
- "先写期望再写模式"依赖人能举出正反例，对完全陌生的数据分布仍需先探索。

### 容易混淆的方法
- 与 `text-processing-pipeline`：本卡是"结果正确性"的排错镜，相邻卡是"结论构建"的流程；不要在还没搭出管道时就用本卡空转。
- 漏检 vs 误检：漏检（该有没有）源于 `==`/方言/过滤过严，误检（不该有混进）源于 `~`/子串/过滤过松，对策相反，先分清再动手。
- 引号纪律有两套：本卡的通用规则（默认双引号、穷举三种）与 grep 特有规则（模式要引、通配符文件名不要引）互补，不要互相覆盖。

### 授权与合规边界
> 待补充（用户自行填写）
