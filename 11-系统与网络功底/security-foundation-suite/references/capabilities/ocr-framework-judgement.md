## I — 方法论骨架 (Interpretation)

**用对话精确化问题定义** — 程序员最初问"如何对磁盘文件排序"是个错误的问题。通过一系列追问（输入规模？内存约束？数据特征？是否允许重复？性能要求？），把模糊需求逐步收敛到可解的精确规格。这一方法对安全工程师同样适用——面对"系统是否安全"这种模糊问题时，必须先用对话把威胁面、资产、入口、约束问清楚，再谈方案。

**多通道算法处理受限内存问题** — 当内存装不下全部数据时，不强行一次加载，而是多次扫描输入，每次只处理一部分。安全场景：处理超大日志文件、批量扫描时按片段分批读取。

**简单程序更安全健壮原则** — 复杂度是安全性的敌人——更多的代码、更多的分支、更多的状态意味着更多攻击面和更多 bug。作者把"简单性"列为与正确性、效率并列的设计目标。安全工程师在审查代码时应优先简化而非堆叠防御。

**边界条件与异常输入检测清单** — 任何处理输入的程序都必须显式回答：重复输入怎么办？越界值怎么办？类型不对怎么办？这是安全工程师做 fuzzing 和输入验证时的核心清单。作者用问题形式给出了一个通用的边界检测清单模板。

**二分查找作为通用探测工具** — 二分查找的本质是"已知目标在某范围内，通过探测中点缩小范围"。这一结构在安全域有大量应用：定位引入漏洞的 commit（git bisect）、定位崩溃的输入区间、定位绕过 WAF 的具体字符。

**不变量驱动的代码验证流程** — 写精细代码时，先写下"每次循环开始和结束时必须为真"的断言（不变量），再围绕不变量推导每一行代码。每条赋值都要证明"执行后不变量仍成立"。安全工程师可用此法验证认证状态机、权限检查流程的每一步都不会泄露中间态。

**循环三性验证法（初始化/保存/终止）** — 任何循环的正确性可分解为三个证明义务：①初始化确立不变量；②每次迭代保持不变量；③终止时不变量蕴含正确结果。再加一个"循环必然终止"的证明。这是安全工程师审查状态机循环、协议握手循环时的结构化方法。

**前置/后置条件的契约编程** — 每个函数都应声明两份契约：前置条件（调用方必须保证的输入状态）和后置条件（被调方承诺的输出状态）。调用方满足前置条件时，被调方才负责后置条件。安全场景下这是 API 边界检查的核心——跨信任域调用时契约必须显式。

**调试提问法** — 优秀调试员不靠猜测，靠提问。面对诡异现象，先问"什么时候开始的""之前正常过吗""变化了什么""能 100% 复现吗"。这套提问法直接适用于安全事件响应——定位入侵时间点、范围、入口。

**封底计算估算系统容量** — 面对规模问题先做粗略计算：估计关键参数→乘除→得到数量级答案。不需要精确，只要能区分"可行/不可行"。安全场景：估算爆破 8 位密码的时间、估算日志存储容量、估算 DDoS 流量是否扛得住。

**安全系数法补偿未知** — 工程师对自己不知道的东西要有敬畏。Roebling 把吊桥铁索强度设计成常规计算的 6 倍，因为他知道气动上升现象他无法建模。安全工程师面对未知攻击面时同样应保留冗余——防御深度、超额容量、额外检查。

**72 法则估算指数增长** — r% 增长率下，约 72/r 个周期后数量翻倍。安全场景：估算密码熵的爆破进度、估算漏洞增长、估算数据积累速度。比精确计算快得多，且足以做可行性判断。

**利特尔法则** — L = λ × W（系统内平均数量 = 到达率 × 平均停留时间）。这是排队论的基本定律，适用于任何稳态流入流出的系统。安全场景：估算并发会话数、估算缓冲队列长度、估算 WAF 待处理请求堆积量。

**性能问题分层定位法** — 性能问题可在多个层次解决：问题定义→系统结构→算法→数据结构→代码优化→系统软件→硬件。不要一遇到性能问题就"换算法"或"加硬件"，而应审视所有层次，选择"加速最大、精力最小"的那层。安全场景同理——安全问题可在设计/架构/实现/配置/硬件多层解决。

**从"单纯建立连接"转向"安全建立连接"** — 网络设计的优先级已从"可达性"切换到"安全可达性"。任何联网方案在评审阶段就应将"自我防卫"作为默认需求，而非事后补丁。这是后续所有安全方法（防火墙、加密、认证、IDS）的存在前提——它们都是为"安全建立连接"服务的分层手段。

**用 OSI 七层模型定位协议与攻击所在层级** — 每种协议、每种攻击都发生在某一层。把现象先归层，可以快速决定下一步排查方向：链路层（ARP 欺骗、MAC 泛洪）、网络层（IP 欺骗、ICMP 重定向、分片攻击）、传输层（SYN flood、会话劫持、RST 注入）、应用层（HTTP/SQL 注入、DNS 投毒）。OSI 模型也界定"各层的责任和义务"，安全控制要落在与攻击同层或更下层才有效。

**用 5 元组识别一条 TCP/UDP 通信流** — 5 元组是网络/安全设备识别"会话"的统一坐标。防火墙规则、IDS 会话跟踪、流量分析、NAPT 转换表全部基于此。任何一条网络行为能否被判定为可疑，第一步通常是先看 5 元组（外部 IP 是否在威胁情报、目的端口是否非业务端口、协议号是否异常）。

**知名端口与动态端口的划分边界** — 端口段三段式（0–1023 知名 / 1024–49151 注册 / 49152–65535 动态）是端口审计的基线。看到客户端向 49152+ 发起连接通常是临时端口反连；看到 1024–49151 范围出现非业务流量可能是后门或误注册；看到知名端口被复用（如 80 端口跑 SSH）需立即告警。

**TCP 三次握手与连接管理流程** — TCP 连接建立走 SYN→SYN+ACK→ACK 三步，断开走 FIN→ACK→FIN→ACK 四步。这一固定流程是 SYN flood 攻击（只发 SYN 不发 ACK，耗尽服务端半连接）、半连接扫描（SYN 后立即 RST）、TCP 会话劫持（预测序列号插入 RST 或数据）的根源。理解握手状态机才能从抓包里看出"半开连接异常累积"、"大量 SYN_SENT 状态"等攻击征兆。

**TCP 序列号与 ACK 实现可靠传输（含丢包/重发识别）** — TCP 给每个字节编号，接收端用"下一个期望序列号"做 ACK。这给安全分析带来两件事：(1) 抓包里同一 5 元组的序列号必须单调递增，若出现"序列号倒退"或"序列号跳跃后又有相同 ACK 重复"，可能是注入/劫持；(2) 3 次重复 ACK 触发高速重发，攻击者可构造"伪造的重复 ACK"逼迫发送端重发数据，配合序列号预测实现会话劫持。重发超时动态调整也意味着攻击者可延迟 ACK 强制触发重发。

**TCP 拥塞控制与慢启动阈值** — TCP 吞吐量"逐步占领网络带宽"——慢启动让拥塞窗口指数增长，到慢启动阈值后线性增长，丢包则窗口减半或重置。这给安全分析两件事：(1) 突发超大流量不符合 TCP 拥塞控制规律的（一开始就满速），通常是 UDP 反射放大攻击或 ICMP flood；(2) 攻击者可故意构造"伪造丢包"诱导 TCP 减速（DoS 降速攻击），需在 IDS 中识别"实际未丢包却大量重传"模式。

**ARP 广播解析与缓存过期机制（ARP 欺骗的根因）** — ARP 在同链路内通过广播问询、单播应答建立 IP→MAC 映射，结果缓存在主机和交换机里。关键风险：(1) ARP 应答不被验证，任何同链路主机都可发送伪造应答把网关 IP 映射到自己 MAC，从而劫持流量（ARP 欺骗/中间人）；(2) 缓存过期机制决定了攻击者必须周期性重发伪造 ARP 应答才能维持劫持，这是 IDS 可检测的周期性特征；(3) ARP 包不穿越路由器，所以 ARP 欺骗只发生在二层广播域内。

**代理 ARP 跨网段伪装主机** — 代理 ARP 让路由器代答另一网段主机的 ARP 请求，使发送方"误以为"目标在同链路。安全含义：(1) 攻击者可主动启用代理 ARP 伪装成另一网段主机接收流量；(2) 网络管理员误开代理 ARP 会让本应隔离的网段"穿透"路由器，破坏子网隔离；(3) 故障排查中遇到"路由器 IP 能 ping 通但实际是另一网段"或"ARP 表显示一个 MAC 对应多个 IP"应怀疑代理 ARP。

**IP 分片只在目标主机重组（分片攻击的物理基础）** — IP 包超过链路 MTU 时由路由器分片，但只在目标主机重组。这给安全带来三类问题：(1) 攻击者故意构造大量小分片让 IDS/防火墙难以重组并检测（小分片攻击 evasion）；(2) 攻击者构造重叠分片让不同设备重组结果不同，绕过检测（Teardrop 类）；(3) 第一个分片含传输层首部，后续分片没有，防火墙若只看首片放行 UDP/TCP 头而忽略后续，可被利用。现代路径 MTU 发现（CU-2-13）通过 DF 位减少路由器分片，但攻击者仍可强制构造分片包。

**路径 MTU 发现（DF 位 + ICMP 不可达）** — 主机在 IP 包设置 DF=1（不分片），路径上 MTU 不够的路由器丢包并回送 ICMP 类型 3 代码 4（Fragmentation Needed and DF Set）携带正确 MTU，主机据此调整后续包大小。安全含义：(1) PMTUD 黑洞——攻击者或错误配置阻断 ICMP 不可达，会导致 TCP 连接对大包卡死（"path MTU 黑洞"）；(2) 攻击者可伪造 ICMP 不可达消息逼迫主机减小 MTU 到极小值，造成性能 DoS；(3) 防火墙若粗暴拦截所有 ICMP 会破坏 PMTUD，正确做法是放行 ICMP type 3 code 4。

**IPv4 首部关键字段的安全读取口径** — IPv4 首部各字段对应一类安全分析切入点：(1) TTL 反映源主机到本机经过的跳数，同一来源的 TTL 突变可能是 IP 欺骗或 NAT 后多个真实主机；(2) 标识/标志/片偏移用于分片重组与分片攻击识别（见 CU-2-12）；(3) 协议号指明上层协议（6=TCP, 17=UDP, 1=ICMP, 89=OSPF 等），用于协议异常检测；(4) "源路径"选项允许发送方指定包的路由路径，是源路由攻击的载体，现代防火墙应丢弃带 LSRR/SSRR 选项的包；(5) 首部校验和只校验首部不校验数据，不能用作完整性证明。

**NAT/NAPT 转换表的生成时机与生命周期** — NAPT 表是 NAT 设备识别内外流量的唯一依据。表项在 TCP SYN 时创建、FIN+ACK 后删除；UDP 没有连接概念，靠空闲超时清理。这给安全分析四个关键点：(1) 内部主动外联才会建表，所以"外部无法主动连内部"是 NAPT 的天然屏障；(2) NAT 重启会清空所有表项，所有 TCP 连接瞬间断开（NAT 不是高可用设备）；(3) 表项数量上限决定 NAT 能支撑的并发连接数，超限会丢包；(4) 攻击者若想从外部打通内部，必须诱导内部先发起连接（NAT 穿越）或利用 UPnP 等机制让 NAT 主动建表。

**DNS 分层解析与缓存机制（DNS 投毒的物理基础）** — DNS 解析走"根→TLD→权威"分层树状查询，解析器和中间域名服务器都会缓存结果。安全含义：(1) 缓存未过期前，解析器会直接返回缓存，攻击者只要在缓存中"投毒"一条错误映射（伪造权威应答的源 IP 和 TXID 让解析器接受），所有用户在该 TTL 内都被劫持；(2) 攻击者可观察递归查询的 TXID 可预测性实施 Kaminsky 攻击；(3) 缓存也意味着合法 IP 变更不会立即生效，安全事件中"DNS 已经改过来了为什么还连旧 IP"是常见现象。

**包过滤防火墙用 SYN/ACK 标志位控制连接方向** — 包过滤防火墙通过 TCP 首部 SYN/ACK 标志位识别"谁发起的连接"。SYN=1 且 ACK=0 表示这是连接建立的首包，必然是发起方；SYN=1 且 ACK=1 是响应方。所以"只允许内网发起的连接"= 丢弃从外网进入的 SYN=1,ACK=0 包。这是无状态防火墙做"方向控制"的经典手法；现代有状态防火墙内部仍用类似判断维护会话表。

**用 DMZ 隔离对外服务与内部网络** — 把需要"对外暴露"的服务器（Web、邮件、DNS）放在专用的"半信任"子网，两侧用防火墙隔离。即使对外服务器被攻破，攻击者也无法直接横向进入内网。这是网络分段与"爆炸半径控制"的基础模式，与零信任/微分段思路一致。

**IDS 与防火墙的互补关系** — 防火墙是"白名单/黑名单匹配"——只要策略匹配就放行，无法判断意图；IDS 是"行为分析"——即使包通过了防火墙，进入内网后的可疑行为仍要被发现。两者必须叠加使用。IDS 部署位置：(1) 边界（防火墙/DMZ 旁）检测外网入侵；(2) 内网全网监控检测横向移动；(3) 关键服务器主机型 IDS 检测主机异常。

**PKI 通过可信赖第三方 + 数字证书验证通信方身份** — 通信双方互不信任时，由双方都信任的 CA（认证机构）签发证书把"身份信息+公钥"绑在一起。验证方用 CA 公钥验签，确认对方公钥真实属于该身份，再用对方公钥加密对称密钥或验证对方签名。这是 HTTPS/SSL/TLS、S/MIME、代码签名的基础。任何"证书是否被信任"问题最终归结为"CA 是否在信任库中"和"证书是否被吊销（CRL/OCSP）"。

**对称加密 + 公钥加密的混合使用模式** — 对称加密快但密钥分发难（如何安全把密钥送给对方）；公钥加密慢但公钥可公开。现实系统混合用：用公钥加密把"对称密钥"安全送到对方，之后大量数据用对称密钥加密。所有 TLS/IPsec 实际加密流程都遵循这一模式。理解此点能解释为什么 TLS 握手阶段慢（公钥运算）但之后传输快（对称运算），以及为什么"对称密钥泄露"比"公钥泄露"危险得多。

**IPsec VPN 的传输模式与隧道模式** — IPsec 在 IP 层加密和认证。两种模式区别：(1) 传输模式只加密 IP 载荷（TCP/UDP 及数据），原 IP 首部保留，适合"端到端"主机间加密；(2) 隧道模式把整个原 IP 包（含首部）作为新包的载荷，外层加新 IP 首部，适合"网关到网关"或"主机到网关"VPN——内部 IP 不暴露。AH 提供完整性认证但不加密；ESP 既加密又认证。理解模式差异才能正确选择 VPN 部署形态。

**TLS/SSL 与 HTTPS 的握手流程** — HTTPS = HTTP over TLS。握手流程：(1) 客户端发 HTTPS 请求，通知支持的加密算法；(2) 服务器返回证书，客户端用 CA 公钥验签确认证书属于该网站；(3) 客户端生成对称密钥，用服务器公钥加密后发出；(4) 服务器用私钥解出对称密钥；(5) 双方用对称密钥加密后续 HTTP 数据。安全要点：证书验证（PKI，CU-2-21）是 TLS 信任根；如果客户端跳过验证或信任所有证书，整个 HTTPS 安全性归零；公钥加密仅用于交换对称密钥（CU-2-22）。

**IEEE 802.1X 的接入认证流程（VLAN 隔离未授权设备）** — 802.1X 在数据链路层做接入控制，未授权设备只能进入"隔离 VLAN"访问认证服务器，认证通过后交换机/AP 切换 VLAN 才放行到业务网络。这是企业有线/无线 LAN 防止"陌生人插上网线就能进内网"的标准做法。流程：(1) 终端接入 → 进入隔离 VLAN；(2) 终端向认证服务器提交用户名/密码或证书（EAP 协议）；(3) 认证服务器通知 AP/交换机该终端可访问的网络；(4) AP 切换 VLAN，终端重置 IP，最终接入业务网络。

**各层加密应用举例（OSI 分层视角看加密覆盖范围）** — 加密在哪一层做，决定了"哪一段数据被保护"。书中给出三层举例：(1) 应用层加密——PGP/S-MIME 加密邮件内容、SSH 加密远程登录会话，保护应用数据本身；(2) 传输层加密——TLS/SSL 加密 HTTP/SMTP 等应用数据流，保护传输内容但 TCP/IP 首部仍可见；(3) 网络层加密——IPsec 加密整个 IP 载荷，保护网络层以上所有内容。关键洞察："在 X 层加密只能保护 X 层以上的数据，X 层及以下的首部仍暴露"。所以选择加密层时需考虑：(a) 是否需要隐藏源/目的 IP（用 IPsec 隧道模式）；(b) 是否需要隐藏应用协议（用应用层加密如 SSH）；(c) 性能开销（越底层加密范围越大但开销越高）。

### 示例 8: 前置/后置条件的契约编程

- **结果**: 【例题】二分查找的前置条件 x[0]<=x[1]<=...<=x[n-1]，后置条件 result==-1 ⇒ t 不存在

## E — 执行步骤 (Execution)

### 用对话精确化问题定义

1. 听到模糊请求时，不要直接给方案 → 标记"问题定义未完成"
  2. 用提问挖掘输入特征：规模？范围？是否重复？关联数据？ → 形成输入规格
  3. 用提问挖掘输出要求：排序？去重？性能上限？ → 形成输出规格
  4. 用提问挖掘环境约束：内存？磁盘？时间？ → 形成约束规格
  5. 把三份规格写下来再设计 → 完成判据：能用一句话复述问题

### 多通道算法处理受限内存问题

1. 估算单次可装入内存的数据量 → 确定通道数 k
  2. 把输入范围划分为 k 段 → 每段都能装入内存
  3. 每个通道只处理一段：读入→处理→写出 → 一遍完成一段
  4. 合并 k 个输出 → 完成判据：全部范围覆盖

### 简单程序更安全健壮原则

1. 评审代码时先问"能不能更短" → 代码长度是复杂度代理指标
  2. 用数据结构替换重复代码 → 见第 3 章数组替换 500 个 if
  3. 删除不必要的功能分支 → 每个分支都是潜在攻击面
  4. 完成判据：同样功能下代码行数显著减少

### 边界条件与异常输入检测清单

1. 列出所有输入字段 → 每个字段单独分析
  2. 对每个字段问：重复？越界？类型错？格式异常？ → 形成问题清单
  3. 为每个问题编写检测分支和错误处理 → 完成判据：每个问题有对应测试
  4. 构造小数据集覆盖每种异常 → 测试集归档

### 二分查找作为通用探测工具

1. 定义"范围"——目标可能存在的区间 → 必须可量化为有序区间
  2. 定义"探测"——中点处能否判定目标在上半还是下半 → 必须有二元判定函数
  3. 循环：取中点→探测→缩半 → 直到区间为空或命中
  4. 完成判据：log₂(范围) 次探测内定位

### 不变量驱动的代码验证流程

1. 写出循环不变量（用断言注释） → 必须精确到可证明
  2. 证明初始化后不变量成立 → 初始赋值要满足
  3. 对循环体每条语句，证明执行后不变量仍成立 → 逐行推导
  4. 证明循环终止时不变量蕴含预期结果 → 完成判据：四性全部成立

### 循环三性验证法（初始化/保存/终止）

1. 列出循环不变量 → 写成断言
  2. 检查初始化：循环前的赋值是否让不变量为真 → 若否则有 bug
  3. 检查保存：循环体每条语句是否保持不变量 → 逐条推导
  4. 检查终止：循环条件何时为假？此时不变量是否给出正确结果？ → 推导结果
  5. 检查终止必然性：每次迭代是否缩小某个有界量？ → 防死循环

### 前置/后置条件的契约编程

1. 为每个公开函数写前置条件（输入约束、状态要求） → 注释形式
  2. 为每个公开函数写后置条件（返回值约束、状态变化） → 注释形式
  3. 在函数入口用 assert 验证前置条件 → 运行时检查
  4. 在函数出口用 assert 验证后置条件 → 运行时检查
  5. 跨模块调用时检查契约是否对齐 → 完成判据：每个边界都有契约

### 调试提问法

1. 现象澄清：什么时候开始？100% 可复现吗？ → 建立现象基准
  2. 时间线：之前正常过吗？变化了什么？ → 定位引入点
  3. 差异：失败和成功的区别是什么？ → 找出变量
  4. 复现：能让我看看你怎么操作的吗？ → 第一手观察
  5. 完成判据：能用一句话描述触发条件

### 封底计算估算系统容量

1. 识别关键参数 → 列出量纲
  2. 给每个参数一个粗略值 → 误差 2~5 倍可接受
  3. 按量纲做乘除 → 用表格消项
  4. 量纲检查：结果量纲是否正确 → 形式正确性
  5. 用第二独立方法交叉验证 → 完成判据：两个方法数量级一致

### 安全系数法补偿未知

1. 列出"我知道的"和"我不知道的" → 知识边界
  2. 对每个"不知道"分配安全系数 → 2x/4x/6x/10x 按风险选
  3. 性能承诺按 2~6 倍降低 → 防超载
  4. 可靠性承诺保留 10 倍冗余 → 防未知失效模式
  5. 规模/成本/进度估计保留 2~4 倍 → 完成判据：每个未知都有对应系数

### 72 法则估算指数增长

1. 确定增长率 r%（每周期） → 周期可以是秒/天/年
  2. 翻倍周期 ≈ 72/r → 得到翻倍时间
  3. 10 次翻倍 ≈ 1000 倍；20 次 ≈ 100 万倍；30 次 ≈ 10 亿倍 → 心算量级
  4. 完成判据：能说出"X 周期后达到 Y 倍"

### 利特尔法则

1. 确定三个量中的两个（L、λ、W） → 已知输入
  2. 用 L = λ × W 推第三个 → 直接计算
  3. 验证流量平衡：进入率 ≈ 离开率 → 稳态假设
  4. 完成判据：三个量量纲一致（个 = 个/时间 × 时间）

### 性能问题分层定位法

1. 列出所有可改动的层次（从问题定义到硬件） → 全景视图
  2. 估算每层可获得的加速 → 用封底计算
  3. 估算每层的改造成本 → 时间+人力+风险
  4. 选加速/成本比最大的层先动 → 完成判据：选定层次并说明理由

### 从"单纯建立连接"转向"安全建立连接"

1. 在网络接入评审时提出"安全可达性"问题（暴露面/认证/加密/审计） → 形成需求条目
  2. 把"自我防卫手段"列入日常运维流程（不仅是故障响应） → 文档化运维 checklist

### 用 OSI 七层模型定位协议与攻击所在层级

1. 拿到异常现象（如"会话被劫持"、"流量被劫持"） → 先判断属于哪一层
  2. 该层之上、之下分别能做什么控制 → 选择检测点/防御点

### 用 5 元组识别一条 TCP/UDP 通信流

1. 抓取数据包 → 提取源 IP、目的 IP、协议号、源端口、目的端口
  2. 在日志/规则库中按 5 元组匹配 → 判定是合法业务流还是异常
  3. 5 元组任一变化即视为新会话 → 不可把不同 5 元组的事件合并

### 知名端口与动态端口的划分边界

1. 列出业务知名端口清单 → 与 0–1023 段对照
  2. 监控 49152–65535 段出站流量 → 发现异常外联（C2 通常藏在此段）
  3. 检查 1024–49151 段监听 → 发现非注册监听端口

### TCP 三次握手与连接管理流程

1. 抓包 → 按 5 元组分离每条 TCP 流
  2. 检查每条流是否走完 SYN/SYN+ACK/ACK 三步 → 没走完即半开连接
  3. 统计半开连接数量与源 IP 分布 → 超阈值判定为 SYN flood

### TCP 序列号与 ACK 实现可靠传输（含丢包/重发识别）

1. 在抓包里按 5 元组排序，画出序列号—时间曲线
  2. 出现序列号回退、跳跃、与已发送数据不连续 → 怀疑注入
  3. 观察重复 ACK 数量 → 异常大量重复 ACK 可能是接收端被诱导或链路被劫持

### TCP 拥塞控制与慢启动阈值

1. 抓流量曲线 → 看是否符合"慢启动—线性增长—丢包回退"曲线
  2. 流量一开始就接近链路上限且为 UDP/ICMP → 怀疑非 TCP 拥塞控制的 flood
  3. TCP 流频繁重传但链路无丢包 → 怀疑注入型降速攻击

### ARP 广播解析与缓存过期机制（ARP 欺骗的根因）

1. 在主机执行 `arp -an` → 检查网关 MAC 是否与设备标贴一致
  2. 在交换机启用 Dynamic ARP Inspection (DAI) / 端口绑定 MAC → 拒绝伪造 ARP 应答
  3. IDS 监控同网段内"同一 IP 出现多个 MAC"或"短时间内同一 MAC 应答多个 IP" → 触发告警

### 代理 ARP 跨网段伪装主机

1. 在主机 ARP 表中查找"一个 MAC 对应多个不同网段 IP" → 怀疑代理 ARP 或攻击
  2. 在路由器检查是否启用代理 ARP（如 Cisco `ip proxy-arp`） → 默认应关闭
  3. 仅对不支持子网掩码的老设备按需启用 → 限定接口范围

### IP 分片只在目标主机重组（分片攻击的物理基础）

1. 在 IDS/防火墙启用 IP 分片重组（虚拟重组） → 检测分片包整体内容
  2. 监控大量小分片流量 → 比例异常即告警
  3. 限制每个源 IP 的并发未重组分片数 → 防止资源耗尽

### 路径 MTU 发现（DF 位 + ICMP 不可达）

1. 在边界防火墙放行 ICMP type 3 code 4（DF 不可达） → 保证 PMTUD 工作
  2. 监控同一源主机收到大量"MTU 极小"的 ICMP 不可达 → 怀疑伪造攻击
  3. 故障排查"大包卡死小包通" → 检查路径上是否有设备阻断 ICMP 不可达

### IPv4 首部关键字段的安全读取口径

1. 抓包 → 提取 TTL/协议号/标志位/Options
  2. TTL 异常：同源主机 TTL 在不同会话间突变 → 怀疑 IP 欺骗或代理后多主机
  3. 检查 Options 字段出现 Source Route → 直接丢弃或告警
  4. 检查协议号是否在期望范围（如主机不应主动发 OSPF 89） → 异常即告警

### NAT/NAPT 转换表的生成时机与生命周期

1. 在 NAT 设备查看转换表（如 Linux `conntrack -L`） → 检查异常外部目标端口
  2. 监控表项数量 → 接近上限预警
  3. 检查是否启用 UPnP/NAT-PMP → 评估是否允许内网主机主动打洞
  4. NAT 设备做容灾时使用 session 同步，否则主备切换会断所有连接

### DNS 分层解析与缓存机制（DNS 投毒的物理基础）

1. 在本地解析器查询域名 → 与权威服务器直接查询对比 → 不一致即怀疑投毒
  2. 检查解析器是否启用 DNSSEC → 启用后能验证应答真实来源
  3. 监控同一域名在短时间内被解析为多个不同 IP → 异常即告警
  4. 安全事件响应时强制刷新解析器缓存（如 `rndc flush`） → 排除缓存干扰

### 包过滤防火墙用 SYN/ACK 标志位控制连接方向

1. 列出业务需要的"外部→内部"开放端口（如 80/443/25） → 仅这些端口允许 SYN=1,ACK=0
  2. 默认拒绝所有外部发起的 SYN=1,ACK=0 包 → 实现内网主动外联、外部不能主动连入
  3. 对出站也用同样原则（如禁止内网主动连外部 22/3389） → 防止 C2 反连

### 用 DMZ 隔离对外服务与内部网络

1. 识别所有"必须对外"的服务器 → 列出对外端口
  2. 将这些服务器迁入 DMZ 子网 → 内外两侧防火墙分别制定策略
  3. 内网→DMZ 仅放行业务必需端口；DMZ→内网 默认拒绝，按白名单放行
  4. DMZ 主机充分加固（HIDS、补丁、最小权限） → 因为它最可能被打

### IDS 与防火墙的互补关系

1. 在防火墙旁部署 IDS → 监控被防火墙放行但行为可疑的流量
  2. 在内网关键节点部署 IDS → 监控横向移动、异常协议
  3. 在重要服务器部署主机型 IDS → 监控文件完整性、进程异常
  4. IDS 配置定期采集日志 + 长期监控 + 异常通知 → 形成"边界+内网+主机"三层检测

### PKI 通过可信赖第三方 + 数字证书验证通信方身份

1. 客户端连接服务器 → 服务器返回证书链
  2. 客户端用本地信任库中的 CA 公钥逐级验签 → 验证证书签名有效
  3. 检查证书域名匹配、有效期、吊销状态（OCSP/CRL） → 任一不符即拒绝
  4. 提取证书中的服务器公钥 → 用于后续 TLS 握手

### 对称加密 + 公钥加密的混合使用模式

1. 握手阶段：用对方公钥加密一个随机对称密钥 → 仅对方私钥能解开
  2. 传输阶段：双方用该对称密钥加解密数据 → 性能开销可控
  3. 会话结束后销毁对称密钥 → 每次会话用新密钥（前向保密）

### IPsec VPN 的传输模式与隧道模式

1. 端到端加密（如两台服务器互信） → 选传输模式，性能开销小
  2. 分支机构与总部内网互联 → 选隧道模式，隐藏内网 IP 结构
  3. 配置 ESP 加密 + 认证；如只需完整性（如防篡改不要求保密）可只配 AH
  4. 注意 NAT 与 IPsec ESP 不兼容（NAT 改首部校验和破坏 AH）→ 需 NAT-T 封装

### TLS/SSL 与 HTTPS 的握手流程

1. 抓 HTTPS 握手包（ClientHello/Certificate/ServerKeyExchange/…） → 验证服务器返回证书链完整
  2. 检查客户端是否真的执行了证书校验 → 跳过校验是常见漏洞
  3. 检查协商出的对称算法是否为弱算法（RC4/DES/3DES） → 升级 TLS 版本
  4. 监控证书过期/吊销 → 提前预警

### IEEE 802.1X 的接入认证流程（VLAN 隔离未授权设备）

1. 在 LAN 交换机和无线 AP 启用 802.1X → 配置认证服务器（RADIUS）
  2. 终端配置 EAP 客户端（用户名/密码或证书） → 提交认证
  3. 配置隔离 VLAN 仅能访问认证服务器和补丁服务器 → 未认证设备无业务访问权
  4. 优先使用 EAP-TLS（证书）而非 EAP-PEAP（密码） → 防止密码撞库

### 各层加密应用举例（OSI 分层视角看加密覆盖范围）

1. 评估要保护什么（仅内容？还是元数据？还是 IP 地址？） → 决定加密层
  2. 仅保护应用内容 → 用 TLS 或应用层加密
  3. 保护 IP 元数据（如隐藏内部 IP 结构） → 用 IPsec 隧道模式
  4. 多层叠加（如 IPsec + TLS） → 防止单层被绕过，但需权衡性能

## B — 失效与边界 (Boundary)

- **用对话精确化问题定义**：直接回答表面问题，给出"合并排序"式答案；正确方向是 1.25MB 也能塞下的位图方案
- **多通道算法处理受限内存问题**：输入是实时流无法重读时不可用；通道数过多时 I/O 成本吞没收益
- **简单程序更安全健壮原则**：过度简化到失去必要的边界检查；把简化当作"删错误处理"的借口
- **边界条件与异常输入检测清单**：只测正常路径；只测一种异常而遗漏组合异常
- **二分查找作为通用探测工具**：判定函数非二元（返回"不确定"）；范围非单调（无法决定往哪半缩）
- **不变量驱动的代码验证流程**：不变量写得太弱（无法推出结果）或太强（无法保持）；忘记证明终止性导致死循环
- **循环三性验证法（初始化/保存/终止）**：跳过第五步导致死循环；初始化看似成立实则边界值不满足
- **前置/后置条件的契约编程**：前置条件过严导致正常调用被拒；后置条件过松导致调用方误用
- **调试提问法**：不问就猜；接受"随机出现"的描述而不追问复现条件
- **封底计算估算系统容量**：忘记量纲检查导致单位错；只算一次不交叉验证
- **安全系数法补偿未知**：系数给了但被业务压力挤掉；只对一个未知给系数而忽略其他
- **72 法则估算指数增长**：把线性增长当指数用 72 法则；增长率不稳定时盲目套用
- **利特尔法则**：非稳态系统（如突发流量）套用；忽略队列长度上限
- **性能问题分层定位法**：只在自己熟悉的层次找答案；层次间有依赖时忽略先后
- **从"单纯建立连接"转向"安全建立连接"**：仅在出事故后补安全；或把安全视为"便利性"的对立面而放弃（书中明确指出二者"作为两个对立的特性兼容并存"）
- **用 OSI 七层模型定位协议与攻击所在层级**：跨层误判（把 TCP RST 攻击当 IP 欺骗处理）；试图在错误层做加密（如仅在 IP 层加密却忽视应用层身份）
- **用 5 元组识别一条 TCP/UDP 通信流**：只看目的端口判定业务（忽略源端口被 NAT 改写）；只看 IP 不看协议号（TCP 80 与 UDP 80 是两条流）
- **知名端口与动态端口的划分边界**：把客户端临时端口（49152+）当作可疑端口封禁，会阻断所有出站；知名端口被劫持却因为"是合法端口"放过
- **TCP 三次握手与连接管理流程**：只看包数量不看状态分布，会把 P2P 高并发误判为 SYN flood；忽略 SYN cookies 启用后会看不到半连接
- **TCP 序列号与 ACK 实现可靠传输（含丢包/重发识别）**：混淆序列号与 ACK 号语义；忽略 PAWS（时间戳）保护导致误判
- **TCP 拥塞控制与慢启动阈值**：把正常慢启动误判为攻击（开始几秒流量低是正常的）；忽略 ECN 显式拥塞通告的影响
- **ARP 广播解析与缓存过期机制（ARP 欺骗的根因）**：仅在主机静态绑定网关 MAC 而忽视其他主机；忽略 IPv6 没有 ARP（用 ICMPv6 邻居发现，攻击机制不同）
- **代理 ARP 跨网段伪装主机**：把代理 ARP 当作"正常路由"忽略，导致跨网段欺骗长期存在
- **IP 分片只在目标主机重组（分片攻击的物理基础）**：只看首片就放行；IDS 与终端重组策略不一致导致检测 evasion
- **路径 MTU 发现（DF 位 + ICMP 不可达）**：把 ICMP 全封导致 PMTUD 黑洞；只放行 ICMP Echo 不放行 ICMP 不可达
- **IPv4 首部关键字段的安全读取口径**：用 TTL 单一值判定"经过几跳"忽略初始 TTL 差异（不同 OS 默认 64/128/255）；把首部校验和通过当作"包未被篡改"
- **NAT/NAPT 转换表的生成时机与生命周期**：把 NAT 当作"安全设备"依赖其阻止外联（攻击者用 DNS/ICMP 隧道绕过 NAPT）；忽略 UDP 表项超时差异
- **DNS 分层解析与缓存机制（DNS 投毒的物理基础）**：把权威服务器 TTL 设置过长导致事件后无法快速生效；忽略客户端自身 DNS 缓存（操作系统/浏览器）
- **包过滤防火墙用 SYN/ACK 标志位控制连接方向**：仅看 SYN=1 不看 ACK=0 会把 SYN+ACK 响应也误杀；有状态防火墙下规则写错仍可能因状态表错位失效
- **用 DMZ 隔离对外服务与内部网络**：DMZ 服务器被攻破后还有通往内网的高权限通道（如运维 SSH）；DMZ 与内网混用同一交换机导致二层穿透
- **IDS 与防火墙的互补关系**：只在边界部署 IDS，错过内网横向移动；IDS 告警量过大被忽略
- **PKI 通过可信赖第三方 + 数字证书验证通信方身份**：信任库中混入不可信 CA（企业 IT 推送的根证书）；忽略证书吊销检查（OCSP Stapling 未启用）；接受域名不匹配的证书
- **对称加密 + 公钥加密的混合使用模式**：对称密钥固定不变导致历史流量被一次密钥泄露全暴露（无前向保密）；用公钥加密大数据导致性能崩溃
- **IPsec VPN 的传输模式与隧道模式**：在 NAT 后用 AH 模式导致校验和失败；隧道模式两端内网网段重叠导致路由冲突
- **TLS/SSL 与 HTTPS 的握手流程**：客户端 `verify=false` 跳过校验；启用 TLS 1.0/1.1 弱版本；忽略证书吊销
- **IEEE 802.1X 的接入认证流程（VLAN 隔离未授权设备）**：隔离 VLAN 仍能访问其他设备（ACL 配置错误）；EAP-PEAP 弱密码被撞库；老设备不支持 802.1X 必须放行（MAC 旁路）
- **各层加密应用举例（OSI 分层视角看加密覆盖范围）**：在传输层加密（TLS）以为隐藏了 IP 地址（其实没隐藏）；在应用层加密以为防住了流量分析（其实 TCP/IP 元数据仍可分析）
