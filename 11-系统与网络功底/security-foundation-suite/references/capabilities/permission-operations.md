# 权限操作安全

## R — 原文 (Reading)

> "$ ls -l | grep '^...s'" / "它表示相应的执行权限位并未被设置，这是一种没有什么用处的suid设置"
>
> — 《Linux与unix shell编程指南》· 第1章 1.6 suid/guid

> "手指轻轻一敲就有可能输入chmod -R这样的命令，它将改变整个文件系统的权限，如果没有做备份的话，没有几年的时间恐怕是无法恢复了"
>
> — 《Linux与unix shell编程指南》· 第1章 1.10 小结

## I — 方法论骨架 (Interpretation)

这个能力解决的是主机上权限维度的两个相反方向的问题：**发现别人留下的风险面**（哪些程序带 suid/sgid、可被借用来提权）和**别让自己制造风险面**（批量改权限时别把整棵树改错）。核心判断是：权限位是一个按位置编码的紧凑字符串，肉眼扫描既慢又易错；而权限变更没有"撤销"操作，只能靠记忆或备份反推——所以前者要用正则按位枚举，后者要靠"先快照、限制半径、变更后比对"。

机制分两条主线。第一条是**风险面枚举**：`ls -l` 的权限串第 4 位是属主 x 位，被 suid 占用后显示为 `s`；用 `grep '^...s'` 按固定位置数点位，比肉眼扫或自己写脚本稳。关键是区分大小写——小写 `s` = suid 且仍有执行权限（真正可被利用的面），大写 `S` = suid 但 x 位没设、文件根本不能执行、可以忽略。作者同时警告：chmod 不做完整性检查，权限位存在不代表它是程序；很多系统会完全忽略脚本上的 suid 位。第二条是**变更安全**：`chmod -R` 把单点错误平摊到整棵子树，且执行时不产生"我改了 N 个文件"的回执；对冲手段是用同一条件先 `find ... -exec ls -l {} \;` 列出将被影响的文件、变更前把权限存档、不用 root 且只在必要子树执行、变更后抽样比对。

为什么把"发现"和"变更"放一张卡？因为它们用的是同一套"按位读权限串"的底层能力，且互为镜像——枚举时你要能从权限串判断 s/S，变更时你要知道 `chmod` 会怎样改写这些位。读完这段的人应能：用正则按位找出真正的 suid 文件、剔除 S 假目标、在改权限前留下可反推的快照。

## A1 — 应用示例 (Application Example)

### 示例 1: 按位枚举 suid 并用大小写过滤假目标
- **类型与来源**: 【例题】《Linux与unix shell编程指南》第1章 1.6 suid/guid（含作者【亲历】用法）
- **问题/输入**: 在一批目录里找出"真正可被利用的 suid 文件"，排除无效设置。
- **方法论的使用**: 在候选目录 `ls -l | grep '^...s'` 只找 suid（前三位任意、第四位为 s）；`ls -l | grep '^...s..s'` 找 suid 且 sgid；剔除含大写 `S` 的条目（无效设置）；逐条核对属主（属主非 root 的 suid 风险完全不同）与文件类型——注意很多系统完全忽略脚本上的 suid 位。
- **结论**: 小写 `s` 才有执行权限、是可利用面；大写 `S` 表示执行位未设、文件不能执行，可忽略。作者警告"不要看到一个文件具有执行权限，就认为它一定是一个程序或脚本"。
- **结果**: 原书【亲历】作者用带 guid 的脚本让指定用户完成数据库备份，避免其以 DBA 身份登录——说明 sgid 也可用于正当的权限委托，不全是风险。

### 示例 2: chmod -R 的爆炸半径与三条对冲
- **类型与来源**: 【转述】作者经验，《Linux与unix shell编程指南》第1章 1.10 小结
- **问题/输入**: 需要批量改权限，但担心"手指一敲改掉整个文件系统"。
- **方法论的使用**: 先用同一条件 `find ... -exec ls -l {} \;` 列出将被影响的文件；把变更前权限存档（`ls -l` 输出或 `stat` 结果重定向到文件）；不用 root 执行、只在必要子树执行（不从高位目录 `-R`）；变更后抽样 `ls -l` 验证并与存档比对。
- **结论**: 风险不在语义难度而在反馈缺失——`-R` 把单点错误平摊到整棵树，且不产生"改了 N 个文件"的回执。作者的三条对冲是：非 root、可监控、有备份；并强调以 root 给脚本设 suid 时"一定要确保能够监控它的使用"。
- **结果**: 原书以"千万不要在手指上贴膏药"比喻手滑，强调输入这类命令时的谨慎；没有交代具体恢复案例。

### 示例 3: 变更半径的快照对照（合成演练）
- **类型与来源**: 【合成演练】按本卡 E 段规则推演，非原书案例，不代表真实运行结果
- **问题/输入**: 要对 `./app/data` 子树做一次 `chmod -R 640`，想在执行前确认半径。
- **方法论的使用**: 先把 `find ./app/data -type f -exec ls -l {} \;` 的输出重定向为快照；把 `-R` 的起点限制在 `./app/data` 而非 `./app`；执行后抽样 `ls -l` 与快照比对，并用 `stat` 验证属主/组未变。
- **结论**: 对照半径由"起点目录 + 快照行数"双重界定，任一项超出预期即判停。
- **结果**: 合成演练结论为"快照行数与计划一致、变更后抽样品位正确"才算完成；此为按规则的推演，非原书实测。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 要排查主机上的提权面，枚举 suid/sgid 文件并剔除无效设置。
2. 需要批量改权限（chmod -R），但担心改错子树、无法恢复。
3. 审计某目录的权限位，想确认"看起来有执行权限"的文件是否真的是可执行程序。

### 语言信号（出现这些就该激活）
- 中文：「找 suid 提权点」「权限面排查」「批量改权限」「chmod 改错了怎么恢复」「suid 命令有哪些」
- English: "find suid binaries", "recursive chmod gone wrong", "suid vs SUID uppercase S", "permission audit"

### 与相邻能力的区分
- 与 `batch-file-operations` 的区别：两者都涉及不可逆操作与"先列清单"，但相邻卡的对象是文件内容/存在性（有留副本这个低成本对冲），本卡的对象是权限位——没有撤销键，只能靠快照反推。
- 与 `cli-forensics` 的区别：相邻卡用 lsof/netstat 看进程"打开了什么/连了哪里"，本卡枚举"哪些程序带提权位"；两者都在主机上但回答不同问题。
- 与 `text-processing-pipeline` 的区别：本卡的 `grep '^...s'` 是按位置数权限串，相邻卡的 grep 是按内容选行；不要混用字段语义。

## E — 可执行步骤 (Execution)

**必需输入**: 目标目录/文件集合；是"枚举风险面"还是"执行权限变更"；允许的半径（哪棵子树）与是否可不用 root。缺"操作意图"时必须先问——枚举与变更是两条不同流程。

**交付物与完成标准**: 枚举任务产出"有效 suid/sgid 清单（含属主、文件类型、s/S 标注）"；变更任务产出"变更前权限快照 + 变更后抽样比对结果"。完成标准是假目标已剔除、半径未越界、变更可反推。

1. **界定目标与半径**
   - 做什么：明确候选目录；对变更任务，把起点限制到必要子树，不从高位目录 `-R`。
   - 完成标准：能写出"只在 <路径> 内操作"的明确边界。
   - 判停：若必须从高位目录开始或必须 root 执行，停止并改为分步/降权方案，不要整把过。

2. **按位枚举（枚举分支）**
   - 做什么：`ls -l <dir> | grep '^...s'` 找 suid；`grep '^...s..s'` 找 suid+sgid；逐条看第 4 位是 `s` 还是 `S`。
   - 完成标准：清单只含小写 `s` 的有效项（大写 `S` 已剔除），并记录属主与文件类型。
   - 判停：若属主非 root 或文件是脚本（很多系统忽略脚本 suid），单独标注而非直接计入风险面；若权限位存在但不能确认是程序，转第 4 步核对文件类型。

3. **快照半径（变更分支）**
   - 做什么：用同一条件 `find <path> ... -exec ls -l {} \;` 列出将被影响的文件并重定向存档；必要时 `stat` 一并存档。
   - 完成标准：快照行数与预期相符，路径均在允许子树内。
   - 判停：若快照里出现子树外的路径，回到第 1 步缩小 find 条件后重新快照。

4. **核对文件类型与完整性**
   - 做什么：对可疑 suid 项确认它是否真是可执行程序（作者：chmod 不做完整性检查，权限位存在不代表它是程序；很多系统忽略脚本 suid）。
   - 完成标准：每项都能回答"是可执行体/脚本/无效设置"中的哪一种。
   - 判停：若无法确认，保留为"待核"而非直接定性；对变更任务，若目标文件类型与预期不符，停止变更。

5. **执行变更并抽样比对**
   - 做什么：以非 root、在必要子树内执行 `chmod`；变更后抽样 `ls -l` 与快照逐项比对。
   - 完成标准：抽样项权限与计划一致，属主/组未被意外改动。
   - 判停：若抽样不符，从快照反推恢复后停止，不要在原状态上继续叠加变更。

## B — 边界 (Boundary) ★

### 不要用的情况
- 只是查看单个文件的权限——`ls -l` 即可，不必上枚举正则。
- 需要修改文件内容而非权限位——转 `batch-file-operations`。
- 系统对脚本 suid 的处理未知——枚举结论必须标注"待核"，不要直接计入风险面。
- 无法留下快照或无法限制子树——不具备安全变更的前提条件，停止。

### 已知失败模式
- **不区分 s/S 导致报告失真**：《Linux与unix shell编程指南》第1章——大写 S 表示执行位未设、文件不能执行，是"没有什么用处的 suid 设置"，当作风险会高估。
- **把有执行权限当程序**：同章——"不要看到一个文件具有执行权限，就认为它一定是一个程序或脚本"；chmod 不做完整性检查。
- **chmod -R 无回执、不可逆**：同书 1.10——"手指轻轻一敲就有可能输入 chmod -R"，改整个文件系统且无撤销键，没备份"没有几年的时间恐怕无法恢复"。
- **以 root 给脚本设 suid 且无监控**：同章——作者要求"一定要确保能够监控它的使用"。
- **高位目录递归**：同书 1.10 的爆炸半径——从高层目录 `-R` 会把无关子树一并改掉。

### 作者与时代的局限
- 枚举靠 `ls -l | grep '^...s'` 按列位置取字符，依赖 `ls` 输出的固定格式；现代 `ls` 带 ACL（权限串末尾 `+`）或 SELinux 上下文时格式可能变化，需核对列位。
- 关于"很多系统忽略脚本 suid"的判断基于当时的 Unix 变体，现代 Linux 行为需实测确认。
- 示例未涉及 capabilities（setcap）等现代细粒度权限机制，suid 不再是唯一的提权面。

### 容易混淆的方法
- 小写 `s`（suid+可执行）与大写 `S`（suid 但执行位未设）：前者是有效风险面，后者可忽略。
- 本卡与 `batch-file-operations` 都讲"不可逆操作+先列清单"：文件类可留副本，权限位类只能快照反推——对策强度不同，不要照搬。
- 枚举 suid（发现风险）与给文件设 suid（制造风险）是相反操作，前者用正则按位筛，后者要受"非 root、可监控、有备份"约束。
