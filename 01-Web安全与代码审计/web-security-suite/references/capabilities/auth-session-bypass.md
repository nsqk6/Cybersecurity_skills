# 认证与会话：找「哪一步的判断可以被单独满足」

## R — 原文 (Reading)

> "If the call to db.getUser() throws an exception for some reason (for example, a null pointer exception arising because the user's request did not contain a username or password parameter), the login succeeds."
>
> 译：如果 db.getUser() 因某种原因抛异常（例如请求里没有 username 或 password 参数导致空指针），登录反而成功。

> — 《The Web Application Hacker's Handbook》Ch6 / Fail-Open Login Mechanisms

> "If you capture 5,000 tokens that are shown to pass the randomness tests, you may decide that this is sufficient. However, to achieve compliance with the formal FIPS tests for randomness, you need to obtain a sample of 20,000 tokens."
>
> 译：如果采集 5000 个通过随机性检验的 token，可以认为够用了；但要符合 FIPS 正式测试，需要 20000 个样本。

> — 同上 Ch7 / Testing the Quality of Randomness

> "短信验证码大部分情况下是由4～6位数字组成，如果没有对验证码的失效时间和尝试失败的次数做限制，攻击者就可以通过尝试这个区间内的所有数字来进行暴力破解攻击。"
>
> — 《Web 攻防之业务安全实战指南》第 9 章 验证码机制测试

## I — 方法论骨架 (Interpretation)

认证类漏洞的共同结构是：**状态判断被放在了错误的一侧**。系统在某处做了一个「是否已通过」的判断，但这个判断可以被单独满足、被跳过、被复用或被预测。因此本能力的核心不是记攻击串，而是**找出每一道认证检查「依赖什么」，然后让那个依赖失效**。

五类依赖，对应五组动作：

1. **依赖「异常即失败」**。fail-open 的本质是异常路径没有显式拒绝（`catch` 后直接掉进成功分支）。判据不是读代码，而是**系统性地让每个输入坏掉**：空串、删除整个名值对、超长/超短、类型互换、同名参数重复，看是否反而放行。
2. **依赖「顺序」**。多阶段登录假定「能到第三阶段的人一定过了前两阶段」。判据是直接请求后一阶段并补上它期望的字段，看是否被当作已通过。作者特别反驳「多阶段更安全」：阶段越多，实现出错的机会越多。
3. **依赖「一次性凭据」**。验证码/重置 token 的安全性取决于四个服务端约束：有失效时间、有失败次数/频率限制、成功即失效、只在服务端生成与比对。任一缺失即可绕过，且不需要图像识别。
4. **依赖「随机」**。token 能否被预测不能靠「看起来乱」，要靠两条独立判据并用：统计检验（有效熵）与结构分析（hex/Base64 解码后是否含用户名、角色、时间戳）。两个方向都会误判——确定性生成器可能通过统计检验，某一位不通过也不代表可预测。
5. **依赖「签名算法由服务端决定」**。JWT 若信任 header 里的 `alg`，就能用 `None`（无签名）或把 RS256 降级为 HS256（公钥当 HMAC 密钥）伪造任意声明。

贯穿全部的一条纪律：**先用自有账号建立基线（正常流程长什么样），再做单变量变异**。没有基线，任何「异常响应」都无法解释是漏洞还是正常分支。

## A1 — 应用示例 (Application Example)

### 示例 1: 畸形请求矩阵打 fail-open
- **类型与来源**: 【例题】《The Web Application Hacker's Handbook》Ch6（mdsec.net/auth/300）
- **问题/输入**: 一个登录接口提交 `username`/`password`。
- **方法论的使用**: ① 完整正常登录一次，记录每个字段与每个响应；② 对每个参数/cookie 依次施加五种变异：空字符串；整对删除；超长与超短；类型互换（数字↔字符串）；同名参数重复提交（同值/不同值）；③ 逐条对比基线与响应，找「本应失败却成功」或「本应报错却进入下一阶段」；④ 把有分歧的变异相互组合（如「删口令 + 提交两个 username」）；⑤ 特别关注多阶段登录：只提交后一阶段字段、跳过前一阶段。
- **结论**: fail-open 不需要读代码就能发现——让输入「坏掉」，看控制流是否掉进成功分支。
- **结果**: 原书称此处列出的每种实现缺陷都在大型银行的 Web 应用中出现过。

### 示例 2: 验证码五项缺陷
- **类型与来源**: 【亲历】《Web 攻防之业务安全实战指南》第 9 章
- **问题/输入**: 注册/投诉功能的 4–6 位短信验证码。
- **方法论的使用**: ① 测有效期：取一个验证码等 5/10/30 分钟再提交 → 仍通过即无失效控制；② 测复用：同一验证码连发两条投诉 → 都成功即未清 session；③ 测回显：抓「发送验证码」响应包，全文搜 4–6 位数字 → 响应里带码等于无验证；④ 测改包：填错码，拦截 Response 把 `res_code:1` 改成 `0` 再 Forward → 进入下一步即校验在客户端；⑤ 测爆破：固定账号对 code 跑 0000–9999，按响应长度/状态码区分。
- **结论**: 验证码的强度取决于服务端四个约束，不取决于图形难度。
- **结果**: 作者在多个站点分别命中：爆破至 46547 后注册成功、验证码重复使用、验证码本地生成并回显、改 `res_code` 绕过。

### 示例 3: 改收件人参数夺重置凭证
- **类型与来源**: 【亲历】《Web 攻防之业务安全实战指南》12.1 / 12.3
- **问题/输入**: 找回密码流程有三个包：发送凭证、校验凭证、提交新密码。
- **方法论的使用**: ① 三包齐抓，记录每个包里的「账号参数」与「收件参数」；② 改收件参数（`email`/`telno`）为自己的地址、账号参数保持受害者 → 自己收到凭证即成立；③ 或改账号参数为受害者、凭证参数用自己已获得的 → 能重置即 token 未与账号绑定；④ 检查响应体/响应头/跳转 URL 是否直接含 4–6 位码或 token；⑤ 检查「重新发送验证码」接口（常复用同一 session，是改收件人最省事的入口）。
- **结论**: 信任链是「能收到凭证 = 是账号主人」；一旦「目标账号」与「收件地址」解耦，整条链断裂。
- **结果**: 作者在三个站点分别命中响应回显验证码、改 email 收到他人重置邮件、改 account 因 token 可复用而重置成功。

### 示例 4: JWT 三种绕过
- **类型与来源**: 【亲历】《泰阿漏洞挖掘自动化赏金技巧手册》技巧 6 / 25
- **问题/输入**: 一个携带 JWT 的接口，header 为 `{"alg":"RS256"}`。
- **方法论的使用**: ① base64url 解 header/payload，记录 `alg`、`kid`、声明字段；② 把 `alg` 改为 `None`（或 `none`/`NONE`），删掉签名段保留 `xxx.`，改 payload 中 `email`/`uid` 为受害者 → 请求被接受即成立；③ 原为 RS256 时改为 HS256，用站点证书/`jwks` 里的公钥做 HMAC 密钥重签；④ 另测「注销后旧 token 是否仍有效」（服务端无黑名单）；⑤ 变体：直接删签名部分发 `header.payload.`，或把 `uid` 改成已知管理员。
- **结论**: JWT 的安全性完全依赖「服务端是否硬编码验签算法」；信任 header 的 `alg` 等于把签名权交给客户端。
- **结果**: 作者从 APK 中提取签发接口，移除签名段后请求成功，再用改过的用户 ID 得到他人 JWT，实现账户接管。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 登录框疑似可以绕过，但不知道从「异常路径」「多阶段」「凭据」哪一侧入手。
2. 有账号锁定/限速，需要判断「换会话/换 cookie/换 IP 头」能否重置计数。
3. 验证码看起来能绕过，需要区分「图形识别」与「服务端约束缺失」两条完全不同的路。
4. 找回密码流程可疑，需要判断是改收件人、改账号、还是猜 token。
5. 站点用 JWT/OAuth，需要验证签名与回调校验是否可信。
6. 会话 token 看起来乱，但不确定能否预测；或 token 里有可读结构。

### 语言信号（出现这些就该激活）
- 中文：「登录能不能绕过」「异常会不会放行」「少传参数会怎样」「多步登录能不能跳步」「验证码能不能绕过」「任意用户密码重置」「重置链接能不能猜」「JWT 能不能伪造」「token 够不够随机」
- English: "fail open login", "login bypass", "multistage login skip", "captcha bypass", "account lockout bypass", "password reset poisoning", "weak reset token", "JWT alg none", "predictable session id", "token entropy"

### 与相邻能力的区分
- 与 `access-control-idor` 的区别：本卡解决「怎么进系统/怎么拿到别人账号」，那张卡解决「进来之后能访问谁的数据」。
- 与 `business-logic-flaws` 的区别：认证流程的顺序假设与那张卡的「业务流程假设」同源，但对象是「身份」，那张卡是「金额/配额/状态」。
- 与 `csrf-ui-redress` 的区别：CSRF 借的是已登录会话，本卡攻的是「会话怎么建立」。
- 与 `deserialization-rce` 中 Shiro `rememberMe` 的区别：那条链把「加密的序列化 Cookie」当攻击载体，终态是 RCE；本卡只关心「身份是否可伪造」。

## E — 可执行步骤 (Execution)

**必需输入**: 至少一个自有账号（用于建立基线与探测锁定）；用户名清单（爆破/枚举用）；能精确重放与改包的代理；接收验证码的邮箱/手机。缺自有账号时无法建立基线，只能做静态推断，结论需标注。

**交付物与完成标准**: 一张「认证环节 → 依赖什么 → 变异动作 → 结果」的表；完成标准是每条结论都有「正常基线 vs 变异后」的对照，且能说清绕过后能做什么（登录某账号 / 重置某账号 / 伪造身份）。

1. **建基线并探锁定**
   - 做什么：正常登录一次记录全字段与响应；对自有账号连发约 10 次错误登录看是否锁定；再正确登录确认锁定是否解除。
   - 完成标准：知道「成功/失败」的判别信号（状态码+长度+关键字+跳转）。
   - 判停：有锁定时先测阈值，再决定字典规模；不要一上来跑大字典把账号锁死。

2. **异常路径矩阵（fail-open）**
   - 做什么：对每个参数/cookie 施加五类变异（空/删名/超长超短/类型互换/同名重复），逐条对比基线；把有分歧的变异组合；多阶段登录时只提交后一阶段字段。
   - 完成标准：找出「本应失败却成功」或「跳过阶段仍前进」的分支。
   - 判停：只试空串不够——「删除参数名」与「给空值」在服务端走不同分支。

3. **多阶段顺序假设**
   - 做什么：用自有账号走完全流程，记录阶段间传递的隐藏字段；直接请求第 3 阶段并补上第 2 阶段本应产生的字段；修改阶段间传递的用户标识；检查最后一步是否对前面收集的数据做全量重校验。
   - 完成标准：能证明「跳步后仍被当作已通过」。
   - 判停：只在浏览器点后退/前进不够，必须用代理直接构造单步请求（前端可能拦、服务端不拦）。

4. **凭据类：验证码与重置 token**
   - 做什么：验证码测五项（有效期/复用/回显/改包/爆破）；重置测三项（改收件人/改账号/token 结构）——同账号连发 3–5 封看 token 长度与字符集，解码看是否含邮箱/uid/时间戳，固定可推导部分只枚举随机段。
   - 完成标准：能定位到「哪一个服务端约束缺失」。
   - 判停：token 强随机 + 服务端存储比对 + 一次性 → 枚举不可行，立即停止；有时区/延迟时先校准服务器时间再猜时间戳。

5. **用户名枚举（作为爆破与社工的前置）**
   - 做什么：用自有有效用户名 + 错口令、随机用户名各登录一次，逐字节比对响应（状态码、跳转、文案、HTML 注释、布局）；内容无差异时改测时间（采集响应时长统计两组分布）；在所有接受用户名的位置重复（注册、改密、忘记密码）。
   - 完成标准：能把「用户名 × 口令」的空间压缩到「口令」。
   - 判停：只看屏幕文案会漏掉源码级差异与时间差；有锁定时不要盲跑字典。

6. **口令爆破的广度优先**
   - 做什么：建立成功/失败判别信号；按口令质量规则裁剪口令表；广度优先（先遍历口令表、对每个用户名各试一次）；有锁定时每次尝试换新会话，或用「锁定了也能从响应差异判断口令对错」的缺陷继续。
   - 完成标准：命中项可复现登录。
   - 判停：深度优先会快速触发单账号锁定；客户端 `failedlogins` 计数 cookie 或会话内计数可被换 cookie 绕过，别当防护。

7. **会话 token 双判据**
   - 做什么：① 结构分析——识别 hex/Base64/分隔符，解码看是否含用户名/角色/时间/序号，改字段重放看是否被接受；查是否「每次登录都相同」（静态 token）、是否允许并发会话；② 统计检验——找「一次请求即发新 token」的端点采集样本（<100 无效，几百可判明显失败，5000 视为够用，FIPS 需 20000），读聚合有效熵，再下钻看哪些片段是结构化的。
   - 完成标准：两条判据都给结论，并说明「哪条是决定性的」。
   - 判停：只跑统计会漏「随机但可读」；看到可读结构就断言可利用也不对，必须实测改字段后是否被接受。

8. **JWT / OAuth 协议层**
   - 做什么：JWT 测三件（`alg=None`、RS→HS 降级、注销后旧 token 复用）；OAuth 测两件（是否带 `state` 且回调校验、`redirect_uri` 是否与 client 绑定）——把 `redirect_uri` 改为外域，未报错且跳转带 `code` 即成立；绕过形态按白名单类型选（`http://白名单域.evil.com`、`http://白名单域@evil.com`、`//evil.com`，必要时二次 URL 编码）。
   - 完成标准：能拿到可用身份（伪造的 JWT / 他人的 code）。
   - 判停：`redirect_uri` 做全等白名单时改域失败；只校验主域后缀的实现可被 `facebook.com.localhost` 类前缀绕过。

9. **限速与来源维度的削弱**
   - 做什么：连续请求直到出现 429/验证码，记录触发点；加 `X-Forwarded-For: 10.0.0.1` 重试是否恢复；轮换内网段（`10/8`、`172.16/12`、`192.168/16`、`127/8`）与七个常见来源头，找出真正被信任的那个。
   - 完成标准：能证明「计数维度可被客户端控制」。
   - 判停：边缘组件用 TCP 源 IP 或取 XFF 最右值时伪造无效；多级代理会 strip 自定义头。

## B — 边界 (Boundary) ★

### 不要用的情况
- 目标已启用统一身份提供方（SSO）+ 强制 MFA + 服务端会话黑名单：本卡多数分支失效，应转向「OAuth/SAML 协议实现」而非口令层。
- 密码重置走「一次性链接 + 强随机 + 短有效期 + 绑定账号」且无收件人参数：枚举与改收件人都不可行。
- JWT 服务端硬编码 `alg` 白名单且校验 `kid` 来源：三种绕过全部失效。

### 已知失败模式
- **只试空字符串**：「删除参数名」与「给空值」走不同分支（原书在逻辑漏洞章节也强调同一纪律）。
- **深度优先爆破**：快速触发单账号锁定，把账号锁死并浪费枚举额度。
- **把客户端计数当防护**：`failedlogins` cookie 或会话内计数，换 cookie/换会话即重置。
- **只看屏幕文案做用户名枚举**：漏掉 HTML 注释、DOM 结构、响应时间三类差异。
- **验证码一上来就上 OCR**：逻辑无缺陷时才需要识别；先测四项服务端约束。
- **token 只做统计检验**：确定性生成器（线性同余、对递增数哈希）可能通过统计检验，但仍可被完全外推。
- **重置 token 猜时间戳不校时**：有时区/延迟时全错，应先校准服务器时间。
- **「有 state 就安全」**：`state` 固定或不校验回调，等于没有。
- **把 `alg=None` 的失败当「JWT 安全」**：还要测降级、`kid` 注入、注销后复用。

### 作者与时代的局限
- 书中「清除会话」「一次性 token」的建议基于服务端 session 架构；现代无状态 JWT + 短有效期 + refresh token 的模型下，「注销即失效」需要额外的黑名单/版本号机制，书中未覆盖。
- 短信验证码的爆破在运营商侧有额外风控（同号码/同 IP 频次），书中的「跑完 0000–9999」在实践中常被上游拦截，需先测真实阈值。
- `SameSite` cookie 的普及改变了「会话只靠 cookie」这一条件的实际强度，判定时须先看 cookie 属性。
- OAuth 2.1 草案已要求 PKCE 与严格 `redirect_uri` 匹配，书中的多数绕过形态在新实现上失效。

### 容易混淆的方法
- **认证 vs 授权**：本卡解决「你是谁」，`access-control-idor` 解决「你能碰谁的数据」；同一请求可能同时命中两者，报告应分别归因。
- **fail-open vs 多阶段跳步**：前者是「异常导致放行」，后者是「顺序假设导致跳步」；修法不同（补异常分支 vs 服务端记状态）。
- **验证码绕过 vs 限速绕过**：前者打「一次性凭据」，后者打「计数维度」；同一登录框可能两者都需要。
- **弱 token vs 静态 token**：前者熵不足可枚举，后者根本不随机（一次泄露即永久沦陷所有账号）。
