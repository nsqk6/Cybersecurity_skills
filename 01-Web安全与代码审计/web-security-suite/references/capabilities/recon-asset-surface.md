# 攻击面测绘：把「一个域名」拆成可测的功能与资产清单

## R — 原文 (Reading)

> "Browse the entire application normally, attempting to visit every link/URL you discover, submitting every form, and proceeding through all multi-step functions to completion. Try browsing with JavaScript enabled and disabled, and with cookies enabled and disabled."
>
> 译：像普通用户那样完整浏览应用，访问发现的每一个链接/URL，提交每一张表单，把每个多步功能走到最后。分别在有/无 JavaScript、有/无 cookie 两种配置下各走一遍。

> — 《The Web Application Hacker's Handbook》Ch4 Mapping the Application / Web Spidering

> "攻击任何目标的第一步是进行侦察，或者简单地说，收集有关目标的信息。侦察是重要的，因为它是您确定应用程序攻击面的方式。为了最有效地寻找漏洞，您需要在决定最有效的方法之前发现攻击目标的所有可能方法。"
>
> — 《Bug Bounty Bootcamp》Ch5 Web Hacking Reconnaissance

> "接下来，在Burp中发送HTTP请求到服务器，检查所使用的HTTP标头，以获取有关技术栈的信息。"
>
> — 《Bug Bounty Bootcamp》Ch5 Tech Stack Fingerprinting

## I — 方法论骨架 (Interpretation)

这个能力解决的是「面对一个只知道域名（或一个 App、一个 IP 段）的目标，怎样在不漏项的前提下把可测范围定下来」。它不是在收集信息，而是在**收缩搜索空间**：从整片互联网 → 该组织的资产 → 该资产暴露的服务 → 该服务上的功能 → 每个功能吃的输入。

核心机制有三层，缺一层后面就全靠运气：

1. **人的行为喂机器**。自动爬虫只看得到链接图，看不到「走完流程才出现的 URL」和「JS 拼出来的 URL」。把浏览器挂在代理后面，人负责触发状态变迁（提交表单、走完多步流程、切换角色），代理负责记录与递归解析响应。两种浏览器配置（JS 开/关、cookie 开/关）各走一遍，是因为服务端常按能力探测走不同代码路径，能多暴露一套内容。
2. **资产维度与功能维度必须分开走**。资产维度是「外→内」：域名→子域→端口/服务→目录→第三方托管→代码仓库→OSINT。功能维度是「用→懂→测」：先以每种角色各注册一个账号把站走通，再把功能按「功能名」而非「页面」建图（`?action=editUser`、`servlet=X&method=Y` 这类单入口分派会让目录爆破彻底失效）。
3. **判断依据必须是响应而不是假设**。目录爆破的准确率完全取决于「存在/不存在」的判别信号；很多应用对不存在的资源返回自定义错误页配 200，拿状态码当判据会全量误报。同理，指纹不能只信 `Server` 头（可被改写、可被 CDN 统一），要用默认路径、报错页、cookie 命名、favicon 哈希交叉验证。

测绘的终点不是一张资产表，而是一张**「功能/资产 → 最可能烂在哪 → 先测哪条」的排期表**。没有这张表，就只能在别人的主站上和几百个猎人抢同一批低垂果实。

## A1 — 应用示例 (Application Example)

### 示例 1: EIS 应用的路径级攻击面取舍
- **类型与来源**: 【例题】《The Web Application Hacker's Handbook》Ch4 末（EIS 应用）
- **问题/输入**: 一个演示应用暴露了 `/auth`、`/core`、`/gb`、`/home`、`/pub`、`/shop` 六组路径，需要决定先测哪一组、每组测什么。
- **方法论的使用**: ① 手工走站，把每组路径下的功能走完（登录、注册、下单、留言）；② 对 `/auth` 做文件名爆破，命中 `Login/Logout/Register/Profile`，其中 `Profile` 返回 302 指向登录页 → 判定为「需认证后才可达」，登记为带 cookie 重放的候选；③ 按「功能形态 → 典型漏洞」映射：`/auth` 挂弱口令/用户名枚举/多阶段登录，`/shop` 挂金额与数量篡改，`/pub` 挂存储型 XSS 与注入，`/core` 挂访问控制；④ 对 `/icons`、`/images` 这类静态目录只做快速扫一眼，不投入时间。
- **结论**: 攻击面按「高价值功能 × 高危漏洞」排序，而不是按目录顺序平均用力。
- **结果**: 原书以该应用贯穿全章演示映射流程，未给出完整测试结论。

### 示例 2: 从 403 里挖出真实资产
- **类型与来源**: 【例题】《Bug Bounty Bootcamp》Ch5 Directory Brute-Forcing（dirsearch 输出）
- **问题/输入**: 对一个域跑目录爆破，结果里出现 `403 /.svn/entries`、`403 /server-status` 与大量 404。
- **方法论的使用**: ① 先请求一个确定存在与一个确定不存在的路径，记录两者状态码/长度/正文特征，建立「不存在」基线；② 分流：200 段直接访问，**403 登记为「存在但需绕过」**（403 本身就是情报——有保护说明后面有东西），301 跟随并记录跳转目标，404 丢弃；③ 对 403 逐条试路径变形、大小写、加 `/.`、换方法、加头；④ 用 EyeWitness 对存活 URL 批量截图，人工挑出后台、目录列表、旧版页面。
- **结论**: 「扫出来一堆 403」不是噪音，是绕过类漏洞的入口清单。
- **结果**: 原书以该输出说明 403 应当作「存在」处理，未逐条给绕过结果。

### 示例 3: 前端渲染页里的隐藏端点
- **类型与来源**: 【转述】《Web Hacking 101》Ch20 个案 7（HackerOne Hacktivity 投票）
- **问题/输入**: 一个功能页 View Source 只有几个空 div，看不出投票入口在哪里。
- **方法论的使用**: ① 判断页面由 JS 渲染 → 去 DevTools Sources 或代理里取 bundle；② `{}` pretty print 展开压缩代码，搜 `POST`/`/api`/`graphql`，在第 20570 行找到投票的 POST 调用；③ 构造该路径的请求并带上当前 cookie → 返回数据即端点存在；④ 另一条路：拦截返回的权限字段（`hacktivity_voting_enabled: false`）改为 `true`，观察隐藏按钮出现及其触发的新请求。
- **结论**: JS bundle 就是一份可读的接口清单，包含当前权限下 UI 不显示的操作。
- **结果**: 原书说明该发现获得平台奖励（swag），未给出金额。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 刚拿到一个 SRC/众测目标（只有域名或一个 App 包名），不知道从哪开始、担心挖到重复洞。
2. 扫描器跑完了，但报告里全是「信息泄露」「目录列表」，需要判断哪些是真资产、哪些是软 404 噪音。
3. 站很硬（WAF + 统一框架），需要找「后加的/第三方的/老版本的」那块软肋。
4. 需要给甲方出一份「攻击面清单 + 测试排期」，而不是一页漏洞列表。
5. 只有一个登录框、别的路都堵死，需要判断是否值得继续投入（转 `source-code-audit`）。

### 语言信号（出现这些就该激活）
- 中文：「怎么摸清这个站的攻击面」「爬虫扫不全」「扫出来一堆 403 还有用吗」「新目标从哪开始」「怎么避免挖到重复洞」「响应头能看出什么框架」
- English: "map the attack surface", "where do I start on a new target", "soft 404", "content discovery false positive", "fingerprint tech stack", "find hidden endpoints in JS bundle", "recon pipeline"

### 与相邻能力的区分
- 与 `source-code-audit` 的区别：本卡在**黑盒/灰盒**下产出「测什么」，那张卡在**有源码**时产出「哪一行有问题」。两者可接力：本卡发现 `.git` 泄露或备份文件 → 转源码审计。
- 与 `access-control-idor` 的区别：本卡只负责把入口和角色列全，具体「换 ID 能不能越权」是那张卡的动作。
- 与 `waf-bypass-encoding` 的区别：本卡遇到 WAF 只记录「有设备、大概是谁」，不展开绕过。

## E — 可执行步骤 (Execution)

**必需输入**: 目标范围（域名/子域通配/App/API 基址，必须明确边界）；至少一个可用账号（有登录态才看得到登录后内容）；一个可交互代理（Burp/ZAP）。缺范围就先问，缺账号就先确认能否注册。

**交付物与完成标准**: 一份「资产清单 + 角色/功能清单 + 入口清单 + 排期表」四件套；完成标准是——随便指一个功能，能答出「它吃什么输入、最可能烂在哪、排在第几位」。

1. **手工走站（功能维度）**
   - 做什么：以每种权限各注册一个账号，点遍所有链接、提交每张表单、把多步流程（注册/下单/支付/退款/邀请）走到完成；分别在有/无 JS、有/无 cookie 下各走一遍。
   - 完成标准：能复述系统有几个业务域、几个角色、数据从哪进、用户之间怎么互动。
   - 判停：若走不通某流程（缺权限/缺测试数据），记录缺口并转为「资产维度优先」。

2. **资产扩张（外→内）**
   - 做什么：WHOIS/反查 → 证书透明度（crt.sh）→ 子域枚举（subfinder/amass/assetfinder 三源合并去重）→ 按命名规律推（`1.`/`3.` 存在则试 `2.`）→ 递归找子域的子域 → Nmap/Masscan 扫端口 + Shodan/Censys 被动查 → 目录爆破 → Wayback/GAU 拉历史 URL。
   - 完成标准：新增资产清单连续一轮不再增长。
   - 判停：若目标只允许单 URL，跳过本步直接进第 3 步。

3. **建「不存在」基线，再判读爆破结果**
   - 做什么：各请求一个确定存在/不存在的资源，记录状态码+长度+正文特征；按 200/403/301/404 分流；对每个 403 登记为「待绕过」。
   - 完成标准：每条命中都能说出「凭什么判断它存在」。
   - 判停：若全站都是软 404（长度一致、200），改用「响应长度聚类 + 关键字」判读，不要用状态码。

4. **功能建图（而非页面建图）**
   - 做什么：找出「功能名在参数里」的实例（`?action=`、`servlet=`、`method=`）；探测非法功能名的报错建立基线；以「功能名 × 方法名」爆破；把结果画成有向图，标出「哪些步骤假设前一步已完成」。
   - 完成标准：图上每条边都能对应一个真实请求。
   - 判停：若为纯 REST（路径段即参数），跳过本步，直接把路径段当参数进第 5 步。

5. **枚举全部输入入口（含隐藏通道）**
   - 做什么：按五类逐条列——查询串之前的路径段、查询串参数、POST 体参数、每个 cookie、每个 HTTP 头（重点 `User-Agent`/`Referer`/`Accept`/`Accept-Language`/`Host`）；对非标准格式（`;foo=bar`、`?a=1$b=2`、内嵌 XML）先解剖格式再放载荷；追加 `X-Forwarded-For` 等平台信任头重放；补带外通道（SMTP 收信、应用主动取 URL、非浏览器 API 写入后回流）。
   - 完成标准：入口清单覆盖「参数名本身」和「参数值」两个层级。
   - 判停：若发现某入口走移动端简化界面（换 UA 响应不同），把它单列为新攻击面。

6. **指纹定版并映射已知问题**
   - 做什么：`nmap -sV` + 响应头（`Server`/`X-Powered-By`/`X-Generator`/`Set-Cookie` 命名）+ Wappalyzer 交叉；用默认路径与报错页验证（不只信头）；版本去 CVE 库/厂商公告比对。
   - 完成标准：技术栈（语言/框架/中间件/前端库）与版本均有至少两个独立证据。
   - 判停：若头被统一改写（CDN），改用 favicon 哈希、默认页、404 页特征指纹；仍无法定版则转 `waf-bypass-encoding` 的指纹节。

7. **出排期表**
   - 做什么：按 17 条经验映射（客户端校验→服务端未复检；数据库交互→SQLi；上传下载→路径穿越/存储型 XSS；回显用户数据→XSS；动态跳转→跳转与头注入；社交→用户名枚举；登录→弱口令/爆破；多阶段→逻辑漏洞；会话→可预测 token；访问控制→纵向/横向越权；模拟他人→提权；明文通信→会话劫持；站外链接→Referer 泄露；外部系统接口→权限捷径；错误消息→信息泄露；邮件交互→邮件/命令注入；第三方组件→已知漏洞）逐项落位，再按「最像有洞 × 最严重」排序。
   - 完成标准：前 10 项每项都能指向具体 URL/参数。
   - 判停：若某功能连续两项都验证无洞，降低其优先级，把时间移到「后加/异构」区域（见 B 段）。

## B — 边界 (Boundary) ★

### 不要用的情况
- 只有一个固定页面、无参数、无表单、无 API 的纯静态展示站：测绘的收益趋近于零，直接做指纹与已知 CVE 比对即可。
- 目标是「已知组件的已知 CVE」场景：不必走完整测绘，指纹定版后直接验证 CVE 更快。
- 已经有完整源码与路由表（白盒）：本卡的资产枚举部分基本可跳过，直接进 `source-code-audit`。

### 已知失败模式
- **软 404 导致全量误报**：拿状态码当判据，把自定义错误页（200 + 固定长度）全当命中。原书明确说「不要假设存在就是 200、不存在就是 404」。
- **直接对全站跑主动爬虫**：会点到登出、删除、支付确认，把会话打断或产生脏数据；原书要求第 4 步前必须先设排除规则。
- **深度优先的资产枚举**：在一个子域上死磕目录，忘了还有 200 个子域没看；应广度优先，先铺开再收敛。
- **只信 `Server` 头**：被运维改写或被 CDN 统一后会得出错误的技术栈，进而查错 CVE。
- **把「用了扫描器」当「测完了」**：扫描器只能覆盖单请求可触发的输入校验类问题，看不到认证/会话/访问控制/业务逻辑。
- **命名规律过度外推**：后加功能与第三方组件的命名常不遵守主站规律；扩展名推断也要防止服务端把 `.txt` 也当脚本解析。
- **把「不一致」直接等同漏洞**：界面风格不同只能作为「优先看这里」的信号，不能当结论。

### 作者与时代的局限
- 书中大量示例基于 2010 年代前后的 ASP/JSP/Java servlet 单入口架构；现代 SPA + GraphQL + 微前端的路由发现方式已不同，需要补「读 bundle」「introspection」两条（本卡已并入，来源为后出版本）。
- 「目录爆破」在有 WAF 与全站软 404 的现代站点上收益显著下降，应更多依赖历史 URL（Wayback/GAU）与 JS 分析。
- 子域枚举的被动源覆盖度随工具生态变化很快，具体工具名可替换，但「多源合并去重 → 探活 → 递归」的顺序不变。

### 容易混淆的方法
- **「内容发现」vs「参数发现」**：前者找路径/文件，后者找参数名（`debug=true`、`admin=1`）；两者的字典与判据完全不同，别混用一套字典。
- **「资产测绘」vs「威胁建模」**：测绘产出「有什么」，威胁建模产出「怕什么」；后者属于设计评审（见 `source-code-audit` 的 B 段）。
- **「指纹」vs「漏洞验证」**：指纹只给出「可能是哪个版本」，版本旧不等于可利用，必须实测。

### 授权与合规边界
> 待补充（用户自行填写）
