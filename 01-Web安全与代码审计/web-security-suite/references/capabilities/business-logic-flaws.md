# 业务逻辑缺陷：找出「若 A 则 B」的隐含假设并让它不成立

## R — 原文 (Reading)

> "Unlike other coding flaws such as SQL injection or cross-site scripting, no common 'signature' is associated with logic flaws."
>
> 译：与 SQL 注入、跨站脚本等其他编码缺陷不同，逻辑漏洞没有通用的「签名」。

> — 《The Web Application Hacker's Handbook》Ch11 / The Nature of Logic Flaws

> "商品金额篡改测试，通过抓包修改业务流程中的交易金额等字段，例如在支付页面抓取请求中商品的金额字段，修改成任意数额的金额并提交，查看能否以修改后的金额数据完成业务流程。"
>
> — 《Web 攻防之业务安全实战指南》10.1 商品支付金额篡改测试

> "一定要测试那些仅应允许执行一次而非多次的操作。"
>
> — 《Bug Bounty Bootcamp》Ch12 Race Conditions

## I — 方法论骨架 (Interpretation)

逻辑漏洞不能「加」出来（没有 payload），只能**建模**出来。方法固定为三步：

1. **把功能读成一句假设**：`功能意图 → 开发者假设 → 若假设被违反会怎样`。例如「改密功能：普通用户会提供旧口令 → 只要请求里出现 `existingPassword` 就是普通用户 → 若删掉该参数，代码会走管理员分支」。
2. **用动作集去违反它**：删参数（一次只删一个）、跳步（直接请求后一阶段）、反向/越界值（负数、0、超大数、超长串）、跨位置提交（把参数放到另一功能/另一阶段）。逻辑漏洞只能被「减」和「乱序」出来。
3. **走完全程再判定**：后段逻辑会消费前段存进会话的数据，只测单步看不到后果。

它与相邻概念的边界很重要：

- **与配置问题的区别**：配置问题在「同一段代码换了参数/环境」下复现；逻辑漏洞在「代码按设计正常执行、但设计假设被违反」时出现。判断依据是「这个行为是否由开发者有意为之的假设导致」，不是「有没有报错」。
- **与越权的区别**：越权是「权限判据错」，逻辑漏洞是「业务规则假设错」；同一请求可能同时命中两者，报告应分别归因。
- **与竞态的区别**：竞态是逻辑漏洞的一个子类，特征是「共享状态被并发覆盖」；单请求即可复现的不属于竞态。

三类高频假设，覆盖绝大多数实战命中：

| 假设 | 违反方式 | 典型后果 |
|---|---|---|
| 「用户一定按顺序走流程」 | 直接请求后一阶段 / 放弃支付后访问回调 URL | 跳过支付、跳过验证、白嫖 |
| 「金额/数量由前端提交且可信」 | 改金额、改数量为负、改运费/优惠券 | 0.01 元买单、负数刷积分 |
| 「这个操作只会发生一次」 | 并发重放同一请求 | 重复退款、超额兑换、余额变负 |

最后一条纪律：**逻辑漏洞的判据是「业务后果」，不是「响应差异」**。改包后页面没报错、订单状态变成「已支付」，才算成立；只看到「参数被接受」不足以定论。

## A1 — 应用示例 (Application Example)

### 示例 1: 删掉一个参数，普通用户变成管理员
- **类型与来源**: 【亲历】《The Web Application Hacker's Handbook》Ch11（Example 2）
- **问题/输入**: 改密功能。管理员改密时不需要旧口令，普通用户需要。
- **方法论的使用**: ① 读功能：`功能意图=改密`、`假设=请求里出现 existingPassword 就意味着是普通用户`；② 用自有普通账号走一遍，记录请求含 `existingPassword`；③ 删除该参数（不是置空，是删名）重放 → 服务端走了管理员分支；④ 把 `username` 改成受害者 → 以管理员身份重置任意用户口令；⑤ 走完全程（提交新口令并登录）确认后果。
- **结论**: 代码用「参数是否存在」当身份信号，是典型的「存在性即语义」缺陷。
- **结果**: 原书说明该缺陷在 AOL AIM Enterprise Gateway 中也出现过（转述）。

### 示例 2: 0.01 元买 100 元充值卡
- **类型与来源**: 【亲历】《Web 攻防之业务安全实战指南》10.1
- **问题/输入**: 网上营业厅下单到支付页，请求里有明文字段承载金额。
- **方法论的使用**: ① 正常下单到支付页，抓「跳转支付」那一次请求，找到金额字段（如 `elecCardConfirm.money`）；② 只改金额为 0.01，其余不动，放行 → 支付平台显示的应付金额同步变化，说明金额由该字段决定；③ 完成支付并观察回调后的订单状态 → 显示「已支付/已完成」即漏洞成立；④ 若金额被服务端重算（改后无变化），转数量维度（0.1、-1、超大值）；⑤ 数量也被锁死时改运费/配送方式/优惠券/积分抵扣。
- **结论**: 关键判据不是「能不能改包」，而是「改完之后支付回调、订单落库、发货这一整条链是否都认这个值」。
- **结果**: 作者以 0.01 元购得 100 元充值卡。

### 示例 3: 并发退款导致余额变负
- **类型与来源**: 【亲历】《Web 攻防之业务安全实战指南》5.6.2
- **问题/输入**: 退款提现接口，单次申请有额度上限。
- **方法论的使用**: ① 定位「校验—扣减」型接口（退款、提现、兑换、领券）；② 单请求跑通一次，确认返回体里余额/次数变化，得到成功基线；③ 用 Burp Intruder/Turbo Intruder 同时发出 20–100 份同一请求；④ 对比账户余额/订单数是否与成功次数一致 → 余额变负或多出订单即成立；⑤ 失败时加大并发、缩短请求体、选业务低峰重试。
- **结论**: 「先查余额再扣减」是两步非原子操作，N 个请求同时读到旧快照就会各自通过校验。
- **结果**: 作者连点两次生成两笔退款申请，余额变负，未经财务审核到账两笔七千余元。

### 示例 4: 业务 ID 换成别人的，直接建应用
- **类型与来源**: 【亲历】《Web Hacking 101》Ch21（MoneyBird）
- **问题/输入**: 建 App 的 POST 请求里带 `business_id`。
- **方法论的使用**: ① 按功能建图：走「创建 App」流程，记录请求里的所有 ID；② 判断该 ID 是否属于当前用户（业务语义上应当属于）；③ 把它改成不属于自己的团队 ID 重放；④ 观察副作用：App 建到了别人的团队下。
- **结论**: 逻辑漏洞常与越权同源——这里的「假设」是「用户只会提交自己的 business_id」。
- **结果**: 作者因此获 100 美元赏金。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 业务流程走完了但感觉「哪里不对」，想知道能不能跳过支付/审批/验证。
2. 下单、领券、兑换、退款涉及金额与配额，想知道能否改值或重复。
3. 系统有多阶段流程（注册→验证→激活、下单→支付→发货），怀疑某一步没校验前置状态。
4. 一个漏洞看起来只是「配置问题」，需要判断它到底是 Bug 还是设计如此。
5. 扫描器什么都没报，但直觉认为业务上能薅，需要一套不依赖 payload 的方法。
6. 需要给甲方出一份「业务安全测试方案」，而不是跑一遍 OWASP Top 10。

### 语言信号（出现这些就该激活）
- 中文：「这是逻辑漏洞还是配置问题」「业务流程能不能绕」「能不能跳过支付」「改成负数会怎样」「并发能不能多领一次」「退款重复到账」「余额变成负数」「业务安全测试从哪开始」
- English: "business logic flaw", "logic vs misconfiguration", "price tampering", "negative quantity", "race condition", "double spending", "forced browsing logic flaw", "remove parameter", "skip payment step"

### 与相邻能力的区分
- 与 `access-control-idor` 的区别：越权是「权限判据错」，本卡是「业务规则假设错」；两者常同源，报告中应分列。
- 与 `auth-session-bypass` 的区别：那张卡针对「身份建立」，本卡的「多阶段跳步」针对「业务状态机」。
- 与 `waf-bypass-encoding` 的区别：本卡不需要绕过任何过滤器——请求本身是「合法」的，只是语义被滥用。
- 与 `source-code-audit` 的区别：白盒时可以直接读状态机与校验顺序；本卡给的是黑盒建模与动作集。

## E — 可执行步骤 (Execution)

**必需输入**: 一个可完整走通的业务流程（测试账号 + 可完成的支付/审批通道，沙箱或最小金额）；业务语义说明（必须知道「正常应该怎样」才能定义「违反」）；能并发重放的代理。缺业务语义就只能做通用测试，命中率会大幅下降。

**交付物与完成标准**: 一张「功能 → 开发者假设 → 违反动作 → 业务后果」的表 + 每个结论的复现步骤；完成标准是后果可观测（订单状态变化、余额变化、权限变化），且能用最小金额/最小影响复现。

1. **建业务全景**
   - 做什么：白盒读开发文档，黑盒手工走完整流程（注册、登录、下单、支付、退款、提现、审批）；对负责人访谈部署、功能模块、数据流、现有安全措施；按行业挑 3–5 个最值钱的业务动作（电商=下单/退款/优惠券；金融=转账/额度；社交=邀请/权限）。
   - 完成标准：能复述系统有几个业务域、几个角色、主流程与分支流程的差别。
   - 判停：只做工具扫描会漏掉全部逻辑类问题；分支流程不要逐个测，归纳相似分支即可。

2. **画状态机并标关键环节**
   - 做什么：把主流程画成有向图，标出每个环节的「输入、服务端应校验什么、状态存哪里（session/DB/隐藏字段）」；特别标出「哪些步骤假设前一步已完成」。
   - 完成标准：图上每条边都有对应请求，每个节点都有状态存储位置。
   - 判停：状态存在客户端（隐藏字段/cookie）时，该节点是重点攻击位。

3. **逐功能写三行假设**
   - 做什么：对每个关键功能写 `功能意图 → 开发者假设 → 若假设被违反会怎样`；从典型假设清单里对照：普通用户一定提供旧口令、用户一定按顺序走流程、金额一定是正数、折扣在结算前已确定、搜索结果不跨越权限边界、配额只被消耗一次。
   - 完成标准：每个功能至少一条可被违反的假设。
   - 判停：写不出假设说明还没理解业务，回第 1 步。

4. **动作集：减、乱序、反向、跨位置**
   - 做什么：① 逐个参数（含 cookie、query、POST）**轮流删除**，一次只删一个，删「参数名」而不只是删「值」；② 强制浏览：直接访问后续阶段的 URL；③ 把参数提交到「不该出现的位置」（另一功能/另一阶段）；④ 提交反向/越界值（负数、0、超大数、超长串）。
   - 完成标准：每个动作都记录「基线 vs 变异」的行为差异。
   - 判停：若被测请求属于多步流程，**必须把流程走到最后再判定**（后段会消费前段存进会话的数据）。

5. **金额与数量维度**
   - 做什么：抓支付跳转请求，改金额 → 看支付平台金额是否同步；完成支付看订单状态；金额被重算时改数量（0.1/-1/超大）；都锁死时改运费/优惠券/积分/配送方式。
   - 完成标准：全链路（支付回调 + 订单落库 + 发货）接受被篡改的值。
   - 判停：只改前端 DOM 显示值通常只影响展示，必须改请求字段；改金额后支付平台金额不变说明服务端重算，不要在金额上继续耗。

6. **一次性操作与并发**
   - 做什么：选「单次合法、两次不该合法」的操作（投票、领券、兑换、退款、转账、邀请奖励）；单跑一次确认成功基线；同一请求并发 20–100 份；核对余额/次数/订单数是否与成功次数一致。
   - 完成标准：出现超额、余额变负、重复到账。
   - 判停：拿「本来就允许重复」的操作（转 10 块）当靶子会假阳性；只发一次会假阴性；串行重放几乎不可能命中窗口。首次不成功就重试多轮，并在报告写明「需重试」。

7. **竞态的结构性判断（白盒补充）**
   - 做什么：定位跨请求存活的状态（实例变量、静态字段、单例、缓存、临时文件、可写数据库行）；构造两会话几乎同时提交，观察是否互相覆盖（余额类看是否超额）。
   - 完成标准：能指出「共享状态在哪、缺哪把锁」。
   - 判停：去共享（改局部变量/请求作用域）后问题消失，说明判断正确；加锁要注意串行化带来的 DoS 面。

8. **定级与报告**
   - 做什么：按「利用场景风险 + 影响严重程度」定级；写清前提（需不需要多账号、需不需要并发、需不需要特定业务状态）；给出最小复现金额/次数。
   - 完成标准：审阅者能照步骤复现，且能判断修法方向（服务端重算 vs 加锁 vs 状态机校验）。
   - 判停：把「业务上允许的行为」误报为漏洞会显著降低报告可信度，提交前先问「开发者会不会说这是设计如此」。

## B — 边界 (Boundary) ★

### 不要用的情况
- 功能本身幂等或允许重复（查询、浏览、转小额）：并发成功不构成漏洞，别把它们当选靶。
- 单次请求就会被业务规则拒绝（转 5000 而余额 3000）：这不是竞态，是正常校验，不要浪费时间。
- 业务流程没有可观测后果（无订单状态、无余额、无权限变化）：无法判定，需先找到可观测点。
- 纯展示型改动（前端 DOM 改价）：不落库就不构成漏洞。

### 已知失败模式
- **只删值不删名**：服务端对空串与缺参的处理通常不同，这是最主要的漏测。
- **只测单步**：漏掉「会话里累积状态」导致的越权与绕过。
- **拿允许重复的操作当竞态靶**：假阳性。
- **并发只发一次就下结论**：成功依赖服务端调度，属概率事件，需多轮重试。
- **请求间隔太大（顺序执行）**：时间窗已关闭，测不出竞态。
- **改金额后支付平台金额不变还继续改**：说明服务端重算，应转数量/运费维度。
- **把配置问题当逻辑漏洞**：同一段代码换参数就复现的，是配置缺陷。
- **不理解业务就判「违反假设」**：会把大量正常分支行为误判为漏洞。

### 作者与时代的局限
- 书中的业务场景以电商、银行、证券、游戏、社交为主；SaaS 的「配额/席位/试用期」、API 的「计费单位」是同类假设的新形态，书中未覆盖但方法可直接迁移。
- 并发测试的成功率高度依赖服务端架构（单机 vs 分布式、有无事务/锁），书中给的「20–100 并发」是经验值，现代高并发服务可能需要更大并发或更精确的对齐（如 HTTP/2 单包多请求）。
- 早期「隐藏字段存价格」的缺陷在现代前后端分离架构下变成「API 返回价格再由前端回传」，形态变了但假设没变。

### 容易混淆的方法
- **逻辑漏洞 vs 越权**：前者违反业务规则，后者违反权限判据；同一请求可能两者都成立。
- **逻辑漏洞 vs 竞态**：竞态是逻辑漏洞的子类，特征是并发覆盖共享状态。
- **逻辑漏洞 vs 配置缺陷**：前者代码按设计执行但假设错，后者是环境/参数配置错。
- **「删参数」vs「参数污染」**：前者试探「存在性语义」，后者利用「解析差异」；两者的判据不同。

### 授权与合规边界
> 待补充（用户自行填写）
