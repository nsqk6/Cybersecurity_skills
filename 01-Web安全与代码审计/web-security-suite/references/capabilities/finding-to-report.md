# 从发现到交付：模糊测试、复现自证与可受理报告

## R — 原文 (Reading)

> "一个漏洞赏金猎人的工作不仅是寻找漏洞，而且还需要向组织的安全团队解释它们。如果您提供一个写得很好的报告，您将帮助您正在与之合作的团队重现漏洞、将其分配给适当的内部工程团队并更快地修复问题。"
>
> — 《Bug Bounty Bootcamp》Ch2 / Writing a Good Report

> "If you want your report to be taken seriously, provide a detailed report which includes, at a minimum: The URL and any affected parameters used to find the vulnerability / A description of the browser, operating system (if applicable) and/or app version / A description of the perceived impact / Steps to reproduce the error"
>
> 译：若想让报告被认真对待，至少包含：发现漏洞所用的 URL 与受影响参数；浏览器/操作系统/App 版本；对影响的描述；复现步骤。

> — 《Web Hacking 101》Ch22 / Vulnerability Reports

> "模糊测试应用程序的过程可以分为四个步骤。您可以首先确定可以在应用程序中进行模糊测试的端点。然后，决定有效数据列表并开始模糊测试。最后，监视您的模糊测试器的结果并寻找异常情况。"
>
> — 《Bug Bounty Bootcamp》Ch25 / The Fuzzing Process

## I — 方法论骨架 (Interpretation)

这个能力覆盖「有了可疑点之后」的最后一段流水线：**批量探测 → 异常筛出 → 手工定性 → 环境复现 → 写报告**。它解决的不是「怎么找洞」，而是「怎么把可疑变成可交付」，以及「怎么不把时间浪费在会被驳回的报告上」。

四段各自的判据不同：

1. **模糊测试（工具段）**。它把「手工试 payload」变成「批量注入 + 差异观察」，效率来自两处：注入点被显式标记（Wfuzz 的 `FUZZ`、Intruder 的 payload position），判据被量化（状态码、响应长度、响应时间）。但它只能发现「单请求即可触发」的输入校验类问题，对业务逻辑、多步利用无能为力——所以它定位可疑点，人工负责定性。小站必须限速，否则事实上构成 DoS。
2. **差异筛读（判读段）**。状态码只是判据之一：200 段=存在、403=存在但需绕过、301=需认证/跳转、响应长度变化=可能被影响、响应时间变长=可能盲注。单一判据必然误报，要两两交叉。
3. **复现自证（纪律段）**。结论正确性的最大杀手是环境：浏览器/OS/App 版本、后端灰度都可能让结论反转。所以必须「最新环境 + 第二套环境」各复现一次，并查该项目的公开披露与已知问题列表。原书的教训是：一个 SOP 绕过在三台机器上都成立，最后发现是 OS 未更新——升级后漏洞消失，且半年前已有人报过。
4. **报告（表达段）**。读者是「要判断优先级、要复现、要写修复」的分析师，所以信息必须自足：**定位**（URL + 参数 + 方法）、**环境**（版本）、**影响**（能被谁利用、达到什么后果）、**步骤**（可重复，含前置账号/数据）。缺任一项，triage 只能回「需要更多信息」，流程就停住。

一条量化约束把这些串起来：平台常把报告质量折成分数（垃圾 -10 / 不适用 -5 / 信息性 0 / 已修复 +7），并用它决定谁能进私有项目。于是「多报」不再中性——一次 N/A 的负分足以把长期积累拉到阈值以下。这把「别乱报」从道德建议变成可计算的约束。

## A1 — 应用示例 (Application Example)

### 示例 1: 八步结构写一份越权报告
- **类型与来源**: 【亲历】《Bug Bounty Bootcamp》Ch2（以 `change_password` 的 `user_id` 越权贯穿）
- **问题/输入**: 一个改密接口的 `user_id` 未校验归属，可改他人密码。
- **方法论的使用**: ① 标题：一句话写清「哪类漏洞 + 哪个 URL/端点 + 后果」（不写「某关键端点上的 IDOR」）；② 摘要：写清请求方法、参数名、为何未校验、攻击者能做什么；③ 定级：Low/Medium/High/Critical + 理由；④ 复现步骤：把前置条件写全（要几个账号、从哪个页面进、点哪个按钮、改哪个参数）；⑤ POC：给现成可打开的 HTML/请求；⑥ 影响：写真实可达的最坏后果（能否接管账号、能否批量），不夸大；⑦ 修复建议：只在清楚根因时给方向（如「校验 user_id 是否属于当前用户」）；⑧ 自检：照自己的步骤重走一遍、验证 POC 可用。
- **结论**: 八段的顺序对应审阅者的决策顺序：先知道是什么/多严重，再知道能不能复现，最后知道怎么修。
- **结果**: 原书对比了「合格版」与「更好版」的复现步骤，说明前置条件缺失是被打回的主因。

### 示例 2: 只报「技术成立」的代价
- **类型与来源**: 【亲历】《Web Hacking 101》Ch22（Shopify 首次提交）
- **问题/输入**: 一个新发现的 XSS，未读披露指南直接提交。
- **方法论的使用**: ① 提交前应逐条读 policy 的 Scope 与 out-of-scope 清单（漏洞类型 + 资产）；② 查该 program 的公开披露与已知问题列表，排除「已被报过/已公告」；③ 用「安全工程师视角」自问：这条会不会排到他 to-do 最底部；④ 若大概率 informative，先按「漏洞链」找升级路径，等能证明影响再提；⑤ 提交前二次自证（换设备/换版本/换账号）。
- **结论**: 「技术上成立」不等于「应该被付费」；不读政策、不查历史、不证明影响，是被判 N/A/duplicate 的三条主因。
- **结果**: 报告被回复「已知问题、请勿提交」，工单关闭并扣 5 分。

### 示例 3: 环境未更新的假阳性
- **类型与来源**: 【转述】《Web Hacking 101》Ch22 / Don't Shout Hello Before Crossing the Pond（Mathias Karlsson 的 SOP 绕过）
- **问题/输入**: `example.com..evil.com` 形式的同源绕过，自测有效，同事 VM 也有效，更新 Firefox 后仍有效。
- **方法论的使用**: ① 复现前确认环境版本（浏览器/OS/App）并与目标一致；② 换第二套环境复现；③ 仍未排除「宿主 OS 未更新」这一层；④ 把 OS 升级到最新后再测 → 漏洞消失；⑤ 查公开披露发现半年前已有人报过，且升级到 OSX Yosemite 10.10.5 即修复。
- **结论**: 「在我机器上能复现」不等于「在目标当前状态能复现」；版本层级要一层层排查（浏览器 → OS → App → 后端灰度）。
- **结果**: 作者放弃提交，避免了一次 duplicate。

### 示例 4: 用模糊测试把「待测面」压到一屏
- **类型与来源**: 【例题】《Bug Bounty Bootcamp》Ch25（`wfuzz -w common_paths.txt http://example.com/FUZZ`）
- **问题/输入**: 一个域，需要批量找目录与 IDOR 可疑点。
- **方法论的使用**: ① 定注入点：列出接收入参的端点/参数/header，按「易感漏洞」分类（数字 ID→IDOR，搜索框→XSS，XML 上传→XXE）；② 选字典：按漏洞类型换字典，并补随机长串、异常编码字符、换行符；③ 执行：`wfuzz -w <dict> http://target/FUZZ` 或 Intruder 标记位置，用 `-` 控制并发避免打挂小站；④ 看结果：按状态码、响应长度、响应时间排序找异常；⑤ 对异常项手工复验并评估影响。
- **结论**: fuzzer 是金属探测器，不是判决器；「状态码不同」只是候选，必须人工定性。
- **结果**: 原书以该命令演示目录枚举与 IDOR 扫描，未给出具体命中结果。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 有一批参数/端点需要批量筛，不想一个个手工试。
2. 扫描器/模糊测试出了一堆「异常」，需要判断哪些是真的。
3. 已经确认漏洞，但报告被回复「无法复现」「需要更多信息」「已知问题」。
4. 不确定一个洞算不算高危，需要在提交前定级。
5. 手上有一堆低危（开放重定向、self-XSS、信息泄露），不知道要不要报、怎么报。
6. 需要在提交前做一次「会不会被判 N/A」的自检。
7. 需要给甲方/团队写一份内部渗透报告（比众测报告更长）。

### 语言信号（出现这些就该激活）
- 中文：「怎么批量测参数」「wfuzz 怎么用」「扫描结果怎么看」「报告怎么写」「提交后被打回」「为什么我的报告是 informative」「这个洞算高危吗」「低危洞要不要报」「本地能复现但不确定」
- English: "web fuzzing workflow", "wfuzz FUZZ", "write a bug bounty report", "report template", "minimum report details", "confirm before reporting", "severity rating", "false positive check", "reproduce on latest version", "bug chaining", "signal score"

### 与相邻能力的区分
- 与 `recon-asset-surface` 的区别：那张卡产出「测什么」，本卡产出「测完之后怎么交付」。
- 与 `business-logic-flaws` 的区别：本卡管「流程与表达」，那张卡管「怎么发现」。
- 与所有漏洞卡的定级部分：本卡提供通用的「受害者模型 + 影响链」定级口径，具体漏洞的判据在各自卡片里。

## E — 可执行步骤 (Execution)

**必需输入**: 已确认的可疑点或漏洞；目标环境的版本信息（浏览器/OS/App/后端）；该项目的 scope 与披露政策。缺 scope 就先读政策——不读就提交是最大的时间浪费。

**交付物与完成标准**: 一份可被 triage 直接受理的报告（含四要素 + PoC + 影响 + 复现环境）+ 一份自己的「已排除项」清单（哪些判过是误报/重复）；完成标准是「一个不了解该功能的人能照步骤独立复现」。

1. **批量探测：定注入点与字典**
   - 做什么：列出接收入参的端点/参数/header，按易感漏洞分类；按类型选字典（路径、ID、XSS、SQLi），补随机长串、异常编码字符、换行符；用 `wfuzz`/Intruder 标记位置执行，小站限速。
   - 完成标准：每个注入点都有对应的字典与「预期异常长什么样」。
   - 判停：目标不允许高频请求时，改小批量 + 加延迟；否则事实上构成 DoS。

2. **差异筛读：三判据交叉**
   - 做什么：按状态码（200 段=存在、403=存在待绕过、301=需认证/跳转）、响应长度（变长=可能被影响）、响应时间（变慢=可能盲注）排序；对每个异常项记录「基线 vs 异常」。
   - 完成标准：异常项收敛到可人工处理的量级（通常 <20 条）。
   - 判停：把「状态码不同」直接当漏洞会产生大量误报；软 404 需先建基线（见 `recon-asset-surface`）。

3. **手工定性**
   - 做什么：对每个异常项构造最小输入，确认「能做什么」（读数据/改数据/执行/绕过），并写清前置条件。
   - 完成标准：能回答「攻击者需要什么、能得到什么」。
   - 判停：只有「响应变了」而说不出后果的，按信息级处理，不提交。

4. **环境复现（两层）**
   - 做什么：记录并匹配版本（浏览器/OS/App/后端）；换第二套环境（另一台机器/虚拟机/同事）复现；查该 program 的公开披露与已知问题列表；若结论依赖旧版本行为，明确验证「当前最新版本是否仍有该行为」。
   - 完成标准：两次独立环境一致，且排除了「已被报过」。
   - 判停：只在单一环境成立时，报告里必须注明环境，否则极易被判 N/A。

5. **定级（受害者模型 + 影响链）**
   - 做什么：① 是否需要受害者交互（需要则降一档）；② 被击中时是否已登录；③ 受害者池与角色（未认证公开页 > 普通用户区 > 管理员区，按「能拿到谁的会话」判断）；④ 能否与其他低危缺陷串联；⑤ 最终能做什么（劫持会话/创建管理员/读敏感数据/横向）；⑥ 用业务语境修正（同一数据对招聘站与约会站敏感度不同）。
   - 完成标准：给出等级 + 一行理由 + 前提条件。
   - 判停：为了多拿赏金故意拔高会损害信誉；一律按漏洞类型定级会与厂商认知错位。

6. **决定报不报（成本核算）**
   - 做什么：估算最可能结局（resolved +7 / informative 0 / N/A -5 / spam -10）；为负则不提；对「大概率 informative」的项先找升级路径（低危串成链）；对「可能 N/A」的项回去读 scope。
   - 完成标准：每条待提交项都有「为什么值得提」的一句话。
   - 判停：为「上榜」提交可疑报告会把分数拉到门槛下；informative 不是零成本，它会拉低均值。

7. **写报告（四要素 + 八段）**
   - 做什么：标题（漏洞类型 + URL/端点 + 后果）；摘要（方法、参数、为何未校验、能做什么）；定级 + 理由；复现步骤（前置账号/数据/点击路径全写）；POC（CSRF 给可打开 HTML、XXE 给 XML 文件、多步给录屏 + 原始请求）；影响（真实可达的最坏后果，不夸大）；修复建议（清楚根因才写）；自检记录。
   - 完成标准：四要素齐全（URL+参数 / 环境版本 / 影响 / 步骤）；他人照步骤能复现。
   - 判停：只给视频不给步骤不够；把「没有名为 csrf_token 的参数」当 CSRF 是典型误判。

8. **提交与跟进**
   - 做什么：按流程提交；两周无回应再礼貌询问进展；确认后配合复测；记录每次被判 informative/N/A 的类型，形成「该公司在意什么」的私有知识。
   - 完成标准：闭环（修复确认或明确关闭原因）。
   - 判停：催促过频、越级投诉会损害账号信誉。

## B — 边界 (Boundary) ★

### 不要用的情况
- 还没有稳定复现就写报告：结论正确性未验证，属于「在穿越池塘之前喊你好」。
- 目标是「已公告的 CVE + 默认配置」且 program 明确不收：不属于本流程的适用范围。
- 内部渗透报告：本卡的四要素仍适用，但还需覆盖资产清单、方法论、整改建议与复测结论，篇幅与结构不同。

### 已知失败模式
- **只给视频不给步骤**：原书明确「仅仅提供视频不够」。
- **复现步骤省略前置账号**：被判「无法复现」。
- **把「没有名为 csrf_token 的参数」直接当 CSRF**：可能是改名、在 header 里、由 JS 注入。
- **用自己长期未更新的环境下结论**：假阳性（原书 OSX 案例）。
- **不查历史披露**：duplicate。
- **只写「怎么触发」不写「能造成什么」**：被降级或忽略。
- **给不出根因却硬写修复方案**：误导对方。
- **未限速的 fuzzer 打小站**：事实上构成 DoS，且可能被封 IP。
- **为凑数量提交 informative**：拉低均值，失去私有项目资格（原书案例：一次 N/A 使分数降到 0.96，次日被拒）。
- **提交后反复催促/越级投诉**：损害长期信誉。

### 作者与时代的局限
- Signal 类信誉机制是 HackerOne 特定时期的规则，各平台（Bugcrowd/众测平台/企业 SRC）算法不同；书中给出的分值（-10/-5/0/+7）不可跨平台套用，但「负分报告有真实成本」这一结论普适。
- 书中的报告模板偏向 Web 漏洞；云配置、供应链、移动端的报告结构需补充（资产标识、影响范围、数据分级）。
- 现代平台普遍要求「影响证明」（如脱敏数据样本、可复现的最小 PoC），纯理论链的受理率进一步下降。
- 「两地复现」在 CI/CD 高频发布的环境下还需要加一条「确认当前部署版本」，否则会测到已下线的旧版本。

### 容易混淆的方法
- **众测报告 vs 内部渗透报告**：前者以「可复现 + 影响」为中心、篇幅短；后者还要覆盖资产、方法论、整改与复测。
- **定级 vs 是否提交**：定级回答「多严重」，提交决策回答「值不值得提、会不会被判 N/A」。
- **漏洞链 vs 单点报告**：链条按最终影响定级，单点按自身影响定级；把链条拆成多个低危提交通常总分更低。
- **模糊测试 vs 手工测试**：前者定位可疑点，后者定性；把 fuzzer 输出当结论是误报的主要来源。

### 授权与合规边界
> 待补充（用户自行填写）
