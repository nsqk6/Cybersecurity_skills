# 访问控制与 IDOR：用「两个身份 × 同一请求」证明越权

## R — 原文 (Reading)

> "Figure 8-3 shows the response returned when each user requests the 'list users' admin function. Here, the responses are identical, indicating that the application is vulnerable, since the ordinary user should not have access to this function and does not have any link to it in his or her user interface."
>
> 译：图 8-3 是两个用户分别请求「列出用户」管理功能时的响应。此处响应完全相同，说明应用存在漏洞——普通用户本不该能访问该功能，其界面上也没有任何链接指向它。

> — 《The Web Application Hacker's Handbook》Ch8 / Testing with Different User Accounts

> "如果应用程序生成的请求中没有标识符，请尝试向请求中添加一个。将id、user_id、message_id或其他对象引用附加到URL查询或POST正文参数中，并查看对应用程序行为是否产生影响。"
>
> — 《Bug Bounty Bootcamp》Ch10 / Bypassing IDOR Protection

> "由于水平权限管理是系统缺乏一个数据级的访问控制所造成的，因此水平权限管理又可以称之为'基于数据的访问控制'。"
>
> — 《白帽子讲 Web 安全》10.3 水平权限管理

## I — 方法论骨架 (Interpretation)

访问控制漏洞只有一个可靠判据：**同一请求在两个权限上下文中都成功**。不是「页面上有没有链接」，也不是「响应有没有差异」。

原因在于，越权有两个正交的维度，而这两个维度各有自己的常见错判：

- **纵向（低→高）**：低权用户调用了管理员功能。错判方式是把「UI 差异」当结论——管理员多一个菜单项是正常的、与授权无关；而「两个响应相同」既可能是漏洞（低权拿到了管理数据），也可能无害（如公开搜索页）。所以 diff 只能用来**定位候选**，结论必须回到「这个功能对该用户是否应当可用」的业务判断。
- **横向（同级 A→B）**：同角色下改了资源标识就能读/写别人的数据。根因不是「没做角色校验」，而是**缺少「用户 → 数据」的归属校验**。RBAC 只回答「这个角色能不能调用这个功能」，不回答「这条数据是不是他的」。因此修法也不同：纵向靠角色/权限表，横向必须在**每条数据访问**上加归属条件（`where owner_id = current_user`）。

三类可测的机制，按「鉴权判据」分类：

| 机制 | 判据长什么样 | 测法 |
|---|---|---|
| 完全没做鉴权 | 无任何校验 | 低权/未登录直接请求高权 URL |
| 做了但用客户端数据判定 | `?admin=true`、隐藏字段 `role`、cookie 里的级别、Referer 来源 | 改掉该字段/头，看功能是否仍可用 |
| 只校验了「主入口」 | 打开菜单时校验，提交/确认步骤默认已通过 | 逐请求重放多阶段流程 |

第三个机制是最容易被漏的：**重放整张站点地图无法复现多阶段流程**（缺前置状态），必须用高权账号走完全程留下请求序列，再用低权会话**逐条重放**。开发者通常只在「入口那一步」做鉴权，后续「提交表单」「确认」步骤假设「能到这一步的人已经过了校验」。

还有一条经常被忽略的维度：**同一功能可能有多个入口**（页面接口、`POST /x/delete`、`DELETE /x`、GraphQL mutation、移动端接口、旧版 API）。鉴权通常写在主路径上，新增入口复用了业务逻辑却没复用鉴权。所以「一致性」本身就是一个可执行的检查项。

## A1 — 应用示例 (Application Example)

### 示例 1: 双账号 + 站点图 diff 找纵向越权
- **类型与来源**: 【例题】《The Web Application Hacker's Handbook》Ch8（mdsec.net/auth/462、468）
- **问题/输入**: 两个账号：管理员与普通用户；目标是「列出用户」管理功能。
- **方法论的使用**: ① 高权账号完整浏览全站并保存站点地图（state file）；② 用低权账号重新请求高权地图中的每个条目（配置低权会话的 cookie/登录宏，把登出加入排除范围）；③ 逐项人工判读三类结果：低权被拒（正确）/ 低权看到同一功能且响应一致（疑似纵向越权）/ 仅 UI 有差异（中性）；④ 横向另做：两个同级账号各取一个「属于自己的资源 URL」，互换身份重放。
- **结论**: 响应相同是「候选」，最终要回到「该功能对该用户是否应当可用」。
- **结果**: 原书以该方法在管理功能上直接发现纵向越权。

### 示例 2: IDOR 四步法（换 ID）
- **类型与来源**: 【例题】《Bug Bounty Bootcamp》Ch10（`messages?user_id=`、`uploads?file=`、`delete_message`）
- **问题/输入**: 两个账号 attacker（`user_id=1235`）与 victim（`1236`）。
- **方法论的使用**: ① 每角色建两个号（见第 E 段第 1 步）；② 用高权号浏览全站，标出「返回用户信息」与「修改用户数据」的功能；③ 逐个功能抓请求，找出含数字、用户名、文件名的参数（URL、body、header、cookie、文件路径都算）；④ 把 attacker 请求里的引用替换成 victim 的 → 响应里出现 victim 数据，或 victim 侧数据被改动即确认；⑤ 再在未登录状态重放，判定是否连认证都不需要。
- **结论**: 验证动作固定为「同一资源、两个身份、只改引用」；双浏览器的意义是让副作用肉眼可见。
- **结果**: 原书以五个端点演示，涵盖读、写、删除三类操作。

### 示例 3: 被挡住时的六种引用变形
- **类型与来源**: 【亲历】《Bug Bounty Bootcamp》Ch10 / Bypassing IDOR Protection
- **问题/输入**: 一个私信接口 `GET /messages?user_id=1236`，直接换 ID 被拒。
- **方法论的使用**: ① 遇到随机串先解码（base64/base64url/hex/URL）→ 还原出可预测 ID 后重编码提交；② ID 是哈希/随机时，多个号观察生成规律与熵，同时去个人主页、其它 API 找泄露的 ID；③ 请求本身不带 ID 时，手工补 `id`/`user_id`/`message_id` 到 query 或 body；④ 换方法（GET↔POST/PUT/DELETE/PATCH）；⑤ 换表示（URL 末尾加 `.json`、改用文件名而非 ID）；⑥ 盲 IDOR：响应不变时去邮箱、导出文件、报表、短信里找副作用。
- **结论**: 绕过的不是 ID 本身，而是「同一资源有多条引用通道，而鉴权只做在其中一条上」。
- **结果**: 作者通过先拿 `conversation_id` 列表、再逐个读取，读到他人私信。

### 示例 4: 同一功能两个入口，鉴权只做了一个
- **类型与来源**: 【亲历】《Bug Bounty Bootcamp》Ch24 / Testing for Broken Access Control
- **问题/输入**: 删除文章有两个入口：`POST /posts/POST_ID/delete` 与 `DELETE /posts/POST_ID`。
- **方法论的使用**: ① 列出应受访问控制限制的功能；② 对每个功能找出全部入口（页面接口、REST 风格端点、GraphQL mutation、移动端接口）→ 入口矩阵；③ 每个入口准备高权/低权两号，用低权打高权入口；④ 被拦时试去掉 token、加 `admin=1`、换方法；⑤ 读原始响应而非渲染后页面——API 常返回页面上不显示的字段（私有 token、他人 ID）。
- **结论**: 漏洞不在「有没有鉴权」，而在「同一功能有几套入口、哪一套忘了加」。
- **结果**: 作者发现取个人资料的 API 额外返回了资料所有者的私有 API token，可据此冒充。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 看到 URL 里有 `id=`/`uid=`/`order_id=`，想知道改成别人的会怎样。
2. 后台页面进不去（302/403），需要判断是「真鉴权」还是「只是藏起来」。
3. 多步流程（添加用户、审批、退款）想验证每一步是否都做了鉴权。
4. 同一个功能有 Web、App、API、旧版四套入口，怀疑某套漏了校验。
5. 响应里出现了不该出现的字段（他人邮箱、私有 token、内部 ID）。
6. ID 是加密/哈希的，看起来「没法改」，想知道还有没有别的引用通道。

### 语言信号（出现这些就该激活）
- 中文：「改 id 能看到别人数据」「越权怎么测」「需要几个账号」「后台进不去」「同一个功能两个接口」「响应里有不该有的字段」「ID 是加密的还能打吗」「App 和网页行为不一样」
- English: "IDOR methodology", "object reference tampering", "horizontal privilege escalation", "vertical privilege escalation", "broken access control", "compare site maps", "forced browsing", "multiple endpoints same action", "inconsistent security controls"

### 与相邻能力的区分
- 与 `auth-session-bypass` 的区别：本卡假设你已有合法身份，问「这个身份能碰谁的数据」；那张卡问「怎么获得身份」。
- 与 `csrf-ui-redress` 的区别：越权用自己的账号，CSRF 用受害者的身份；前者不需要受害者做任何事。
- 与 `business-logic-flaws` 的区别：越权是「权限判据错」，逻辑漏洞是「业务规则假设错」；同一请求可能同时命中，报告应分别归因。
- 与 `recon-asset-surface` 的区别：那张卡负责把入口和角色列全，本卡负责判定。

## E — 可执行步骤 (Execution)

**必需输入**: 每个权限级别两个账号（attacker/victim）+ 一个未登录会话；能保存并按另一会话重放整张地图的工具；能改包的代理。缺对照账号就无法判定，必须补齐。

**交付物与完成标准**: 一张「功能 → 入口 → 参数族 → 水平/垂直/未授权三向结论」的矩阵；完成标准是每条越权都有「A 的请求 + B 的数据出现在响应/副作用里」的证据。

1. **建号矩阵**
   - 做什么：列出站点角色/权限层级；每个角色建两个号（标 attacker/victim）；再留一个未登录会话。
   - 完成标准：能同时覆盖水平（同级 A→B）、垂直（低→高）、未授权（无凭证）三维。
   - 判停：只允许一个账号时，改用「数字 ID 区间遍历 + 响应长度/状态码分叉」做近似判断，并在报告注明局限。

2. **摸敏感功能**
   - 做什么：用最高权限号走一遍全站，标出「返回用户信息」与「修改用户数据」的功能（我的订单、保单、地址、消息、发票、导出、审批）。
   - 完成标准：功能清单可按「读/写/删」分类。
   - 判停：若功能太多，按「涉及钱/身份/隐私」排序，先测前 20%。

3. **抓引用参数并归类**
   - 做什么：逐个功能抓请求，找出所有「看起来像主体标识」的参数，归入五族：订单/保单号（`orderId`、`policyNo`）、手机号（`username`、`telno`）、用户 ID（`uid`、`userId`、`taskHeader.taskId`）、地址/文件 ID（`deliverId`、`file`）、邮箱/发件人（`email`、`inputFrom`）；URL 路径段与 header 也算。
   - 完成标准：每个功能至少标出一个可篡改引用。
   - 判停：请求里完全没有标识符 → 进第 4 步的「补参数」分支。

4. **三个方向逐个打**
   - 做什么：① 水平——把引用换成 victim 的同类值（或 ±1 遍历）；② 垂直——把身份类参数（`uid`、`role`、`userType`、`menuId`）改成管理员的值，或直接请求高权 URL；③ 未授权——清空 cookie 重放同一 URL。
   - 完成标准：响应里出现他人数据，或他人侧数据被改动，或未登录仍返回数据。
   - 判停：服务端从 Session 取身份时任何参数篡改都无效 → 转第 5 步（多阶段）与第 6 步（客户端判据）。

5. **多阶段逐请求重放**
   - 做什么：用高权账号完整走一遍流程，在代理历史里定位完整请求序列；切到低权账号；对序列中**每个请求**用「以当前会话重放」功能发送（保留低权 cookie，仅替换 body/URL）；特别覆盖表单提交页、重定向目标、无参数的中间请求。
   - 完成标准：能指出「第几个请求没有鉴权」。
   - 判停：只重放第一步会得出「鉴权正常」的错误结论；同一浏览器多窗口共享 cookie，测多身份需用不同浏览器/机器。

6. **客户端判据与藏起来的功能**
   - 做什么：用高权账号观察请求里所有「像权限标志」的字段（`admin`、`role`、`level`、`isAdmin`）；用低权账号注入/修改这些字段（query 与 body 都试）；对关键功能逐个删除或伪造 `Referer`；对后台路径字典做探测，确认「藏起来」的页面是否真做了鉴权。
   - 完成标准：能证明「鉴权判据本身来自客户端」。
   - 判停：删掉即失败说明它在用 Referer 做授权；界面不显示该参数时只能靠爆破参数名（`admin=true`、`debug=true`）。

7. **被挡住时的引用变形**
   - 做什么：按第 A1 示例 3 的六条逐条试（解码/预测/补参数/换方法/换表示/盲 IDOR）；换方法时注意 GET↔POST、PUT、PATCH、DELETE 的鉴权常不一致；换表示时试 `.json` 后缀、文件名代替 ID。
   - 完成标准：至少排除「所有通道都做了归属校验」。
   - 判停：盲 IDOR 因「响应没变」被判为不存在是常见错误，必须去邮箱/导出/报表找副作用。

8. **跨端一致性**
   - 做什么：列出该功能的所有入口（Web、App、第三方集成、API、旧版端点）；在每个入口执行同一动作，记录各自触发的校验步骤；比对哪个入口少一步；用「本应被拦」的条件在弱入口重试。
   - 完成标准：能写出「Web 端有 X 校验，App 端无」这样的对照句。
   - 判停：把「UI 上没显示该步骤」当成「服务端没校验」是误判，必须以请求为准。

9. **403/401 的路径层绕过**
   - 做什么：对确认存在但被拦的路径逐个试变形：`/admin..;/`、`/admin/`、`/admin/.`、`//admin//`、`/admin%20/`、`/%20admin%20/`、`/accessible/..;/admin`、`/.;/admin`、`/admin;/`、`/%2e/admin`；再试 `X-Original-URL`/`X-Override-URL`/`X-Rewrite-URL`；再试来源 IP 头（`X-Forwarded-For`、`X-Originating-IP`、`X-Remote-IP`、`X-Client-IP`、`X-Remote-Addr`）填 `127.0.0.1`/内网段；最后换方法（GET→POST/PUT/OPTIONS/TRACE）。
   - 完成标准：拿到 200 且内容确为目标功能。
   - 判停：后端也做了 Session 级鉴权时，路径变形只能绕过「路径规则」、进不去业务；`..;/` 依赖 Tomcat/Spring 一类会截断 `;` 参数的容器。

## B — 边界 (Boundary) ★

### 不要用的情况
- 所有数据访问都在数据层统一加了 `owner_id` 约束、且详情/导出/API 共用同一查询构造器：横向越权的空间基本为零，不要在参数变形上耗时间。
- 目标只有一个账号且不允许注册：无法做对照实验，只能做「未授权」与「ID 遍历」两类近似判断，结论强度下降。
- 功能本身就是公开的（公开搜索、公开主页）：响应相同不构成越权，先确认业务语义。

### 已知失败模式
- **把「响应不同」当安全、把「响应相同」当漏洞**：原书明确两类都会误判；diff 只用于定位候选。
- **只测页面入口，不测 API/移动端**：最常出问题的那一套往往没有页面。
- **只看渲染结果**：漏掉响应体里的敏感字段（原书案例：资料 API 额外返回他人私有 token）。
- **只重放第一步**：多阶段流程会得出「鉴权正常」的错误结论。
- **把「隐藏 URL」「导航里没有」当访问控制**：字典一扫就出来。
- **把水平越权当垂直越权修**：加角色判断后改 id 依然能越权，因为缺的是归属校验。
- **只改数字 ID，遇到编码/哈希就放弃**：漏掉解码、补参数、换方法、换表示四条通道。
- **盲 IDOR 判为不存在**：响应不变但有邮件/导出副作用。
- **只在一个位置试路径变形**：同一路径在子目录下可能有不同的 per-directory 配置。

### 作者与时代的局限
- 书中「比较站点地图」的做法依赖 Burp 的 state file 功能，现代 SPA 下地图覆盖度下降，需结合「读 bundle 找端点」与「抓 App 流量」。
- 早期的「隐藏管理目录」在云原生架构下常被网关统一拦截，路径变形（`..;/`、`%20`）的有效性取决于具体代理/容器组合，需要按技术栈选择而非全表硬试。
- 现代框架的 ORM 常默认加作用域（如 Laravel 的 global scope），但「导出/报表/批量接口」常绕过 ORM 直写 SQL，这一层仍是高频失守点。

### 容易混淆的方法
- **越权 vs CSRF**：前者用自己的身份，后者借受害者的身份。
- **越权 vs 认证绕过**：前者需要合法身份，后者连身份都不需要。
- **IDOR vs 竞态**：IDOR 换的是「对象」，竞态换的是「时机」；两者都表现为「看到了不该看到的/多做了不该做的」。
- **水平 vs 垂直**：同角色之间 vs 跨角色；修法不同（归属校验 vs 权限表）。

### 授权与合规边界
> 待补充（用户自行填写）
