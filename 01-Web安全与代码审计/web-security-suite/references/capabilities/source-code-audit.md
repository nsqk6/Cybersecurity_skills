## I — 方法论骨架 (Interpretation)

源码审计的难点不是「看不懂代码」，而是**搜索空间太大**。所以方法的核心是三步收敛：

1. **选入口**（决定你先看哪）。三条路各有代价：① 盯敏感功能点（上传/下载/登录/导入）——精准但会被不规范命名骗过；② 搜敏感关键字再回溯调用链——快且能定向，但容易漏逻辑漏洞；③ 通读全文——最全但最慢。渗透场景下应把 ② 当默认，用 ① 补「业务上必然存在的功能」，只有在「只有一个登录框、别的路都堵死」时才用 ③。
2. **把「漏洞」拆成两个可分别判定的条件**：**危险汇聚点**（`eval`/`system`/`unserialize`/`move_uploaded_file`/`Db::query`）与**可控来源**（`$_GET`/`$_POST`/`$_COOKIE`/`$_SERVER`/`php://input`/`getallheaders()`）。两者在同一条数据流上相遇才成立——搜到函数只是起点，必须回溯到「用户可控且未过滤」。
3. **按可利用性排序**：命令执行 > 代码执行 > 文件上传 > 文件包含 > SQL 注入 > 文件下载 > 逻辑漏洞 > SSRF > XSS。先打能直接 getshell 的。

三个高频盲区，每个都能让审计结论反转：

- **权限不在当前方法里**。看到上传只校验 MIME 就以为拿下，实际卡住的是父类 `ComController` 里的 cookie 认证——而那个认证本身可伪造（`$user = cookie('user')`）。所以「追到父类/中间件」是必做动作。
- **权限表查不到 ≠ 不能访问**。细粒度权限系统里，方法可能不在权限表，但在「免登录白名单」里（如禅道「方法名含 `ajax` 就跳过验证」）。必须同时看两张表并求交集。
- **过滤函数≠安全**。`addslashes`/`mysql_real_escape_string` 的保护力依赖「拼接处有引号」；`escapeshellarg` 只在「整个参数被它包住」时有效；`intval` 只对整数参数有效；`htmlspecialchars` 只防 XSS 不防 SQL。判据是「过滤函数 + 拼接形态」这个二元组，不是函数名。

最后一条纪律来自反例：**公开 EXP 打不动不等于漏洞不存在**。四种原因（已打补丁 / 被设备拦 / 环境差异 / 漏洞不成立）后续动作完全不同。正确顺序是「本地搭同版本复现 → 证明漏洞真实 → 再排查目标为什么不行」，且判定「已打补丁」要有证据（补丁遗留文件、版本号、diff）。

## A1 — 应用示例 (Application Example)

### 示例 1: grep 危险函数 → 回溯 → 构造验证
- **类型与来源**: 【例题】《Bug Bounty Bootcamp》Ch22（PHP `unserialize` 片段，示例取自 OWASP）
- **问题/输入**: 一套 PHP 源码，目标是找 RCE。
- **方法论的使用**: ① 按语言 grep 危险函数：PHP `eval/assert/system/exec/shell_exec/passthru/popen/反引号/include/require/unserialize`；Python `eval/exec/os.system/pickle.loads/yaml.load`；JS `document.write/document.location.href`；Ruby `system/exec/%x/Marshal.load`；② 命中 `unserialize($_COOKIE['data'])`，向上追来源 → 直接来自 Cookie，外部可控；③ 继续追该类：`__wakeup()` 里 `eval($this->hook)` → 反序列化时 `hook` 属性可控；④ 构造序列化对象把 `hook` 设为 `system('id')`，编码后放 Cookie 验证；⑤ grep 凭据关键词（`key/secret/password/encrypt/API/login/token`）与格式正则（GitHub token `[a-f0-9]{40}`）补漏。
- **结论**: 审计 = 一次 grep + 一次人工追链；「危险函数 + 可控来源」两个条件都成立才算候选。
- **结果**: 原书以该片段推导出反序列化 RCE，未给出对真实站点的利用结果。

### 示例 2: 三条路线的取舍与合并
- **类型与来源**: 【转述】《PHP代码审计入门指南》PHP 代码审计思路
- **问题/输入**: 一套中等规模 PHP 项目，审计时间只有两天。
- **方法论的使用**: ① 先做功能审计：列出上传、登录、下载、导出、支付、找回密码等关键功能，每条功能对应 1–2 个高价值漏洞假设；② 再做反向审计：搜危险函数（按能力分组），对每个命中点回溯参数来源，标记「可控且未过滤」；③ 时间允许再做正向审计：从 `$_GET/$_POST/$_REQUEST/php://input` 出发追到 sink，补上反向审计漏掉的「二次赋值/间接调用」；④ 三条路线产出合并去重，按「可控性 × 危害」排序；⑤ 时间不足时只做 1+2，并在报告注明「未做全量正向追踪」。
- **结论**: 三条路线是三组取舍，不是三选一的教条；按时间预算组合使用。
- **结果**: 原书以优缺点表形式给出，未绑定具体项目。

### 示例 3: 追到父类才发现认证可伪造
- **类型与来源**: 【亲历】《163酒仙桥六号部队__152-渗透测试之通过代码审计打点》
- **问题/输入**: 案例二：ThinkPHP 二开系统，上传点只校验 MIME。
- **方法论的使用**: ① 按 ② 搜危险函数（`uploadFile`、`move_uploaded_file`）得到候选点；② 对候选点回溯入口，确认「参数是否外部可控 + 是否有前置认证」；③ 上传点本身无认证校验，但继续跟进父类 `ComController` → 发现 `$user = cookie('user')` 直接取 cookie 作为身份；④ 伪造该 cookie 即通过认证 → 上传 + 认证伪造组合成 getshell；⑤ 注意 .NET 场景：aspx 里没有业务代码，只看 aspx 会得出「没有上传逻辑」的错误结论，要追 `.cs`/dll。
- **结论**: 「只看到上传没过滤就以为拿下」会漏掉「认证在父类」这一层；而这一层往往比上传本身更脆。
- **结果**: 作者用「MIME 校验缺失 + cookie 认证可伪造」组合 getshell；另一案例是「任意文件下载 → 下载配置拿到域用户 → 下载 dll 反编译 → 发现上传未过滤」。

### 示例 4: 用高危函数反查权限表
- **类型与来源**: 【亲历】《163酒仙桥六号部队__094-对HW期间遇到的禅道系统深入挖掘》
- **问题/输入**: 禅道 11 级用户组，权限划分很细，正向「一个组一个组看能干什么」是 O(组数×功能数)。
- **方法论的使用**: ① 找到权限定义表（`zt_grouppriv`，`Group=11` 即 guest）→ 建立「方法 → 所需权限」映射；② 找到免登录白名单（`isOpenMethod`）→ 记录所有「不需要登录就能进」的方法；③ 搜高危函数得到候选方法清单 → 与上面两张表求交集；④ 交集里的方法逐个实测；⑤ 特别注意：`file` 模块的 `ajaxUpload()` 在权限表里没有条目，但白名单规则是「方法名含 `ajax` 就跳过验证」→ guest 组也能调。
- **结论**: 反向做是 O(漏洞点数)，且天然优先命中「低权限也能 getshell」的高价值组合；「权限表查不到 ≠ 不能访问」。
- **结果**: 作者用 guest 组账号 + `file-ajaxUpload` + `1.php::$DATA` 上传 getshell（影响 ≤9.2，9.3 改白名单）。

### 示例 5: 公开 EXP 失效的四种原因
- **类型与来源**: 【亲历】《163酒仙桥六号部队__094》（快速验证 / 问题排查）
- **问题/输入**: 一个公开 EXP 打过去「页面空白」，无任何反应。
- **方法论的使用**: ① 本地搭同版本环境复现 → 复现成功说明 EXP 本身有效；② 在目标上找补丁痕迹（版本号接口、补丁遗留文件、报错页差异）→ 区分「已修」与「被拦」；③ 本例最终靠根目录下的 `ok.txt` 这个补丁产物文件确认「已打补丁」；④ 读补丁 diff 找绕过点（`__construct` + `checkKey()`），发现默认 `sso->turnon` 无值、`block` 模块整体不可达 → 绕过失败；⑤ 及时止损，转「挖同系统的新洞」（guest 组上传 getshell）。
- **结论**: 「打不动」有四种原因，判错方向会让后续所有绕过都白做；补丁分析失败要及时止损。
- **结果**: 作者完成「EXP 失败 → 本地复现 → 判定已打补丁 → 绕过失败 → 转挖新洞」的完整四段。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 拿到一套源码（开源二开、外包交付、泄露备份、反编译 dll/jar），不知道从哪看起。
2. 渗透时「只有一个登录框」，需要从代码里找突破口。
3. 需要判断「这个 CMS 有没有洞」而不是逐个功能点手测。
4. 代码里到处都是 `addslashes`/`htmlspecialchars`，需要判断哪些地方其实仍可注入。
5. 权限系统很复杂（多角色、多模块），需要快速找出「低权限也能 getshell」的入口。
6. 公开 EXP 打不动，需要判断是补丁、拦截还是环境问题。
7. 需要给开发一份「哪里该改、为什么」的清单，而不是一堆 payload。

### 语言信号（出现这些就该激活）
- 中文：「拿到源码怎么开始审」「grep 哪些函数」「PHP 敏感函数清单」「这套代码哪里可能命令执行」「用了 addslashes 还安全吗」「这套系统权限分得很细怎么打」「网上 EXP 打不进去」「是不是已经修复了」
- English: "source code review grep", "dangerous functions audit", "PHP dangerous functions audit", "where to start code review", "source code audit entry point", "why addslashes is not enough", "low privileged user RCE", "public exploit not working", "is it patched or blocked"

### 与相邻能力的区分
- 与 `recon-asset-surface` 的区别：那张卡在无源码时产出「测什么」，本卡在有源码时产出「哪一行有问题」；本卡可接收那张卡发现的 `.git` 泄露/备份文件作为输入。
- 与 `injection-channel-selection` 的区别：本卡是白盒「有没有拼接」，那张卡是黑盒「能不能注」；两者结论应互相印证。
- 与 `waf-bypass-encoding` 的区别：本卡处理代码层过滤缺陷（清洗不彻底、转义上下文错），那张卡处理设备层与协议层。
- 与 `finding-to-report` 的区别：本卡产出「漏洞与根因」，那张卡产出「可被受理的报告」。

## E — 可执行步骤 (Execution)

**必需输入**: 源码或可反编译产物；框架类型（ThinkPHP/Spring/Django/.NET 等，决定入口文件位置）；一个能做函数跳转/引用查找的编辑器（F12 跳定义、Shift+F12 查引用）。缺框架信息时先看目录结构与入口文件。

**交付物与完成标准**: 一份「候选点 → 来源是否可控 → 是否有过滤 → 前置认证 → 可利用性排序」的清单；完成标准是每条候选都有「可控 + 汇聚」两个证据，且按 命令执行 > 代码执行 > 上传 > 包含 > SQLi > 下载 > 逻辑 > SSRF > XSS 排好序。

1. **建代码地图**
   - 做什么：看目录结构定位入口（`index.php`、`route`、`Controller`、`web.xml`）；找配置文件（`.env`/`config.php`/`application.yml`）拿数据库、密钥、调试开关；找权限定义表与免登录白名单。
   - 完成标准：能说出「请求从哪进、经过哪些中间件、到哪里落库」。
   - 判停：闭源且无源码时，先找任意文件下载/备份泄露/`.git`，拿不到则转黑盒能力卡。

2. **选入口（三条路线的组合）**
   - 做什么：时间紧 → 反向（搜危险函数）；要覆盖业务 → 功能审计（上传/登录/下载/导出/支付/找回）；目标是「只有一个登录框」→ 正向（从输入追到 sink）或通读。
   - 完成标准：明确本轮用哪条路线、覆盖了什么、没覆盖什么。
   - 判停：只做反向会漏「参数经过一次赋值后才进 sink」的链路；只做功能审计会漏同功能的其他入口。

3. **搜危险汇聚点（按能力分组，不按名字）**
   - 做什么：命令执行（`system/exec/passthru/shell_exec/反引号/popen/proc_open/pcntl_exec`）；代码执行（`eval/assert/preg_replace` 的 `/e`/`call_user_func/create_function`）；文件包含（`include/require` 及 `_once`）；SQL（`mysql_query/mysqli_query/pg_query/PDO::query/Db::query/SqlHelper`）；文件读写（`file_get_contents/fopen/fwrite/file_put_contents/move_uploaded_file/extractTo`）；XML（`DOMDocument::loadXML/simplexml_load_*`）；反序列化（`unserialize/pickle.loads`）；文件上传（`uploadFile`）。
   - 完成标准：每个命中点都记录了文件、行号、函数。
   - 判停：只搜原生函数会漏框架封装与动态调用（`call_user_func($f,...)`、`$fn()`）——要补搜框架的等价 API。

4. **回溯来源（可控性判定）**
   - 做什么：对每个命中点向上追参数赋值链，直到来源是 `$_GET/$_POST/$_REQUEST/$_COOKIE/$_SERVER/php://input/getallheaders()` 之一；中间有二次赋值、数组取值、字符串拼接的都要跟到底。
   - 完成标准：能画出「输入 → ... → sink」的完整路径（哪怕跨 5 个文件）。
   - 判停：来源是常量/配置/数据库内生成时，判不可控；但要确认「数据库里的值是否曾经由用户写入」（存储型可控）。

5. **判过滤是否成立（二元组判据）**
   - 做什么：记录链路上的过滤函数与位置；对 SQL 看拼接模板有无引号包裹（无引号则数字型注入仍成立）；对命令看 `escapeshellarg` 是否包住完整参数；对文件看后缀/路径校验是否可绕；对 XSS 看编码是否匹配输出上下文。
   - 完成标准：每条给出「过滤有效 / 可绕 / 未过滤」三态之一。
   - 判停：`PDO::prepare` 也要看是否 `ATTR_EMULATE_PREPARES=true`（模拟预处理仍有宽字节面）；`intval` 只对整数参数有效。

6. **追权限（这一步最容易被跳过）**
   - 做什么：对候选方法查「所需权限」与「免登录白名单」两张表并求交集；继续追父类/中间件/注解（`@PreAuthorize`、`beforeAction`、middleware）；注意字符串匹配型白名单（「方法名含 `ajax` 就跳过」）与「判账号名而非组名」的缺陷。
   - 完成标准：能回答「最低哪个角色能调到这个方法」。
   - 判停：权限表查不到时不要直接判「不可访问」，必须看白名单；父类认证逻辑本身可能可伪造（cookie/header 取值）。

7. **排优先级并实测**
   - 做什么：按可利用性排序；对每条构造最小输入验证（如 `admin'--` 登录绕过、`?p=1%00<script>`、序列化对象放 Cookie）；验证时用本地环境，避免污染目标数据。
   - 完成标准：至少一条从「静态可疑」升级为「动态确认」。
   - 判停：输入不可控即误报，看到 `eval()` 就报漏洞是审计里最常见的噪音来源。

8. **处理「打不动」**
   - 做什么：本地搭同版本复现 → 找补丁痕迹（版本接口、遗留文件如 `ok.txt`、报错页差异）→ 判「已修/被拦/环境差异/不成立」→ 已修则读 diff 找绕过点，绕不过转挖新洞；被拦则转 `waf-bypass-encoding`。
   - 完成标准：给出四选一的结论 + 证据。
   - 判停：补丁绕过失败要及时止损，不要在一个已封死的模块上继续消耗。

9. **定性（Bug 还是功能缺失）**
   - 做什么：对每个发现问「若攻击者不存在，这个现象会不会导致功能异常」——会=Bug（必须修），不会=功能缺失（进需求池）；Bug 再分因：实现写错（注入）vs 缺少校验环节（遍历、未校验上传类型），后者更适合用规范/框架/清单批量解决。
   - 完成标准：报告里每项都标注类别与根因。
   - 判停：把所有问题都报成高危会淹没真实高危；用「这是设计如此」把注入降级也是错的。

## B — 边界 (Boundary) ★

### 不要用的情况
- 只有编译产物且无符号/无反编译条件（如强混淆的 Go/Rust 二进制）：本卡的可读性前提不成立，转逆向能力。
- 框架重度封装且源码只有业务层（如只给 Controller，不给 vendor）：危险函数多在框架内，需先确认框架版本是否有已知 CVE，而不是逐行读业务代码。
- 目标只有一个静态页面、无任何服务端逻辑：审计收益为零。

### 已知失败模式
- **看到 `eval()` 就报漏洞**：输入不可控即误报，这是审计噪音的最大来源。
- **只 grep 不追数据流**：大量「函数存在但不可达」的噪音，且漏掉「二次赋值后才进 sink」的真洞。
- **漏框架封装与动态调用**：`Db::query`、`request()->file()->move()`、`call_user_func($f,...)`、`$fn()`。
- **只看当前方法不看父类**：认证常在父类/中间件里，且那一层可能更脆（原书案例：cookie 直接当身份）。
- **权限表查不到就判不可访问**：漏掉免登录白名单与字符串匹配规则。
- **看到 `intval`/`addslashes` 就判安全**：前者只对整数有效，后者只在有引号拼接时有效。
- **把 `htmlspecialchars` 当 SQL 防护**：它只防 XSS。
- **把 `preg_replace` 的 `/e` 用到 PHP7+**：该修饰符已移除，对老代码才成立。
- **`$_FILES['file']['name']` 里的换行**：PHP 会自动去掉，某些文件名绕过在此不成立。
- **公开 EXP 打不动就写「无此漏洞」**：四种原因未分诊，会产生误报（原书反例）。

### 作者与时代的局限
- 书中的函数表以 PHP 5/7 早期为主；PHP 8 移除了大量函数（`create_function`、`assert` 的字符串形式、`/e`），需按版本裁剪。
- 现代框架（Laravel/Symfony/Spring Boot）把大量危险操作封装进容器与 ORM，审计重点已从「找函数」转向「找绕过框架保护的写法」（原生 SQL、`DB::raw`、反序列化入口、模板 `|raw`）。
- 「通读全文」在百万行项目上不可行，现代实践更多依赖 SAST + 人工验证；书中明确「自动化审计工具不考虑在内」，这一取舍需按团队能力调整。
- 供应链维度（依赖库 CVE、composer/npm 投毒）书中未覆盖，属于另一个能力域。

### 容易混淆的方法
- **代码审计 vs 渗透测试**：前者看「代码怎么写的」，后者看「系统怎么响应的」；同一漏洞两者结论应互相印证，冲突时以动态验证为准。
- **反向审计 vs 正向审计**：从 sink 回溯 vs 从 source 追踪；前者覆盖全但慢，后者快但漏二次赋值。
- **Bug vs 功能缺失**：前者「不攻击也会功能异常」，后者「只是没做某项加固」；定责与修法不同。
- **权限表 vs 白名单**：前者管「谁能调」，后者管「谁不用登录就能调」；必须一起看。
