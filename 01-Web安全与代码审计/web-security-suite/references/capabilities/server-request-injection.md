# 服务端发起的请求与结构化消息注入

## R — 原文 (Reading)

> "Server-side HTTP redirection attacks allow an attacker to specify an arbitrary resource or URL that is then requested by the front-end application server."
>
> 译：服务端 HTTP 重定向攻击允许攻击者指定任意资源或 URL，由前端应用服务器去请求它。

> — 《The Web Application Hacker's Handbook》Ch10 / Injecting into Back-end HTTP Requests

> "%E5%98%8A => U+560A => 0A"
>
> — 《Web Hacking 101 中文版》七、CRLF 注入

> "如果攻击者输入了 http://foo.com/nope{{7*7}} ，开发者的代码会渲染 http://foo.com/nope49"
>
> — 《Web Hacking 101 中文版》十六、模板注入

## I — 方法论骨架 (Interpretation)

这一族漏洞的共同点：**用户数据被拼进了「另一种语法的消息」里**，而那条消息由服务端自己发出或自己解析。语法种类决定了逃逸方式，也决定了危害落点：

| 消息语法 | 逃逸字符/结构 | 危害落点 |
|---|---|---|
| XML（XXE/SOAP） | `<!DOCTYPE>` / 闭合标签 / 注释 | 读文件、探内网、改业务字段 |
| URL（SSRF） | 目标段、路径、`@`、`#`、`?` | 让服务器去请求内网/元数据 |
| HTTP 头 / SMTP | `\r\n`（CRLF）、单独一行 `.` | 注入新头、拆分响应、代发邮件 |
| 查询串 | 同名参数（HPP）、追加参数（HPI） | 覆盖后端固定值、触发后端开关 |
| 模板 | `{{ }}` / `{% %}` / `<%= %>` | 服务端表达式求值 → 读文件 → RCE |
| 跳转目标 | `Location` 值 | 钓鱼可信度、OAuth 取码 |

四步通用流程：

1. **定位「第二次使用」**。这类漏洞几乎都出现在「应用收下你的输入，再拿它去构造另一个请求/消息」的位置：图片预览、抓取标题、webhook、支付网关对接、发信、模板渲染、重定向。找不到这个「二次使用点」，payload 再多也没用。
2. **确定语法层与逃逸字符**。不是「加个引号」，而是「在这个语法里，什么字符能让解析器提前结束当前上下文」：XML 是 `>` 与 `]]>`，HTTP 头是 `\r\n`，URL 是 `@`/`#`/`?`。
3. **用差分证明「我控制了那条消息」**。最快的判据是「让服务端去访问一个我能观测的地址」（自建 HTTP/DNS），而不是猜回显。
4. **评估可达范围**。SSRF 要看能否到内网/云元数据；XXE 要看能否读文件/探端口；SSTI 要看「能求值」之后能否读配置、能否 RCE；HPP 要看后端取首/取尾/拼接。

关键取舍：**能出网就用带外，不能出网就用差分（时间/长度/错误）**。这条分叉贯穿整族漏洞——它决定了你是十秒确认，还是半小时盲猜。

## A1 — 应用示例 (Application Example)

### 示例 1: XXE 读文件到内网探测
- **类型与来源**: 【例题】《The Web Application Hacker's Handbook》Ch10 / Injecting XML External Entities（`POST /search/128/AjaxSearch.ashx`）
- **问题/输入**: 一个 Ajax 搜索接口，请求体是 XML（`Content-Type: text/xml`）。
- **方法论的使用**: ① 确认 body 是 XML；② 在原 XML 前插入 `<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///windows/win.ini" > ]>`，在会被回显的元素里写 `&xxe;`；③ 响应出现 `[fonts]` 等段落 → 外部实体被解析且回显；④ 换成 `file:///etc/passwd` 或应用配置文件验证可读范围；⑤ 换成 `http://192.168.1.1:25`，用 banner/报错/时间差判断内网服务；⑥ 不回显时用 `file:///dev/random` 观察连接挂起（DoS 面）。
- **结论**: 成立前提是三条同时满足——解析 XML、允许 DOCTYPE/外部实体、实体值可被观测。
- **结果**: 原书给出读取 `win.ini` 并回显的完整请求与响应。

### 示例 2: 从 `loc=` 参数读到 SSH banner
- **类型与来源**: 【例题】《The Web Application Hacker's Handbook》Ch10 / Server-side HTTP Redirection
- **问题/输入**: 一个 `loc=` 参数被拼进后端 HTTP 请求的目标地址。
- **方法论的使用**: ① 把值改成自己控制的域名，监控自己服务器是否收到请求（确认「服务端在发请求」）；② 无回连时看响应时间，明显延迟说明后端在尝试出站但被网络策略挡住；③ 确认 SSRF 后加端口：`loc=192.168.0.1:22` → 响应里出现 `SSH-2.0-OpenSSH_4.2` banner；④ 用 Intruder 扫内网 IP/端口，试 `127.0.0.1` 上的其他服务。
- **结论**: 控制「目标」是 SSRF；控制「参数名」是 HPI；重复同名参数是 HPP——三者是三个不同的可控点。
- **结果**: 原书以该请求演示内网端口识别（banner 回显）。

### 示例 3: CRLF 绕过编码校验做响应拆分
- **类型与来源**: 【转述】《Web Hacking 101 中文版》七、CRLF 注入（Twitter `redirect_after_login`）
- **问题/输入**: 一个参数被写进响应头；直接提交 `%0d%0a` 被过滤。
- **方法论的使用**: ① 先打裸载荷 `%0d%0aX-Test: 1`，看原始响应头（不是 HTML 源码）是否新增一行；② 被拦后改用「在 UTF-8 中合法、解码后低位字节是 0x0A」的字符：`%E5%98%8A` 代 `%0A`、`%E5%98%8D` 代 `%0D`；③ 服务器做编码转换时把它还原成换行 → 注入 `location` 头 + 空行 + `svg/onload`；④ 升级为响应拆分：注入 `Content-Length` 构造两个完整响应，污染缓存。
- **结论**: 过滤器拦的是「字面换行」，编码转换发生在过滤之后，语序颠倒就产生绕过。
- **结果**: 原书说明该问题在 Twitter 获 3500 美元赏金（转述）。

### 示例 4: `{{7*7}}` 的两个反例
- **类型与来源**: 【转述】《Web Hacking 101 中文版》十六、模板注入（Uber 两案例）
- **问题/输入**: `developer.uber.com` 的 `?q=` 参数；另一处是用户姓名，页面显示为纯文本。
- **方法论的使用**: ① 提交 `?q=wrtz{{7*7}}` → 返回 `wrtz49`，确认服务端模板求值；② 对姓名处提交 `{{1+1}}`，页面是纯文本看不出效果，但同一字段被渲染进邮件时打印出 `2`；③ 进一步用 `{% for %}` 循环在邮件渲染阶段执行 Python 代码；④ 评估过滤强度：若 `{{4+4}}` 返回 8 但 `{{4*4}}` 返回文本 `{{44}}`（`*` 被过滤）、括号被禁、长度限 30，则「能求值但不能利用」，应降级为信息级。
- **结论**: 判据是「算术自证」（输出 49 而非原串），且必须检查**所有渲染位置**（页面/邮件/PDF/通知），不能只看页面。
- **结果**: 原书说明两处分别获 3000 与 10000 美元赏金（转述）。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 参数值形如 URL/host/IP（`url=`、`src=`、`image=`、`feed=`、`webhook=`），想知道能否打内网。
2. 请求体是 XML（SOAP、Ajax、导入），想验证能否读文件或改业务字段。
3. 有发信/邀请/反馈功能，想验证邮件头注入或命令注入。
4. 有跳转参数（`redir=`、`next=`、`return=`），需要判断是开放重定向还是无害固定跳转。
5. 页面/邮件/PDF 里出现了自己输入的原文，想验证模板注入。
6. 同一功能前后端都设了值（`toAccount=9876`），想验证能否用同名参数覆盖。

### 语言信号（出现这些就该激活）
- 中文：「SSRF 怎么确认」「参数里能带 URL」「XXE 怎么验证」「SOAP 注入怎么测」「邮件功能能注入吗」「跳转参数能出站吗」「{{7*7}} 是什么」「同名参数传两次会怎样」「响应头能注入吗」
- English: "server-side request forgery", "blind XXE", "SOAP injection", "email header injection", "open redirect bypass", "SSTI", "HTTP parameter pollution", "response splitting", "cloud metadata 169.254.169.254"

### 与相邻能力的区分
- 与 `injection-channel-selection` 的区别：载荷不是 SQL 片段，而是「另一条消息的目标/结构」；判据也不同（回连 vs 布尔差异）。
- 与 `command-file-injection` 的区别：本卡的终态通常是「让服务器请求/解析」，未必执行代码；SSTI 可以升级到 RCE，但入口是模板语法不是 `eval` 参数。
- 与 `csrf-ui-redress` 的区别：开放重定向让「受害者浏览器」跳转，SSRF 让「服务器」去请求；前者只影响点击者，后者能打内网。
- 与 `waf-bypass-encoding` 的区别：本卡处理语法层逃逸（`@`、`?`、`\u`），那张卡处理设备层拦截。

## E — 可执行步骤 (Execution)

**必需输入**: 可疑的「二次使用点」与其参数；一个可观测的自建地址（HTTP + DNS，用于回连判定）；能读原始响应头与耗时的代理。缺回连地址时只能靠差分，结论强度会下降，需在报告里注明。

**交付物与完成标准**: 每个点一行「语法层 → 逃逸方式 → 证据（回连/差分/回显）→ 可达范围」；完成标准是证据可重复且能说清「影响边界到哪」（外网回连 / 内网端口 / 文件读取 / 代码执行）。

1. **分类：这条输入进的是哪种消息**
   - 做什么：看参数形态与功能语义——值是 URL/host → SSRF 面；body 是 XML → XXE/SOAP 面；有发信功能 → SMTP 面；有 `redir`/`next` → 跳转面；输入出现在渲染结果里 → 模板面；前后端都设值 → HPP 面。
   - 完成标准：能写出「输入 → 消息语法 → 逃逸字符」三元组。
   - 判停：若值既不是 URL 也不进任何结构化消息，转 `xss-context-runtime` 或 `injection-channel-selection`。

2. **SSRF：先证明「服务端在发请求」**
   - 做什么：把值改成自己控制的域名，监控 HTTP/DNS 日志；无回连时看响应时间（明显延迟说明在尝试出站）；再测 `127.0.0.1`、`2130706433`、`localhost`、`0.0.0.0`、`10.0.0.1` 找未被拦的写法。
   - 完成标准：收到来自目标 IP 的请求，或稳定可复现的时间差。
   - 判停：完全无出网迹象且无时间差 → 可能是「只做校验后复制」而非代理，换点。

3. **SSRF：绕前置校验（按校验类型选形态）**
   - 做什么：白名单且允许域内有跳转 → `https://pics.example.com/123?redirect=127.0.0.1`；白名单用弱正则 → `https://pics.example.com@127.0.0.1`、`https://127.0.0.1/pics.example.com`；黑名单 → 自己服务器返回 `Location: http://127.0.0.1`；只拦 IPv4 → 试 `::1`/`fc00::`；只做后缀校验 → 加 `?`/`#` 截断、多余斜杠、`%00`；DNS 层 → 把自己的 A/AAAA 指到内网。
   - 完成标准：通过校验且回连/响应证明请求落到了非预期目标。
   - 判停：连续三种形态均被同一规则拦下，说明是语义级校验，转 `waf-bypass-encoding` 评估是否值得继续。

4. **SSRF：升级到内网与元数据**
   - 做什么：加端口看 banner（`host:22`、`host:6379`）；用 Intruder 扫内网网段常见端口；试 `169.254.169.254` 等云元数据地址；能渲染 HTML 时把可控页面拉进响应做 XSS。
   - 完成标准：拿到内网服务标识或元数据内容（凭证需评估权限范围）。
   - 判停：无回显（盲 SSRF）时改用「写文件 + `file://` 读回」自证：让内网服务往 `/tmp` 写已知内容，再用同一 SSRF 的 `file://` 读回；副作用可见即证明可写。

5. **XXE：三段式验证**
   - 做什么：① 插入 `<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///..."> ]>` 并在回显元素写 `&xxe;`；② 换成目标 OS 的敏感文件验证范围；③ 换成 `http://内网IP:端口` 探服务；④ 不回显时用 `file:///dev/random` 看连接挂起。
   - 完成标准：文件内容出现在响应里，或内网目标出现可区分响应。
   - 判停：`Content-Type` 必须匹配 XML，否则应用不按 XML 处理；解析器禁用 DTD/外部实体时整族失效（现代默认多为禁用）。

6. **SOAP / XML 结构篡改**
   - 做什么：每个参数提交 `</foo>` → 有解析错误说明输入进了 XML；改提交 `<foo></foo>` → 错误消失说明可重新配平；提交 `test<foo/>` 与 `test<foo></foo>` 看归一化差分；多参数时一个放 `<!--`、另一个放 `-->` 造成服务端消息被注释。
   - 完成标准：业务结果随伪造元素改变（如 `ClearedFunds=True` 生效）。
   - 判停：无任何错误反馈时只能盲猜结构，成功率极低，应改用「参数顺序 + 同名元素取首/取尾」的试探。

7. **SMTP：头注入 → 命令注入**
   - 做什么：每个可控字段（From/Subject/Message/隐藏 To）提交 `<youremail>%0aCc:<youremail>` 与 `%0d%0a` 版本；再试 `Bcc:`；升级为 `%0aDATA%0afoo%0a%2e%0aMAIL FROM:...` 让服务器代发新邮件；同一批功能顺手测 OS 命令注入。
   - 完成标准：**以自己收件箱为准**（响应成功不代表信真的发出）。
   - 判停：只过滤了一种换行（LF vs CRLF）时另一种仍可能通过，两种都要试。

8. **HTTP 头 / 跳转 / HPP**
   - 做什么：头注入——提交 `%0d%0aFoo: bar` 看原始响应头是否新增一行，被拦时试 `%00%0d%0a`、`%250d%250a`、Unicode 过编码；开放重定向——区分固定目标与可控目标，按过滤器类型试大小写/前导空格/`//host`/`http:\\host`/`本站域名.攻击者域名`；HPP——同一参数提交两次（`?uid=A&uid=B`）先测该层取哪个，再对应用已固定的值追加同名参数覆盖。
   - 完成标准：能指出「我控制的是哪一段」（新增头 / Location 值 / 后端取到的参数值）。
   - 判停：跳转前缀含 `http://域名/`（带斜杠）时通常只能站内跳，别再耗时间。

9. **模板注入：算术自证 + 可利用性评估**
   - 做什么：判断技术栈（Flask/Jinja2、Rails/ERB、AngularJS）→ 在所有渲染位置注入 `{{7*7}}`（页面、邮件、PDF、通知）→ 出现 `49` 即求值；再测可用字符与长度上限，构造最小表达式（先求值 → 再读配置 → 最后命令执行）。
   - 完成标准：区分「能求值」与「能利用」；只到前者时降级为信息级。
   - 判停：过滤了 `*`/`()`/`[]` 且长度受限时，先算「最短可用表达式是否放得下」，放不下就判不可利用。

## B — 边界 (Boundary) ★

### 不要用的情况
- SSRF 目标做了域名/IP 全等白名单且禁内网、禁跳转、禁 DNS 重绑定：此时绕过空间基本为零，不要用变形表硬耗。
- XML 解析器显式禁用 DTD 与外部实体（`disallow-doctype-decl`、`XMLConstants.FEATURE_SECURE_PROCESSING`）：XXE 整族不成立。
- 重定向目标固定（不接收用户输入）：不存在开放重定向，别把「跳转到登录页」当漏洞。
- JSON 接口强制 `Content-Type: application/json` 且后端不解析表单：SMTP/表单型 HPP 不适用。

### 已知失败模式
- **把「能请求外网」当 SSRF 结论**：价值最高的是内网与云元数据，只验证外连等于没验证。
- **忽略盲 SSRF**：无回显就判「不存在」；应改用写文件读回、DNS 回连或时间差。
- **XXE 忽略 `Content-Type`**：不匹配时应用根本不按 XML 解析，会误判「不支持外部实体」。
- **SOAP 无错误反馈时硬猜结构**：成功率极低，应先找有报错的实例确认机制存在。
- **SMTP 以响应为准**：响应「发送成功」而收件箱没信，说明被上游丢弃或进了垃圾箱。
- **头注入只看浏览器渲染**：必须看原始响应头，否则注入的头在渲染后不可见。
- **HPP 只改值不加同名参数**：改值会被服务端拒绝或忽略，追加同名参数才触发解析差异。
- **模板注入只看页面**：原书两案例中有一处的页面显示是纯文本，漏洞只在邮件渲染时触发。
- **把「能算 7*7」直接报 RCE**：过滤导致实际不可利用时属误报（原书作者自己给出 `{{4*4}}` 反例）。

### 作者与时代的局限
- XXE 在 2010 年代是高频漏洞，现代框架与语言运行时默认禁用外部实体，实际命中率已大幅下降；但「禁用不彻底」的实现仍存在，判据（能否读文件）不变。
- SSRF 的云元数据（169.254.169.254）与 IMDSv2 是书出版后的新战场，书中未覆盖；本卡已补入，但具体凭证路径需按云厂商文档。
- 开放重定向在现代浏览器与 OAuth 规范下危害被进一步约束（`redirect_uri` 全等校验普及），但其作为「SSRF 白名单绕过跳板」的价值反而上升。
- Flash 相关的 Referer/cookie 构造技巧已全面失效。

### 容易混淆的方法
- **SSRF vs 开放重定向**：前者让服务器请求，后者让浏览器跳转；同一参数可能两者都能做，但危害与报告定级不同。
- **XXE vs SSRF**：XXE 是「借 XML 解析器发起请求」，SSRF 是「应用自身代理 HTTP 请求」；前者常需 DOCTYPE，后者只需一个 URL 参数。
- **HPP vs 参数篡改**：篡改是改值，HPP 是**加同名参数**利用解析差异；后者依赖技术栈，没有通用载荷。
- **CRLF 注入 vs 请求走私**：前者利用未过滤的换行改写本条响应，后者利用前后端对 body 长度的理解差异影响他人请求。

### 授权与合规边界
> 待补充（用户自行填写）
