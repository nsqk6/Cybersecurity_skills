# 端点持久化与入口冗余

## R — 原文 (Reading)

> 以往的经验看，还是写一个 webshell 上去，做一下权限的维持，太多次反弹回来的 shell 掉了以后，权限一去不复返。

> — 163 酒仙桥六号部队《一次 Shiro 反序列化引起的域控沦陷》· 1. 拿到权限

> 有意思的是，CompatTelRunner.exe 不是系统启动运行或者用户登录，它是一个周期性的任务，这样可以逃避很多检测。

> — 163 酒仙桥六号部队《红队之浅谈基于 Windows telemetry 的权限维持》· Microsoft Compatibility Telemetry

## I — 方法论骨架 (Interpretation)

这个能力解决的是「怎么保证明天还能进来」，但它真正的判断点不在「用什么手法」，而在**先分清要维持的是哪一种「在」**。

两类维持物的失败方式完全不同：

- **会话是「活」的**：依赖进程存活、网络链路、C2 可达。目标重启、杀软更新、网络策略调整、C2 域名被封，任一发生就永久失去入口。
- **落点是「死」的**：一个文件躺在 web 目录、一个注册表键躺在 HKLM，只要对应服务还在跑就能重新触发，且重建成本接近零。

所以正确的顺序是：**先落一个低成本的二次入口（冗余），再用它去建高质量会话**。这里的「冗余」不是「多留几个后门」，而是「在同一个入口上留两条互相独立的路径」——一条内存会话、一条可重触发的落点。判断标准很硬：C2 会话掉线后，能不能在几分钟内通过另一条路径重建。

在这个框架下再谈「持久化手法」，判断轴有三个：

1. **触发方式**：启动项（Run 键、启动目录）、服务、计划任务——这三类是终端产品重点监控的对象，规则最成熟；周期性系统任务、WMI 事件订阅、COM 劫持这类「复用系统自身机制」的触发方式绕开了按启动项建模的检测。
2. **是否需要落地文件**：落地文件会被静态扫描，纯注册表/纯配置的维持物只被行为检测覆盖。
3. **进程生命周期**：这是最容易被忽略的一条。借系统任务执行的子进程会**随任务进程结束而结束**——如果载荷是个长连接，任务一结束它就断。所以这类维持点的正确用法是「注入到其它进程」或「执行短命令」，而不是「直接起一个 C2」。

以 CompatTelRunner 为例：它是微软自带的遥测程序，运行时枚举 `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\AppCompatFlags\TelemetryController` 下的子键，把 `Command` 值经 `CreateProcessW` 启动。于是只要在该路径下新建子键并写入命令，就能借合法进程执行，且触发方式是「周期任务」而非启动项。但它的约束也很硬：任务进程结束后子进程一起结束；新版本还增加了运行模式检查（系统版本、`CommercialDataOptIn`、电源/电池状态、`RunsBlocked` 计数），不满足条件时不执行命令。

最后一条纪律：**持久化是「加噪声」的动作**，每一个维持物都是一个可被基线比对出来的差异。所以要么少留（一两个高质量落点），要么留得「像系统本来就有」。留五个后门不是更安全，是五倍的暴露面。

## A1 — 应用示例 (Application Example)

### 示例 1: 拿到 shell 后先写 webshell 做锚点
- **类型与来源**: 【亲历】163 酒仙桥六号部队《一次 Shiro 反序列化引起的域控沦陷》· 1. 拿到权限
- **问题/输入**: 通过 Shiro 反序列化拿到一个反弹 shell，尚未进入内网。
- **方法论的使用**: 不急着做横向，先在 web 可写目录写一个加密 webshell（冰蝎/哥斯拉类）作为「重连锚点」；用 webshell 反向弹 C2 会话；后续所有工具投递、凭据抓取都从 C2 会话做，webshell 只在会话丢失时启用。作者的理由是经验性的：「太多次反弹回来的 shell 掉了以后，权限一去不复返」。
- **结论**: 会话是活物、webshell 是死物；先有死物，活物掉了才有退路。
- **结果**: 原书交代该次任务据此维持住了入口并完成后续域内动作。

### 示例 2: 借 CompatTelRunner 的周期任务执行
- **类型与来源**: 【实验】163 酒仙桥六号部队《红队之浅谈基于 Windows telemetry 的权限维持》
- **问题/输入**: 已拿到管理员权限，需要在目标上留一个「重启后仍能触发」的入口，且不想新建计划任务。
- **方法论的使用**: 确认前提（管理员权限、可写 HKLM、系统为 2008R2/2016/Win7/Win10、有网络）；在 `...\TelemetryController\<任意名>` 下新建 `Command`（REG_SZ，填要执行的 exe），并新建 DWORD `Nightly=1`（24 小时一次；另有 Oobe/Maintenance 两种模式）；立即用 `schtasks /run /tn "\Microsoft\Windows\Application Experience\Microsoft Compatibility Appraiser"` 手动触发验证，而不是等 24 小时。
- **结论**: 复用的是系统自带任务的触发链，没有自建任务，因此绕开了「按新建计划任务建模」的检测；但载荷必须能在「任务进程结束后」继续存在，否则一触发就断。
- **结果**: 原书交代 msf handler 收到 SESSION1；同时在反汇编层面给出字段映射（Command/Nightly/Oobe/Maintenance）与失败条件（子进程随任务结束、新版运行模式检查）。

### 示例 3: 【合成演练】会话掉线后的重建判定
- **类型与来源**: 【合成演练】原书未提供完整故障演练，以下仅按本卡 E 段规则推演，不代表现实结果
- **问题/输入**: 假设已按示例 1 留下 webshell + C2 会话；某次 C2 会话因域名被封而消失。
- **方法论的使用**: 按 E 段第 6 步的重建判据执行：先确认 webshell 是否仍可访问（web 服务是否在跑、文件是否被清理）；可访问则用它重新弹一个指向备用监听器的会话；不可访问则判定「冗余失效」，检查是文件被删（静态查杀）还是目录被清（运维清理），据此决定是否换目录重落。
- **结论**: 冗余的价值只有在「能重建」时成立，所以冗余本身需要验证，不能假设它一直在。
- **结果**: 本演练不产出「成功/失败」结论，只产出「哪一层失效」的定位。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 刚拿到 shell，需要决定要不要先做冗余再横向。
2. 反弹 shell 老是掉，需要判断是网络问题还是缺落点。
3. 需要留一个重启后仍能触发的入口，但不想新建计划任务/服务。
4. 留了维持物后发现「一触发就断」，需要判断是不是进程生命周期问题。
5. 评估「留几个后门合适」，担心噪声。

### 语言信号（出现这些就该激活）
- 中文：「shell 掉了进不去」「怎么维持权限」「权限维持不被杀软发现」「telemetry 持久化」「重启后还能不能进」「留几个后门合适」
- English: "webshell as fallback", "session lost after reboot", "compatTelRunner persistence", "fileless persistence windows", "persistence noise tradeoff"

### 与相邻能力的区分
- 与 `kerberos-ticket-abuse` 的区别：票据是凭据层访问，重启后内存票消失；本卡是主机层自启动，重启后仍可触发。
- 与 `lateral-execution-channels` 的区别：横向手段（服务/任务）常顺带形成事实上的持久化，但那不是设计目的；本卡是显式设计「下次还能进」。
- 与 `c2-tunnel-infrastructure` 的区别：那张卡解决「通道断了怎么修」，本卡解决「会话没了怎么重建」；前者是网络层冗余，后者是载体层冗余。

## E — 可执行步骤 (Execution)

**必需输入**: ①已控主机与当前权限；②入口类型（web 应用 / 远程执行 / 交互式会话）；③可写目录或可写注册表路径；④objective 的时长（本次要维持多久、跨不跨重启）。缺 ④ 必须先问——不跨重启就不需要持久化，只需要冗余。
**交付物与完成标准**: 一份「维持物台账」：每个维持物含载体（文件/注册表/任务）、触发方式、重启后是否存活、被清理的风险点、验证方式与最近一次验证时间。完成标准是「C2 会话掉线后能在 5 分钟内通过另一条路径重建」这条判据被实际验证过一次。

1. **判「要冗余还是要持久化」**
   - 做什么：写下 objective 的时长与是否跨重启。跨重启 → 需要持久化；只在本次行动内 → 只需要冗余（一条备用通道）。
   - 完成标准：能回答「重启后我还要不要能进」。
   - 判停：若不跨重启，跳过第 4 步，只做第 2–3 步。

2. **先落「死」的落点**
   - 做什么：入口是 web 应用 → 在**可写且会被解析**的目录写加密 webshell（避免放上传缓存等会被清理的临时目录）；入口是远程执行 → 留一个可重触发的执行原语（如一个可调用的脚本/任务）。
   - 完成标准：落点能被独立访问/触发，且不依赖当前会话。
   - 判停：若目录不可写或不被解析，换目录；找不到可写目录时不要强行落地，先只做步骤 3 的会话冗余。

3. **用落点反向建高质量会话**
   - 做什么：从落点弹一个 C2 会话；此后所有工具投递、凭据抓取都从这个会话做，落点只在会话丢失时启用。
   - 完成标准：会话稳定，且落点仍独立可用（没有被会话行为影响）。
   - 判停：若落点与 C2 共用同一域名/端口，等于没有冗余——换独立通道。

4. **选持久化载体（优先复用系统机制）**
   - 做什么：按「检测成熟度」排序选择：复用系统周期任务（如 CompatTelRunner 的 TelemetryController 子键）> WMI 事件订阅 > COM 劫持 > 服务 > 计划任务 > 启动项（Run 键/启动目录，规则最成熟）。
   - 完成标准：选定载体并写下「它绕开了哪一类检测、又暴露在哪一类检测下」。
   - 判停：若目标 EDR 对注册表写入有完整性监控（常见于对 `AppCompatFlags` 的监控），该路径不可用，换下一档。

5. **处理进程生命周期（关键）**
   - 做什么：判断载荷是否需要长连接。需要 → 让载荷注入其它进程，或让维持点只负责「启动一个短命令」由短命令再去建立会话；不需要 → 可直接执行短命令。
   - 完成标准：明确了「任务进程结束后载荷还在不在」。
   - 判停：若载荷是直接起的 C2 长连接，而触发方式是周期任务，必然一触发就断——回第 4 步换设计。

6. **立即验证，不等周期**
   - 做什么：手动触发（`schtasks /run /tn "..."` 或直接调用对应接口），观察是否执行、会话是否上线；记录触发时间。
   - 完成标准：至少一次成功触发，且有证据（会话 ID、进程、日志）。
   - 判停：若手动触发不执行，先查运行模式条件（系统版本、`CommercialDataOptIn`、电源状态、`RunsBlocked` 计数）——新版 CompatTelRunner 有这些前置检查。

7. **做一次「重建演练」**
   - 做什么：主动断掉 C2 会话（或等它自然掉），只用落点重建一次；记录耗时。
   - 完成标准：重建成功且耗时在可接受范围（目标：5 分钟内）。
   - 判停：若重建失败，说明冗余是假的——回到第 2 步重新落点，不要假设「下次会好」。

8. **清理与台账更新**
   - 做什么：任务结束前按台账逐个移除维持物（删注册表子键、删 webshell、删任务），并确认移除后目标上没有残留的可触发路径。
   - 完成标准：台账每一项都有「已移除 / 保留（理由）」状态。
   - 判停：若移除动作本身产生显著事件（删除服务 7040），记录该权衡，由 `evasion-and-opsec` 判断是否值得清。

## B — 边界 (Boundary) ★

### 不要用的情况
- 行动只持续几小时且不跨重启：持久化是纯增噪声，只需要一条备用通道。
- 目标有应用白名单（AppLocker/WDAC）+ 注册表完整性监控：系统机制复用类路径的成功率大幅下降。
- Web 目录由 CI/CD 自动同步（每次发布覆盖）：webshell 会在下次发布时被清掉，属「假冗余」。
- 目标对 `AppCompatFlags` 有专门监控：CompatTelRunner 路径已被公开多年，主流 EDR 已有针对性规则。

### 已知失败模式
- **只留内存会话**：目标重启或 C2 被封即永久失去入口（09 的原始教训）。
- **webshell 放在会被清理的临时目录**：上传缓存下次清理即失效。
- **任务进程结束后子进程跟着结束**：046 原文明确「如果是任务进程结束后，我们的子项也会跟着结束进程」，直接把 C2 长连接挂在周期任务上会一触发就断。
- **忽略新版 CompatTelRunner 的运行模式检查**：系统版本、`CommercialDataOptIn`、电源/电池状态、`RunsBlocked` 计数任一不满足就不执行命令。
- **冗余与主通道共用同一域名/端口**：主通道被封时冗余一起失效。
- **留太多后门**：每个维持物都是基线差异，五个后门等于五倍暴露面。
- **不做重建演练**：以为有冗余，真掉线时才发现落点早已被清理。
- **不清理**：残留的注册表子键与 webshell 是最直接的溯源线索。

### 作者与时代的局限
- 案例集中在 Windows 7/2008R2/2016/10，CompatTelRunner 的注册表结构在新版本（Win11）中仍有变化，字段与运行模式检查需要现场复核。
- 未讨论 Linux 侧持久化（cron、systemd unit、SSH authorized_keys、PAM），而多份案例表明 Linux 主机常是凭据链的关键节点。
- 未讨论「持久化被 EDR 主动狩猎」的现状：注册表遥测路径、WMI 事件订阅、COM 劫持都已是公开狩猎项，书中「可以逃避很多检测」的判断需要按当前检测能力重估。
- 未讨论持久化对「红队演练结论」的影响：留后门会改变蓝队的可见面，可能让「未被发现」的结论失真。

### 容易混淆的方法
- **冗余 vs 持久化**：冗余解决「这次会话掉了怎么回来」，持久化解决「重启后怎么回来」。前者是载体备份，后者是自启动机制。
- **复用系统任务 vs 新建计划任务**：前者绕开「按新建任务建模」的检测，但受系统任务自身逻辑约束（运行模式、进程生命周期）；后者可控性高但检测规则成熟。
- **端点持久化 vs 凭据持久化**：票据/口令是「能认证」，重启后仍需重新获取；端点持久化是「能执行」。
- **webshell vs 内存马**：webshell 是文件（可被静态查杀、可被发布覆盖），内存马依附进程（重启即失）。两者失败方式不同。
