# 域内侦察与突破路径定位

## R — 原文 (Reading)

> 在攻陷一台机器后，不要一味的直接去抓取机器密码、去做一些扫描内网的操作，因为如果网内有 IDS 等安全设备，有可能会造成报警，丢失权限。

> — 《红蓝对抗之Windows内网渗透》· 信息收集（开篇）

> SPN 扫描通过请求特定 SPN 类型的服务主体名称来查找服务，与网络端口相比，SPN 扫描的主要特点是不需要通过连接网络中的每个 IP 地址来检查服务端口，因此不会因触发内网中的安全设备规则而产生大量的告警日志。

> — 《内网学习笔记合集-TeamsSix》· SPN 扫描

> 当有了上述信息后，就可以对发现到的域管或者登录着域管的机器进行攻击，只要能拿下这些机器，就可以有相应的权限去登录域控。

> — 《红蓝对抗之Windows内网渗透》· 1.6 会话收集

## I — 方法论骨架 (Interpretation)

这个能力解决的是「刚打进内网、只有一两台机器时，用什么顺序把『值不值得冒险』问清楚」。它的前提是一个不对称：**你只有一次告警预算**。抓 lsass、跑全端口扫描、跑全量 BloodHound 这三件事的告警价值最高，任何一件触发告警，可能就意味着行动终止；而 `net user /domain`、`setspn`、`netstat`、`tasklist` 这类系统自带命令产生的流量与正常域内管理行为同构。

所以顺序是：**先用零成本手段把结构问清楚，再决定为哪一步冒险**。

结构可以用四个问题钉住（域内定位四问）：
1. 我在不在域里（`ipconfig /all` 看 DNS 与域后缀、`net config workstation`）；
2. 主域/DC 是谁（`net time /domain` 返回的主机通常是主域或 DC 之一；`net view /domain`、`net group "Domain Controllers" /domain`）；
3. 域管是谁（`net group "domain admins" /domain`）；
4. 域里有哪些机器、哪些服务（`net group "domain computers" /domain` + SPN 查询）。

结构清楚后，找「下一个跳点」而不是「下一个漏洞」。两条零成本线索价值最高：

- **SPN（服务主体名称）**：服务要支持 Kerberos 必须在 AD 里注册 SPN，而 SPN 只是 LDAP 里的普通属性——任何域用户都能查。于是「资产台账」可以直接从目录服务读出来，不必逐台敲门。附带收益：SPN 注册在**域用户账户**下的条目就是 Kerberoastable 候选。
- **会话（谁登录在哪台）**：横向的瓶颈不是「我有什么权限」，而是「哪里有高权限凭据躺在内存里」。`NetSessionEnum`/`Invoke-UserHunter` 告诉你域管此刻登录在哪台主机——那台机器上就有可窃取的 token 或 lsass 凭据。攻它比一步步提权到域管快得多，因为它把「提权问题」换成了「就近窃取问题」。

当确实需要扫描时，把它从「扫网段」换成「验证假设」：已知有 ActiveMQ 就只打 61616，已知有 1433 就只连 1433，单次交互少、特征分散，失败也只损失一个假设。BloodHound 同理，要先在「信息完整度」和「被发现概率」之间显式选择：仅 LDAP 采集不碰主机但拿不到会话与本地管理员；默认全量采集等价于十分钟内全网可见。

最后一条判据：**侦察的目的不是把图画全，而是找到一条能推进 objective 的最短路径**。图再全，如果指向的是高噪声动作，也不该走。

## A1 — 应用示例 (Application Example)

### 示例 1: 从 Shiro 反序列化入口到定位域控
- **类型与来源**: 【亲历】163 酒仙桥六号部队《一次 Shiro 反序列化引起的域控沦陷》· 2.1.3–2.1.5
- **问题/输入**: 通过 Shiro 反序列化在一台 Web 服务器上取得命令执行，机器双网卡，不确定是否在域内。
- **方法论的使用**: 先 `ipconfig /all` 判断 DNS 指向与域后缀，发现第一台机器其实是工作组机器（不在域内），只能先收集本机信息；再借助这台机器的双网卡访问到内网第二台机器，`net view` 定位域控 IP，`net user administrator /domain` 验证当前身份在域内可解析，`net group "domain admins" /domain` 取域管名单。
- **结论**: 四问的答案是「不在域 → 转到能访问域的机器 → 主域 X → DC 一台 → 域管 3 个」，后续所有域内动作都建立在这四个事实上。
- **结果**: 原书交代最终拿到域控；过程中作者自评中途全段扫 MS17-010「动作其实有些大，对方如果有安全设备应该已经告警」，与「先用零成本手段」的原则相反。

### 示例 2: 用 setspn 代替端口扫描找服务
- **类型与来源**: 【亲历】《内网学习笔记合集-TeamsSix》· SPN 扫描；【例题】《渗透测试实战（第三版·红队版）》CSK 案例第 40 码线
- **问题/输入**: 域内普通用户权限，需要在不通扫全网段的前提下找到可攻击的服务。
- **方法论的使用**: 以普通域用户上下文执行 `setspn -T <domain> -Q */*`，得到「服务类型 + 主机 FQDN + 端口」，按服务类型分类（MSSQL / HTTP / TERMSRV / WSMAN / DNS 各自对应后续攻击面），并把「SPN 注册在域用户账户下」的条目单独列出作为 Kerberoasting 目标。
- **结论**: 服务台账可以从目录服务直接读，不必逐台敲门；SPN 查询本身就是 Kerberos 票据行为的一部分，与正常域内查询同构。
- **结果**: TeamsSix 用该命令枚举出 DC 上的 DNS 服务与 MSSQL；CSK 案例用同一手法发现 `csk-github` 的 HTTP 服务。两次都没有触发扫描告警。

### 示例 3: 会话快照把「提权问题」换成「就近窃取」
- **类型与来源**: 【转述】《红蓝对抗之Windows内网渗透》· 1.6 会话收集（综合 PowerView / psloggedon / netview 三种工具取舍）
- **问题/输入**: 已有普通域用户权限，目标是不经过本地提权直接拿到域管上下文。
- **方法论的使用**: 先 `net group "domain admins" /domain` 取名单，再用 `Get-NetSession`/`Invoke-UserHunter` 查各主机登录会话，筛出「域管当前在线」的主机（会话是瞬时快照，下线即失效），在那台机器上找域管进程窃取 token 或抓 lsass。
- **结论**: 下一跳由「高权限凭据此刻在哪」决定，不由「我当前权限能到哪」决定。
- **结果**: 原书未给出单一完整战例，只给出工具取舍：`Invoke-StealthUserHunter` 隐蔽性相对较高但「涉及的机器不一定全面」。这条取舍本身就是本卡的核心对价。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 刚拿到第一台内网主机（webshell / 反弹 shell），不知道下一步该收集什么、按什么顺序做。
2. 需要在不触发 NIDS/HIDS 的前提下摸清域结构（域、DC、域管、机器清单）。
3. 需要找「下一个跳点」：哪台机器值得打、为什么值得打。
4. 手上有域用户权限，想判断能不能直接走到域控，还是必须绕道。
5. 决定要不要跑 BloodHound / 端口扫描，需要评估这次动作的告警代价。

### 语言信号（出现这些就该激活）
- 中文：「进了内网第一步做什么」「刚拿到 shell 先干嘛」「怎么判断在不在域里」「找域控 IP」「怎么找域管在哪台机器」「不扫描怎么找内网服务」「内网一扫就掉线」「BloodHound 会不会被发现」
- English: "what to do after getting a shell", "enumerate domain controllers", "who are domain admins", "find where domain admins are logged on", "enumerate services without scanning", "SharpHound detection", "quiet internal scanning"

### 与相邻能力的区分
- 与 `external-recon-pretext` 的区别：那张卡面向组织与人的公开情报，产出角色与接近路径；本卡面向已控主机所在的域结构，产出服务清单、可达路径与跳点排序。
- 与 `credential-extraction` 的区别：本卡只回答「去哪儿取、值不值得去」，不回答「怎么取出来」；取 lsass/DPAPI/DCSync 的具体手法在那张卡。
- 与 `lateral-execution-channels` 的区别：本卡产出「打哪台」，那张卡产出「用什么协议打」。

## E — 可执行步骤 (Execution)

**必需输入**: ①一个可执行命令的据点（shell/webshell/远程执行任一）；②当前身份与权限级别；③objective 的一句话（拿数据 / 拿域控 / 测检测能力）；④已知的出口与网段信息（没有就先做第 1 步）。缺 ③ 必须先问。
**交付物与完成标准**: 一份「域结构卡 + 跳点排序表」：结构卡含是否入域、域名、DC 列表、域管名单、服务台账（SPN 结果）；跳点表每行含主机、可达证据、其上高价值凭据、预计告警代价、是否推进 objective。完成标准是能直接回答「下一台打哪台、为什么、代价多大」。

1. **建立基线（不动手，只观察）**
   - 做什么：`whoami /all`、`systeminfo`、`ipconfig /all`、`route print`、`netstat -ano`、`tasklist`、`net share`；看是否装了 EDR/杀软（进程名、驱动、服务）。
   - 完成标准：知道当前权限、补丁级别、网卡与路由（有几张网卡、能到哪些网段）、本机是否装了终端防护。
   - 判停：若发现 EDR 且当前只有普通用户权限，先不要跑任何凭据抓取，跳到第 2 步走纯只读路线。

2. **判「在不在域」（四问之一）**
   - 做什么：`ipconfig /all` 看 DNS 是否指向域内 DNS、是否有域后缀；`net config workstation` 看当前登录域；`net time /domain` 看能否返回时间服务器。
   - 完成标准：得到「在域 / 不在域」的确定结论，以及域名。
   - 判停：若不在域，本卡主体流程不成立，改走「工作组机器 → 找能访问域的机器」路径（找配置文件、共享、历史连接），拿到域内据点后再回第 2 步。

3. **定位 DC 与域管（四问之三、四）**
   - 做什么：`net view /domain`、`net group "Domain Controllers" /domain`、`net group "domain admins" /domain`、`net user administrator /domain`。
   - 完成标准：DC 的 IP/主机名列表 + 域管账号名单；确认当前身份能在域内正常解析。
   - 判停：若域命令全部返回空或报错，先检查 DNS 与 445/135/389 可达性，不要直接判定「没有权限」。

4. **读服务台账（SPN，零落地）**
   - 做什么：`setspn -T <domain> -Q */*`（或 Rubeus、GetUserSPNs.vbs）；按服务类型分类；把注册在**域用户账户**下的 SPN 单独列出。
   - 完成标准：得到「服务类型 + 主机 FQDN + 端口」清单；Kerberoastable 候选单列。
   - 判停：若需要枚举「未注册 SPN 的自研服务」，SPN 覆盖不到，转第 5 步定向探测。

5. **定向探测（只在有假设时做）**
   - 做什么：对每个候选服务只访问其对应端口与协议（已知有 1433 才连 1433），全程限并发、限速率；不做全网段端口矩阵。
   - 完成标准：拿到「可利用服务清单」，且入口主机没有掉线/告警迹象。
   - 判停：若发现入口主机出现异常（会话断、进程被杀、流量被限），立即停手并转 `evasion-and-opsec` 复盘暴露点。

6. **查会话，定跳点**
   - 做什么：`Get-NetSession` / `Invoke-UserHunter` / `netview` / `psloggedon` 查「域管登录在哪台」；优先选域管**当前在线**的主机；同时看这些主机上的服务（结合第 4 步台账）。
   - 完成标准：跳点表按「域管在线 + 服务可利用 + 告警代价低」排序，至少有一台进入候选。
   - 判停：若查询返回空，可能是低权限看不到管理员会话（「看不见」≠「不存在」），改用 `Invoke-StealthUserHunter` 或换更高权限据点；若高频轮询会被 NetSessionEnum 审计抓到，降低频率。

7. **决定是否动用高噪声手段（BloodHound / 扫描）**
   - 做什么：先明确要回答的问题——是「ACL/委派/组关系的权限路径」还是「当前会话与本地管理员」。前者用仅 LDAP 的采集方式；后者才需要连主机，并要限定 OU/网段、降并发、避业务高峰。
   - 完成标准：采集方式与问题匹配，且写下了「这次采集的暴露代价」。
   - 判停：若只做了 LDAP 采集，不得据此断言「没有到 DA 的路径」；若默认全量采集在成熟蓝队环境，视为高概率告警，需先获得组织内决策。

8. **回绑 objective，输出「下一跳」结论**
   - 做什么：把跳点表与 objective 对齐，只保留能推进目标的行；对每行写「打它能解锁哪一步」。
   - 完成标准：写不出「解锁哪一步」的行被删除；最终给出一条主路径 + 一条备选。
   - 判停：若所有跳点都需要高噪声动作，回到 `engagement-governance` 重估目标（可能 objective 本身选错了路径）。

## B — 边界 (Boundary) ★

### 不要用的情况
- 目标网段有全流量 NDR 且已建立基线：SPN/会话查询虽然单次低噪声，但「一台非管理主机在短时间内枚举全域会话」本身就是高置信异常，频率比手段更关键。
- 只有工作组机器、且没有任何域内可达路径：本卡的四问全部无法回答，硬跑域命令只会浪费入口。
- 目标是「取某个具体文件」而非「拿域控」：此时最短数据路径可能完全不需要域结构，直接找文件所在主机更快（见 `engagement-governance` 的成败指标）。
- 需要精确的权限关系图（谁能对谁写）时：net 系列命令给不出 ACL 边，必须用图查询类工具，本卡只能给骨架。

### 已知失败模式
- **上来就抓密码或全端口扫描**：《红蓝对抗之Windows内网渗透》开篇明写会触发 IDS 告警并丢失权限。作者在 Shiro 案例中自评全段扫 MS17-010「动作其实有些大」。
- **在工作组机器上跑域命令**：全部返回空或报错，容易被误读为「域内没有信息」。
- **把 `net time /domain` 返回的主机当成唯一 DC**：作者只把它当辅助判断（「主域一般用作时间服务器」）。
- **把会话空结果当成「域管不在线」**：低权限查不到管理员会话是常态，这是可见性问题。
- **用会话快照做长期结论**：会话是瞬时状态，域管下线后结果即失效；基于旧快照排的跳点表会在执行时全部落空。
- **只查 LDAP 就断言「没有到 DA 的路径」**：仅 LDAP 采集拿不到会话与 localadmin，结论会系统性偏乐观。
- **默认全量 BloodHound**：中型企业不到 10 分钟跑完，也意味着 10 分钟内全网可见；采集器本身也可能被杀。
- **SPN 覆盖误判**：只看得到「注册了 SPN 的服务」，自研未注册服务看不到；内置账户（LocalSystem/NetworkService）自动注册的 SPN 不能用于 Kerberoasting。

### 作者与时代的局限
- 案例环境集中在 Windows Server 2008R2/2012R2/2016 + 传统 AD，未覆盖 Azure AD / 混合加入（Hybrid Azure AD Join）场景。混合环境下 `net view /domain` 类命令大量失效，侦察要转到 AAD Connect、Intune、Graph API 面。
- `net view`、`net group` 依赖 NTLM/NetBIOS 与 445/139 可达；在强制 SMB 签名、禁用 NTLM、开启 SMB 加密的现代环境里，其中一部分命令会直接失败，需要换 LDAP 查询（`Get-ADUser`/`ldapsearch`）。
- 会话枚举的审计面在近年被强化（NetSessionEnum 默认审计、EDR 对 `Invoke-UserHunter` 的签名识别），书中「低噪声」的判断需要按当前检测能力重新校准。
- 书中未讨论「侦察行为本身被 UEBA 关联」的问题：单条命令低噪声，但十分钟内跨 20 台主机的会话查询会形成模式。这一点要在 `evasion-and-opsec` 里补。

### 容易混淆的方法
- **SPN 查询 vs 端口扫描**：SPN 覆盖「有 SPN 的服务」，端口扫描覆盖「所有监听端口」，两者互补而非替代；SPN 查不到非 Kerberos 服务与自研服务。
- **会话收集 vs BloodHound**：会话收集是点查询、低噪声、实时；BH 是全局图、高噪声、快照。前者回答「现在打谁」，后者回答「结构上有没有路」。
- **域内定位 vs 域内提权**：四问只建立事实，不含任何提权动作；把「找到 DC」当成「拿下 DC」是最常见的进度误判。

### 授权与合规边界
> 待补充（用户自行填写）
