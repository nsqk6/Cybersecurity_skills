## I — 方法论骨架 (Interpretation)

这个能力回答："这个容器对外暴露了什么？对内又能碰到什么？"容器网络里最容易出事的不是"能不能连通"，而是"以为只开了内网的端口其实对公网开放""以为隔离开了其实能横扫兄弟容器"。它把网络暴露拆成三个方向分别判断：宿主↔外界、容器↔容器、容器↔宿主本地信任。

方向一，端口映射语法决定对外范围。`-p HostPort:ContainerPort` 若省略了绑定 IP，Docker 默认绑到 `0.0.0.0`（所有网卡，包括公网网卡），很多"只在内网用"的服务因此意外对公网开放。判据落在语法上：写没写 `IP:` 前缀决定"全网可达"还是"仅该地址可达"。要重点区分 `EXPOSE` 与 `-p`：`EXPOSE` 只声明意图、参与 `-P` 随机映射，本身不发布端口——看到 Dockerfile 里 `EXPOSE 22` 不能直接判为"已对外开放"。而 `-P` 随机映射（书中为 49000–49900）仍绑 0.0.0.0 且可被扫描发现，"端口不固定"不是安全理由。

方向二，容器间默认互通需要主动收紧。默认所有容器接在同一 `docker0` 网桥且 iptables FORWARD 放行，任一容器被拿下即可横向打所有兄弟容器（数据库、内部 API）。书中方案是 `--icc=false` 把默认策略改为 DROP，再用 `--link` 为成对容器写定向 ACCEPT，把横向面收敛成显式白名单；白名单粒度还受 `EXPOSE` 约束——只有声明过的端口才能被访问。但这个方案有强烈的时代局限：书中自己指出"引入 docker network 后基本不用了"，现代应改用自定义网络的成员关系或 NetworkPolicy 做隔离。

方向三，`--net=host` 放弃网络命名空间，继承宿主全部本地信任关系。网络命名空间是容器隔离里最容易被"为图方便"放弃的一层。放弃后：端口空间与宿主合并（可抢绑 80/22）、可直连仅监听 127.0.0.1 的管理服务（D-bus、本地 agent、metadata 代理）、可触达宿主网络栈配置。判据不是"能不能通网"，而是"是否把宿主的所有本地信任关系一并继承给容器"。若同时叠加 `--privileged`，书中明确"容器会被允许直接配置主机的网络堆栈"，命中即判定可篡改宿主网络。

三个方向要综合看：一个容器可能"对外端口收敛得很好"，但同时开了 host 网络、能连宿主本地 metadata 服务。只有把三个方向都列清楚，才算完成暴露面盘点。

## A1 — 应用示例 (Application Example)

### 示例 1: 数据库容器被公网扫描到
- **类型与来源**: 【转述】《Docker技术入门与实战_第3版》第 7 章（`docker ps` 输出 `0.0.0.0:80->80/tcp` 及 db 容器不用 -p/-P 的示例）+【合成演练】排障场景
- **问题/输入**: 某团队说"数据库容器只给内网应用用"，但公网扫描发现其端口开放。
- **方法论的使用**:
  1. 查实际映射：`docker ps` 的 PORTS 列显示 `0.0.0.0:3306->3306/tcp` → 前缀 0.0.0.0，绑到了所有网卡。
  2. 改为 `-p 127.0.0.1:3306:3306`，或按书中示例让 db 容器完全不加 `-p`/`-P`，容器间通过 `--link`/自定义网络互访。
  3. 复核是否用了 `-P` 随机映射——即便端口随机仍绑 0.0.0.0 可被扫到，须去掉。
- **结论**: "省略 IP 前缀 = 绑全网"是意外暴露的根因，端口映射必须显式写绑定地址。
- **结果**: 原书给出 `docker ps` 的真实输出与"db 容器不暴露端口"的做法，未交代该演练结果；按 E 段输出暴露清单与收敛动作。

### 示例 2: 为连宿主服务加 host 网络后误入本地信任域
- **类型与来源**: 【转述】《docker_practice》第 9 章 --net=host 参数说明 +【合成演练】排障场景
- **问题/输入**: 容器内连不上宿主上只监听 127.0.0.1 的 agent，有人提议"加 --net=host 就行了"。
- **方法论的使用**: 确认 `NetworkMode: host` → 判定已放弃网络边界；枚举宿主仅绑 127.0.0.1 的服务（agent、D-bus、metadata 代理）→ 这些对该容器全部变为可达；检查是否叠加 privileged → 若有则可改宿主网络栈。另按书中提示，host 网络与"配置容器 DNS/主机名"参数同用会破坏宿主配置。
- **结论**: host 网络不是连通性补丁，而是信任域扩展；应改用宿主可达地址或显式放行，而非放弃网络边界。
- **结果**: 原书只给出参数原理，未交代该演练结果；按 E 段判停条件转"需评估信任域扩展"。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 想知道"这个容器端口对外吗""数据库容器怎么被扫到了"。
2. 容器连不上宿主服务，有人想用 `--net=host` 或 `--privileged` 解决，需要评估后果。
3. 要限制容器横向移动，问"容器之间默认能互访吗""--icc 是什么"。
4. 区分 `EXPOSE` 与 `-p`、解读 `docker ps` 的 PORTS 列。
5. 基于自定义网络/CNI 设计容器间隔离策略（需将书中的 `--link` 方案现代化）。

### 与相邻能力的区分
- 与 `container-privilege-surface-hardening` 的区别：host 网络只放开网络栈，`--privileged` 放开全部设备与能力；判断顺序先 privileged，再看 host 网络。
- 与 `docker-daemon-api-exposure` 的区别：本能力管容器的端口与横向，daemon 能力管"引擎自身从哪被控制"。
- 与 `container-isolation-boundary-assessment` 的区别：本能力只看网络方向暴露，后者做整体隔离与信任域评估。
- 与 `cloud-credential-and-storage-attack` 的区别：本卡管容器端口与容器间横向；那张卡里"SSRF 读 169.254 实例元数据"也用到 host 网络/本地可达性，但目标是拿云角色临时凭证，不是收敛容器端口——若容器开了 host 网络且能连 metadata 代理，应在两卡间联动判定。

## E — 可执行步骤 (Execution)

**必需输入**: `docker ps` 的 PORTS 列 / `docker port` / 编排文件 `ports:`；容器 `NetworkMode`；宿主仅监听 127.0.0.1 的服务清单；容器间依赖关系。缺"哪些服务确需互访"必须先问（一开默认拒绝会全断）。
**交付物与完成标准**: 三方向暴露清单——对外映射（含绑定地址）、容器间可达矩阵、host 网络继承的本地信任；每项给出收敛动作。完工标准是意外暴露清零、横向面为显式白名单。

1. **对外映射盘点（宿主↔外界）**
   - 做什么：取 `docker port` / PORTS 列，看前缀是 `0.0.0.0` 还是 `127.0.0.1`；区分 `EXPOSE`（声明）与 `-p`（发布）。
   - 完成标准：列出所有实际发布端口与绑定地址。
   - 判停：`0.0.0.0:PORT->` 且为数据库/管理面/内部 API → 判意外暴露，改 `-p 127.0.0.1:PORT:PORT`；不需宿主暴露的服务去掉 `-p`/`-P`。

2. **容器间横向盘点（容器↔容器）**
   - 做什么：梳理依赖；单机 bridge 场景可写 `DOCKER_OPTS=--icc=false`（保留 `--iptables=true`）并重启 daemon，`iptables -nL` 的 FORWARD 链应出现 DROP；为成对容器加 `--link` 生成定向 ACCEPT；核对被访问容器 `EXPOSE` 集合即允许集合。
   - 完成标准：默认拒绝、互访为显式白名单。
   - 判停：自定义网络/K8s 环境不要照抄 `--icc=false`——改用自定义网络成员关系或 NetworkPolicy，否则失效；只加 `--icc=false` 不加白名单会全断，须先理清依赖。

3. **host 网络与本地信任盘点（容器↔宿主本地）**
   - 做什么：确认 `NetworkMode: host` → 视为已放弃网络边界；枚举宿主仅绑 127.0.0.1 的管理面/agent/metadata 代理 → 全部视为对该容器可达；检查是否叠加 privileged。
   - 完成标准：列出 host 网络继承的全部本地信任关系。
   - 判停：叠加 privileged 判定可篡改宿主网络，转 `container-privilege-surface-hardening`；host 网络与 DNS/主机名参数同用时标注"会破坏宿主配置"，需复原。

4. **汇总与判停**
   - 做什么：合并三方向清单，确认没有"端口收敛但 host 网络敞开"的遗漏。
   - 完成标准：三方向逐项有结论，遗漏项登记。
   - 判停：host 网络容器且跑不可信镜像时，不得判定暴露面已收敛。

## B — 边界 (Boundary) ★

### 不要用的情况
- 评估 daemon 自身监听与主体授权时用 `docker-daemon-api-exposure`。
- 判断容器内 cap/挂载/privileged 时用 `container-privilege-surface-hardening`。
- 需要整机整体安全结论时用 `container-isolation-boundary-assessment`。

### 已知失败模式
- **只看 Dockerfile 的 EXPOSE 就判暴露**：EXPOSE 只是声明，不发布端口（第 7 章）。
- **用 `-P` 随机映射以为安全**：仍绑 0.0.0.0 且可被扫描发现。
- **host 网络当连通性补丁后不复原**（第 9 章警告）：与 DNS/主机名参数同用会破坏宿主配置。
- **只加 `--icc=false` 不加 `--link`**：业务全断后匆忙回滚；忘记 `--iptables=true` 等于没生效。
- **照抄 `--icc=false + --link` 到自定义网络时代**：书中已注明此法"基本不用"，须改用 NetworkPolicy/成员关系。

### 作者与时代的局限
- 书中网络方案基于 docker0 单机网桥；现代 Docker 自定义 bridge、overlay、CNI/K8s NetworkPolicy 已取代 `--icc=false + --link`，迁移时保留"默认拒绝 + 显式白名单"的思路而非照抄命令。
- 端口 49000–49900 的随机映射范围是当时版本行为，需以当前版本实测。
- `--net=host` 在 Linux 与 Docker Desktop 上的实现差异较大，判据需结合平台。

### 容易混淆的方法
- **对外 vs 对内**：`-p`/端口映射管宿主↔外界，`--icc`/`--link`/NetworkPolicy 管容器↔容器。
- **EXPOSE vs -p**：声明意图 vs 实际发布。
- **host 网络 vs privileged**：前者仅网络栈、后者全部设备与能力；先判 privileged。
