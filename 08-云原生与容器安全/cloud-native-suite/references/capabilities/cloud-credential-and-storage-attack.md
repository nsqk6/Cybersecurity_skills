## I — 方法论骨架 (Interpretation)

这个能力处理一个完整的云身份攻击面："拿到（或怀疑拿到）云凭据之后，怎么判断它值不值得打、能打到哪一步、为什么有时用不了，以及防守侧怎么把泄露影响锁死。"它把云攻防里最高频的 AK/SK 与对象存储问题收拢成一条链。

链的第一环是搜集。AK/SK 不是一个点，而是一组固定泄露面：APK 文件、Web 页面/JS、phpinfo、GitHub 关键词搜索、已 getshell 主机上的配置文件。做成清单逐项过，能把"拿到一个 WebShell"升级为"拿到云账号身份"。拿到后用行云管家/OpenAPI Explorer 导入验证有效性，并记录 AK 属于主账号还是 RAM 子账号。

第二环是判价值。AK 的利用价值取决于背后 IAM 策略的粒度，而不是 AK 本身：主账号 AK 等于全权限，IAM/RAM 子用户 AK 可能被限制到只能读某个桶。判据是"先判权限、再定打法"——用只读 API（Describe*/List*）探测边界，画出能访问的资源范围，再决定利用深度（读数据 / 建命令 / 重置密码）。见到 AK 就以为能接管 EC2，或遇到细粒度权限就误判"AK 没用"，都是错的。

第三环是选利用链。有两条主链：其一，云助手命令链——`DescribeRegions`/`DescribeInstances` 摸清资产 → `CreateCommand` 建 Base64 脚本（≤16KB）→ `InvokeCommand`/`RunCommand` 触发，把身份凭据直接转成实例上的代码执行；其二，SSRF + 元数据链——借业务 SSRF 读 169.254 元数据端点，先取 region/vpc-id，再从 `cam/security-credentials/{role-name}` 拿实例角色的临时凭证，把"一个 SSRF"升级为"实例绑定角色身份"。两条链的前提不同：前者要 ECS 写权限的 AK，后者要 SSRF 且元数据服务未强制 IMDSv2 token。

第四环是专门的对象存储判据。对象存储被攻破的入口可归为五类（主密钥 / SDK 代码 / 工具配置 / 前端直传 / 账号登录），把"桶配错"这个笼统说法拆成可逐条排查的清单。前端直传本身不安全与否，判据在凭据类型与权限：前端必须放临时密钥（STS）且最小权限；一旦前端是永久密钥或临时凭据权限配错，抓前端代码/流量就能拿到可用凭据。

还有一个独立的"事后诊断"分支：从小程序/APP 拿到的 AK/SK 若配了 STS，会带 Token 且有时效（默认 1800 秒），过期后自然读不到桶信息。判据是"AK/SK 之外有没有 Token + 拿不到桶信息"——命中即判 STS 过期，而不是密钥错误或权限不足，此时应转去抓 STS 接口本身（前端申请临时密钥的签发点）。

最后是防守侧止血。泄露不可避免，能控的是爆炸半径：停用主账号 AK 直接调用、改建 RAM 用户按业务最小分权；AK 移出代码、独立存储并定期轮换；查最后访问时间禁用僵尸 AK；操作日志投递 OSS/SLS 固证。仅"定期更新 AK"而不做最小权限，旧 AK 仍全权限——这是最常见的假止血。

整条链走完，产出的是"凭据清单 + 价值判定 + 可用利用链 + 存储可达性 + 止血动作"。

## A1 — 应用示例 (Application Example)

### 示例 1: WebShell 低权限 → AK → 云助手拿主机
- **类型与来源**: 【例题】《云安全攻防入门》第四章（原文"拥有 WebShell 低权限的情况下搜集阿里云 Access Key 利用" + CreateCommand/InvokeCommand 脚本示例）
- **问题/输入**: 已有一个低权限 WebShell，想扩大到主机控制。
- **方法论的使用**:
  1. 按泄露面清单逐项搜：APK、Web/JS、phpinfo、GitHub 关键词、主机配置文件 → 在配置文件中找到 AK/SK。
  2. 导入验证有效性，判定是主账号 AK（有 ECS 权限）。
  3. `DescribeRegions`/`DescribeInstances` 拿到实例 ID 列表。
  4. `CreateCommand` 建 Base64 脚本（≤16KB）→ `InvokeCommand`/`RunCommand` 触发，脚本在目标实例执行并回传结果。
- **结论**: AK 不只是"读数据"的凭据，云 API 自带在实例上执行运维命令的能力，是身份转代码执行的关键一跳。
- **结果**: 原书给出脚本示例与命令，未交代特定目标的处置结果；本卡不编造"拿到主机"的具体战果。

### 示例 2: 小程序 AK/SK 读不到 OSS——STS 过期诊断
- **类型与来源**: 【例题】《云安全攻防入门》第四章（原文提问"通过小程序或者 JS 获取的 AK/SK 却无法利用是怎么回事？"）
- **问题/输入**: 从小程序提取到 AK/SK，但读不到存储桶信息。
- **方法论的使用**:
  1. 观察凭据构成：是否同时有 stsToken、是否签入前端直传逻辑 → 判定 STS 模式。
  2. 尝试读桶 → 失败且无桶信息 → 符合"AK/SK 已过期（默认 1800 秒）"特征。
  3. 不判"AK 无效/权限小"而放弃，转去抓 STS 接口本身（前端申请临时密钥的端点），定位可重放的凭据签发点。
- **结论**: "读不到桶"可能是临时密钥过期而非密钥错误；判据是 Token + 读桶失败。
- **结果**: 原书给出诊断逻辑与例题，未交代抓 STS 接口后的具体结果；本卡不编造。

### 示例 3: SSRF 借实例角色拿临时凭证
- **类型与来源**: 【例题】《云安全攻防入门》第四章（原文给出腾讯云 metadata 端点路径清单）
- **问题/输入**: 目标业务存在 SSRF，想确认能否打到实例元数据。
- **方法论的使用**:
  1. 经 SSRF 访问 metadata 端点取版本与基础信息 → region / local-ipv4 / vpc-id。
  2. 枚举角色名（`cam/security-credentials` 路径）。
  3. 请求 `{role-name}` 临时凭证 → 拿到可用的临时 AK/SK/Token 访问云资源。
- **结论**: 与直接用泄露主 AK 不同，这条链借的是实例绑定的角色身份，Step 3 才是价值兑现点。
- **结果**: 原书给出端点清单，未交代具体目标结果；若绑定角色无敏感权限，临时凭证价值有限——按 E 段据实标注。

### 示例 4: RAM 最小权限止血
- **类型与来源**: 【转述】《云安全攻防入门》第四章 防御思路（原文"配置 RAM 用户……就算 AK 泄漏造成的影响也是有限"）
- **问题/输入**: 发生 AK 泄露，需要止血并防止再次扩大。
- **方法论的使用**:
  1. 停用主账号 AK 直接调用，改建 RAM 用户按业务分最小权限。
  2. AK 移出代码，改存独立文件/数据库并定期轮换。
  3. 查最后访问时间禁用闲置 AK，操作日志投递 OSS/SLS 固证。
- **结论**: 止血的重点是"缩小爆炸半径"，仅轮换而不分权的旧 AK 仍全权限。
- **结果**: 原书给出防御原则，未交代该场景的具体处置结果；按 E 段输出止血清单。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 找到 AK/SK 不知道下一步怎么做，或想知道"密钥一般藏在哪"。
2. 想知道"有 AK 怎么拿主机""AK 能执行服务器命令吗"，判断能否从身份跨到代码执行。
3. 拿到 AK 后读不到东西、或 AWS 场景"AK 权限很小怎么办"，需要判断 IAM 粒度是否值得继续。
4. 前端/小程序暴露了 AK，想判断是不是漏洞、直传凭据安不安全。
5. OSS/COS/S3 存储桶怎么打、凭据从哪来、桶 ACL 怎么判。
6. AK 泄露后要止血："怎么限制 AK 权限""least privilege for cloud keys"。
7. 存在 SSRF，想知道"169.254.169.254 怎么利用"、能不能拿到角色临时凭证。

### 语言信号（出现这些就该激活）
- 中文：「找到 AK 了接下来干嘛」「密钥一般藏在哪」「有 AK 怎么拿主机」「AK 能执行服务器命令吗」「AWS 的 AK 读不到东西」「这个 AK 权限很小怎么办」「AK 过期了」「前端拿的密钥读不到 OSS」「前端暴露了 AK 是不是漏洞」「OSS/COS 怎么打」「S3 bucket 攻击面」「AK 泄露了怎么止血」「SSRF 怎么打到云元数据」「169.254.169.254 怎么利用」
- English: "where to look for cloud credentials", "pivot from cloud key to instance", "IAM user key is it useful", "STS temporary credentials not working", "presigned URL / STS in frontend safe", "S3 bucket attack vectors", "least privilege for cloud keys", "SSRF to cloud metadata credentials"

### 与相邻能力的区分
- 与 `cloud-attack-surface-and-responsibility` 的区别：那张卡划分"打什么、算谁的"总范围，本卡处理凭据与对象存储的具体攻防；那张卡判停后路由到本卡。
- 与 `container-escape-path-assessment` 的区别：那张卡借 SSRF 读元数据属于"云身份"链（本卡）；若已进入容器并要逃逸宿主机，用那张卡。两者共享 SSRF 入口但目标不同。
- 与 `container-incident-forensics` 中"操作留痕"的区别：本卡把日志投递 OSS/SLS 作为止血固证动作，那是取证与可见性的专门能力。
- 与 `cloud-platform-lateral-movement` 的区别：本卡的横向靠云 API 凭据，那张卡的横向靠云平台节点配置文件里的硬编码凭据。

## E — 可执行步骤 (Execution)

**必需输入**: 一个落脚点（WebShell / 源码仓库访问权 / APK 样本 / 前端代码流量）或已获取的一对 AK/SK；目标云厂商（阿里/腾讯/AWS/华为，命名不同但相通）；是否已有 SSRF；云账号管理权限（防守侧）。缺"凭据来自哪里、是否带 Token"必须先问。
**交付物与完成标准**: 凭据清单（位置/类型/账号类型/权限边界）+ 可用利用链判定 + 对象存储可达性 + 止血动作清单。完工标准是每条凭据写明"有效/过期/受限"及对应打法或止血动作。

1. **按泄露面清单搜集凭据**
   - 做什么：在已控资产上逐项检索 APK、Web/JS、phpinfo、GitHub 关键词、配置文件。
   - 完成标准：每类位置都有明确检索动作与结论。
   - 判停：命中后用行云管家/OpenAPI Explorer 导入验证；记录主账号 AK 还是 RAM 子账号 AK；无命中则转其他攻击面，不在此步死磕。

2. **判凭据类型与价值**
   - 做什么：判永久/STS（有无 Token）；主账号/IAM 子用户；用只读 API（Describe*/List*）探权限边界。
   - 完成标准：画出可访问资源范围，给出"值得打/受限/过期"结论。
   - 判停：无 Token 且读桶失败 → 判 STS 过期，转第 4 步抓 STS 接口；受限 AK 不匹配高权限打法，按权限选深度；AWS 细粒度场景按最新文档复核。

3. **选并利用主链**
   - 做什么：云助手链——`DescribeInstances` → `CreateCommand`（Base64，≤16KB）→ `InvokeCommand`/`RunCommand`；元数据链——SSRF 读 metadata 基础信息 → 枚举角色名 → 取 `{role-name}` 临时凭证。
   - 完成标准：命中的链有明确执行路径与前提核对。
   - 判停：无 ECS 写权限的 RAM 子账号调 CreateCommand 会失败、脚本 >16KB 被拒——按失败模式排除，不硬试；元数据强制 IMDSv2 token 时该链不通。

4. **对象存储专项判定**
   - 做什么：按五类初始访问路径（主密钥/SDK/工具配置/前端直传/账号登录）逐项查；命中凭据验证桶读写权限；结合桶 ACL（私有/公有读私有写/公有读写）判最终可达性；前端直抓凭据判"永久 or 临时+最小权限"。
   - 完成标准：五类都有结论，桶是否可任意下载/写入有明确判定。
   - 判停：见前端有密钥就判漏洞是错的——按规范生成的临时最小权限密钥不算漏洞；反过来"有临时密钥"也不能直接判安全，须核权限配置。

5. **止血与防御（防守侧）**
   - 做什么：停用主账号 AK 直接调用、建 RAM 用户分最小权限；AK 移出代码、独立存储、定期轮换；查最后访问时间禁用闲置 AK；操作日志投递 OSS/SLS。
   - 完成标准：无硬编码 AK、无僵尸 AK、有可固证日志、泄露影响面收窄到授权资源。
   - 判停：仅轮换不做最小权限视为未止血；GitHub Token scan 等工具不能替代分权。

6. **汇总与路由**
   - 做什么：合并凭据清单、价值判定、利用链、存储可达性、止血动作。
   - 完成标准：每条凭据有明确处置，无"拿到就放着"的悬空项。
   - 判停：凭据类问题已闭环；涉及云平台节点横向的转 `cloud-platform-lateral-movement`；涉及操作留痕取证的转 `container-incident-forensics`。

## B — 边界 (Boundary) ★

### 不要用的情况
- 目标是传统 Web 漏洞（SQL 注入、文件上传）且不涉及云凭据时用对应 Web 能力，本卡只处理云身份与对象存储。
- 只是划分攻击面与责任（"算谁的"）时用 `cloud-attack-surface-and-responsibility`，本卡在范围明确后动手。
- 已取得云平台节点 root、要跨网段收集配置做横向时用 `cloud-platform-lateral-movement`。
- 需要还原云上操作链、判取证可见性时用 `container-incident-forensics`。

### 已知失败模式
- **只搜代码仓库不搜 APK/前端 JS**（4章）：漏掉最常见的密钥泄露面。
- **拿到 AK 就当主账号用**：忽略它可能是受限 RAM/IAM 子用户，遇到细粒度权限就误判"AK 没用"。
- **无 ECS 权限的 RAM 子账号调 CreateCommand**：必然失败；脚本 >16KB 被拒。
- **只拿内网 IP/vpc-id 就停手**：漏掉角色临时凭证这一步，SSRF 价值只兑现了一半。
- **误判 STS 过期为"AK 无效/权限小"而放弃**：实际是临时密钥过期，应转抓 STS 签发点；只拿 AK/SK 忘了配套 stsToken。
- **只盯桶 ACL 忽略凭据侧泄露**（4章）：五类入口缺一类就可能漏查；各厂商命名不同（OSS/COS/OBS/S3）导致漏查。
- **见前端有密钥就判漏洞 / 见有临时密钥就判安全**：两个方向都要按"临时 + 最小权限"判据复核。
- **仅"定期更新 AK"而不做最小权限**（4章防御思路）：旧 AK 仍全权限，属假止血。

### 作者与时代的局限
- 第四章以阿里云为主、AWS 场景原文自述"海外云场景经验不足需另查文档"；AWS IAM 细粒度权限的具体打法须查最新文档。
- STS 默认 1800 秒是文中取值，实际可到 2h/36h 不等；凭据工具（行云管家、OpenAPI Explorer）形态随云控制台迭代变化。
- 云 API 名称与路径（DescribeInstances/CreateCommand/cam/security-credentials）以各厂商当前文档为准，文中示例反映当时版本。
- 对象存储厂商命名（OSS/COS/OBS/S3）不同但机制相通，本卡按机制归纳，具体命令需按厂商调整。

### 容易混淆的方法
- **搜集 vs 利用**：CU-2-03 是搜集路径清单，CU-2-04/06 是两条利用链；先列清单再选链。
- **永久 vs 临时密钥**：前端直传判据的核心是凭据类型 + 权限，不是"有没有直传功能"。
- **STS 事后诊断 vs 配置判据**：CU-2-07 是"用不了之后为什么"，CU-2-10 是"配置是否安全"，两者都涉及 STS 但方向相反。
- **凭据侧 vs 桶 ACL**：对象存储可达性由"凭据有没有权限"和"桶 ACL 放不放"共同决定，只查一边会漏。
- **攻击 vs 防御**：CU-2-08 的 RAM 最小权限是防守判据，与搜集/利用链立场相反但共用同一套权限概念。
