# 云平台后渗透横向与配置收集

## R — 原文 (Reading)

> 这里有两种场景：· 获取到 OpenStack 控制台权限；· OpenStack 下的虚拟主机权限；……攻击策略：Ø 网络暴露：管理控制台，弱口令、高危漏洞 Ø 网络暴露：API 接口，未授权访问、越权、高危漏洞 Ø 网络暴露：三方组件引入的接口 Ø 网络暴露：容器服务 Ø 网络暴露：运营/运维服务。

## I — 方法论骨架 (Interpretation)

这个能力回答云平台场景里后渗透阶段的问题："拿到一台云主机/一个控制台权限之后，怎么把战果从单点放大到整朵云？"它分两段：先确定起点并选对初始突破路径，再靠系统性"翻配置"把单点变成全局。

第一段是起点判定与五类暴露面。先把当前位置归为"有 OpenStack 控制台权限"还是"只有 OpenStack 下的虚拟主机权限"，两条链的后续动作完全不同——这是整个打法的分叉点。然后按五类网络暴露面逐项排查：管理控制台（弱口令、高危漏洞）、API 接口（未授权访问、越权、高危漏洞）、三方组件引入的接口、容器服务、运营/运维服务。判据是"当前站在哪一层"——VPC 下的虚拟主机通常与管理网段做了逻辑隔离，从内网端口（keystone 5000 等）找管理网段是常规尝试路径，但不能假设一定能到达。

第二段是配置收集放大。单点 getshell 后如何放大到整朵云，靠的不是继续打漏洞，而是"翻配置"——计划任务、历史命令、环境变量、运维脚本、认证配置文件（keystone.conf/nova.conf 等）里往往硬编码了跨网段的节点凭据。拿到一批节点账号后可以再翻数据库配置，取得全部 SSO 账号，进而定位监控系统扩大控制面。政务云案例中 294 个节点凭据就藏在计划任务脚本里——只翻 `/etc` 而忽略计划任务，就会错失整条放大链。

两段的交付物不同：第一段产出"起点 + 可达暴露面清单"，第二段产出"节点凭据清单 + 影响范围评估"。把它们串起来，才形成"一个 Web 漏洞 → 全省政务云"的完整放大机制。

要特别强调一个边界：原文明确指出"一般情况是虚拟主机无法到达管理网段，已做逻辑隔离"。因此"只有虚机权限"这一起点下，找管理网段的动作要先验证可达性，不能把"扫描到端口"等同于"能打通管理网"。

## A1 — 应用示例 (Application Example)

### 示例 1: 某省政务云的配置横向链
- **类型与来源**: 【转述】《云安全攻防入门》第五章控制台权限场景（原文完整链路）
- **问题/输入**: 从搜索引擎入手，目标是某省政务外网上的政务云平台，需要评估单点到全云的放大路径。
- **方法论的使用**:
  1. 起点判定：从外网进入政务外网、找到政务云平台（3A 认证、基于 OpenStack 二次开发），属平台侧目标。
  2. 初始突破：命中 Shiro 反序列化漏洞 → 获取 OpenStack 云平台系统 root 权限。
  3. 网络可达性：网卡信息显示可跨 172/10/192 网段。
  4. 配置收集放大：翻系统任务计划，发现运维脚本，脚本中存储云平台节点所有账号密码 → 获取 294 个云节点服务器权限。
  5. 继续扩大：翻数据库配置取全量账号 → 519 个 SSO 账号 → 定位监控系统 → 1400+ 云主机。
- **结论**: 单点突破后的放大靠"翻配置"，计划任务脚本是关键信息源，远超只翻 `/etc` 的收益。
- **结果**: 原书交代了 294 节点、519 SSO 账号、1400+ 云主机的规模；本卡不扩展为任何未交代的后续动作。

### 示例 2: 只有虚机权限时寻找管理网的判停
- **类型与来源**: 【合成演练】（依据《云安全攻防入门》第五章"虚拟主机权限"场景与原文"虚机通常无法到达管理网段"的警告，按本卡 E 段规则推演，不对应真实目标）
- **问题/输入**: 已拿到 OpenStack 下一台虚拟机的权限，想找管理网段。
- **方法论的使用**:
  1. 起点判定：只有虚拟主机权限，不是控制台权限 → 走虚机链。
  2. 在内网尝试找 keystone 5000 及各组件端口，定位管理网入口。
  3. 先验证可达性：原文明确"一般情况虚拟主机无法到达管理网段，已做逻辑隔离"——若实测不可达，如实标注该路径不成立，不假设能打通。
  4. 转而盘点虚机自身能触达的五类暴露面，按实际可达面选路径。
- **结论**: 找管理网段是"常规尝试"而非"必然可达"；把扫描到端口当成打通管理网是误判。
- **结果**: 合成演练不产出真实突破结果；按 E 段判停条件，不可达即排除该路径，不编造"拿到控制权"。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 要打 OpenStack 或自建云平台，问"OpenStack 怎么打""有哪几种初始场景"。
2. 拿下一台 OpenStack 虚机，想知道"怎么找控制端""能不能到管理网段"。
3. 拿到云平台某节点 root/WebShell 后，想知道"怎么扩大战果""云环境后渗透怎么横向"。
4. 评估一次云平台入侵的影响范围（多少节点、多少账号、多少主机）。
5. 复盘时想确认"294 个节点凭据为什么没被发现"——即配置收集是否漏了计划任务。

### 与相邻能力的区分
- 与 `cloud-attack-surface-and-responsibility` 的区别：那张卡是云子域总入口（攻击面分类 + 责任边界），本卡是平台侧拿下一台后的横向放大。
- 与 `cloud-credential-and-storage-attack` 的区别：那张卡的横向靠**云 API 凭据**（AK/SK、角色临时凭证），本卡的横向靠**节点配置文件里的硬编码凭据**（运维脚本、keystone.conf）。两者都叫"横向"但凭据来源与手法不同。
- 与 `container-escape-path-assessment` 的区别：那张卡跨的是容器→宿主机边界，本卡跨的是云节点→其他云节点的网段边界。

## E — 可执行步骤 (Execution)

**必需输入**: 已在 OpenStack 环境内有立足点（虚机权限或控制台权限），或能外网访问控制台；能读取目标节点的文件系统、计划任务、历史命令、环境变量。缺"当前起点是控制台权限还是虚机权限"必须先问——这条决定后续链路。
**交付物与完成标准**: 起点判定 + 可达暴露面清单 + 节点凭据清单 + 影响范围评估（节点数/账号数/主机数）。完工标准是"一个漏洞能放大到什么程度"有量化结论，且每条凭据都注明来源文件。

1. **判定起点**
   - 做什么：确认当前是"OpenStack 控制台权限"还是"OpenStack 下虚拟主机权限"。
   - 完成标准：起点明确，选定对应链路。
   - 判停：控制台权限走第 3 步五类暴露面；虚机权限先走第 2 步找管理网。

2. **虚机权限：找管理网并验证可达**
   - 做什么：在内网找 keystone 5000 及各组件端口定位管理网段。
   - 完成标准：管理网入口是否可达有明确结论。
   - 判停：原文警告"一般情况虚拟主机无法到达管理网段，已做逻辑隔离"——实测不可达即排除该路径，不假设打通；可达再进入五类面排查。

3. **五类网络暴露面排查**
   - 做什么：逐项检查管理控制台（弱口令/高危漏洞）、API 接口（未授权/越权/漏洞）、三方组件接口、容器服务、运营运维服务。
   - 完成标准：五类都有结论，拿到或提升控制权。
   - 判停：不要只扫控制台忽略 API 未授权访问；每类命中都要记录具体入口与前提。

4. **配置收集与凭据提取**
   - 做什么：系统性收集计划任务、历史命令、环境变量、运维脚本、认证配置文件（keystone.conf/nova.conf 等），提取跨网段节点账号密码。
   - 完成标准：列出所有信息源与提取到的凭据清单，每条注明来源文件。
   - 判停：拿到单点就停是常见失败；只翻 `/etc` 忽略计划任务会漏掉关键凭据（政务云案例中 294 节点凭据就在计划任务脚本里）。

5. **扩大控制面与影响评估**
   - 做什么：用节点凭据登数据库取全量账号，定位监控系统，统计节点数/SSO 账号数/云主机数。
   - 完成标准：输出影响范围评估，量化到具体数量级。
   - 判停：凭据仅可登单节点时不得夸大影响面；涉及云 API 凭据的横向转 `cloud-credential-and-storage-attack`。

6. **汇总与路由**
   - 做什么：合并起点、暴露面、凭据、影响范围成一张横向链图。
   - 完成标准：每个放大步骤都有依据文件与可达性支撑。
   - 判停：链上任一环节只有假设无实证时，不得判定"已接管整朵云"。

## B — 边界 (Boundary) ★

### 不要用的情况
- 目标是租户侧业务资产、不涉及云平台时用 Web/凭据类能力，本卡针对 OpenStack 云平台底座。
- 只有 AK/SK、没有节点 shell 时用 `cloud-credential-and-storage-attack`，本卡依赖已落地的节点文件系统访问权。
- 要跨容器→宿主机边界时用 `container-escape-path-assessment`，本卡跨的是云节点间网段。
- 需要还原云上操作链与取证可见性时用 `container-incident-forensics`。

### 已知失败模式
- **假设虚机能直达管理网段**：原文明确"一般情况虚拟主机无法到达管理网段，已做逻辑隔离"——把扫描到端口当成打通是误判。
- **拿到单点就停，不做配置收集**：错失整条放大链。
- **只翻 `/etc` 忽略计划任务里的运维脚本**：政务云案例 294 个节点凭据就藏在计划任务脚本中。
- **只扫控制台忽略 API 未授权访问**：五类暴露面缺一类就可能漏掉突破口。
- **用假设代替实证**：没有可达性/凭据来源支撑就宣称"接管整朵云"。

### 作者与时代的局限
- 政务云案例来自特定环境（3A 认证、OpenStack 二次开发、Shiro 反序列化），是真实规模记录而非通用打法；不同云平台架构与隔离策略差异大。
- OpenStack 版本与组件端口（keystone 5000 等）随版本演进，须按目标实际版本核对。
- 案例中 Shiro 反序列化是当时的漏洞入口；现代平台可能已修复或改用其他认证，不能照搬入口。
- 原文以国内政务云/自建 OpenStack 为主，公有云托管场景的横向机制不同。

### 容易混淆的方法
- **初始突破 vs 后渗透横向**：CU-2-14 解决"从哪进去"（两场景五暴露），CU-2-15 解决"进去后怎么放大"（翻配置）。
- **控制台权限 vs 虚机权限**：两条链的起点不同，找管理网的可达性假设也不同。
- **配置凭据 vs 云 API 凭据**：本卡翻的是节点文件里的硬编码账号密码，`cloud-credential-and-storage-attack` 用的是 AK/SK 与角色临时凭证，判据与工具都不同。
- **翻配置 vs 继续打漏洞**：放大阶段的核心是信息收集，不是继续利用新漏洞。
