# 容器与云取证、日志可见性盲区

## I — 方法论骨架 (Interpretation)

这个能力回答："事件发生了，证据还在吗？看得见什么？记录能不能用来还原？"它把三件事收在一张卡里——容器现场固化、云上取证可见性、日志与监控盲区——因为它们共享同一个判据：**证据在哪一层、谁控制那一层、记录是不是可用**。

第一件是容器现场固化。容器文件系统是易失的，一旦 `docker rm` 存储层随之销毁，而攻击者常清理痕迹甚至销毁容器。commit 把当前可写层连同所有改动冻结成不可变证据副本，之后可离线挂载、逐层比对，不必在活体上反复操作破坏证据。反直觉点：在 `image-build-supply-chain` 里 commit 被明令禁止用于交付（黑箱、不可复现），但在取证场景这些"缺点"变成优点——它恰好能冻结攻击者的落地文件与篡改痕迹。判据是用途：只用于取证留证，绝不用于交付。时序必须严格：先隔离不断电不删除 → 立刻 commit → 另存元数据 → 离线分析 → 从可信基线重建且不复用。

第二件是云上取证可见性。"云上每次扫描和操作都会被记录在云日志中"决定了两件事：攻击方要考虑行动被记录（操作日志投递 OSS/SLS 可固证），防守方要开审计才能追溯。可见性按服务模型切：IaaS 下客户能查自己 VM 内部，但网络流量、内存快照、磁盘镜像这些标准取证动作都要 CSP 支持；PaaS/SaaS 越往上越依赖 CSP 提供的日志与分析。判据是"证据在哪一层、谁控制那一层"——别以为"IaaS 自己有 root 就能查一切"，网络层与 hypervisor 层数据拿不到；需要 CSP 支持的应在 SLA 里预先约定数据内容与格式，而不是等事件发生才发现关键数据不提供。

第三件是日志与监控盲区。日志"有"不等于"可用"，三个信号要核：①时钟同步与时区标记（否则跨源时间戳无法对齐，时区缺失导致误读）；②新增云资源的日志是否自动接入数据流（否则动态资源出现盲区——请求被记录但由哪个实例动态提供没记下来，根因无法定位）；③日志是否防篡改（只读存储、日志服务器与应用服务器分离）。虚拟化还有两个特有盲区：同一物理机上 VM 间可能走硬件背板通信，绕过网络层安全设备，必须用 Hypervisor API 内嵌虚拟设备补监控；VM 关机期间威胁在演化，冷启动时镜像可能已过时，需在启动路径前置虚拟补丁/NAC 隔离，更新规则库并扫描通过后再放行。

三件事合起来，交付物是"证据副本 + 可见性诊断 + 盲区处置"：既保住已有证据，也标出"查不到/看不准"的地方并给出补偿手段。

## A1 — 应用示例 (Application Example)

### 示例 1: 书中点出的"保存现场"用途
- **类型与来源**: 【转述】《docker_practice》第 5 章（原文一句话："被入侵后保存现场"）
- **问题/输入**: 书中仅指出 commit 有"保存现场"这一特殊用途，未给具体事件。
- **方法论的使用**: 按机制推演——被入侵容器可写层含攻击者落地文件，commit 将之冻结为证据镜像，使离线逐层分析成为可能，不必在活体上反复操作。
- **结论**: commit 的正当性来自"固化易失存储层"，与交付场景的禁令不矛盾（用途不同）。
- **结果**: 原书仅给一句话，未交代任何具体入侵事件或结果；不据此编造"成功取证"情节。

### 示例 2: 应用容器异常外连的现场固化演练
- **类型与来源**: 【合成演练】（依据本卡 E 段规则推演，不对应真实事件，不编造现实结果）
- **问题/输入**: 一个对外 Web 容器被监测到异常外连，容器仍在运行，需要保全现场。
- **方法论的使用**:
  1. 事件确认后先隔离：停对外服务、摘除网络，但不 `docker rm`、不断电。
  2. 立刻 `docker commit <容器> <现场镜像名>` 固化可写层。
  3. 另存 `docker inspect`、`docker diff`、进程与网络快照，与证据镜像一并归档。
  4. 离线 `docker save` 解包逐层分析，配合层搜索定位新增/篡改文件。
  5. 取证完成后从可信基线重建业务，不复用被入侵容器。
- **结论**: 先固化后分析、全程少碰活体，才能保住可信任的证据链。
- **结果**: 合成演练不产出真实取证结果；按 E 段判停条件执行，不宣称查明了 attacker 或拿到任何具体证据。

### 示例 3: 按服务模型判取证可见性
- **类型与来源**: 【例题】《云计算安全指南v3.0》D9 9.3.4（原文按 IaaS/PaaS/SaaS 分述取证依赖程度）
- **问题/输入**: 一家公司的业务跑在 IaaS 上，发生事件后想在 VM 内取内存快照与网络流量做取证。
- **方法论的使用**:
  1. 定位证据所在层：内存快照与网络流量不在 VM 内部。
  2. 判控制方：这两类证据由 CSP 控制的 hypervisor/网络组件掌握。
  3. 结论：客户只能查 VM 内部，内存/网络/磁盘镜像证据需 CSP 支持 → 走 SLA 支持请求，并在后续合同里预先约定数据内容与格式。
- **结论**: "有自己的 root"不代表"能查一切"；证据层与控制方错位时，必须依赖 CSP。
- **结果**: 原书给出分述原则，未交代该公司的具体取证结果；本卡不编造。

### 示例 4: 云日志与虚拟化盲区联合诊断
- **类型与来源**: 【合成演练】（依据指南 D9 9.3.3 三信号与 D13 13.1.3/13.1.6 盲区描述，按本卡 E 段规则推演）
- **问题/输入**: 事件后拿到的云日志"对不上"，同时怀疑 VM 间通信没被监控到。
- **方法论的使用**:
  1. 核时钟/时区标记 → 发现某来源缺时区，跨源时间戳无法对齐，标注"日志不可直接用于关联"。
  2. 核新增 VM 是否自动接入日志流 → 发现一台动态扩容的实例没有日志，标注盲区。
  3. 核防篡改 → 日志服务器与应用服务器分离、只读存储，判可用。
  4. 虚拟化面：判 VM 间通信是否走背板 → 网络层不可见，改用 Hypervisor API 内嵌监控；列冷启动 VM，前置虚拟补丁/NAC 隔离后再放行。
- **结论**: 日志"有"不等于"可用"；网络层看不到的流量要用 Hypervisor 层补，冷启动 VM 要前置检查。
- **结果**: 合成演练不产出真实取证结果；按 E 段输出可见性诊断与盲区处置清单。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 容器被入侵、被植入后门或异常外连，担心攻击者清痕或销毁容器。
2. 想在容器被删除前冻结可写层，得到不可变证据副本并离线逐层分析。
3. 云上发生事件，想知道"能拿到内存镜像吗""网络流量记录去哪查""取证要找谁"。
4. 日志"对不上"、时间戳无法关联，想判断日志能不能当证据。
5. 怀疑 VM 间通信绕过了网络监控，或担心关机 VM 重启后带漏洞上线。
6. 想搞清楚 `docker commit` 除"学习"之外的正当用途（与交付禁令区分）。

### 语言信号（出现这些就该激活）
- 中文：「容器被入侵了怎么取证」「怎么保留容器现场」「docker commit 有什么用」「容器被删了还能查吗」「云上怎么做取证」「能拿到内存镜像吗」「云上操作会留日志吗」「怎么溯源云上攻击」「日志对不上」「日志能不能当证据」「VM 之间流量怎么监控」「虚拟网络盲区」「关机的虚拟机安全吗」「VM 重启后要不要重新检查」
- English: "container incident response evidence", "preserve compromised container", "cloud forensics visibility by service model", "cloud audit trail visibility", "logs inconsistent across sources", "VM backplane traffic invisible", "instant-on gap VM"

### 与相邻能力的区分
- 与 `image-build-supply-chain` 的区别：同一 `docker commit`，在那里是"禁止用于交付"的反例，这里是"固化现场"的正当用法——判据是用途。
- 与 `cloud-attack-surface-and-responsibility` 的区别：那张卡按服务模型判"责任归属"（谁该修），本卡按同一模型判"取证可见性"（谁能查），维度不同。
- 与 `container-isolation-boundary-assessment` 的区别：那张卡做整体隔离评估与信任域划分，本卡只处理已发生事件后的证据与可见性。
- 与 `cloud-credential-and-storage-attack` 的区别：那张卡把日志投递 OSS/SLS 作为止血固证动作，本卡专门判日志质量与可见性边界。

## E — 可执行步骤 (Execution)

**必需输入**: 事件已确认；容器仍在运行或处于 exited 状态（未被删除）；磁盘余量足够存放证据镜像；所用服务模型（IaaS/PaaS/SaaS）；可访问云上各类日志（审计/错误/安全/性能）与 Hypervisor API。缺"容器是否还在、证据在哪一层"必须先问——已删则存储层已丢，无法固化。
**交付物与完成标准**: 证据镜像（commit 产物）+ 元数据归档 + 可见性诊断 + 盲区处置清单。完工标准是证据链完整、活体未被反复操作、日志可关联、盲区有补偿手段、业务已用干净容器重建。

1. **定事件层与服务模型**
   - 做什么：明确事件发生在哪一层（容器可写层 / VM 内 / 网络 / 平台 / 应用），所用服务模型是什么。
   - 完成标准：证据所在层与控制方（客户/CSP）明确。
   - 判停：证据层由 CSP 控制的，直接跳转第 4 步走 SLA 支持路径，不设计自查方案。

2. **容器现场固化（容器可写层）**
   - 做什么：先隔离但不断电、不 `docker rm` → 立刻 `docker commit <容器> <现场镜像名>` → 另存 `docker inspect`、`docker diff`、进程与网络快照一并归档。
   - 完成标准：证据镜像与元数据成对归档，磁盘留有完整副本。
   - 判停：容器已被删除则存储层已丢，本步无法执行，转从镜像侧分析基线差异；磁盘余量不足先清理无关数据再 commit，不拖延。

3. **云日志留痕与投递（云上操作面）**
   - 做什么：确认目标云是否开启操作日志审计与投递；行动/事件后核对日志是否覆盖登录、API 调用、配置变更；防守侧把日志投递 OSS（固证）+ SLS（高效检索）。
   - 完成标准：能还原操作链，且日志有异地投递。
   - 判停：只开日志不异地投递时，日志本身可能被攻击者清除——标注为未闭环。

4. **证据可见性与 CSP 支持**
   - 做什么：按服务模型判该层能否自取；需 CSP 支持的在 SLA 中预先约定数据内容与格式。
   - 完成标准：每类证据写明"可自取/需 CSP"及依据。
   - 判停：IaaS 下网络流量、内存快照、磁盘镜像需 CSP 支持，不判"自己有 root 就能查"；未见 SLA 约定时标注合同缺口。

5. **日志质量三信号核对**
   - 做什么：①核各日志源时钟同步与时区标记；②确认新增云资源日志自动接入数据流；③检查防篡改（只读存储、服务器分离、访问控制）。
   - 完成标准：三信号都有结论，时间戳可跨源对齐、动态变化有反映、日志不可随意改写。
   - 判停：任一不满足则标注"日志不可直接用于分析"，不据此下取证结论。

6. **虚拟化盲区处置**
   - 做什么：判 VM 间通信是否走背板（网络层不可见）→ 用 Hypervisor API 内嵌虚拟设备/硬件辅助虚拟化补监控；列长期关机后可能启动的 VM → 启动路径前置虚拟补丁/NAC 隔离，更新规则库并扫描通过后再放行；VM 迁移时每 VM 装安全工具或新入区强制检查。
   - 完成标准：背板流量与迁移盲区有监控补偿，冷启动 VM 不能直接暴露。
   - 判停：只部署传统网络 IDS/防火墙对背板流量无效，必须走 Hypervisor 层；认为"镜像制作时打了补丁就一劳永逸"是误判。

7. **离线分析与重建**
   - 做什么：离线 `docker save` 解包逐层分析（配合 `image-build-supply-chain` 层搜索）与基线比对；取证完成后从可信基线重建业务，证据镜像归档留存不推回仓库。
   - 完成标准：产出落地文件清单与差异报告，业务运行于干净容器。
   - 判停：全程不再在活体容器上执行命令（避免污染时间线与 mtime）；现场镜像推回仓库会把后门分发给所有人，必须避免。

## B — 边界 (Boundary) ★

### 不要用的情况
- 容器尚未被删除但事件未确认时，不要急于 commit——先确认事件范围，避免误把正常容器当现场。
- 需要交付/复用镜像时用 `image-build-supply-chain`，那里 commit 是禁令。
- 容器已被 `docker rm`、存储层已丢时本能力无法固化现场，只能从镜像侧分析。
- 需要整体隔离评估用 `container-isolation-boundary-assessment`；判责任归属用 `cloud-attack-surface-and-responsibility`。

### 已知失败模式
- **先 `docker rm` 再想取证**：存储层随容器销毁，证据永久丢失（E 段第 2 步判停）。
- **在活体容器里大量执行命令**：污染时间线与文件 mtime，破坏证据可信度（E 段第 7 步）。
- **把现场镜像当可用基线推回仓库**：会把后门分发给所有人，与 commit 交付禁令冲突。
- **只 commit 不另存元数据**：脱离活体后 inspect/diff/进程与网络快照无法补采，证据链不完整。
- **以为云上和内网一样"无痕"**（第四章）：忽略操作日志；只开日志不异地投递，日志本身可能被清除。
- **以为 IaaS"自己有 root 就能查一切"**（指南 D9 9.3.4）：网络层和 hypervisor 层数据拿不到；等事件发生才发现 CSP 不提供关键数据。
- **忽略动态资源带来的日志盲区**（指南 D9 9.3.3）：请求被记录但由哪个实例动态提供没记下来，根因无法定位；时区缺失导致时间戳误读。
- **只部署传统网络 IDS/防火墙**（指南 D13 13.1.3）：对背板流量和迁移 VM 束手无策。
- **认为镜像制作时打了补丁就一劳永逸**（指南 D13 13.1.6）：忽略关机期间威胁演化，冷启动 VM 带洞上线。

### 作者与时代的局限
- 原书对容器取证仅以一句话指出 commit 的"保存现场"用途，未给完整流程；本卡时序与纪律是按该命令机制与 E 段规则推演的方法论，不宣称作者亲历或书中明载。
- 云取证与日志可见性内容来自《云计算安全指南v3.0》的 IaaS/PaaS/SaaS 三分框架；当代 Serverless/容器服务的证据形态与可控范围不同，需按实际服务模型重判。
- 现代取证有更专业的内存抓取、卷快照、编排层审计工具，commit 只解决"可写层固化"这一环，不覆盖内存与网络流量证据。
- K8s 等编排环境中容器可能被自动重建，现场保全需结合节点与编排层机制，不能只靠单机 commit。

### 容易混淆的方法
- **取证用途 vs 交付用途**：同一 commit，取证正当、交付禁止——判据是用途。
- **固化 vs 查清**：核心是保全证据，"查清"是离线阶段的后续工作。
- **操作留痕 vs 日志质量**：CU-2-11 判"是否留痕"，CU-2-13 判"记录能否用于分析"，两者独立。
- **责任归属 vs 取证可见性**：同一服务模型下，"谁该修"与"谁能查"结论可能不同。
