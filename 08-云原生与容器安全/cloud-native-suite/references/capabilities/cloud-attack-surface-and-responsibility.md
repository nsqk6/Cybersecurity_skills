# 云上攻击面与责任边界判定

## R — 原文 (Reading)

> 针对租户的攻击：对于在云上的目标，依然存在常见的 Web 漏洞，SQL 注入、弱口令、文件上传、SSRF，除此之外上云还出现了新的攻击方式，例如：AccessKey 泄露接管服务器、存储桶配置不当、传统漏洞结合云特性获取实例元数据。

> — 《云安全攻防入门》第一章 公有云攻击面介绍

> 例如，Amazon 的 AWS EC2 基础设施作为服务，供应商负责 Hypervisor 层以下层次的安全责任，这意味着它们只负责诸如物理安全，环境安全和虚拟化安全等这些安全控制。与之相应，用户则负责与 IT 系统（实例）相关的安全控制，包括操作系统、应用和数据。

> — 《云计算安全指南v3.0》D1 1.5.2 什么是云计算的安全性 / D9 9.2 云结构安全参考模型

## I — 方法论骨架 (Interpretation)

这个能力回答两个上云后最先遇到、也最常被答错的问题："上云之后渗透思路要不要变？云上有哪些新的攻击面？""这个配置错误算云商的还是算我们的？"它是云子域的总入口——先把范围划清，再决定用哪张专项卡。

第一维是攻击面分类。上云并没有消灭传统 Web 漏洞，而是在其上叠加了云特性攻击面。正确的划分依据是"谁来承担后果"：租户侧打的是单个业务资产，沿用常规渗透方法（SQL 注入、弱口令、文件上传、SSRF 等），但要额外加上云特有入口——AccessKey 泄露接管服务器、存储桶配置不当、传统漏洞结合云特性去读实例元数据。平台侧打的是多租户底座，要围绕架构模块（计算、存储、中间件、虚拟化）逐层找入口。只按传统 Web 打会漏掉 AK/OSS/元数据，只盯云特性又会漏掉 Shiro、Fastjson 这类常规漏洞——两条线必须都列。

第二维是责任边界。责任是按"控制可见性"切的：谁能看到并配置某一层，谁就对那层的失配负责。IaaS 下云商负责 Hypervisor 及以下（物理安全、环境安全、虚拟化安全），用户负责 OS、应用、数据；SaaS 几乎全归云商；PaaS 居中——平台自身归云商，平台上的应用与开发方式归用户。判据是"出错的那一层，配置权在谁手里"，而不是笼统说"上云就安全/不安全"。

把两维合起来，交付物是一张"攻击面 + 责任"对照表：每一行写明目标资产、攻击面类型、故障所在层、控制方、下一步动作（自查还是向 CSP 提 SLA 支持请求）。这张表决定了后续路由：租户侧凭据类问题转 `cloud-credential-and-storage-attack`，对象存储转同卡，容器逃逸转 `container-escape-path-assessment`，平台侧初始突破与横向转 `cloud-platform-lateral-movement`，取证可见性转 `container-incident-forensics`。

一个常见误区要单独点出："用了云安全服务就不用管 OS 以上"是错的——IaaS 下 OS/应用/数据配错仍是用户责任；反过来 SaaS 下客户几乎没有技术层面的遏制手段，只能靠合同与 CSP 支持。

## A1 — 应用示例 (Application Example)

### 示例 1: IaaS 与 SaaS 的责任对照
- **类型与来源**: 【例题】《云计算安全指南v3.0》D1 1.5.2（原文以 AWS EC2 与 Salesforce CRM 作对照）
- **问题/输入**: 两个业务系统分别跑在 AWS EC2（IaaS）和 Salesforce CRM（SaaS）上，出现配置错误，需要判定责任方。
- **方法论的使用**:
  1. 归类服务模型：EC2 = IaaS，Salesforce CRM = SaaS。
  2. 定位故障层：假设是 OS 补丁缺失（EC2）与应用访问控制配置（CRM）。
  3. 对照分界层判责任：IaaS 下 OS/应用/数据归用户 → EC2 的 OS 补丁由用户负责；SaaS 下应用与平台归云商 → CRM 侧客户只能向 CSP 提支持请求。
- **结论**: 同一个"配置错误"在不同服务模型下责任方完全相反，判据是"配置权在谁手里"。
- **结果**: 原书以两者作对照说明责任边界，未交代具体事件处置结果；按 E 段输出责任归属与下一步动作。

### 示例 2: 阿里云上业务系统的攻击面两条线盘点
- **类型与来源**: 【合成演练】（依据《云安全攻防入门》第一章原文的两条攻击面分类，按本卡 E 段规则推演，不对应任何真实目标）
- **问题/输入**: 某业务部署在阿里云 ECS + OSS 上，要评估"上云后渗透思路要不要变"，列出完整攻击面清单。
- **方法论的使用**:
  1. 确认目标是租户资产（某业务系统）而非云平台本身。
  2. 租户侧传统 Web 漏洞列清单：SQL 注入、弱口令、文件上传、SSRF。
  3. 租户侧云特性列清单：AccessKey 泄露、OSS 存储桶配置、传统 SSRF 结合实例元数据。
  4. 平台侧按架构模块列入口（若目标含平台组件）：计算/存储/中间件/虚拟化逃逸，本例为纯租户资产故标注"不涉及"。
- **结论**: 两类清单都必须列出；只做传统 Web 渗透会漏掉 AK/OSS/元数据，只盯云特性会漏掉常规漏洞。
- **结果**: 合成演练不产出真实目标的渗透结果；按 E 段输出攻击面与责任表，凭据类问题路由到 `cloud-credential-and-storage-attack`。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 目标上云后不确定"渗透思路要不要变""云上有哪些新的攻击面"，需要先划范围。
2. 出现配置错误或安全事件，要判断"算云商的还是我们的""SLA 里该找谁负责"。
3. 系统分布在不同服务模型（IaaS/PaaS/SaaS）上，需要分别确定patching、配置、取证的责任方。
4. 已经开始具体测试，但需要先决定用哪张专项卡（凭据 / 对象存储 / 容器逃逸 / 平台横向 / 取证）。
5. 团队误以为"用了云安全服务就万事大吉"，需要纠正"谁可控哪层"的认知。

### 语言信号（出现这些就该激活）
- 中文：「上云之后渗透思路要不要变」「云上有哪些新的攻击面」「这个配置错误算云商的还是我们的」「SLA 里该找谁负责」「IaaS 下谁负责打补丁」「用了云服务是不是就不用管系统了」
- English: "where do I start on a cloud asset", "cloud attack surface vs traditional web", "who is responsible for patching in IaaS", "shared responsibility model", "Alibaba Cloud pentest scope"

### 与相邻能力的区分
- 与 `cloud-credential-and-storage-attack` 的区别：本卡划分攻击面与责任范围（总入口），那张卡处理凭据与对象存储的具体攻防；本卡判停后路由到它。
- 与 `cloud-platform-lateral-movement` 的区别：本卡识别"目标是租户还是平台"，那张卡处理平台侧（OpenStack）拿下一台后的横向放大。
- 与 `container-incident-forensics` 中"服务模型判取证可见性"的区别：本卡判的是**责任归属**（谁该修），那部分判的是**证据可见范围**（谁能查），两者按不同维度切同一服务模型。

## E — 可执行步骤 (Execution)

**必需输入**: 目标是否上云、部署在哪家云、是租户资产还是平台底座；用到的服务类型（IaaS/PaaS/SaaS）；故障或评估发生的具体层次（物理/虚拟化/OS/网络/应用/数据）。缺"目标是租户还是平台、服务模型是什么"必须先问。
**交付物与完成标准**: 一张"攻击面 + 责任"对照表——每条写明目标资产、攻击面类型（传统/云特性）、故障层、控制方、下一步动作（自查 / CSP SLA / 路由到专项卡）。完工标准是两条攻击面线都有清单、每个故障层都有明确责任方。

1. **确认目标形态与范围**
   - 做什么：判断目标是租户资产还是云平台本身，完成"被打的是某个业务系统还是云底座"的定位。
   - 完成标准：能一句话指出目标形态。
   - 判停：租户资产进入第 2 步；平台底座（服务商侧）进入第 3 步平台侧列入口。

2. **列租户侧两条攻击面清单**
   - 做什么：传统 Web 漏洞（SQL 注入、弱口令、文件上传、SSRF）+ 云特性点（AK 泄露、存储桶配置、传统漏洞结合元数据）逐项列举。
   - 完成标准：两类清单都列出，无一类为空。
   - 判停：命中凭据类转 `cloud-credential-and-storage-attack`；命中容器逃逸转 `container-escape-path-assessment`；只列清单不在此步做利用。

3. **列平台侧架构模块入口（如涉及）**
   - 做什么：按架构模块逐层列入口——文件处理、中间件、数据库产品、开源组件、虚拟化逃逸。
   - 完成标准：形成"模块 → 攻击面"映射。
   - 判停：确认是纯租户资产时标注"不涉及"，不强行编造平台侧入口。

4. **归类服务模型并定责任**
   - 做什么：归类 IaaS/PaaS/SaaS，说出该模型的分界层；定位故障层；按"配置权在谁手里"判责任方。
   - 完成标准：每个故障层都有"用户/CSP"归属与下一步动作。
   - 判停：IaaS 下 OS/应用/数据配错判用户责任；SaaS 下客户无技术遏制手段时，动作定为"向 CSP 提 SLA 支持请求"，不写自查方案。

5. **汇总与路由**
   - 做什么：合并攻击面清单与责任判定，给每个攻击面标注负责方与后续专项卡。
   - 完成标准：对照表可直接作为测试/整改的范围依据。
   - 判停：任一攻击面无责任方或无路由去向时，不得判定"范围已划清"。

## B — 边界 (Boundary) ★

### 不要用的情况
- 已经明确目标与责任、要动手 exploitation 时——用 `cloud-credential-and-storage-attack`、`cloud-platform-lateral-movement` 等专项卡，本卡只划范围。
- 纯容器内部隔离评估时用 `container-isolation-boundary-assessment`，本卡处理的是"上云"这一层的分类与责任。
- 纯合规条款梳理（治理、审计条款）不是本卡范围——本卡只按"控制可见性"判技术责任边界，不代替合规映射。
- 取证时"看得见什么"的可见性边界（指南 D9 9.3.4）归 `container-incident-forensics`，本卡不重复。

### 已知失败模式
- **只按传统 Web 渗透打**（第一章警告）：漏掉 AK/OSS/元数据这类云特有入口。
- **只盯云特性**：反过来漏掉 Shiro、Fastjson 等常规漏洞，两条线缺一不可。
- **以为用了云安全服务就不用管 OS 以上**（指南 D1/D9）：IaaS 下 OS/应用/数据配错仍是用户责任。
- **把"上云"笼统判成安全或不安全**：不落到"哪一层、配置权在谁手里"，结论不可执行。
- **SaaS 场景下写自查方案**：客户几乎没有技术层面遏制手段，应走 SLA 而非自查。

### 作者与时代的局限
- 《云安全攻防入门》以国内云（阿里/腾讯）为主，第一章的攻击面分类反映当时云产品形态；新型云服务（Serverless、容器服务、AI 平台）需补充新入口。
- 《云计算安全指南v3.0》的责任模型基于 IaaS/PaaS/SaaS 三分法；当代 FuncaaS/CaaS 等混合模型边界更模糊，须按实际控制可见性重新判断。
- 第四章（AWS 场景）原文自述"海外云场景经验不足需另查文档"——本卡对 AWS IAM 细粒度权限只给分类框架，具体打法需查最新文档。

### 容易混淆的方法
- **攻击面分类 vs 责任归属**：本卡两维独立——"打什么"（租户/平台）不等于"算谁的"（IaaS/PaaS/SaaS 分界）。
- **责任归属 vs 取证可见性**：同一服务模型可按两维切，"谁该修"与"谁能查"结论可能不同（后者见 `container-incident-forensics`）。
- **平台侧 vs 租户侧**：平台侧针对多租户底座，租户侧针对单业务资产，后果承担方不同，判据不同。
