# 容器隔离边界评估

## R — 原文 (Reading)

> 评估 Docker 的安全性时，主要考虑三个方面: 由内核的命名空间和控制组机制提供的容器内在安全；Docker 程序（特别是服务端）本身的抗攻击性；内核安全性的加强机制对容器安全性的影响。

> — 《docker_practice》第 11 章 安全（开篇评估框架）

> 当然，与虚拟机方式相比，通过命名空间来实现的隔离并不是那么绝对。运行在容器中的应用可以直接访问系统内核和部分系统文件……即必须保证镜像的来源和自身可靠。

> — 《Docker技术入门与实战_第3版》第 19 章 19.1 命名空间隔离的安全

> 尽管控制组不负责隔离容器之间相互访问、处理数据和进程，但是它在防止恶意攻击特别是拒绝服务攻击方面是十分有效的。

> — 《Docker技术入门与实战_第3版》第 19 章 19.2 控制组资源控制的安全

> 将运行 Docker 容器的机器划分为不同的组，互相信任的机器放到同一个组内；组之间进行资源隔离；同时进行定期的安全检查。

> — 《Docker技术入门与实战_第3版》第 19 章 19.7 本章小结

## I — 方法论骨架 (Interpretation)

这个能力回答一个高频但常被答错的问题："这套容器环境到底安全不安全，隔离够不够用？"它的核心主张是：容器不是单一安全对象，而是三层责任的叠加，评估必须分层进行，否则结论必然偏颇。

三层分别是：内核隔离层（namespace 提供视图隔离、cgroup 提供资源配额）、Docker 自身层（daemon/API 是攻击面）、外部加固层（能力白名单、AppArmor/SELinux、只读挂载等补偿机制）。任何一层单独拿出来都不构成安全结论——只看到"namespace 开了"就下结论，等于把后两层完全漏掉。

为什么必须分层？因为三层的失败后果、取证对象、修复手段都不同：隔离层失效导致逃逸；daemon 层失守导致整机沦陷；加固层缺失导致漏洞没有补偿。把它们混在一起说"安全/不安全"，就无法给出可执行的整改项。

第二层关键洞察是：namespace 隔离的是"视图"而不是"内核"，所有容器共用同一个内核、系统调用面完全暴露。因此隔离强度的上限由内核自身决定，`/proc/sys` 可写、设备节点、内核漏洞都是逃逸面。判据是——一旦不能保证"容器内跑的代码可信"，就应判定该容器与宿主处于同一信任域，不能再声称它构成独立边界。

第三层关键洞察是：cgroup 只做"用量配额与计费"，不做"访问裁决"。它能让一个容器打不满宿主，但不能阻止容器读宿主文件、连内网、开 socket。所以看到 `--memory`、`--cpu-quota`、`--pids-limit` 只能得出"抗资源耗尽"的结论，绝不能推导出"权限被限制"——这是实践中最常见的误判。

最后，评估的粒度不止于单容器，还要上升到宿主级信任域：同一宿主上的容器共享内核，逃逸或横向移动会让同机容器全部落入同一爆炸半径。因此分组依据是"这些容器/租户是否互相信任"，而不是"是否属于同一业务系统"。把不同信任级别的负载混跑，等于用一个内核把它们焊在同一信任域里。

把四步走完，得到的不是"安全/不安全"一个词，而是一张三层各自结论 + 宿主信任域划分的诊断表——这才是能指导整改的交付物。

## A1 — 应用示例 (Application Example)

### 示例 1: 某平台"已开 namespace 就安全"的结论复核
- **类型与来源**: 【合成演练】（依据本卡 E 段规则推演，按《docker_practice》第11章三层框架、《Docker技术入门与实战》19.1/19.2 原则）
- **问题/输入**: 团队声称"我们的容器平台用了 namespace + 内存限制，隔离没问题"，需要复核这个结论是否成立。
- **方法论的使用**:
  1. 内核隔离层：查 `/proc/self/status` 确认 CapEff、确认未启用 user namespace，检查容器内 `/proc/sys`、`/proc/irq`、`/proc/bus` 可写——发现可写，判定视图隔离不足以约束状态修改。
  2. 资源层：查 `docker inspect` 的 memory/cpu/pids 限额齐全，得出"抗 DoS 可用"。
  3. 访问控制层：查 capabilities、挂载、网络策略——发现运行着第三方镜像且无 AppArmor/SELinux，越权抗性为空。
  4. 宿主信任域：同机混跑对外 Web 与内部数据库容器，信任级别不同。
- **结论**: 三层中只有"资源层 + 部分视图隔离"成立，加固层与信任域划分缺失，原结论不成立；该环境只能说"隔离可用"，不能作为生产安全结论。
- **结果**: 原书未提供该具体演练的结果（合成演练不编造现实结果）；按 E 段应输出三层诊断表并触发能力2（运行时加固）与能力1宿主拆分。

### 示例 2: 多租户平台"能不能跑不可信代码"的判定
- **类型与来源**: 【转述】《Docker技术入门与实战_第3版》第 19 章 19.1（镜像来源可靠性原则）+【合成演练】场景化推演
- **问题/输入**: 在线评测平台想用容器执行用户提交的不可信代码，问"namespace 够不够"。
- **方法论的使用**: 按 19.1 的判据，先确认容器与宿主共用内核（容器场景恒为是）→ 不存在硬件级边界；再查容器内应用是否可信 → 用户提交代码不可信；于是"镜像/应用可信"这唯一剩余防线失效。
- **结论**: 不能靠调 namespace 解决，必须换更强边界（虚拟机 / gVisor 类沙箱），或判定为同一信任域并严格限制爆炸半径。
- **结果**: 原书未说明该平台最终结果（原书仅给出原则，无案例）；按 E 段判停条件应转"需要更强隔离边界"的结论，不得停留在"已隔离"。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 要回答"这套 Docker/K8s 环境安全吗""容器隔离够不够"这类总体评估问题，需要先定维度再动手。
2. 准备在同一宿主上混跑不同信任级别的负载（对外服务、第三方镜像、多租户），需要判断是否构成独立信任域。
3. 有人拿"开了 namespace""配了内存限制""跑了 CIS 检查"当安全验收结论，需要复核这个结论是否以偏概全。
4. 要决定"能否用容器跑不可信代码 / 在线评测 / CI 执行任意脚本"，需要判断隔离边界的类型是否匹配。
5. 安全建设初期，需要先确定评估框架，再决定接下来跑哪些具体检查（基线、扫描、加固）。

### 语言信号（出现这些就该激活）
- 中文：「这套 Docker 环境安全吗」「容器隔离够不够用」「namespace 能不能跑不可信代码」「配了内存限制是不是就安全了」「多租户怎么隔离」「评估一下容器平台风险」「容器和虚拟机隔离哪个强」
- English: "how secure is our container setup", "evaluate docker isolation", "is container isolation enough", "run untrusted code in container", "does memory limit make it secure", "multi-tenant container isolation"

### 与相邻能力的区分
- 与 `container-security-tooling` 的区别：本能力给的是**评估维度划分**，工具链能力给的是**逐项打勾的检查清单**（Docker Bench / clair）。先用本能力分层，再决定跑哪些工具。
- 与 `container-privilege-surface-hardening` 的区别：本能力判断"隔离是否够用"，提权面能力处理"具体哪些配置让容器等价 root"；本能力在判停时会路由到它。
- 与 `container-network-exposure` 的区别：本能力看隔离与信任域整体，网络暴露能力只看端口与容器间横向的暴露范围。
- 与 `container-escape-path-assessment` 的区别：本能力是**防御侧**"隔离够不够"的整体评估，那张卡是**攻击侧**拿到 Shell 后判定并利用逃逸路径；本能力判停时若发现已进入容器，转那张卡。
- 与 `cloud-attack-surface-and-responsibility` 的区别：本能力处理容器内部隔离边界，那张卡是云子域总入口（上云后攻击面分类与服务模型责任边界），两者按"容器层 / 云层"分工。

## E — 可执行步骤 (Execution)

**必需输入**: 一台可登录的容器宿主机（或镜像 + 编排配置）；`docker info`、`/proc/self/status`、`/sys/fs/cgroup`、`docker inspect` 等只读信息；容器内 `--net`/挂载/能力配置；资产清单与信任级别。缺"应用/镜像是否可信"这一项必须先问清。
**交付物与完成标准**: 一张三层诊断表——内核隔离层结论、Docker 自身层结论、加固层结论，外加宿主信任域划分建议；每层都要写明"能挡什么、挡不住什么"。任一层为空要在表中显式标注，不得省略。

1. **内核隔离层盘点**
   - 做什么：记录内核版本、启用的 namespace 类型、cgroup 版本与挂载点；确认容器与宿主共用内核（恒为是）；检查容器内 `/proc/sys`、`/proc/irq`、`/proc/bus` 是否可写；确认是否启用 user namespace。
   - 完成标准：得出"隔离原语是否可用"的结论，并明确写出"共用内核、不存在硬件级边界"这一前提。
   - 判停：若 `/proc` 高危路径可写且未启用 user namespace，标注"隔离不足以约束状态修改"，继续第 2 步；若镜像/应用不可信，跳到第 4 步直接判定需换更强边界。

2. **Docker 自身层（daemon/API）盘点**
   - 做什么：查 daemon 监听方式（unix socket / TCP）、是否有 TLS、谁能访问 socket → 得到控制面暴露面结论。
   - 完成标准：写出"控制面是否暴露、可达主体是谁"的结论。
   - 判停：若发现无认证 TCP 监听或 docker 组人员过宽，转 `docker-daemon-api-exposure` 能力做专项收敛，本层标注"高危待整改"。

3. **加固层盘点**
   - 做什么：列出能力白名单（CapEff/CapAdd）、AppArmor/SELinux/GRSEC 是否启用、挂载是否只读 → 得到"逃逸后的止损能力"结论。
   - 完成标准：明确"是否有补偿控制"。
   - 判停：若加固层为空，转 `container-privilege-surface-hardening` 与 `container-security-tooling`；本层标注"无逃逸补偿"。

4. **宿主信任域划分**
   - 做什么：列出每台宿主上的容器清单与信任级别（对外/内部/第三方/多租户）；同一宿主出现不同信任级别即标记拆分；确认组间无共享 daemon、socket、卷。
   - 完成标准：给出按互信关系的分组建议，而非按业务划分。
   - 判停：若存在跨信任级别混跑，输出拆分建议并绑定定期基线检查（`container-security-tooling`）。

5. **汇总交付**
   - 做什么：把四步结论合并成诊断表；三层任一为空时明确写"该环境安全结论只停留在隔离可用层，不能作为生产评估结论"。
   - 完成标准：交付物可直接作为整改输入，每条结论附对应能力的跳转。
   - 判停：若三层齐全但信任域仍混跑，结论仍不能定为"生产可用"。

## B — 边界 (Boundary) ★

### 不要用的情况
- 需要判断"镜像里有没有 CVE 或敏感数据"时——那是 `image-build-supply-chain` 与 `container-security-tooling` 的范围，本能力只看隔离与责任分层。
- 需要逐项配置打勾的合规清单时——用 Docker Bench，本能力只决定"该跑哪些检查"。
- 需要评估虚拟机/裸金属的硬件级隔离时——本能力前提就是容器共用内核，不适用有独立 hypervisor 边界的场景。

### 已知失败模式
- **只看 namespace 就下结论**（《docker_practice》第11章警告）：把"容器内看不到宿主进程"当成整体安全，漏掉 daemon 层与加固层。
- **把 cgroup 当访问控制**（《Docker技术入门与实战》19.2 警告）：用"资源限额已配"当作安全验收通过，多租户平台只配 cgroup 不配 capabilities，任一容器可读他人数据。
- **把 CIS 检查当成交付结论**：只看总分/WARN 而不看具体项，忽略 daemon 配置文件权限等关键偏差。
- **按业务而非互信分组**（19.7 警告）：把第三方镜像与核心库放同一台机，只做网络隔离不做宿主隔离，同机逃逸直接绕过网络策略。

### 作者与时代的局限
- 两书成文于 Docker 早期（1.x 时代），默认模型是单机 bridge 网络；`--icc=false + --link` 等用法书中已注明"引入 docker network 后基本不用"，在 K8s/CNI 环境下需要用 NetworkPolicy 等机制替代。
- 书中对"可信镜像"的强调基于早期生态，当今需结合镜像签名、SBOM 等手段，本框架只提供维度不提供这些具体工具。
- 内核版本与默认能力集随 Docker/内核迭代变化，具体能力位清单需按当前环境实测，不可照抄书中列表。

### 容易混淆的方法
- **namespace vs cgroup**：前者管"看见什么"（视图隔离），后者管"用多少"（资源配额），都不是访问控制——不要写进权限控制清单。
- **隔离强度 vs 信任域**：隔离够用不等于可以把不同信任级别负载混跑；两者是独立的判断。
- **评估框架 vs 检查清单**：本能力是分层框架，不是 Docker Bench 的逐项打勾；先分层，再选工具。
