## I — 方法论骨架 (Interpretation)

这个能力回答一个后渗透阶段的具体问题："我拿到的这个 Shell 到底在不在容器里？如果在，应该走哪条逃逸路？什么情况下应该怀疑是蜜罐但又不轻易放弃？"它把"识别环境 → 分类弱点 → 选匹配手法 → 复核误判"串成一条链。

第一环是环境识别，必须用互补证据交叉，而不是单点下结论。三个证据：容器根目录几乎总有 `/.dockerenv` 文件；`/proc/1/cgroup` 里能 grep 到 `docker`；`ps aux` 进程数异常少且看不到 init/systemd。任一命中即容器信号，三者综合可把环境定性为容器/虚机/物理机。这一步之所以重要，是因为后续动作完全不同——容器要判断逃逸，物理机/虚机走常规提权与横向。

第二环是逃逸路分类。逃逸不是碰运气试 CVE，而是按成因分三类：容器自身组件漏洞（containerd-shim、runC 等）、配置不当（Capabilities、特权模式、危险挂载）、内核漏洞。判据是"当前环境的弱点属于哪一类"，然后选对应手法。避免在没漏洞的环境里硬套 CVE——每个 CVE 都有触发前提，条件不符就是白费功夫。

第三环是两条具体高频路径。配置不当路：特权容器几乎等价于宿主 root——`fdisk -l` 能列出磁盘、`CapEff` 等于 `0000003fffffffff` 两个硬指标命中任一，就能走"挂载宿主磁盘 + chroot"拿到宿主文件系统访问。组件漏洞路：CVE-2020-15257 需要"containerd 版本落在 1.3.9 前或 1.4.0~1.4.2"且"`/proc/net/unix` 能看到 containerd-shim socket"两个条件同时成立，再用 CDK shim-pwn 反弹宿主机 shell，两者缺一不可。

第四环是蜜罐误判复核。作者亲历的反例说明：把"Alpine 内核 / 容器环境"这类单一表象直接当成蜜罐结论并放弃，是典型的启发式判断当结论。正确的做法是怀疑时用 `mount`、`df -h` 查挂载与磁盘，拿实际证据说话，先不放弃、实测逃逸与横向可能性，再验证或排除风险。

四环走完，产出的是"环境定性 + 逃逸路归类 + 具体手法与触发条件 + 是否放弃的复核结论"，而不是一句"试试逃逸吧"。

## A1 — 应用示例 (Application Example)

### 示例 1: 护网某银行上网设备的特权容器逃逸
- **类型与来源**: 【亲历】《云安全攻防入门》第六章 配置不当 / 特权模式
- **问题/输入**: 护网行动中拿到某银行上网设备的 WebShell，需判断环境并扩大控制。
- **方法论的使用**:
  1. 先按环境识别三证交叉：`/.dockerenv` 存在 → 确认在容器中。
  2. 判逃逸路归类：怀疑配置不当（特权模式）。
  3. 验证硬指标：`fdisk -l` 能列出磁盘；`cat /proc/self/status | grep CapEff` 得到 `0000003fffffffff` → 特权容器成立。
  4. 走逃逸手法：`mkdir` 挂载点 → `mount /dev/sda3` → `chroot` 切 bash → 添加用户 SSH 登录，取得宿主机文件系统访问。
- **结论**: 特权容器是"配置不当"类逃逸的最直接路径，两个硬指标足以定性，不必先找内核漏洞。
- **结果**: 原书亲历交代到"添加用户 SSH 登录"这一结果；本卡不扩展为任何未交代的后续战果。

### 示例 2: Alpine 内核被误判为蜜罐
- **类型与来源**: 【亲历】《云安全攻防入门》第六章 关于容器蜜罐
- **问题/输入**: 攻防演练中，同事通过 Shiro 拿到 Shell 交给内网同事，后者看到内核为 Alpine 就判定是蜜罐并放弃。
- **方法论的使用**:
  1. 不采信"这是蜜罐"的转述结论，亲自复核。
  2. 按环境识别确认是容器；怀疑蜜罐时用 `mount`、`df -h` 查挂载与磁盘，取实际证据。
  3. 不预先放弃，实测逃逸与横向可能性。
- **结论**: 单一表象（内核发行版）不足以支撑"蜜罐"结论；放弃前必须实测。
- **结果**: 原书亲历明确交代"亲自测试发现蜜罐可被逃逸可横向渗透"——即该目标被误判，实际可逃逸可横向。

### 示例 3: CVE-2020-15257 的双条件判定
- **类型与来源**: 【例题】《云安全攻防入门》第六章（原文给出 cdk_linux_amd64 run shim-pwn reverse 命令）
- **问题/输入**: 想复现 containerd-shim API 暴露逃逸，但不确定当前容器是否满足条件。
- **方法论的使用**:
  1. 查版本：确认 containerd 在 1.3.9 之前或 1.4.0~1.4.2 → 版本条件命中。
  2. 查 host 模式：`cat /proc/net/unix | grep 'containerd-shim'` → socket 可见，host 模式条件命中。
  3. 两条件同时成立，用 CDK shim-pwn 反弹宿主机 shell（需容器可出网下载 CDK）。
- **结论**: 版本区间与 host 模式缺一不可；只满足其一就利用失败，不应判定"CVE 无效"。
- **结果**: 原书给出利用命令与失败模式（runc not found 时需 `ln -s /usr/sbin/runc /usr/sbin/docker-runc`），未交代具体复现目标的结果；本卡不编造。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 拿到一个 Shell，先要判断"这是容器还是物理机/虚机"，再决定后续是逃逸还是常规提权。
2. 已确认在容器内，想知道"容器怎么逃逸、逃逸有哪几类、当前环境该走哪条路"。
3. 遇到特权容器或老版本 containerd，想快速确认是否具备逃逸前提（`fdisk`/`CapEff`/`/proc/net/unix`）。
4. 听到别人说"这是蜜罐别打了"，需要独立复核而不是盲从。
5. 复现特定 CVE（CVE-2020-15257、CVE-2019-5736）前，先核对触发条件，避免硬套。

### 语言信号（出现这些就该激活）
- 中文：「这是容器还是物理机」「怎么判断在 docker 里」「容器怎么逃逸」「逃逸有哪几类」「怎么判断是不是特权容器」「特权容器怎么逃逸」「privileged CapEff」「shim-pwn 利用条件」「这是蜜罐别打了吧」「Alpine 是不是蜜罐」
- English: "am I in a container", "container escape techniques", "privileged container CapEff", "CVE-2020-15257 exploit", "should I skip this container honeypot"

### 与相邻能力的区分
- 与 `container-privilege-surface-hardening` 的区别：那张卡是**防御侧**审计配置（哪些配置让容器等价 root），本卡是**攻击侧**拿到 Shell 后判定并利用逃逸路径；两者共享 privileged/CapEff 判据但立场相反。
- 与 `container-isolation-boundary-assessment` 的区别：那张卡评估"隔离够不够用"的整体框架，本卡只处理"已进入容器后怎么出去"的具体路径。
- 与 `cloud-platform-lateral-movement` 的区别：后者是云平台节点 root 后的横向放大（配置收集），本卡是单容器边界的逃逸。

## E — 可执行步骤 (Execution)

**必需输入**: 一个已获得的 Shell；容器内可读 `/proc/self/status`、`/proc/1/cgroup`、`/proc/net/unix`、`fdisk`、`mount`、`df -h` 等信息；内核版本与容器运行时版本；能否出网下载 CDK。缺"是否已拿到 Shell、Shell 是否在容器内"必须先问。
**交付物与完成标准**: 一张逃逸路径判定表——环境定性（容器/虚机/物理机）、弱点归类（自身漏洞/配置不当/内核漏洞）、匹配手法与触发条件、蜜罐复核结论。完工标准是每条路径都写明"成立/不成立及依据"，不成立的路径明确排除而非含糊保留。

1. **三证交叉识别环境**
   - 做什么：`ls -alh /.dockerenv` 查文件；`cat /proc/1/cgroup | grep docker` 查 cgroup；`ps aux` 看进程数是否异常少、有无 init/systemd。
   - 完成标准：三证综合给出明确的环境定性。
   - 判停：任一命中即为容器信号，进入第 2 步；三证皆无则按物理机/虚机处理，本能力不适用，转常规提权路径。

2. **按三分类归当前弱点**
   - 做什么：读内核版本、Capabilities、挂载信息、运行时版本，把弱点归为"自身组件漏洞 / 配置不当 / 内核漏洞"之一。
   - 完成标准：归类明确，并列出该类下的候选手法。
   - 判停：配置不当优先验证（最快），再试自身组件漏洞，内核漏洞最后；不在无漏洞环境硬套 CVE（如 CVE-2019-5736 需管理员 exec 触发）。

3. **配置不当路：特权容器验证**
   - 做什么：`fdisk -l` 能否列出磁盘；`cat /proc/self/status | grep CapEff` 是否等于 `0000003fffffffff`。
   - 完成标准：两指标任一命中即判定特权容器成立。
   - 判停：命中则 `mkdir` 挂载点 → `mount /dev/sdaX` → `chroot` 切 bash（挂载前先 `fdisk` 确认 sda1/sda3，避免挂错分区）；无 `capsh` 时在他机解码 CapEff。

4. **组件漏洞路：containerd-shim 双条件验证**
   - 做什么：确认 containerd 版本在 1.3.9 前或 1.4.0~1.4.2；`cat /proc/net/unix | grep 'containerd-shim'` 看 socket 是否可见。
   - 完成标准：版本 + host 模式双条件都成立。
   - 判停：任一不成立即排除该路，不判"CVE 无效"；成立则用 CDK shim-pwn（需出网），报 `runc not found` 时先 `ln -s /usr/sbin/runc /usr/sbin/docker-runc`。

5. **蜜罐怀疑复核与汇总**
   - 做什么：怀疑蜜罐时用 `mount`/`df -h` 查挂载与磁盘取实证；不预先放弃，实测逃逸与横向可能性；把各路结论汇总成判定表。
   - 完成标准：每条路径有"成立/不成立 + 依据"，蜜罐怀疑有实证支撑。
   - 判停：仅凭 Alpine 内核或他人转述不得判放弃；实测无路径且无实证才标注"疑似蜜罐，待进一步验证"。

## B — 边界 (Boundary) ★

### 不要用的情况
- 确认环境不是容器时——本卡的能力只针对容器逃逸，物理机/虚机转常规提权与横向。
- 还没有任何 Shell 落脚点时——先获得执行通道，本卡不解决初始打点。
- 做防御侧配置审计（"我们的容器能不能被逃逸"）时用 `container-privilege-surface-hardening`，立场不同。
- 云平台节点 root 后的跨网段横向放大用 `cloud-platform-lateral-movement`，本卡只跨容器边界这一层。

### 已知失败模式
- **只看 Alpine 内核就判蜜罐放弃**（第六章亲历反例）：把启发式表象当结论，错失可逃逸可横向的目标。
- **不看版本条件硬套 CVE**：CVE-2019-5736 需管理员 exec 触发；CVE-2020-15257 需版本区间 + host 模式双条件，缺一失败。
- **mount 错磁盘分区**：未先 `fdisk -l` 确认 sda1/sda3 就挂载 chroot，方向错误。
- **CDK 反弹报 runc not found**：需建软链 `ln -s /usr/sbin/runc /usr/sbin/docker-runc`，否则利用链断。
- **CapEff 无 capsh 直接判不可解**：容器里无解码工具时应换机解码，不是特权不成立。
- **只拿内网 IP/vpc-id 就停手**（元数据场景，见 `cloud-credential-and-storage-attack`）：漏掉角色临时凭证这一步。

### 作者与时代的局限
- 书中 CVE 与 CDK 命令针对当时的 containerd 版本与工具形态；新版 containerd/runC 已修复相关漏洞，版本区间与利用方式须按当前实测。
- 亲历案例来自特定攻防演练环境（银行上网设备、政务场景），不能泛化为所有容器都可按同一手法逃逸。
- 书中强调"不能轻易相信别人说的话"属经验性纪律；现代容器运行时（containerd/CRI-O、gVisor、Kata）边界差异较大，判据需结合运行时类型。

### 容易混淆的方法
- **环境识别 vs 逃逸利用**：三证交叉是前置判定，不是逃逸本身；顺序是先识别后选路。
- **配置不当 vs 组件漏洞**：特权容器（CapEff/fdisk）与 containerd-shim（版本/socket）是两类独立前提，判据不同。
- **蜜罐怀疑 vs 蜜罐结论**：怀疑是假设，必须用 `mount`/`df -h` 实证复核，不能直接转成放弃动作。
- **攻击侧 vs 防御侧**：本卡的 CapEff 判据与 `container-privilege-surface-hardening` 相同，但一个用来利用、一个用来收敛。
