# 主机现场多线并行排查

## R — 原文 (Reading)

> 一般会从系统排查、进程排查、服务排查、文件痕迹排查、日志分析等方面进行，整合相关信息，进行关联推理，最后给出事件结论

> — 《网络安全应急响应技术实战指南》· 1.4 网络安全应急响应现场处置流程

> 你打开命令行敲 netstat -nao。它不仅给出协议、本地/对端地址和状态，还给出与该连接关联的进程号（PID）。

> — 《Cybersecurity Blue Team Toolkit》· Chapter 1「Fundamental Networking and Security Tools」→「NetStat」

> 进程查杀是一个危险操作，所以可以考虑先暂停，看看是否符合预期，再决定是否杀死进程

> — 《windows应急响应手册》· 挖矿病毒 `0x05 处理异常进程` · 4. 进程查杀

## I — 方法论骨架 (Interpretation)

这个能力解决的问题是：**拿到一台（或一批）可疑主机，不知道从哪查起，也不知道查到什么程度算查完。**

单点排查（只看进程、只看启动项）必然漏，因为攻击者的驻留方式与运行方式不在同一处：无文件载荷没有落盘文件，WMI 订阅不在启动项，CLR 劫持不改任何可执行文件，"只连一次"的 C2 在你看的时候早已断开。可靠做法是把证据分成**五条互相独立的线**同时铺开，最后靠时间线对齐：

| 证据线 | 回答的问题 | 典型数据源 |
|---|---|---|
| 系统 | 谁有权进来、系统被改成什么样 | 账号与组、启动项、计划任务、补丁、防火墙规则 |
| 进程 | 现在在跑什么、谁拉起来的 | pid/PPID、路径、命令行、加载模块、签名 |
| 服务 | 有什么在后台常驻 | 服务注册表、ImagePath、SDDL、驱动 |
| 文件痕迹 | 落过什么、跑过什么 | 临时目录、Recent、Prefetch、Amcache、ShimCache、按时间窗新增文件 |
| 日志 | 什么时间发生过什么 | 安全/系统/应用日志、Web 访问、数据库登录、中间件日志 |

三条纪律决定这套方法能不能出结论：

1. **先降噪再判断**。`netstat -nao` 之前先关掉浏览器等已知联网程序，剩余连接才可逐一解释；Autoruns 先过滤已知正常项，异常才浮出来。不做降噪的结果是"一堆可疑项"却给不出结论。
2. **先保状态再动手**。查杀前先挂起（suspend），观察"业务是否异常、外连是否停止"来确认因果关系，再恢复（resume）验证 pid 不变，最后才终止。杀进程是不可逆动作。
3. **结论必须来自交叉印证**。五条线各自给出的是"可疑项"，只有同一条时间线上的"账号—进程—文件—外连—日志"能对上，才算事件结论。

现场还有一个反直觉点：**攻击者会主动规避你的观察通道**。有的挖矿木马监测到任务管理器启动就暂停挖矿、等工具关闭再恢复，表现为"一打开任务管理器 CPU 就正常"；有的替换 `ls`/`ps` 让列表看起来干净；有的把 `history` 的 `HISTSIZE` 设为 0。所以每条证据线都要准备**第二条读数通道**——任务管理器不行就用 `wmic cpu get LoadPercentage /value`，`ps` 不行就用 `/proc` 目录做差集，`history` 为空就当信号而不是当结论。

## A1 — 应用示例 (Application Example)

### 示例 1: 从一条外连查到整条驻留链
- **类型与来源**: 【亲历】《Cybersecurity Blue Team Toolkit》· Chapter 1「Investigating the Unexpected」
- **问题/输入**: 防火墙告警显示内网一台主机在向可疑地址发起连接。
- **方法论的使用**: 关掉浏览器后跑 `netstat -nao`，把"对端地址奇怪"变成"PID 1234 在连 1.2.3.4:4444"；用 PID 反查进程路径与签名（任务管理器/Process Explorer）；对可疑自启项用 Autoruns 全量枚举并过滤正常项；用 Process Explorer 核对父进程与加载模块；再用 PsLoggedOn 确认本机有谁登录。
- **结论**: 网络异常必须落回"本机的一个进程"，才谈得上判断是否恶意。
- **结果**: 原书以此说明"先看清再处置"——并明确警告"如果你把攻击者的插头拔掉，就丢失了宝贵的取证信息"。

### 示例 2: Linux 主机被入侵的十二条命令基线
- **类型与来源**: 【转述】《网络安全应急响应技术实战指南》· 2.1.2 / 2.2 / 2.4 / 2.5
- **问题/输入**: 一台对外提供 Web 服务的 Linux 主机，疑似被上传 Webshell 并提权。
- **方法论的使用**: 账号线 `awk -F: '{if($3==0)print $1}' /etc/passwd` 查 UID=0 的非 root 账户、`awk -F: 'length($2)==0 {print $1}' /etc/shadow` 查空口令；登录线 `last`/`lastb`/`lastlog`；进程线 `netstat -anpt` 找外连 → `ls -alt /proc/<PID>` 取可执行文件 → `lsof -p <PID>` 取打开的文件；隐藏进程用 `ps -ef` 与 `ls /proc` 做差集；文件线 `find / -ctime 0 -name "*.sh"`、`find /tmp -perm 777`、`find / -perm -04000 -uid 0`；命令替换用 `ls -alt /bin` 比对时间与大小；日志线 `grep "Accepted " /var/log/secure` 统计来源 IP。
- **结论**: 单看 `ps` 会被 hook 欺骗；`ps` 与 `/proc` 的差集才是隐藏进程的判据。
- **结果**: 原书以 PID 2963 的恶意外连、777 权限的 `crloger8`、`/etc/init.d` 下的挖矿启动项等实例演示各条命令的命中形态。

### 示例 3: 任务管理器一开 CPU 就正常（合成演练）
- **类型与来源**: 【合成演练】按本卡 E 段推演；机制出自《136-手把手教你做挖矿应急响应》
- **问题/输入**: 用户报"服务器很卡"，但一打开任务管理器 CPU 就回落到 10%。
- **方法论的使用**: 不采信该读数，改走命令行通道 `wmic cpu get LoadPercentage /value` 连续采样；拿到高占用 pid 后不经任务管理器，直接取进程路径、命令行与启动时间；再比对文件创建时间与进程启动时间，确认"启动的就是这个文件"。
- **结论**: "工具打开后现象消失"本身就是反调试守护的判据，不是"问题不存在"。
- **结果**: 原书作者自述最初误以为是任务管理器导致，分析样本后才发现是守护机制；未给出该演练的实际结果。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 拿到一台可疑主机（或一批），需要一份"从哪查起、查到什么算完"的清单。
2. 单点排查已经做过（只看了进程/只看了启动项），但给不出结论，怀疑有遗漏。
3. 需要交叉验证某条线索：告警说是木马，但进程列表看起来正常。
4. 需要在不能装 EDR/Sysmon 的客户环境里，只用系统自带命令完成排查。
5. 需要在 Windows 与 Linux 混合环境中用同一套"五线"结构组织排查，避免漏项。

### 语言信号（出现这些就该激活）
- 中文：「上机以后从哪查起」「怎么保证排查没漏」「有没有隐藏进程」「任务管理器看不到」「这台机器有没有被搞」「排查清单」
- English: "host triage checklist", "where do I start on a compromised host", "hidden process detection", "linux incident response commands", "what to check first on a suspect machine"

### 与相邻能力的区分
- 与 `ir-evidence-order` 的区别：那张卡是时间轴（先取证后处置），本卡是空间轴（同时看五条线）；两者叠用，本卡的五条线都在"固定证据"与"定位"之间展开。
- 与 `persistence-sweep-windows` 的区别：本卡给"五线并行"的框架与跨平台命令基线；那张卡是"持久化"这一条线的 Windows 深度清单（计划任务、服务、WMI、CLR 等点位级做法）。
- 与 `log-forensics-integrity` 的区别：本卡的"日志"线只做时间线串联；日志源可信度、完整性校验、被清理后的反推在那一张。

## E — 可执行步骤 (Execution)

**必需输入**: 主机访问方式（本地/远程/镜像）、操作系统与版本、事件现象与时间窗、是否允许装工具（Sysinternals/Sysmon/EDR）、业务方联系人（用于确认"某个进程是不是业务程序"）。缺"业务方联系人"时必须先问，否则无法区分业务程序与恶意程序。

**交付物与完成标准**: 一份《主机排查表》，五条线各一节，每条发现含：证据类型、原始值（路径/命令行/pid/时间）、判断（正常/可疑/恶意/待确认）、依据、后续动作。完成标准是"每条可疑项都能被解释或已被证伪"。

1. **访谈与定范围**
   - 做什么：问清事件类型、时间范围、涉及网段与主机、系统架构、近期变更（上线、加账号、开端口）。
   - 完成标准：得到一份排查清单与一个时间窗（精确到小时）。
   - 判停：若时间窗无法确定，先用"最早告警时间 −24h"作初始窗，后续按证据修正。

2. **系统线：账号、启动项、任务、补丁、防火墙**
   - 做什么：Windows 用 `net user` + `lusrmgr` + `wmic useraccount` + SAM 交叉（详见 `persistence-sweep-windows`）；Linux 查 UID=0、空口令、可登录 shell、sudoers 异常、特权组。启动项与计划任务按"枚举全部再过滤"的方式做，不做单点目视。
   - 完成标准：账号清单有基线可比；新增/异常账号有结论；计划任务与自启项逐条可解释。
   - 判停：若发现隐藏账号或隐藏服务，转 `persistence-sweep-windows` 深度处置。

3. **进程线：从外连到文件**
   - 做什么：先降噪（关浏览器等已知联网程序）再 `netstat -nao`；按"异常对端地址 + 异常高位端口"筛候选；用 pid 取路径、命令行、父进程、签名、加载模块。可疑进程先**挂起**观察业务与外连变化，确认后再恢复/终止。
   - 完成标准：每个可疑连接有 pid，每个 pid 有绝对路径与启动参数，且能说明"谁拉起来的"。
   - 判停：若进程已不存在，转第 6 步"守株待兔"或内存镜像分析；若挂起后连接仍在但无数据，不要误判为挂起失败（挂起不必然断连）。

4. **服务线**
   - 做什么：枚举服务注册表全部子键，逐个 `sc query`，捕获取"拒绝访问"的项（SDDL 隐藏的信标）；校验 ImagePath 指向文件的 Authenticode 签名与发布者。
   - 完成标准：服务清单完整（含不可见项），每个非微软签名二进制有结论。
   - 判停：命中"拒绝访问"或非白名单签名，转 `persistence-sweep-windows`。

5. **文件痕迹线**
   - 做什么：按时间窗捞新增文件（`forfiles /m *.exe /d +YYYY/M/D /s /p c:\` 或 `find / -ctime 0`）；查临时目录、用户目录、`$Recycle.Bin`；解析执行痕迹（Prefetch 运行次数与首末时间、Amcache 的 SHA1、ShimCache 是否执行过、UserAssist、SRUM、Jump Lists）；核对创建/修改/访问时间的逻辑矛盾。
   - 完成标准：候选文件清单收敛到可人工复核的量级；每个候选有"是否执行过"的结论。
   - 判停：若 Server 版无 Prefetch/SRUM（原书已在 Server 2016 上验证为空），改用 Amcache + ShimCache + 日志 4688，不要据此断定"没运行过"。

6. **瞬时行为捕获（进程已消失时）**
   - 做什么：把恶意域名在 hosts 中指向固定 IP（同时阻断 C2 与稳定解析），部署轮询脚本：`netstat -ano | findstr <IP>` 命中即 `wmic process where processid=<pid> get name,executablepath,commandline` 追加落盘；等待触发（重启、等定时任务、或用浏览器访问该域名模拟）。
   - 完成标准：结果文件里出现 pid、绝对路径、完整命令行。
   - 判停：若多次等待仍无命中，说明触发条件未满足（时间/用户交互/特定网络），转流量侧回溯（`traffic-hunt-c2`）。

7. **日志线：串时间线**
   - 做什么：按"登录 → 提权 → 落地 → 外连"四类事件拉取，把五条线的发现按时间戳排到一条轴上，标注每个断点。
   - 完成标准：时间线能解释"最早异常是什么、之后每一步是什么"。
   - 判停：若关键日志缺失或被清，转 `log-forensics-integrity` 做完整性反推。

8. **关联推理与结论**
   - 做什么：只保留被两条以上证据线支持的判断；对孤立可疑项标注"待确认"而不是强行定性；输出事件结论（是否真实、入口、影响面、是否仍有驻留）。
   - 完成标准：结论与证据一一对应；"待确认"项有下一步动作。
   - 判停：若结论显示存在多个不同手法的驻留点，转 `incident-scoping`。

## B — 边界 (Boundary) ★

### 不要用的情况
- **纯性能/容量问题**（CPU 高但是业务增长、磁盘满但是日志轮转失败）：没有对手，五线排查会浪费窗口。
- **主机已被重装或镜像已被覆盖**：五条线里至少三条（进程、服务、文件痕迹）已失效，只能做日志与网络侧。
- **容器化环境直接照搬**：Pod 重启即重建文件系统，`/proc` 与文件痕迹的判据不成立，需改用节点侧与运行时层证据。

### 已知失败模式
- **只做进程排查**：找不到无文件载荷、纯计划任务型驻留、WMI 订阅（《windows应急响应手册》多处强调）。
- **五条线各查各的、不做时间线对齐**：得到一堆可疑项却给不出入口（《网络安全应急响应技术实战指南》· 1.4）。
- **先下结论再找证据**：会系统性忽略反向证据（"这个可疑文件其实是运维工具"）。
- **用同一款被 hook 的工具交叉验证**：`ps` 被替换后用另一个基于 `ps` 的脚本验证，结论一致但都错。
- **反复开关任务管理器**：把挖矿进程反复杀掉又拉起，误以为已清理（《136》）。
- **直接 `taskkill` 进程树**：守护进程立刻拉起新实例，同时丢掉内存证据（《windows应急响应手册》· 挖矿 `0x05`）。
- **删文件前不查句柄**：遇到"文件正在使用"，或删完被服务/计划任务重新释放；更糟的是丢掉唯一能定家族的样本。
- **只用 `net user` 判断有无异常账号**：`$` 结尾账户天然不可见。

### 作者与时代的局限
- 《windows应急响应手册》全部结论基于 Windows Server 2016，Prefetch/SRUM/TaskCache 行为在其他版本需复验。
- Sysinternals 的部分工具（如 Autoruns 的过滤默认值）随版本变化，原书截图中的"看不到某类任务"在旧版本上结论可能不同。
- Linux 十二条命令基线偏重 CentOS/Ubuntu 系，对使用 systemd-journald 全量日志、或容器化宿主机的发行版覆盖不足。
- 各书均假设"能上机、能跑命令"。真实场景中常遇到 EDR 拦截、命令被 hook、无管理员权限，原书未给这些受限条件下的替代路径。

### 容易混淆的方法
- **"隐藏进程"与"进程已退出"**：前者是 `ps` 与 `/proc` 不一致，后者是两个来源都没有；处理方向完全不同。
- **"挂起"与"终止"**：挂起保留全部状态但切断行为，可恢复；终止不可逆。
- **"文件时间戳异常"与"时间戳被篡改"**：安装包解压、镜像克隆、时区差异都会造成时间异常；篡改的判据是"修改时间早于创建时间"这类逻辑矛盾，而不是"时间看着不对"。
- **"五线并行"与"五个工具"**：并行指的是证据来源互相独立，不是把五个工具都跑一遍。

### 授权与合规边界
> 待补充（用户自行填写）
