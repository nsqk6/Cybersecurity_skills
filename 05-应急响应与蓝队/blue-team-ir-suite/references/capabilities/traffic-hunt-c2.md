# 流量形状与隐蔽信道狩猎

## R — 原文 (Reading)

> 为不常见的数据流分析网络数据(例如，客户机发送的数据明显多于从服务器接收的数据)。使用通常没有网络通信或从未见过的网络的进程是可疑的。分析数据包内容，以检测不符合所使用端口的预期协议行为的通信。

> — 《ATT&CK手册》· 九 C&C「1.1、常用的端口」→「1.1.3、检测」

> 拿到网络流量后，我们按时间、源IP、源端口、目标IP、目标端口、应用协议这六个元素来标识访问关系及统计访问频率，通过自学习模式生成白名单和profile规则，按照我们的管控规则自定义黑名单，对后续流量按照白名单、黑名单、profile规则的顺序进行匹配

> — 《企业安全建设指南：金融行业安全架构与技术实践》· 13.3.2 异常访问检测系统

> 首先是请求的dns 域名前存在一段加密的字符串，其次dns 记录分布于TX T 记录、MX 记录和CNAME 记录。

> — 《038-内网穿透从搭建到溯源》· 各协议层隧道分析

## I — 方法论骨架 (Interpretation)

这个能力解决的问题是：**流量全程加密、没有解密能力，甚至没有已知恶意 IOC，还能不能发现 C2 与外传。**

答案是能，因为加密藏得住**内容**，藏不住**形状**。可观测的不变量有四类：

1. **方向与比例**：正常客户端下载远多于上传（请求小、响应大）；被控主机与数据外传相反——发送明显多于接收。
2. **节律**：机器比人机械。固定间隔（如每 60 秒 ± 抖动）、固定包长、固定握手序列，是最强的 beacon 特征。
3. **端口—协议一致性**：443 上应该跑 TLS，如果握手字节、证书、后续 record 结构不符合，就是协议错配。反过来，`filtered` 也不是"端口关闭"，而是探测包被中间设备丢弃——它本身是"这里有防火墙"的证据。
4. **关系**：谁在跟谁说话。IDS 看单包特征，抓不到"每个包都合法、关系不合法"的访问（例如分支机构的机器直接 RDP 到总部核心库）。把会话压缩成六元组（时间、源 IP、源端口、目的 IP、目的端口、应用协议）并统计频次，超出历史基线的关系就是异常。

落地时按"由粗到细、由不需解密到需要解密"排序：

- **第一层（无需解密，全网可做）**：关系基线偏离（新出现的关系、消失的关系、频率突变）→ 候选主机名单；
- **第二层（无需解密）**：方向不对称 + 节律机械 + 包长分布异常 → 候选会话；
- **第三层（部分可做）**：端口—协议一致性、TLS 指纹与证书异常（自签、CN 与 SNI 不符、有效期极短）→ 候选 C2；
- **第四层（语义层）**：DNS 域名随机性（DGA）、记录类型异常（TXT/MX/CNAME 承载长随机串）、超长查询名 → 候选隧道；
- **第五层（主机侧闭环）**：把候选会话落回进程 pid，才谈得上定性。

四条纪律：

1. **先有基线再谈异常**。同一现象在不同环境含义相反：备份、更新、日志上报都会命中"方向不对称"；研发环境的多次失败登录是改密码，DMZ 服务器则可能是爆破。
2. **候选不等于结论**。所有判据只产出"候选名单"，定性必须叠加"进程从未联网""目的域从未出现""新注册域名"这类上下文，把量级压到人工可复核。
3. **匹配顺序决定告警量**。频度分析先于名单匹配（先算频率，超阈值即告警），然后白名单命中即忽略、黑名单命中即告警、profile 命中即忽略、全未命中才是"未知流量"——顺序错了，告警会被白名单淹掉或反之。
4. **不依赖 IOC**。对手换基础设施就失效的检测不是检测。形状类判据的价值恰恰在于不依赖已知恶意地址。

## A1 — 应用示例 (Application Example)

### 示例 1: 六元组关系异常抓横向
- **类型与来源**: 【亲历】《企业安全建设指南》· 13.3.2
- **问题/输入**: IDS 告警量很大但抓不到内网横向；已划安全域、有堡垒机与域控。
- **方法论的使用**: 按六元组聚合访问关系并统计频率，用自学习期生成白名单与 profile；上线后按"频度 → 白名单 → 黑名单 → profile → 未知"匹配；策略优先覆盖三类场景——跨区域访问（办公↔业务、总部↔分行、DMZ 主动外连）、重点资产（域控、补丁服务器、堡垒机、网络设备、领导终端、大数据平台）、特殊协议（RDP 非 3389、SSH 非 22、内网出现 PPTP/L2TP/VNC/PCAnywhere）。
- **结论**: 典型判据是"历史上 A 和 B 经常访问 C 的 1433，突然有一天 D 也来访问"；频率类判据是"加入域的办公电脑每天认证次数为个位数，某天某 IP 不断认证"。
- **结果**: 原书以这两类判据说明"协议合法、关系非法"的访问只能靠关系与频率发现。

### 示例 2: 分层判读隧道流量
- **类型与来源**: 【亲历】《038-内网穿透从搭建到溯源》
- **问题/输入**: 内网出现异常流量，怀疑有隧道，但不知是哪种。
- **方法论的使用**: 先判层——ICMP 看单位时间包数量、单包大小、payload 是否为固定填充（正常 ping 是 4 个 32 字节固定字符串，隧道是短时间大量 128 字节且内容含命令回显）；TCP 看短时间大量 ACK 夹杂 PSH、data 段含明文命令；SSH 因全程加密，内容看不出异常，只能看**连接关系**——同一 PID 同时与外网和内网建立连接即端口转发特征；DNS 看查询名前的加密串与记录类型（TXT/MX/CNAME）；HTTP 看请求参数（`cmd`/`target`/`port`）与"参数里的 IP 端口 ≠ 数据包实际 IP 端口"。
- **结论**: 每层都有"与正常流量不同"的统计或结构特征，但作者明确提醒这些特征可被伪装。
- **结果**: 原书用 icmpsh、powercat+nc、SSH 本地/远程/动态转发、dnscat2、reGeorg+Proxifier 逐层实测，并在 SSH 案例中通过"同一 PID 3104 分别与外网和内网建连"确认隧道。

### 示例 3: 长度阈值拦隐蔽信道（合成演练）
- **类型与来源**: 【合成演练】按本卡 E 段推演；阈值与失败边界出自《企业安全建设指南》· 13.3.3
- **问题/输入**: 出口防火墙可配策略，怀疑有人用 DNS 隧道外传数据。
- **方法论的使用**: 设 ICMP 包长阈值（基线 32/56 字节，超阈值丢弃并报警）；设 DNS 长度阈值（UDP > 512 或 TCP > 1024 丢弃并报警）；对 ICMP 加频次规则（单位时间请求数超阈值告警，但不对 DNS 用频次法——终端 DNS 请求量本身大）；收敛 DNS 出口到指定服务器，有条件再阻断 TXT/NULL（注意 SPF 与情报查询会用 TXT）。
- **结论**: 这套办法部署在防火墙上、不依赖全镜像，但"无法完全阻拦有耐心的黑客"。
- **结果**: 原书给出 PTunnel magic `0xD5200880` 的特征示例，并指出"黑客改 magic 重编译就不行了"。本演练不假设阻断成功。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 只有 NetFlow/全流量，没有解密能力，需要判断"有没有 C2"。
2. IDS 说没问题，但主机侧明显异常（CPU 高、DNS 请求暴增），怀疑隧道。
3. 需要区分"正常的大流量"与"数据外传"。
4. 需要发现"协议合法、关系非法"的横向访问。
5. 想要不依赖威胁情报黑名单的检测手段（对手会换 IP/域名）。

### 语言信号（出现这些就该激活）
- 中文：「怎么发现 C2 通道」「加密流量怎么看」「这段流量是不是隧道」「DNS 请求量异常」「内网横向怎么从流量发现」「数据外传怎么查」
- English: "detect beaconing without decryption", "C2 traffic shape", "DNS tunneling detection", "lateral movement network detection", "data exfiltration over encrypted channel"

### 与相邻能力的区分
- 与 `log-forensics-integrity` 的区别：那条看日志（谁登录、跑了什么），本卡看流量（谁在跟谁说话、说了多少）。两者在时间线对齐时互为补证。
- 与 `ir-toolchain` 的区别：本卡给"像不像"的判据；工具卡给"是哪个进程"的定位手段（netsh trace → pcapng → pid）。
- 与 `detection-rule-engineering` 的区别：本卡是单次流量的手工判读与狩猎思路；规则工程把那套判据固化成阈值、关联与告警量约束。

## E — 可执行步骤 (Execution)

**必需输入**: 可用的流量数据（NetFlow / 全流量镜像 / DNS 查询日志 / 代理日志）、观察时间窗、内网网段与重点资产清单、正常业务基线（至少一周）、已知 IOC（可空）。缺"正常基线"时先做一段自学习，不要直接上阈值。

**交付物与完成标准**: 一份《流量狩猎记录》，含：判据层（关系/形状/协议/DNS）、命中会话清单（五元组、字节数、包数、时长、节律）、每个候选的上下文（进程/目的域历史/注册时间）、结论（恶意/业务/待确认）。完成标准是"候选收敛到可人工复核的量级，且每条有结论"。

1. **建立关系基线**
   - 做什么：按六元组聚合访问关系，统计每关系的频率与时段分布，形成白名单与 profile；把管控规则写成黑名单。
   - 完成标准：基线覆盖主要业务时段（含工作日与周末）。
   - 判停：若自学习期已混入攻击流量，白名单会被污染，必须用"资产清单 + 业务访谈"复核一遍再上线。

2. **找关系异常**
   - 做什么：筛"新出现的关系"（历史从未出现）、"消失的关系"（本该有却没有）、"频率突变"（数量级变化）、"跨区域直连"（办公→业务、分支→总部核心、DMZ 主动外连）。
   - 完成标准：每个异常关系有主机归属与业务解释。
   - 判停：命中重点资产（域控、堡垒机、数据库）的异常关系，立即转第 5 步做主机侧闭环。

3. **找形状异常**
   - 做什么：按会话统计上下行字节比（发送远多于接收优先）；检查包长分布（固定大小/固定分片）；检查时间间隔（固定周期 ± 抖动）；标记"机器节律"会话。
   - 完成标准：形成候选会话名单，标注每条命中的判据。
   - 判停：叠加"进程从未联网""目的域从未出现"两条上下文后仍剩余大量候选，说明基线不合格，回第 1 步。

4. **协议一致性校验**
   - 做什么：对可疑会话检查端口与协议是否自洽（443 是否真是 TLS 握手、证书是否自签/CN 与 SNI 不符/有效期极短）；对 DNS 检查记录类型（TXT/MX/CNAME 承载长随机串）、查询名长度与熵、单位时间查询数；对 ICMP 检查包长与 payload。
   - 完成标准：错配项单独列出，并给出"是伪装 C2 / 是内部自研协议 / 是业务代理"的判断。
   - 判停：若为目标资产且协议错配，按高优先级处置，不必等进程定位。

5. **主机侧闭环**
   - 做什么：把候选会话的目标 IP/端口拿到主机上比对 `netstat -ano`（Windows）或 `ss -anpt`（Linux），取 pid → 进程路径 → 命令行 → 启动时间；对瞬时连接用 hosts 固定 + 轮询脚本捕获；对隧道用抓包取 pid。
   - 完成标准：每个候选会话对应到一个可解释的进程。
   - 判停：若流量侧命中但主机侧无对应进程（时间已过），转"守株待兔"或抓包方案，不要据此否定流量判据。

6. **DGA/域名层判断**
   - 做什么：对 DNS 日志中的域名计算随机性分数（N-Gram 或熵）；排除白名单（CDN、常用 SaaS、内部域）；对高分且非白名单域名叠加旁证（首次出现、注册时间短、解析失败率高）。
   - 完成标准：候选域名可人工复核；白名单来源可审计。
   - 判停：纯靠分值告警会误伤 CDN，必须叠加旁证才能定性。

7. **输出与移交**
   - 做什么：把结论分成"恶意/业务/待确认"三类；恶意项给 IOC 与阻断建议；待确认项给下一步观察指标；把可固化的判据移交规则工程。
   - 完成标准：每条结论有证据与判据；移交项有责任人。
   - 判停：若同一判据反复误报，回 `detection-rule-engineering` 调整阈值或加白，而不是关闭判据。

## B — 边界 (Boundary) ★

### 不要用的情况
- **无基线的新环境**：直接套阈值必然误报，先做自学习。
- **纯加密且无元数据的场景**（只有加密 payload、无流统计）：形状判据失效，需靠端点侧。
- **业务本身就是"上传为主"**（视频监控回传、备份、日志外送、代码推送）：方向不对称判据在这类网段上无意义。
- **只有单包、无会话聚合能力**：关系与频率判据都需要会话级数据。

### 已知失败模式
- **只用恶意域名/IP 情报匹配**：对手换基础设施即失效。
- **仅凭方向不对称定性**：备份、更新、日志上报都会命中。
- **把压缩/分片外发当普通大流量**：基于固定阈值的检测会失效（《ATT&CK手册》· 十 Exfiltration）。
- **对 DNS 用频次法**：正常解析量大且习惯各异，误报极高。
- **把 `filtered` 当"端口关闭"**：它是"探测包被丢弃"，恰恰说明中间有过滤设备。
- **把端口号当服务身份**：443 上可能是自定义协议，8443 上可能是正常业务。
- **只看单一协议**：攻击者换层复用（ICMP → DNS → HTTPS → WebSocket）。
- **把特征当铁律**：原书明确说"如果隧道程序想做，完全可以做到和正常网络连接没区别"。

### 作者与时代的局限
- 六元组方案成型于 2015 年前后，对 QUIC/HTTP3、DoH/DoT、域前置（domain fronting）、CDN 隧道这些"把 C2 藏在合法大流量里"的手法覆盖不足。
- TLS 指纹（JA3/JA4）与证书透明度日志在原文中未涉及，属于本卡之外可叠加的现代判据。
- 长度阈值类手段（ICMP 32/56、DNS 512/1024）依赖"攻击者不做分片/不伪装"，对耐心对手基本无效，原书作者自己承认这一点。
- 各书均假设能看到出口流量；在 BYOD、远程办公、纯云环境下采集点缺失，方法不成立。

### 容易混淆的方法
- **"异常访问检测"与"入侵检测"**：前者看关系与频率，后者看载荷特征；两者检测的是不同层的事实。
- **"隧道"与"代理"**：隧道是把一种协议封装在另一种里，代理是转发；前者看封装特征，后者看连接图。
- **"beacon 节律"与"心跳"**：业务心跳也是固定周期（如每 30 秒健康检查）；区别在于目的是否出现过、进程是否该联网。
- **"外传"与"同步"**：云盘同步、代码推送、日志上报都是"发送多于接收"，必须结合资产角色判断。
