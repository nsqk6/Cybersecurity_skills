# 影响范围圈定与攻击链回溯

## R — 原文 (Reading)

> 定损过程就是确定受害范围的过程 …… 统计出与受害系统使用了相同密码的服务器 / 统计出与受害系统部署了相同存在漏洞或特有服务的服务器

> — 《windows应急响应手册》· 善后阶段 · `0x01 定损`

> 上下跳的线索都断了，只能从头开始排查其他服务器。

> — 《128-记一次内网失陷的应急响应》· 现场应急

> 很多防守方队员会仅仅只处理告警设备中对应告警IP 的服务器，而忽略了对攻击链的梳理，从而导致尽管处理了告警，但仍未能将蓝队排除在内网之外。

> — 《蓝队视角下的防御体系突破》· 第四章 九、多点潜伏

## I — 方法论骨架 (Interpretation)

这个能力解决的问题是：**一台机器确认失陷后，"还有没有别的"和"从哪进来的"这两个问题都必须回答，否则清理等于没做。**

它有两个方向，必须都走：

**方向一：从已知受害点向外推（定损）。** 不靠猜，靠找共性。六个可枚举的维度：相同密码、相同漏洞或特有服务、同一管理人员、可用 SSH 密钥直登、可用 RDP 已保存凭据直登、受害期间频繁交互。前四个回答"攻击者能顺着什么过去"，后两个回答"这台机器平时和谁说话"。取并集后按规模分流：数量少则逐台走常规安全检查；数量多则用安全设备看这些机器是否发起过攻击，并强制改密（每台不同）。

注意五个常被忽略的点：
- **密钥直登与 RDP 已保存凭据不需要知道密码**，所以"改密码"这一招对它们完全无效；
- **负载均衡后端是天然的"同漏洞"集合**，一台中招意味着同组都可能中招；
- **改密不能批量改成同一个新口令**，否则把定损结果重新合并成一组新的共性；
- **同一镜像批量部署的机器**是"同口令 + 同漏洞"的双重命中；
- **受害期间频繁交互**要用内网 DNS、流量、堡垒机日志来算，不能凭印象。

**方向二：从证据残片向前回溯（攻击链）。** 真实入侵的日志一定是残缺的：应用默认不开访问日志、history 被清、安全日志被删。所以推进方式不是"补全一条完整链"，而是**每条链各取一段，用时间戳对齐；某个节点没日志就放弃它，换下一个还留着日志的节点**。这是本能力最核心的动作——换节点，而不是死磕。

可用的节点类型与它们各自的"幸存证据"：

| 节点 | 幸存证据 |
|---|---|
| 应用服务器 | 部署包/`war`/`jar` 上传时间、应用版本、Web 访问日志、中间件日志 |
| 反向代理/Nginx | access log（常是唯一记录了真实来源 IP 的地方） |
| 域控 | 远程登录日志、杀软告警、隔离区文件、杀软信任区 |
| 堡垒机 | 登录日志 + **操作录屏**（非文本证据） |
| VPN | 登录成功/失败记录、是否有爆破痕迹 |
| 终端 | 密码本、邮件附件、隐藏扩展名的可执行文件、文件创建时间 |
| 网络设备 | NetFlow、DNS 查询、防火墙 permit/deny |

第三层是**入口反推**，两类典型：

- **Web 类**：由 Webshell/被篡改文件的创建时间锁定时间窗 → 在该窗口的 Web 日志里找异常 URI/参数/UA → 定位可控参数 → 隔离环境复现 → 清马 + 修漏洞。关键陷阱：**默认日志不记 POST body**，所以"日志里没有上传记录"不能否定上传，要看接口与参数行为。
- **服务暴露类**：枚举受害主机的监听端口 → 映射到组件（6379 Redis、389 LDAP、445 SMB、3690 SVN、50070 Hadoop、8080 Tomcat）→ 核对是否默认无认证/默认口令 → 查访问日志与文件时间确认是否被利用。大量失陷不是被 0day 打进来，而是某个组件以默认配置暴露。

最后必须防的一个反模式：**只处理告警 IP 那台机器**。攻击者刻意用不同的 Webshell、不同的后门程序、不同的协议建立多个特征不同的据点，清掉最显眼的那个，其余转静默，等防守松懈再复活。清理完成后必须观察一段时间（外连、DNS、异常登录），确认无复活才算结束。

## A1 — 应用示例 (Application Example)

### 示例 1: 十步跨节点回溯一条完整入侵链
- **类型与来源**: 【亲历】《128-记一次内网失陷的应急响应》
- **问题/输入**: 内网多台机器告警，但不知道入口在哪。
- **方法论的使用**（按原书推进顺序）:
  1. 从告警点入手：网络连接 → 进程 → 确认是**定时任务反弹 shell**，拿到反弹周期与目标；
  2. 查定时任务日志，取**最早**一次反弹时间，作为入侵时间下界；
  3. `secure` 日志无异常 → 转查应用：部署了什么、版本多少 → 对出 JBoss 4.0.5.GA / CVE-2017-7504；
  4. 用应用产物时间佐证：`war` 包上传时间 7/2 2:24，与 2:35 的反弹吻合 → 确认入口；
  5. 上一跳无线索（JBoss 默认不开 access 日志）→ **换节点**：查其他告警主机，从 Webshell 访问日志经 nginx access 拿到真实来源 IP；
  6. 追到主域控：杀软告警 → `frpc.ini` 里的外连 IP；隔离文件 → shellcode 加载器与 CS 地址；杀软信任区 → `mimi.exe`；
  7. 安全日志被删 → 改查远程登录日志，拿到 RDP 来源与时间；
  8. 堡垒机：登录日志 + **操作录屏**确认操作范围、可疑登录用户与时间；
  9. VPN：查该用户登录记录，**1 次登录成功、无爆破痕迹** → 倾向口令泄漏而非漏洞；
  10. 访谈 + 办公机取证：桌面密码本、可疑邮件附件、隐藏扩展名的可执行文件、沙箱行为、释放文件创建时间 → 全链时间自洽。
- **结论**: 一起通过钓鱼邮件打穿内网的案例。
- **结果**: 原书以此链完成定性，并明确"上下跳的线索都断了，只能从头开始排查其他服务器"是推进常态。

### 示例 2: Webshell 反推上传接口
- **类型与来源**: 【转述】《网络安全应急响应技术实战指南》· 6.2 案例、7.3 错误处置
- **问题/输入**: 网站根目录发现 Webshell，文件创建时间 2017-07-08 01:02:10。
- **方法论的使用**: 以创建时间为锚点查该时刻前后的 Web 日志；日志中**没有上传记录**（默认不记 POST body），但存在可疑 Webservice 接口，`buffer`/`distinctPath`/`newFileName` 三个参数均可自定义 → 在隔离环境复现，确认可任意文件上传 → 清马 + 修漏洞 + 系统层排查是否已提权。
- **结论**: "日志里没有上传记录"不能作为"不是上传进来"的依据。
- **结果**: 原书复现后确认该接口可写入任意文件；并把"只用备份恢复 / 只删 Webshell"列为错误处置方法（漏洞仍在，很快二次被篡改）。

### 示例 3: 六维定损的清单化（合成演练）
- **类型与来源**: 【合成演练】按本卡 E 段推演；维度与判据出自《windows应急响应手册》· `0x01 定损`
- **问题/输入**: 一台对外 Web 服务器确认被控，需要判断内网还有多少台处于同一风险面。
- **方法论的使用**: 拉六张清单——同密码（含统一运维口令、批量镜像默认口令）、同漏洞/同特有服务（同版本中间件、同 LB 后端）、同管理员、可 SSH 密钥直登、可 RDP 已保存凭据直登、受害期间频繁交互；取并集后按数量分流；改密时每台不同。
- **结论**: 定损的输出不是"结论"而是"清单 + 处置分流"。
- **结果**: 原书未给出该演练的具体数量；《076》的复盘指出"禁止外网访问后，大部分病毒扩散都是因为内网服务器使用了同一套口令"，可作为"同密码"维度的典型后果。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 一台机器确认失陷，需要回答"还有没有别的机器"。
2. 需要写事件报告的"影响范围"章节，但只有零散证据。
3. 内网失陷但不知道入口，日志多处缺失。
4. 网站被挂马/被传 Webshell，需要找上传点。
5. 清理完仍有告警，怀疑存在多点潜伏。

### 语言信号（出现这些就该激活）
- 中文：「这台机器中招了，还有没有别的」「怎么确定影响范围」「内网失陷了但不知道从哪进来的」「webshell 怎么找源头」「清完过两天又中了」
- English: "blast radius of this compromise", "how to scope a compromised host", "trace intrusion path with missing logs", "webshell root cause", "multiple backdoors on one host"

### 与相邻能力的区分
- 与 `ir-evidence-order` 的区别：那张卡的第 6 段只是"善后定损"的入口；本卡把定损与回溯做成完整方法。
- 与 `containment-decisions` 的区别：本卡回答"范围有多大、怎么进来的"，那张回答"现在挡住什么"。多点潜伏场景下本卡必须先于清理完成。
- 与 `attacker-attribution` 的区别：本卡追的是"攻击怎么走"，那张追的是"攻击者是谁"。前者是技术与时间线，后者是身份与线索交叉。

## E — 可执行步骤 (Execution)

**必需输入**: 已知受害主机与 IOC、资产与账号台账、堡垒机/RDP/VPN 记录、网络拓扑与数据流、Web/中间件日志留存情况、访谈对象（系统/应用/网络管理员）。缺"资产与账号台账"时本卡会退化为凭印象，必须先补。

**交付物与完成标准**: 一份《范围与攻击链报告》，含：六个维度的清单与并集、每台主机的排查结论、攻击链时间线（含断点与替代证据源）、入口判定与依据、残留风险清单。完成标准是"并集内每台机器有结论，攻击链每个转折有证据或明确标注为推断"。

1. **定损六维枚举**
   - 做什么：与网络安全负责人、系统管理员、应用管理员、网络管理员对表，逐维拉清单（同密码 / 同漏洞或同特有服务 / 同管理员 / 可密钥直登 / 可 RDP 已保存凭据直登 / 受害期间频繁交互）。
   - 完成标准：六张清单齐全，每张有来源与时间。
   - 判停：若并集主机数超过逐台处理能力，转批量处置（`containment-decisions`），但仍需保留清单用于后续抽查。

2. **并集分流处置**
   - 做什么：数量少→逐台走常规安全检查；数量多→用安全设备看这些机器是否对内/对外发起过攻击，并强制改密（每台不同、强口令）。
   - 完成标准：每台有"已查/待查/已改密/已隔离"状态。
   - 判停：若发现某台在并集外但行为相似，扩大维度重跑第 1 步。

3. **建立时间锚点**
   - 做什么：从可用证据里找最早、最确定的几个时间点（定时任务最早反弹、Webshell 文件创建时间、`war` 包上传时间、加密文件最早时间、告警首次触发）。
   - 完成标准：至少两个独立锚点，且相互不矛盾。
   - 判停：锚点互相矛盾时，先校验时区与时钟同步，再判断哪个证据源更可信（参考 `log-forensics-integrity` 的分级）。

4. **逐跳回溯（换节点，不死磕）**
   - 做什么：从当前节点找"上一跳"证据；若无，换一个还留着日志的节点（应用 → 代理 → 域控 → 堡垒机 → VPN → 终端）。每跳记录：时间、来源、证据类型、结论。
   - 完成标准：链条能连到"人"或"入口"，中间断点有替代证据源。
   - 判停：连续两个节点无线索时，转第 6 步从入口侧反推，不要继续在同一节点深挖。

5. **入口反推（Web 类）**
   - 做什么：用文件创建时间定窗 → 查该窗口 Web 日志（URI/参数/UA/来源）→ 代码审计找可控参数 → 隔离环境复现 → 清马 + 修漏洞 + 系统层排查。
   - 完成标准：能指出"哪个接口的哪个参数导致写入"，并已复现。
   - 判停：无法复现时标注"入口推断"，不要写成"确认"。

6. **入口反推（服务暴露类）**
   - 做什么：`netstat`/`ss` 列全部监听端口 → 映射组件 → 逐项核对认证状态（Redis 直连、LDAP 匿名、SMB 弱口令、`.svn`/`.git` 残留、中间件默认口令）→ 查访问日志与文件时间确认利用时点。
   - 完成标准：每个暴露面有"已收敛/已确认被利用/未利用"的结论。
   - 判停：发现未授权访问就只改口令、不做主机排查，是典型漏项——必须同时查持久化。

7. **多点潜伏检查**
   - 做什么：假设"还有第二套"，用与本次完全不同手法做一次全量持久化普查（`persistence-sweep-windows` 或 Linux 对应面）；检查同一 Webshell 是否在多台出现、是否存在异构后门。
   - 完成标准：全部持久化点位有结论。
   - 判停：发现第二套手法即判定为对抗性植入，清理必须一次性覆盖全部已知据点，并禁止把本地磁盘/剪贴板挂载到受害机。

8. **观察与收尾**
   - 做什么：清理后持续观察外连、DNS、异常登录、新增文件（至少一个业务周期）；把入口修复项与控制项落到责任人。
   - 完成标准：观察期内无复发；改进项进入跟踪表。
   - 判停：若复发，回到第 4 步重做回溯，而不是重复清理同一处。

## B — 边界 (Boundary) ★

### 不要用的情况
- **单机、无内网连接、无凭据复用**：六维定损会得出"只有一台"，此时直接处置即可，不必展开全链回溯。
- **纯外部扫描/暴力破解未成功**：没有立足点，不需要攻击链回溯，转暴露面收敛。
- **资产台账完全缺失且无法访谈**：六维枚举无法完成，只能给"无法定损"的结论，不能编造范围。

### 已知失败模式
- **只处理告警那台机器**：攻击者刻意多点、异构，清掉最显眼的据点，其余转静默（《蓝队视角下的防御体系突破》· 多点潜伏）。
- **在一台机器上死磕**：history 被清就认为无解（《128》的推进方式正相反——换节点）。
- **只看文本日志，忽略操作录屏与用户访谈**：堡垒机录屏常是唯一能还原"攻击者做了什么"的证据。
- **拿到一层就停止**：追到"内网失陷"就结案，不问"怎么进来的"，入口永远不堵。
- **把"同密码"当唯一定损维度**：漏掉密钥直登与 RDP 已保存凭据——这两条不需要口令。
- **批量改成同一新口令**：制造新的共性。
- **因日志无 POST 内容就否定上传入口**：方向直接错。
- **只清 Web 层不做系统层排查**：漏掉提权后的持久化。
- **清理后立刻关闭监控**：无法判断是否复活。

### 作者与时代的局限
- 六维定损面向"口令/漏洞/管理员"这类传统横向路径，对"云 IAM 角色继承""K8s ServiceAccount 跨命名空间""CI/CD 凭据链"覆盖不足。
- 跳板链案例是单次实战，其推进顺序依赖于该环境恰好保留了 nginx/堡垒机/VPN 日志；换到日志全无的环境，方法需退化为纯终端取证。
- 入口反推高度依赖"日志时间与文件时间同步"，原书未讨论时钟漂移的处理。
- 原书案例以 Windows + JBoss 为主，对现代微服务（容器重建、滚动发布）中的"文件创建时间"可靠性未做讨论——容器里文件时间常是镜像构建时间，不是落地时间。

### 容易混淆的方法
- **"定损"与"资产梳理"**：定损是从已知受害点向外推，资产梳理是从全量资产向内收。
- **"攻击链回溯"与"日志分析"**：前者核心动作是换节点，后者是在一个节点上读细。
- **"入口"与"据点"**：入口是进来的地方（漏洞/口令/钓鱼），据点是进来后待的地方（后门/账号/服务）；修入口不等于清据点。
- **"复现"与"推断"**：复现要求能在隔离环境重现该请求产生该结果；推断只是逻辑上可能。

### 授权与合规边界
> 待补充（用户自行填写）
