# 攻击者身份溯源

## R — 原文 (Reading)

> 一般来说我们劫持到的数据有u i d 、邮箱、手机号、登录名或真实姓名等

> 从一封邮件，一个域名，逐步探索出许多条信息，根据种种线索的指向，到最后汇集到了同一个人完成了闭环。

> — 《115-钓鱼邮件溯源之你写给我的信不是这么说的》· 分析溯源

## I — 方法论骨架 (Interpretation)

这个能力解决的问题是：**已有攻击者的某个锚点（一个 uid、一个域名、一封邮件、一次扫描连接），能不能收敛到"是谁"。**

前提认知：**单条线索永远不足以指认一个人**。whois 可以没有注册电话，手机号可能未注册，社交账号可能被冒用，代理 IP 后面是几十万人。可靠的方法不是"找到决定性证据"，而是**用多条弱线索收敛，直到所有线索指向同一个对象**——即"闭环"。闭环的判据是：至少两条**互相独立**的线索（不同平台、不同数据来源、不同时间）指向同一人，且没有反证。

三条主流起点，各自的机制不同：

**起点一：受控页面劫持（攻击者来访问我的页面）。** 利用 `script` 标签的 `src` 不受同源限制，在自建/伪装页面或钓鱼邮件页面植入 jsonp 劫持代码，回调时把访问者的 cookie/uid 带到自己的收集端。得到 uid 后向外扩：uid → 手机号/邮箱 → 用运营商公开号段规则把被隐藏的手机号"枚举"出来（前 3 位运营商 + 中间 4 位归属地 + 1 位 + 后 3 位，若已知活动地区可把候选压到几百个）→ 手机号反查邮箱 → 实名信息 → 职场类应用搜手机号拿任职信息。每一步都是用**一个平台的设计功能**去补上**另一个平台缺失的字段**。

**起点二：协议特性反取（攻击者来连我的服务）。** 蜜罐只记录行为是不够的；某些协议允许服务端主动向客户端索取数据。MySQL 的 `LOAD DATA LOCAL INFILE` 就是典型：文件读取请求由**服务端**发起、**客户端**执行并回传。所以冒充服务端即可指定读取客户端本机任意文件。两个包足够：Greeting 包完成握手，Response TABULAR 包发出读文件请求。若把文件名换成 UNC 路径，客户端会用本机 NTLM hash 去认证，配合监听端即可拿到 Net-NTLM hash。同类思路还有：构造特定响应让客户端发起 DNS/HTTP 请求，从而暴露内网出口与主机名。

**起点三：文档/基础设施线索（攻击者留下了一封邮件或一个域名）。** 沿"注册痕迹"这条主线铺开：邮件里的域名 → 解析地址 → whois（注册商、注册邮箱、注册时间）→ 用该邮箱反查还注册过哪些域名 → 访问新站点拿到客服 QQ/电话 → 电话/QQ 在多平台交叉（微信、支付宝、职场类 App）→ 实名校验 → 与已有记录比对。"查不到"也是信息：可能该号为虚假号或未注册，应换一条线索而不是放弃。

三条纪律：

1. **锚点优先**。先找能区分个体的字段（uid、邮箱、手机号、微信号），而不是先看 IP。攻击者普遍用代理，IP 只能定位到出口，需看 `X-FORWARDED-FOR` 或拿下代理服务器才能看到真实来源。
2. **隔离环境操作**。访问钓鱼站点、打开附件、连蜜罐，全部在隔离环境；不要在宿主机上直接打开。
3. **闭环才算结论**。单一平台的结论只能作为"线索"，写进报告时必须标注置信度。

## A1 — 应用示例 (Application Example)

### 示例 1: jsonp 劫持 → uid → 实名
- **类型与来源**: 【亲历】《086-记一次某大型活动溯源红队身份》
- **问题/输入**: 演习期间需要确认攻击方身份。
- **方法论的使用**: 在自建/伪装系统中植入 jsonp 劫持代码，诱使攻击方访问；回传数据落盘（`data.php`），提取 uid/邮箱/手机号/登录名/真实姓名；手机号不完整时按"前 3 位 + 归属地 4 位 + 1 位 + 后 3 位"生成候选，用号段库筛选；手机号反查邮箱、邮箱反查其他注册站点（whois 反查同邮箱注册的域名）；支付宝读取实名（不实际转账）；职场类 App 搜手机号拿任职信息；多源交叉确认。
- **结论**: 溯源的目标不是 IP 而是人；每条线索都是用一个平台的功能补另一个平台的空白。
- **结果**: 原书称最终关联出真实姓名与入职信息；本卡不引用具体身份，仅保留方法链。

### 示例 2: 伪造 MySQL 服务端取回客户端文件
- **类型与来源**: 【亲历】《142-溯源反制之MySQL蜜罐研究》
- **问题/输入**: 希望反制来扫描/爆破的客户端，拿到其本机信息。
- **方法论的使用**: 起假 MySQL 服务监听 3306 → 回 Greeting 包（版本可伪造，如 8.0.12）→ 收到登录请求后回认证成功 → **等客户端先发来第一条查询**（`SET NAMES utf8mb4` 之类）→ 回 Response TABULAR 包（`chr(len(filename)+1) + "\x00\x00\x01\xFB" + filename`）指定目标文件 → 收数据。要骗过扫描器还需按其探测顺序回应 `SHOW VARIABLES`、`SHOW WARNINGS`、`SHOW COLLATION`。取微信身份：先读 `C:\Windows\PFRO.log` 找用户名，再读 `WeChat Files\All Users\config\config.data` 取 wxid → 生成二维码 → 扫码加好友。取 NTLM：文件名设为 UNC 路径 + `responder` 监听。
- **结论**: 协议特性本身可以被防守方利用；不需要恶意客户端，只需要它按协议正常响应。
- **结果**: 原书成功读到攻击者 `C:/1.txt`，并让 SNETCracker 判定为弱口令。同时明确失败边界：bettercap 实现"不支持二进制与大于 16KB 的文件"，且客户端必须先发一次查询才有时序正确性。

### 示例 3: 一封钓鱼邮件的 whois 链（合成演练）
- **类型与来源**: 【合成演练】按本卡 E 段推演；链条形态出自《115-钓鱼邮件溯源》
- **问题/输入**: 员工收到一封"返京疫情统计"邮件，只有一个域名可用。
- **方法论的使用**: 提取邮件要素（主题、域名、发件人显示名）→ 沙箱访问站点看是否收集信息后跳转真站 → 查解析与 whois（本例无注册电话，但有注册邮箱）→ 用注册邮箱反查其他域名 → 访问新站拿客服 QQ/电话 → 电话在微信/支付宝查不到（记录为"查不到也是信息"）但绑定 QQ → QQ 反查微信拿到手机号 → 手机号做实名校验 → 与已有记录比对。
- **结论**: 七步里每一步都可能断，靠"换平台"继续，而不是靠"更努力地查同一个平台"。
- **结果**: 原书作者称所有线索最终指向同一人形成闭环；本演练不假设具体身份，只演示链条结构。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 演习/实战后需要给出"攻击方是谁"的结论，而不是只有 IP。
2. 收到钓鱼邮件，需要判断是谁发的、是否与已知团伙相关。
3. 有扫描器/爆破工具在打自己的蜜罐，想反查其来源与工具使用者。
4. 已有零散线索（一个手机号、一个域名、一个 uid），需要判断能否闭环。
5. 需要评估"现有线索是否足以支撑结论"，避免在报告里写过头。

### 语言信号（出现这些就该激活）
- 中文：「想溯源攻击队是谁」「这封钓鱼邮件是谁发的」「拿到了手机号怎么往下查」「蜜罐怎么拿到攻击者信息」「只有一封邮件怎么溯源」
- English: "attribution from a single uid", "trace a phishing email to a person", "whois pivot", "rogue MySQL server read client files", "de-anonymize an attacker"

### 与相邻能力的区分
- 与 `incident-scoping` 的区别：那张追"攻击怎么走"（路径与范围），本卡追"是谁"（身份与线索交叉）。两者常并行：路径给出时间与地域，身份给出人。
- 与 `containment-decisions` 的区别：本卡不做处置；但溯源结果会影响处置（例如确认是内部人员则范围完全不同）。
- 与 `detection-validation-coverage` 的区别：蜜罐在本卡是"取证与反取"工具，在那一张是"高置信度告警源"。

## E — 可执行步骤 (Execution)

**必需输入**: 起始锚点（uid/邮箱/手机号/域名/邮件原文/IP）、可用的查询手段（whois、反查、号段库、平台账号）、隔离分析环境、已有线索库（用于去重与交叉）。缺"起始锚点"时先做采集（布点/蜜罐/邮件头分析），不要凭猜测开始。

**交付物与完成标准**: 一份《溯源线索表》，每行含：线索值、来源平台、获取方式、时间、置信度、与其他线索的关系（一致/冲突/无关）。完成标准是"至少两条独立线索指向同一对象，或明确结论为'无法闭环'"。

1. **选起点并采集锚点**
   - 做什么：按场景选三条路径之一——布点劫持（页面/邮件）、蜜罐反取（协议特性）、文档与基础设施（邮件/域名）。
   - 完成标准：拿到至少一个可区分个体的字段（不是 IP）。
   - 判停：若只拿到代理 IP，先看 `X-Forwarded-For`、时间戳与 UA 特征，仍无法区分则转其他起点。

2. **锚点扩展（第一跳）**
   - 做什么：uid → 邮箱/手机号；邮箱 → 同邮箱注册的其他域名；域名 → whois（注册商/注册邮箱/注册时间）；手机号 → 归属地与号段。
   - 完成标准：每个新字段标注来源与获取时间。
   - 判停：若某平台返回空，记录"查不到"并换平台，不要在同一平台反复尝试。

3. **枚举补全（信息不完整时）**
   - 做什么：手机号缺位时用"运营商前 3 位 + 归属地 4 位 + 1 位 + 后 3 位"生成候选，结合已知活动地区缩小范围，再逐个校验。
   - 完成标准：候选集收敛到可人工核对的量级。
   - 判停：候选过多且无地区线索时，放弃枚举，转其他锚点。

4. **跨平台交叉**
   - 做什么：用同一标识在多个平台检索（邮箱、手机号、QQ、微信、职场类应用、代码托管、论坛）；记录每个平台的"有/无/不一致"。
   - 完成标准：形成交叉矩阵（标识 × 平台）。
   - 判停：出现明显冲突（同名不同人）时，把冲突项单列，不要为了闭环强行合并。

5. **闭环判定**
   - 做什么：检查是否满足"两条以上独立线索指向同一对象"且"无反证"；独立指不同数据来源、不同获取方式。
   - 完成标准：结论有置信度（高/中/低）与依据。
   - 判停：不满足时输出"无法闭环"，并把已得线索归档供后续使用。

6. **蜜罐反取（使用协议特性时）**
   - 做什么：按协议时序实现服务端（以 MySQL 为例：Greeting → 认证成功 → 等首条查询 → Response TABULAR）；按扫描器探测序列回应常见查询以维持"可信服务"假象；记录客户端回传的数据与连接元信息。
   - 完成标准：拿到客户端本机文件或认证材料，且记录完整时序。
   - 判停：若客户端不发首条查询、或文件超过实现上限（原书实现为 16KB），换目标文件或换协议，不要期待"大文件"。

7. **归档与移交**
   - 做什么：把线索表、原始回传数据、时序记录归档；标注哪些字段可用于后续布点（如下次用同一 uid 关联）。
   - 完成标准：他人可据此复现每一步查询。
   - 判停：涉及个人信息的字段按内部流程处理，不在报告正文扩散。

## B — 边界 (Boundary) ★

### 不要用的情况
- **只有 IP**：代理/NAT/云主机环境下 IP 基本不具备个体区分力，继续投入产出比极低。
- **攻击者使用一次性身份**（一次性邮箱、虚拟号、临时设备）：链条会在第一跳就断，不要强行推演。
- **需要"确定性结论"的场合**（司法、对外通报）：本卡产出的是"线索收敛"，不是证据链；证据要求另立。
- **蜜罐反取用于非自控资产**：只能对自己拥有/控制的蜜罐与服务实施，对第三方系统套用同一手法属于另一类行为。

### 已知失败模式
- **拿到代理 IP 就停止**：没看 `X-Forwarded-For`，也没考虑拿下代理服务器看连接。
- **只靠单一平台结论**：同一手机号可能被冒用或未注册。
- **把"查不到"当"不存在"**：查不到本身是信息（虚假号/未注册），应换线索而非结案。
- **威胁情报"无异常"就判定无害**：钓鱼域名常未被标记（《115》明确指出本例情报未发现异常）。
- **在宿主机直接打开钓鱼链接/附件**：分析行为本身导致失陷。
- **jsonp 劫持后不回传落盘**：数据只在内存/控制台，事后无法复核。
- **MySQL 蜜罐时序错误**：不等客户端首条查询就发 TABULAR 包，客户端直接断开。
- **只回认证成功不回后续包**：扫描器不认为爆破成功，攻击者不会来连。

### 作者与时代的局限
- jsonp 劫持依赖目标浏览器允许跨域 `script` 加载且未做 CSP/隔离，现代浏览器与企业策略下成功率显著下降。
- 手机号枚举依赖"号段可枚举、平台无频率限制"，各平台风控升级后该方法基本失效。
- 微信/支付宝类平台的接口与可查字段随时间变化极大，原书的具体路径不可照搬。
- 蜜罐反取的实现（bettercap 版）明确不支持二进制与大文件，实用性受限。
- 各书均未讨论溯源结论的错误代价（误指认），也未给"排除法"流程。

### 容易混淆的方法
- **"溯源"与"反制"**：溯源是识别身份，反制是对攻击者资产采取动作；前者是分析，后者是另一类行为，不能混为一谈。
- **"线索"与"证据"**：前者可来自公开查询，后者需可验证、可复现、来源可追溯。
- **"蜜罐记录"与"蜜罐反取"**：前者只观察行为，后者主动向客户端索取数据，能力与风险都不同。
- **"同名"与"同一人"**：同名、同头像、同昵称都不构成关联，必须有可验证的标识（手机号、邮箱、实名）交叉。
