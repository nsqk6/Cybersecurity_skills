# 检测覆盖度与有效性验证

## R — 原文 (Reading)

> 白盒检测（过程验证）是指建立自动化验证平台，对安全防护框架的管控措施实现100%的全面验证，并可视化集成至安全运维平台中，管控措施失效能够在24小时内发现。

> — 《企业安全建设指南：金融行业安全架构与技术实践》· 20.2 安全验证框架

> 只有当横向和纵向结果中都显示监控正常，才认为是监控正常；否则均认为是有问题的，需要进行整改，确保不会遗漏。

> — 同上 · 22.2 矩阵式监控

> 工程能力决定入侵发现效果 …… 入侵检测的本质：采集数据标记异常

> — 《大型互联网企业的入侵检测》· 工程能力决定入侵发现效果

## I — 方法论骨架 (Interpretation)

这个能力解决的问题是：**"设备装了、规则写了、告警没响"，到底是没攻击，还是坏了？**

管控措施失效是**静默的**：规则被平台自动禁用、采集器挂了、短信网关停了、镜像流量断了，界面一切正常。所以"有效性"不能靠观察界面，只能靠**主动制造一次真实事件，看它是否按设计走完全链路**。

三层验证必须都做，缺一层就会得出错误结论：

**第一层：在位性（装没装、跑没跑）。** 用"横纵交叉"的矩阵式监控：横向从系统侧查每台机器的进程/服务/配置，判断该装的监控是否在跑；纵向从监控侧导出已纳管设备列表。两张表按"系统类型 × 监控类型"交叉，只有两方都说 OK 才算 OK；一方 OK 一方 Fault 记为 Diff（查是程序问题还是网络不通）；两方都 Fault 说明确实缺失。副产品是能反查资产清单错误——某设备装了监控却不在资产清单里，说明清单漏记。

**第二层：端到端有效性（在位后能不能真的告警）。** 白盒验证：为每类管控措施定义一条"最小真实事件"（登录来源非堡垒机地址、可疑进程创建、恶意外连），用自动化平台按计划触发，逐段核对 **Sensor 感知 → 采集入库 → 规则命中 → 告警送达 → 工单生成**，任何一段断即为失效。两条硬约束防止自欺：验证事件必须"自动化模拟真实事件产生，**不能使用插入记录的方式**"（否则只验证了数据库写入）；验证事件要带唯一标识、时间分散（否则会形成告警风暴，让值班人员把验证告警当噪声）。

**第三层：覆盖度（该测的有没有测）。** 用 ATT&CK 当检查表坐标系：战术是有先后的攻击阶段，技术是某阶段的具体手法。对每个阶段问一个问题——"如果对手在这一段动，我靠哪条日志/哪个传感器看见他？"答不上来的阶段就是盲区。注意覆盖不均：多数攻击技术手册只在 C&C、Exfiltration 等章节给出完整"缓解/举例/检测"三段，Initial Access、Execution 章节大量是载荷代码，没有检测段——不能把整本书当检测手册用。

覆盖度还要接受一个现实：**ATT&CK 单项全覆盖会筋疲力尽**。可行的取舍是"对外聚焦高危端口 + Web 攻防，对内按失陷假设 + 横向移动建检测"（全网蜜罐、重点系统纵深、AD/邮件/知识库、运维与 Agent 平台）。

能力度量可以写成乘性关系：**发现能力 = 数据完整度 × 场景覆盖度 × 闭环率**。任一项接近零，整体就接近零——这解释了"买了很多设备仍然发现不了"。三个因子分别对应：数据源覆盖率与完整性、历史 TTPs 与 ATT&CK 关键路径的规则覆盖、告警的处置闭环比例与误报率。

最后一条常被忽略的自查：**Sensor 自身就是最大的攻击面**。安全 Agent 拥有全网最高权限与最广部署面，一旦更新通道或指令通道被控，就是现成的全网分发通道（2013 年韩国事件即通过防病毒厂商的病毒定义更新服务器分发恶意软件）。所以四条约束必须成立：控制指令只允许固化的动作、严禁预留执行系统命令接口；更新包必须审核后才可上传，且只从更新服务器选择并校验哈希；下发控制指令需人工确认；更新分批分区域灰度。

## A1 — 应用示例 (Application Example)

### 示例 1: 矩阵式监控把"信心"变成"缺口"
- **类型与来源**: 【亲历】《企业安全建设指南》· 22.2.1
- **问题/输入**: 团队认为自己监控覆盖很好，要证明"全覆盖"。
- **方法论的使用**: 建资产平台并与 IP 分配系统、扫描工具联动，保证清单是活数据；把系统类型（约 10 项）与监控类型（约 9 项）做成矩阵，每格标"需要安装/N/A/责任人"；生成横向报表（逐系统查进程/服务/配置）与纵向报表（逐监控系统导出纳管列表）；交叉比对出 OK/Fault/Diff/N/A 四态；日报与值班看板集成，红色项每天亮灯、晨会督导整改。
- **结论**: 实施前"对监控覆盖率还是很有信心的"，生成报表后"发现问题隐患还是比较多的"——信心不等于覆盖。
- **结果**: 原书称其团队自 2012 年底起研究部署一年多，"将全部种类和数量的设备纳入矩阵式监控，发现了较多监控整改项。结果证明，安全监控系统失效的事件大大降低"。

### 示例 2: 白盒验证的四段核对
- **类型与来源**: 【亲历】《企业安全建设指南》· 20.2
- **问题/输入**: 需要证明"管控措施失效能在 24 小时内发现"。
- **方法论的使用**: 为每类措施定义最小真实事件并写成自动化脚本（如从非堡垒机地址登录、创建可疑进程）；平台按计划触发，事件打唯一标识、时间分散；逐段核对 Sensor 日志 → 采集入库 → 规则命中 → 告警送达 → 工单生成；平台能识别"验证未通过"并自动通知运维；与黑盒（众测、红蓝对抗）并行。
- **结论**: 白盒保证"设计的功能在跑"，黑盒保证"设计本身够不够"，两者不能互相替代。
- **结果**: 原书列出验证平台要达成的四个目标（Sensor 监测有效、信息采集有效、检测规则有效、告警方式有效），并要求"24 小时内发现失效"。

### 示例 3: 三因子定位"为什么没发现"（合成演练）
- **类型与来源**: 【合成演练】按本卡 E 段推演；三因子框架与三个大事件案例出自《大型互联网企业的入侵检测》
- **问题/输入**: 一次真实入侵被发现时已横向多台，需要解释"为什么没早发现"。
- **方法论的使用**: 盘数据完整度（该类主机 EDR 覆盖率是否 100%、系统调用/运行时数据是否采到、NIDS 是否覆盖该网段、业务日志是否完整）→ 盘场景覆盖度（该手法是否在历史 TTPs 与 ATT&CK 关键路径内、是否有对应规则）→ 盘闭环率（该类告警历史闭环比例、平均研判时长、误报率）。按"修复成本从低到高"排序：先补覆盖，再补规则，最后查闭环。
- **结论**: 三因子是相乘关系，任一项为零则整体为零；不要用采购新产品掩盖覆盖率不足。
- **结果**: 原书给出的三个"大事件里的小失误"可作参照——震网因自动感染内网符合扫描特征被 NIDS 抓到；Equifax 因 Struts S2-045 导致 Java 启动异常子进程被 HIDS 抓到；HackingTeam 因慢速扫描、凭据抓取工具、AD 非预期登录被关联发现。此处仅转述，不推演本演练的最终数字。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 要回答"我们的检测能力到底怎么样"，而不是"我们买了什么"。
2. 攻击进来了但没告警，需要归因（规则？覆盖？平台？人？）。
3. 需要向管理层/审计证明管控措施"确实在工作"。
4. 要做 ATT&CK 覆盖度评估，但不想陷进"全矩阵打勾"。
5. 怀疑某台设备的 Agent 装了但没生效，或某类告警从来没送达。

### 语言信号（出现这些就该激活）
- 中文：「怎么证明安全设备真的在工作」「SOC 有效性怎么度量」「攻击进来了为什么没告警」「检出率怎么提升」「ATT&CK 怎么用在防守」「监控全覆盖了吗」
- English: "prove controls work", "detection validation", "purple team exercise", "ATT&CK coverage mapping", "why did we miss the intrusion", "monitoring coverage assurance"

### 与相邻能力的区分
- 与 `detection-rule-engineering` 的区别：那张管"规则写得对不对、日志进不进得来"；本卡管"整套检测在不在位、能不能端到端跑通、覆盖够不够"。规则正确但 Agent 没装，只有本卡能发现。
- 与 `defense-readiness-baseline` 的区别：那张是稳态建设顺序与基线（资产、漏洞、补丁、权限）；本卡是"验证已建能力是否有效"。
- 与 `traffic-hunt-c2` 的区别：那张是人工狩猎，本卡是把狩猎能力固化成可验证的覆盖项。

## E — 可执行步骤 (Execution)

**必需输入**: Sensor/Agent 清单与部署范围、资产清单、监控系统纳管列表、ATT&CK 映射能力、告警历史与处置记录、可编排的验证脚本能力。缺"资产清单"时矩阵无基准，先补清单。

**交付物与完成标准**: 一份《检测有效性报告》，含：矩阵四态报表（OK/Fault/Diff/N/A）、白盒验证结果（逐措施逐段通过/失败）、覆盖度热图（战术 × 是否有遥测/是否有规则）、三因子评分与缺口清单、整改项（到人/期限）。完成标准是"每个缺口都有补偿方案或已接受的风险记录"。

1. **建矩阵（在位性）**
   - 做什么：明确"监控标准"（系统类型 × 监控类型，每格标需要安装/N/A/责任人）；生成横向报表（逐系统查进程/服务/配置）与纵向报表（逐监控系统导出纳管列表）；交叉比对出四态。
   - 完成标准：Fault 项立即整改，Diff 项逐个排查（程序问题 or 网络不通）。
   - 判停：若某类系统无监控标准，先定标准再检查，否则矩阵无格可填。

2. **反查资产清单**
   - 做什么：把四态报表与资产清单对撞，找"装了监控但不在清单"与"在清单但无任何监控"的设备。
   - 完成标准：资产清单准确性被动补齐。
   - 判停：若清单与现网差异超过阈值，先修清单，否则后续所有覆盖度结论都不可信。

3. **定义最小真实事件**
   - 做什么：为每类管控措施写一条可复现的验证事件（登录来源异常、可疑进程创建、恶意外连、权限变更），并写清"预期在哪一段被看见"。
   - 完成标准：每类措施都有脚本，且脚本不依赖"插入记录"。
   - 判停：若某类措施无法用真实事件验证（如物理控制），改用人工抽查并记录方法局限。

4. **端到端验证**
   - 做什么：按计划触发，事件带唯一标识、时间分散；逐段核对 Sensor → 采集 → 规则 → 告警 → 工单；记录每段的耗时。
   - 完成标准：五段全部通过；任一段断即记为失效。
   - 判停：若告警送达失败但规则命中，判定为"通道失效"而非"检测失效"，修通道即可。

5. **覆盖度映射**
   - 做什么：按战术顺序列清单，每战术只保留"本环境真实出现过/可能发生"的技术；逐条读该技术的检测段，写下需要的观测面（进程/网络/认证/文件/注册表）；对照现有遥测打勾，无则登记盲区。
   - 完成标准：盲区清单带补齐方案与优先级。
   - 判停：若追求全矩阵覆盖导致规则爆炸，按"对外高危端口+Web / 对内失陷假设+横向"收敛范围。

6. **事后归因（漏检时）**
   - 做什么：按"深度 → 覆盖 → 平台 → 告警质量 → 人"五级顺序排查：该攻击路径逐跳确认哪一层本该发现；单点测不到→改规则；覆盖不到→补 Sensor；平台问题→查采集器存活/解析入库/规则是否被自动禁用/阈值/告警通道；告警质量→降噪调阈值；最后才谈人的责任心与技能。
   - 完成标准：定位到具体失效环节，而不是"要加强重视"。
   - 判停：若发现是"灰色地带"（无人关注的互联网资产、测试系统、管理后台、有已知漏洞的第三方应用），转 `defense-readiness-baseline` 做暴露面收敛。

7. **能力度量（三因子）**
   - 做什么：分别量化数据完整度、场景覆盖度、闭环率；三者相乘作为整体能力估计；按"误报压到个位数/日、告警描述用自然语言、工单化"设定工程标准。
   - 完成标准：三个因子都有数据来源与计算方式。
   - 判停：任一因子接近零时，不要在另外两项上投入，先补短板。

8. **Sensor 自身加固**
   - 做什么：审计指令接口（移除可执行任意系统命令的接口）；建更新审核流程（上传前审核、只从库中选择、下发前校验哈希）；下发控制指令需人工确认；更新分批分区域灰度；把 Sensor 可用性纳入健康度监控。
   - 完成标准：四条约束可验证（接口清单、审核记录、确认记录、灰度记录）。
   - 判停：若某 Sensor 无法满足"无命令执行接口"，评估替换或加网络层限制。

9. **输出与闭环**
   - 做什么：把整改项按"修复成本低/命中概率高"排序；日报/看板亮灯；每季度复盘失败模式是否复发（告警被批量忽略、规则被自动禁用、无人认领的资产仍在增加）。
   - 完成标准：整改项关闭率可统计。
   - 判停：若整改长期不关闭，问题在流程而非技术，转管理侧处理。

## B — 边界 (Boundary) ★

### 不要用的情况
- **没有任何 Sensor 的从零环境**：先做建设（`defense-readiness-baseline`），验证无对象。
- **只有单机、无集中平台**：白盒验证的"五段"不存在，只能用人工抽查。
- **把验证当渗透测试**：白盒验证只证明"已知功能在跑"，不证明"未知盲区不存在"。

### 已知失败模式
- **用"插入一条告警记录"代替真实事件**：链路后段全没验证到。
- **验证事件集中在同一时刻触发**：值班人员把验证告警当噪声，久而久之连真告警一起忽略。
- **只看界面绿灯**：采集器挂了、网关停了，界面依然正常。
- **靠 Excel 人工比对矩阵**：不可持续，作者早期即如此，后转系统化。
- **把"没出事"当"做得好"**：没发现异常很可能是发现能力不够。
- **用采购替代覆盖治理**：作者点名"投入重金去测试该引入哪些概念产品（防 APT、威胁情报、态势感知），其实这些都离不开安全监测设备"。
- **只做白盒不做黑盒**：设计的功能都在跑，但设计本身有盲区。
- **忽略 Sensor 自身被利用**：安全软件成为分发通道。

### 作者与时代的局限
- 矩阵式监控的"系统类型 × 监控类型"粒度来自 2012–2015 年的物理机/虚拟机环境，云原生下的"系统"边界模糊（Pod、Serverless），矩阵需重新定义。
- 白盒验证假设"能编排脚本且能触达生产"，在强隔离或 OT 环境中不可行。
- ATT&CK 覆盖度映射在原文中只有原则，没有给出"技术 → 遥测"的映射表，实际落地需要大量人工判断。
- 三因子模型是定性框架，原书未给出各因子的量化公式，本卡只保留"乘性关系"这一判断。

### 容易混淆的方法
- **"在位性"与"有效性"**：装了 ≠ 能告警；矩阵查前者，白盒查后者。
- **"白盒验证"与"红蓝对抗"**：前者验证已知功能，后者检验未知盲区。
- **"覆盖度"与"检出率"**：覆盖度是"有没有能力看见"，检出率是"看见的里面抓到了多少"；覆盖度为零时检出率无意义。
- **"告警闭环率"与"告警处理量"**：前者看是否真的处置完，后者只看翻了多少条。

### 授权与合规边界
> 待补充（用户自行填写）
