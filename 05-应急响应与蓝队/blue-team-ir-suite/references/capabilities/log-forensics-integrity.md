# 日志取证与完整性反推

## R — 原文 (Reading)

> 清除audit 日志
> cat /dev/null > /var/log/audit/audit.log #清除日志文件

> — 《ATT&CK手册》· 六 Credential Access（bash_history 与 audit 日志两节）

> 这些日志不是以纯文本存储的，而是二进制，这让清除稍微困难一些。

> — 《IT-security》· Cover your tracks · UTMP and WTMP

> 要让数据能被彻底的删除，就需要被新的数据覆写。只有在被旧数据占据的那个空间被新的数据覆盖（覆写）掉，旧的数据才算是真正的被删除了

> — 《数字安全实用手册》· 第7章 删除信息

## I — 方法论骨架 (Interpretation)

这个能力解决的问题是：**攻击者会清日志，而"日志里没有可疑记录"到底是"没发生"还是"被删了"，必须能区分。**

核心机制是**按抗抵赖能力给日志源分级**，而不是把所有日志当等价证据：

| 级别 | 日志源 | 抗抵赖性 | 原因 |
|---|---|---|---|
| 低 | `~/.bash_history`、PowerShell 历史 | 几乎为零 | 用户态写入，`HISTSIZE=0` 即不记录，`rm`/重定向即清空 |
| 中 | 应用日志（Web access/error、数据库审计） | 中 | 文本文件，可被 `grep -v <自身IP>` 过滤后覆盖，但行号/字节数会留下不一致 |
| 中高 | 二进制登录记录（utmp/wtmp/lastlog） | 较高 | 非纯文本，"清除稍微困难"，可用 `who`/`last`/`lastlog` 读 |
| 高 | 内核审计（auditd / Windows 安全日志） | 高 | 系统调用层记录"谁在什么时间读了哪个文件"，`type=PROCTITLE`/`type=PATH` 能留下完整命令 |
| 最高 | **离机集中 + 只追加**的日志 | 最高 | 本机 root 一条命令可清空 audit，但清不掉已外发的部分 |

关键推论：**"日志被清空"这个事实本身就是证据。** 所以调查的起点不是"找可疑行"，而是"找该有却没有的部分"：

- 覆盖时间范围有缺口（某几小时为空、某文件比同网段其他主机小一个数量级）；
- 行号/字节数与轮转记录不符（`grep -v` 过滤后覆盖的典型痕迹）；
- 时间线出现无法解释的断层（登录记录连续，但 `lastlog` 显示中间有登录）；
- 多源互相矛盾（`wtmp` 有登录，`auth.log` 无对应条目）；
- `history` 为空、或 `HISTSIZE=0`、或 `HISTFILE` 被改指——历史为空本身是信号，不是"没操作"。

第二层机制是**从反取证手法反推必查项**。攻击者要清什么，就是要查什么：文本日志、二进制登录记录、命令历史、文件本体（`shred` 覆写）、内存、注册表。这条思路的价值在于它不依赖"知道攻击者用了什么工具"，只依赖"清痕迹这件事必然留下不对称"。

第三层是**介质层**：删除只是把索引标记为可用空间，内容仍在，可用未分配空间/回收站/页面文件（`pagefile.sys`、`hiberfil.sys`）恢复；但 SSD 的 TRIM 会在后台擦除，恢复概率显著下降，覆写工具在 SSD 上也基本无效。所以"能不能恢复"要先问介质类型。

最后一条纪律：**先做镜像再分析**。在原件上跑恢复工具、在线杀毒、甚至只是挂载写入，都会覆盖待恢复数据。

## A1 — 应用示例 (Application Example)

### 示例 1: 攻击者读 bash_history 反被 audit 记录
- **类型与来源**: 【转述】《ATT&CK手册》· 六 Credential Access（bash_history 与 audit 两节）
- **问题/输入**: 一台 Linux 主机疑似被提权，`~/.bash_history` 已被清空。
- **方法论的使用**: 不把 history 当证据，转查 auditd。原书给出的日志片段里，攻击者执行 `sudo cat ~/.bash_history | grep password > bash.txt` 这一动作被 audit 以 `type=PROCTITLE`（完整命令行）与 `type=PATH`（访问的文件路径）记录下来。也就是说：**攻击者清 history 的动作，被审计日志记下来了**。
- **结论**: shell 历史只是线索层，审计日志才是留痕层；两者证据价值不在一个量级。
- **结果**: 原书未给出最终定性结论，但明确指出 Ubuntu 默认未装 audit、默认不写 messages 日志，需自行开启——即"默认状态下你根本没有这一层"。

### 示例 2: 用"该有却没有"定位清理痕迹
- **类型与来源**: 【转述】《IT-security》· Cover your tracks（On Linux / UTMP and WTMP / Command history）
- **问题/输入**: Web 服务器疑似被入侵，管理员说"日志里没看到异常"。
- **方法论的使用**: 先取二进制登录记录 `who`/`last`/`lastlog` 建立时间线；再核对 `/var/log/messages`、`/var/log/auth.log`、Apache `access.log`/`error.log` 的覆盖时间范围、文件大小、轮转情况；再查 `echo $HISTFILE` / `echo $HISTSIZE` 是否被改；最后对关键文件做时间戳与内容双重校验。判据是"整段缺失/行数与其他主机明显不一致/时间线无法解释的断层"，而不是"日志里有可疑行"。
- **结论**: 攻击者用 `grep -v '<自身IP>' access_log > a && mv a access_log` 过滤后覆盖，会留下行号/字节数异常；这类"不对称"比可疑行更难伪造。
- **结果**: 原书同时指出攻击者会用 `mv` 覆盖原文件、用 `shred -zu` 覆写——因此主机侧缺失的部分要用网络侧（防火墙、IDS、代理）补齐。

### 示例 3: 4625 里的协议判别（合成演练）
- **类型与来源**: 【合成演练】按本卡 E 段推演；判据出自《windows应急响应手册》· 知识点附录 `0x03`
- **问题/输入**: 一台 Windows 服务器安全日志里 4625（登录失败）数量激增，需要判断是 RDP 爆破还是 SMB 横向。
- **方法论的使用**: 筛 4625 导出，看"源网络地址"与"源端口"——源端口为 0 归为 RDP 方向（失败发生在协议协商/凭据阶段），有源端口归为 SMB 方向（客户端先建 TCP 会话）。**不要只筛"登录类型 10"**：成功的 RDP 交互式登录才记 10，失败记录是 3，按 10 筛会把整批爆破记录漏掉。再用同一源 IP 检索 4624 判断是否已爆破成功，并核对该账号是否在 Administrators / Remote Desktop Users 组。
- **结论**: 事件 ID 与 Logon Type 相同的情况下，源端口是唯一可用的协议判别位。
- **结果**: 原书作者用 goby、fscan、官方 mac 远程工具分别制造失败日志，发现三者登录类型均为 3，随后总结出源端口差异；本演练不假设一定已爆破成功。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 攻击者明显清过日志（history 空、日志有断层），需要判断"还能不能还原"。
2. 需要判断某份日志能不能作为结论依据（而不是"日志里这么写的"）。
3. 需要从"日志缺失"反推攻击时间窗与操作范围。
4. 需要区分同一事件 ID 下的不同攻击路径（如 RDP 爆破 vs SMB 横向）。
5. 被删的样本/日志需要从介质层恢复。

### 语言信号（出现这些就该激活）
- 中文：「history 被清了怎么办」「日志被删了还能查吗」「Linux 取证看哪个日志」「日志可不可信」「4625 一大堆怎么看」「文件删了还能恢复吗」
- English: "log tampering investigation", "anti-forensics", "auditd vs bash_history", "deleted file recovery", "which log source is trustworthy", "RDP brute force vs SMB in event logs"

### 与相邻能力的区分
- 与 `host-triage-parallel` 的区别：那张卡的"日志线"只做时间线串联；本卡解决"日志本身可不可信、缺了什么、缺的部分怎么补"。
- 与 `traffic-hunt-c2` 的区别：本卡用日志回答"谁做了什么"，那张用流量回答"谁在跟谁说话"；主机侧日志缺失时，网络侧日志是本卡的主要补证源。
- 与 `detection-rule-engineering` 的区别：本卡是事后取证（证据够不够、可信不可信），那张是事前设计（采什么、存多久、怎么告警）。但两者的"日志源分级"认知共享。

## E — 可执行步骤 (Execution)

**必需输入**: 主机访问权限或镜像、介质类型（HDD/SSD、是否启用 TRIM）、日志留存范围与轮转策略、同类主机的正常日志规模（用于比对）、网络侧日志可得性。缺"介质类型"必须先问，否则无法回答"能不能恢复"。

**交付物与完成标准**: 一份《日志取证结论》，含：证据源清单（源/级别/覆盖时间/完整性判断）、时间线（含断点标注）、缺口清单（缺什么/为什么判断是缺失）、补证来源（网络侧/其他主机）、结论与置信度。

1. **先做镜像，不在原件上分析**
   - 做什么：对磁盘做只读镜像（含未分配空间），所有恢复与解析在副本上进行。
   - 完成标准：镜像哈希与原件一致；原件保持只读。
   - 判停：若业务不允许停机镜像，先做日志与关键文件的逻辑采集，并在结论里标注"未获取未分配空间"。

2. **给日志源分级**
   - 做什么：按上表把每个可用日志源标为"低/中/中高/高/最高"，并记录其覆盖时间与轮转配置。
   - 完成标准：每个结论都能追到"哪一级证据"。
   - 判停：若唯一可用证据是 shell history，结论只能写"线索"，不能写"事实"。

3. **完整性校验（找"该有却没有"）**
   - 做什么：核对每个日志的覆盖起止时间、文件大小、行数与轮转记录；与同角色主机比对规模；检查 `HISTFILE`/`HISTSIZE` 是否被改；检查审计服务是否在跑（`auditctl -s`、Windows 审核策略）。
   - 完成标准：每个日志给出"完整/有缺口/被篡改"的判断及依据。
   - 判停：发现缺口即记录为可疑，不用等找到"可疑行"。

4. **时间线重建（多源交叉）**
   - 做什么：把 utmp/wtmp/lastlog（`who`/`last`/`lastlog`）、认证日志、服务创建（7045）、任务创建（4698）、进程创建（4688）、Web 访问、数据库登录按时间排轴；标注每个断点与矛盾点。
   - 完成标准：能回答"最早异常何时、之后每一步何时"。
   - 判停：若关键节点全无日志，转第 6 步用介质层恢复。

5. **协议/路径判别**
   - 做什么：对同类事件用可区分字段分流（如 4625 看源端口区分 RDP/SMB）；对登录失败统计来源 IP、时间分布、账号分布，再用成功登录（4624）判断是否已得手。
   - 完成标准：每条攻击路径有对应的日志证据，不是"猜的"。
   - 判停：若日志字段不足以区分，明确写"不可判别"，不要用推测填空。

6. **介质层恢复**
   - 做什么：从未分配空间、回收站、`pagefile.sys`/`hiberfil.sys`、浏览器缓存、邮件缓存中恢复被删对象；对恢复出的文件核对时间与内容，与已知 IOC 比对。
   - 完成标准：恢复出的候选文件有时间、有哈希、有来源位置。
   - 判停：若介质是 SSD 且已启用 TRIM，降低"能恢复"的预期，转其他证据源（日志、内存、网络设备）。

7. **反取证识别**
   - 做什么：判断是否存在覆写/清理：关键目录"过于干净"、时间戳成片一致、日志行号跳变、`shred` 类工具痕迹、审计服务被停。
   - 完成标准：能区分"没发生"与"发生了但被清理"。
   - 判停：确认存在系统性清理时，把结论从"未发现"改为"发现清理行为"，并据此提升事件等级。

8. **补证与结论**
   - 做什么：主机侧缺失的部分用网络侧（防火墙 permit/deny、IDS、代理、DNS）、堡垒机录屏、VPN 登录记录、其他主机日志补齐。
   - 完成标准：结论的每个关键节点至少有两个独立来源，或明确标注"单一来源"。
   - 判停：若补证后仍无法确定入口，转 `incident-scoping` 做跨节点推理。

## B — 边界 (Boundary) ★

### 不要用的情况
- **日志从未开启**：没有 auditd、没有审核策略、没有集中采集时，本卡的方法只能得出"无证据"，不能得出"未发生"。
- **SSD + TRIM 已生效**：介质层恢复基本不成立，不要把时间浪费在恢复软件上。
- **日志时间未同步（NTP 偏差大）**：时间线重建会得出错误因果，先校正时钟偏差再排轴。
- **容器/Serverless**：日志随实例销毁，主机侧取证不成立，只能靠集中采集与平台侧审计。

### 已知失败模式
- **只导出 `history` 当证据**：可被 `HISTSIZE=0` 完全抑制，也可被 `history -c` 清空。
- **把日志留在本机同一分区**：攻击者 `cat /dev/null >` 一条命令即清空，事后无法证明发生过什么。
- **只看"有的可疑行"**：漏掉"该有却没有"这条更强的判据。
- **在原件上跑恢复工具**：反复读写覆盖未分配空间，把"可能恢复"变成"确定不可恢复"。
- **在 SSD 上套用 HDD 的覆写/恢复经验**：结论失真。
- **只筛 Logon Type=10 找 RDP 爆破**：失败记录是类型 3，整批漏掉。
- **相信 `last` 就代表完整登录史**：wtmp 可被 `utmpdump` 类工具改写，需与认证日志交叉。
- **忽略时区**：UTC 与本地时间混用会让时间线整体偏移数小时。

### 作者与时代的局限
- auditd 的规则配置在原书中只有示例级描述，缺少"哪些 syscall/路径必须覆盖"的完整清单；不同发行版默认策略差异很大。
- Windows 侧原书以 Server 2016 为准，审核策略默认值与 4688 是否带命令行（需开启"包括命令行"策略）在其它版本不同。
- 未覆盖云平台审计日志（CloudTrail、ActionTrail 类）与 K8s 审计日志，这些在现代事件中往往是唯一幸存证据。
- "二进制日志更难清"这一判断在 root 权限下并不成立——攻击者可以直接改写或替换文件，只是会留下更多不一致。

### 容易混淆的方法
- **"日志缺失"与"日志未开启"**：前者是攻击痕迹，后者是配置缺口；处理方向完全不同（一个是提事件等级，一个是补采集）。
- **"删除"与"覆写"**：删除留内容，覆写不留；判断依据是介质上是否还能捞到残留。
- **"审计日志"与"应用日志"**：前者在内核层、难篡改；后者在应用层、常被"过滤自身 IP 后覆盖"。
- **"时间线重建"与"事件排序"**：前者要求多源交叉与时区校正，后者常只是按一个日志文件的行序读。
