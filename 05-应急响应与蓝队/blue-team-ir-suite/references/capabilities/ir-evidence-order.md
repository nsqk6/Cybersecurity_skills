# 应急响应取证与处置顺序

## R — 原文 (Reading)

> 在发生任何安全事件时，确定安全事件真实存在以后，第一步都建议固定证据，固定证据一般有以下几种类型，受害单位可以根据实际需求选择

> — 《windows应急响应手册》· 远控后门 / 挖矿病毒 / 勒索病毒等各章 `0x00 固定证据`（同一段落在 8 个事件章重复）

> PDCERF 方法最早于1987 年提出，该方法将应急响应流程分成准备阶段、检测阶段、抑制阶段、根除阶段、恢复阶段、总结阶段

> — 《网络安全应急响应技术实战指南》· 1.3.2 PDCERF（6 阶段）方法

> 不建议关闭受感染的计算机。 某些类型的恶意软件保留在内存中，并且不会在硬盘上创建文件

> — 《inclident-response-guide》· 推荐的 IR 流程和规则 · 隔离受攻击的计算机

## I — 方法论骨架 (Interpretation)

这个能力解决的问题是：**事件已确认，但现场只有一次，而接下来每一个动作都会销毁一部分证据。**

应急现场同时存在三条互相冲突的时间轴：

1. **扩散轴**——恶意程序正在横向、正在加密、正在外传，每拖一小时损失扩大；
2. **证据轴**——内存、连接表、进程、临时文件都是易失的，关机/杀进程/清文件即永久失去；
3. **业务轴**——客户和业务方要求"先恢复再说"。

三条轴不能同时最优，只能按"不可逆程度"排序。核心机制是把动作分成三类并严格分级：

- **可逆动作**（只读采集、抓包、挂起进程、网络层隔离）：先做，做得越多越好；
- **半可逆动作**（删除恶意文件、停服务、改配置）：必须先把对象身份、路径、启动参数、样本副本固定下来再做；
- **不可逆动作**（关机、重装、格式化、全盘杀毒、恢复备份覆盖）：放到最后，且必须留下"为什么此时才做"的记录。

由此得到单事件作业的固定七段：**确认真实性 → 固定证据 → 定 IOC（定性） → 定位宿主对象 → 处置 → 善后（定损） → 常规安全检查（持久化普查）**。它与组织级的 PDCERF 六阶段是两套刻度：PDCERF 管"整场响应到哪一段、该向谁上报"，七段管"这一台机器上下一步交付什么"。实际使用时先用 PDCERF 定位阶段（比如现在处于"抑制"），再用七段决定手上这台机器的动作顺序。

"第一步固定证据"不是教条，而是因为它同时满足扩散轴和证据轴：证据采集几乎全是只读动作，不阻断响应，却决定了事后能不能证明"是否真被入侵、从哪里进来、影响了什么"。反过来，先杀毒再排查的代价不是"少一份报告"，而是**定损和定责都失去依据**——你无法证明被加密的是 3 台还是 300 台。

还有一个必须记住的判据：**杀软已拦截 ≠ 不用响应**。拦截成功只说明这一份样本被认出，不说明投递渠道已断、也不说明没有同源未检出样本。反复被拦截本身就是"存在持续投递"的信号。

## A1 — 应用示例 (Application Example)

### 示例 1: 挖矿事件的七段落地
- **类型与来源**: 【转述】《windows应急响应手册》· 挖矿病毒章 `0x00`–`0x08`；《网络安全应急响应技术实战指南》· 5.2.3
- **问题/输入**: 一台 Windows 服务器 CPU 长期 90% 以上，客户要求"直接杀毒重启"。
- **方法论的使用**:
  1. 确认真实性：CPU 曲线、外连记录、告警三者可复述——不是误报；
  2. 固定证据：先导内存镜像（因为挖矿常带守护、且可能是无文件载荷），再做磁盘/日志采集；此处**没有**先重启；
  3. 定 IOC：外连矿池域名/IP、主程序 MD5；
  4. 定位：`netstat -ano` 拿 pid → 进程路径 → 启动参数 → 启动时间；同时 `schtasks` 与注册表 TaskCache 找守护；
  5. 处置：按"断矿池 → 拆驻留 → 删文件"的顺序，而不是先 kill；
  6. 善后：按定损六共性拉"同口令 / 同镜像 / 同管理员"清单；
  7. 常规安全检查：把 40 余项持久化点位过一遍（隐藏账户、隐藏服务、WMI、CLR 等）。
- **结论**: 处置对象不是"一个进程"，而是"进程 + 守护 + 外连"三件套。
- **结果**: 原书给出该顺序的验收标准——"挖矿木马不再重启，不存在可疑外连为止"。

### 示例 2: 只删 Webshell 的返工
- **类型与来源**: 【转述】《网络安全应急响应技术实战指南》· 6.2 / 7.3 错误处置方法
- **问题/输入**: 网站首页被挂博彩链接，运维已用备份把首页覆盖回去，要求"结案"。
- **方法论的使用**: 按七段回退检查——第 2 段（固定证据）缺失：没有保留被篡改文件与原 Webshell 样本；第 3 段（定性）缺失：不知道入口是上传、包含还是弱口令后台；第 4 段（定位）缺失：没有 pid、没有落地路径、没有 Web 日志时间点。于是"恢复备份"只完成了第 5 段的一半。
- **结论**: 删马/还原页面属于"半可逆动作"，跳过前四段就等于把入口留在原地。
- **结果**: 原书明确把"只用备份恢复网页 / 只删 Webshell"列为错误处置方法，后果是漏洞仍在、很快二次被篡改。

### 示例 3: 客户坚持先重启（合成演练）
- **类型与来源**: 【合成演练】按本卡 E 段规则推演，非原书案例
- **问题/输入**: 云主机告警"疑似内存马"，客户要求立刻重启"清一下"。
- **方法论的使用**: 先判断重启会销毁什么——内存马、C2 配置、解密密钥全部只在内存；再判断重启能得到什么——客户期待的是"恢复业务"，而重启并不修复入口。改为：暂停/冻结实例（若平台支持）→ 导出内存 → 快照 → 网络层隔离 → 采集完毕后由业务方选择重启窗口。
- **结论**: 关机/重启是"不可逆动作"，必须放在证据固定之后。
- **结果**: 原书未提供该场景结果；此处仅给出动作顺序，不假设处置成败。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 客户/领导说"机器中招了，先杀毒重启吧"，需要有人把顺序掰回来。
2. 刚接手一个已确认的入侵事件，需要一份"现在这一步做什么、交付什么"的作业单。
3. 需要在"业务止血"和"证据保全"之间做取舍，且必须向非技术方解释理由。
4. 事件处理完要写报告，发现前面没留证据，定损定责写不出来。
5. 要给别人（新人、外包、分支机构的 IT）一套可复用的单机处置模板。

### 语言信号（出现这些就该激活）
- 中文：「先重启再说」「先杀毒」「先把网断了还是先取证」「处置顺序是什么」「出了事第一步做什么」「证据还要不要留」「PDCERF」「应急响应流程」
- English: "should I power off the infected host", "containment vs forensics", "incident response order of volatility", "first steps after compromise", "PDCERF phases"

### 与相邻能力的区分
- 与 `containment-decisions` 的区别：本卡解决"整条作业链的顺序与证据保全"，那张卡解决"抑制手段怎么选"（断网/隔离/关机/批量清除）以及勒索等特定场景的取舍。两者在"抑制"这一步交汇，本卡只规定它必须发生在证据固定前后什么位置。
- 与 `host-triage-parallel` 的区别：本卡给时间轴（先做什么），那张卡给空间轴（一台机器上要同时看哪几条证据线）。
- 与 `incident-scoping` 的区别：本卡的第 6 段"善后定损"只是入口，范围圈定的具体方法在 `incident-scoping`。

## E — 可执行步骤 (Execution)

**必需输入**: 受害主机标识（主机名/IP）、事件现象或告警原文、可用的采集工具与存储位置、业务影响窗口（能否断网/能否重启）、事件上报层级要求。缺"业务影响窗口"必须先问，否则无法决定抑制方式。

**交付物与完成标准**: 一份《单事件处置记录》，含：证据清单（类型/文件名/哈希/采集时间/采集人）、IOC 表（值/类型/出处/时间）、宿主对象表（pid/路径/命令行/启动时间/父进程）、处置动作流水（动作/时间/执行人/回滚方式）、定损清单（主机/账号/共性维度）、持久化普查结论（逐项通过/命中）。

1. **确认真实性**
   - 做什么：把告警还原成可复述的事实（哪台机器、什么时间、什么现象、哪个设备报的），排除误报与已知业务行为。
   - 完成标准：能用一句话说清"发生了什么"，且至少两个独立来源支持。
   - 判停：若为误报，记录误报原因并转检测规则治理（`detection-rule-engineering`），不进应急流程。

2. **固定证据（只读、易失性优先）**
   - 做什么：按"内存 → 连接/进程/登录会话 → 日志 → 磁盘镜像 → 快照"的顺序采集；先采内存是因为它最易失。云/虚拟化环境优先"暂停/冻结"而非关机（关机快照会丢失内存态）。采集完立即做副本，所有分析在副本上做。
   - 完成标准：每份证据有哈希、采集时间、采集人；原件封存且未被工具改动。
   - 判停：若业务不允许任何采集动作，先做网络层隔离并书面记录"证据将不完整"，再转第 5 步。

3. **定 IOC 与定性**
   - 做什么：从证据里提取域名/IP/URL/文件哈希/文件路径/服务名/账号；判断事件类型（挖矿/远控/勒索/钓鱼/隧道/暴力破解/无文件）与可能的家族。
   - 完成标准：每个 IOC 标注出处（哪台设备、什么时间、哪条日志）；事件类型有依据。
   - 判停：家族无法定性不影响继续；若判为勒索，立即转 `containment-decisions` 的勒索分支（先隔离、先查备份）。

4. **定位宿主对象**
   - 做什么：把 IOC 落回本机对象——pid、可执行文件绝对路径、启动参数、启动时间、父进程、加载模块、对应服务/计划任务/自启项。
   - 完成标准：恶意进程与文件路径一一对应，且能解释"它是怎么被拉起来的"。
   - 判停：若进程已消失（非持续性事件），转 `host-triage-parallel` 的"守株待兔"分支；若无文件痕迹，转内存镜像分析。

5. **处置（半可逆动作，先确认后执行）**
   - 做什么：按"切断再生源 → 停驻留 → 停进程 → 删文件 → 清引用"的顺序；每个动作前记录对象身份，动作后可复验。
   - 完成标准：主程序与守护项同时消失；复验命令（`netstat`/`schtasks`/`sc query`）结果与预期一致。
   - 判停：若杀完立刻重生，说明驻留未拆净，回到第 4 步而不是反复杀；若已确认是多点潜伏（人为布置的多个后门），转 `incident-scoping`。

6. **善后定损**
   - 做什么：按"同口令 / 同漏洞或同服务 / 同管理员 / 可密钥直登 / 可 RDP 已保存凭据直登 / 受害期间频繁交互"六维拉清单，取并集后分流处置。
   - 完成标准：六张清单齐全，并集主机逐台有结论（已查/待查/已改密）。
   - 判停：若并集规模超出逐台处理能力，转批量处置（`containment-decisions` 的驱逐式清除）。

7. **常规安全检查（持久化普查）**
   - 做什么：按 `persistence-sweep-windows` 的点位清单全量过一遍，不只看本次发现的类型。
   - 完成标准：清单逐项标注"通过/命中/不适用"，命中项已处置并复验。
   - 判停：若发现第二套完全不同手法的持久化，判定为对抗性植入，转 `incident-scoping` 做攻击链梳理。

8. **归档与复盘**
   - 做什么：把证据、IOC、时间线、处置流水、定损结论归档；把根因转成改进项（规则、覆盖、流程），每条到人、有期限、可验证。
   - 完成标准：改进项进入跟踪表；同类事件的检测规则或控制项已更新。
   - 判停：若改进项无法落到具体控制，转 `detection-validation-coverage` 立项验证。

## B — 边界 (Boundary) ★

### 不要用的情况
- **纯可用性故障**（硬件、容量、配置错误）不适用：这类问题没有对手，取证顺序会让恢复变慢。
- **恶意样本已在隔离环境**、真实主机未被波及：直接进样本分析（`ir-toolchain`），不需要现场七段。
- **已经重装/格式化完毕**才想起流程：此时只能做"事后补证"（日志、网络侧、备份、其他主机），不能声称完成了证据固定。

### 已知失败模式
- **先杀毒再排查**：样本与内存态双失，无法定家族、无法定损、无法判断入口（《windows应急响应手册》全书的段落顺序即针对此）。
- **把"抑制"当"根除"**：隔离完就结案，入口仍在（《网络安全应急响应技术实战指南》· PDCERF 段）。
- **用"贴便签"式的记忆管理代替流程**：临时提升日志级别后忘记回滚，磁盘写满导致系统崩溃（《Cybersecurity Blue Team Toolkit》Ch9 明确警告过同类事故）。
- **以"告警消失"为结束条件**：攻击者刻意布置多点、异构后门，清掉最显眼的那个就以为结束（《蓝队视角下的防御体系突破》· 多点潜伏）。
- **恢复阶段用已被加密的备份**：二次感染，见 `containment-decisions`。
- **在受害机上直接跑分析工具**：在线杀毒、Autoruns 清理、恢复软件扫描都会改动证据。
- **只处理告警那台机器**：同一批镜像/同一口令下的其他主机保持静默。

### 作者与时代的局限
- 手册的实测环境集中在 Windows Server 2016，个别结论（Prefetch 是否开启、TaskCache 行为、服务 SDDL 表现）在其它版本上需本地复验。
- 云环境取证在原书中只有一句"暂停/冻结优于关机"，缺少主流云平台的具体操作路径与法律保全流程。
- PDCERF 是 1987 年的模型，对"云上多租户""供应链投毒""无文件内存马"这类现代场景只提供阶段名词，不提供判据。
- 各书均未覆盖容器/K8s 场景下的证据固定（Pod 重建即销毁现场），该场景需另建方法。

### 容易混淆的方法
- **"先隔离再取证"与"先取证再隔离"**：原书两处主张看似冲突（《windows应急响应手册》先固定证据；《136-手把手教你做挖矿应急响应》先拔网线）。实际不冲突的关键在于"断网 ≠ 关机"：网络层隔离不破坏磁盘与内存证据，且能冻结现场。真冲突只发生在"关机/重启"这个动作上。
- **"内存取证"与"内存扫描"**：前者是镜像保全（可复核），后者是在线查杀（改变状态）。
- **"事件分级"与"事件分类"**：分级决定上报层级与资源投入，分类决定处置分支；两者混用会导致"按类型定级"（把一次扫描告警当重大事件）。

### 授权与合规边界
> 待补充（用户自行填写）
