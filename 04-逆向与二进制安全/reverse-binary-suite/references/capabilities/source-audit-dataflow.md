# 源码审计数据流与候选点回溯

## R — 原文 (Reading)

> Typically, you must identify where user-malleable data enters the system through an interface to the outside world... Then you study the different ways in which user-malleable data can travel through the system, all the while looking for any potentially exploitable code that acts on the data.
> — 《The Art of Software Security Assessment》Ch1 Input and Data Flow

> You start with the lowest-level routines that grant access to application assets or could harbor a vulnerability... You then trace backward through the code to see whether these routines expose any vulnerabilities accessible from an application entry point.
> — 《The Art of Software Security Assessment》Ch4 General Candidate Point Approach (CP1)

> You can see the bug right away by examining the code, but a black box or fuzz-testing tool would probably miss this basic vulnerability.
> — 《The Art of Software Security Assessment》Ch1 Auditing Versus Black Box Testing

## I — 方法论骨架 (Interpretation)

这张卡解决「面对一份源码，怎么系统性地找出真实可利用的漏洞，而不是一堆误报」的问题。核心公式是：**漏洞 = 用户可控数据 × 危险操作 × 二者连通**。单看危险操作会得到大量误报（本函数危险但外部不可达），单看输入点会漏掉深层组件。因此追踪必须记录数据在每个环节经历的校验、变换、存储——「中途被无关安全代码挡住」是常见伪漏洞来源，而「看起来安全但其实只是碰巧被挡」是常见漏报来源。

两条方向互补的取材路径：正向数据流追踪从输入点出发（命令行、网络、文件、环境变量、IPC），追到它被消费的每一处，画出经过的组件与存储；在每个消费点判定有无长度/类型/字符集校验、校验是否覆盖该数据形态；对「几乎有漏洞」的点回溯确认拦截代码是否真在该路径上，并记录拦截理由（安全设计还是巧合）；最后从危险操作反向回溯到入口交叉验证。反向候选点法（CP1）把搜索空间从「所有代码」压到「所有危险调用」——产出候选点清单（工具报告、grep 结果、经验清单），读函数体判危险是否真实，再找所有调用点逐个检查参数是否用户可控、长度是否可超限。优势是路径少见效快，代价是结论上限由候选点选得好不好决定，且逻辑/设计类漏洞几乎不产生可搜索的候选点。

第三条路是「指纹搜索」：特定漏洞类在源码或汇编层留下固定 fingerprint——格式串/SQL 注入对应固定函数名，符号扩展对应 `movsx`，有符号右移对应 `sar`（无符号为 `shr`），无界拷贝对应 strcpy/strcat/sprintf/gets。用指纹可在几分钟内把全代码库压成几十个待验点，且二进制层能穿透 typedef/macro 伪装；但指纹只覆盖「已知模式」，且编译器优化会让汇编「看起来不一致」，不能只凭表象下结论。

黑盒与代码审计必须两条腿走路：黑盒/模糊测试只能触达「输入能直接驱动的路径」，当漏洞藏在只有特定关键字、特定状态、特定配置才进入的分支时（如仅当 query string 含 `mode=` 才执行的 sprintf），随机输入根本走不到那行；看代码能直接看到危险构造，但判断是否可利用又要回到「输入能否到达」。对「需特殊状态」的候选，回到黑盒构造该状态再验一次。

沉淀工具让判断可复用：ACC 日志把每个动态分配的「分配公式 / 长度校验 / 拷贝长度」三列并排 + 第四列疑点，不一致直接跳出（内存破坏几乎都源于这三者不一致）；函数审计日志把「函数原型 + 每个返回值语义 + 错误条件 + 哪些返回值不可信」固化成表，每读一个新调用点只需查表判断是否误用返回值。验证手法上，边界值用例取负/零/正三段的最近边界（小负数、0x80000000、0、0x7FFFFFFF），多输入时先做约束消减（剔除不可能状态）与无关输入消减；desk-check 把代码片段所有变量列成表、填入怀疑值、逐行更新，把「某行执行后某变量越界」变成可直接观察的事实。最后，信任按传递闭包审——「我只信任本机 root 进程」会退化成「我信任任何能冒充 root 的东西」，要沿链找到最外层可攻击点；并检查自定义分配器/字符串封装/系统 API 的真实语义，不默认它们与 libc 等价。

## A1 — 应用示例 (Application Example)

### 示例 1: 会议调度系统的跨组件溢出
- **类型与来源**: 【转述】《The Art of Software Security Assessment》Ch1 Input and Data Flow
- **问题/输入**: 会议描述字段长度 >1000 字符，单看创建函数似乎有长度检查，为何总是漏报？
- **方法论的使用**: 列出所有输入点并标注可控程度；任选输入正向追到它被消费的每一处，画出经过的组件与存储（含数据库、缓存）；发现该字段要经「创建 → 入库 → 月底报表生成」才触发溢出，攻击路径跨多个组件；在每个消费点判定校验是否覆盖该数据形态；再从危险操作反向回溯交叉验证是否有遗漏路径。
- **结论**: 只在单个函数内看数据流会把「本函数内安全」当成「端到端安全」；把巧合的拦截（某处顺手做的长度检查）当安全设计，重构后即失效。
- **结果**: 原书以此说明端到端追踪的必要性，并在多个消费点记录拦截理由。

### 示例 2: 从 sprintf 候选点回溯到可控 name/domain
- **类型与来源**: 【例题】《The Art of Software Security Assessment》Ch4 CP1 + Ch1 mode= 例题
- **问题/输入**: 静态扫描报告给出 `util.c:1293: sprintf() used on a stack buffer`，如何判定是否真的可利用？
- **方法论的使用**: 读函数体确认危险真实存在（sprintf 到栈缓冲区）；找出所有调用点（如 `construct_email()`），逐个检查参数 name/domain 是否用户可控、长度能否超限；对「需特殊状态才可达」的点（如仅当 query string 含 `mode=` 才执行 `sprintf(buf,"MODE=%s",ent->value)`），回到黑盒构造该关键字再验一次；记录判定理由（谁控制、上限多少）。
- **结论**: 只看候选点本身不看调用者，会把「本函数危险」误报成「可利用」；黑盒工具不会想到构造 `mode=` 关键字，必须代码审计补位。
- **结果**: 原书以该例题说明候选点法与黑盒互补，并给出可达性判定的三态结论（有入口可达 / 需特殊状态 / 不可达）。

## A2 — 触发场景 (Future Trigger)

### 用户会在什么情境下需要它
1. 手上有一份静态扫描报告或 grep 出的危险调用清单，需要判断哪些是真漏洞、哪些是误报。
2. 想确认「这个参数能不能被用户控制」「污点数据最终流到哪」，做端到端的污点追踪。
3. 黑盒/fuzz 跑完没问题，但怀疑代码里藏着只有特定条件才触发的漏洞。
4. 审一段逻辑复杂、多变量多次重赋值的代码，人脑推演不可靠，需要外化状态。
5. 审完发现自定义分配器/字符串封装与标准库行为不同，怀疑之前的判断建立在错误假设上。

### 语言信号（出现这些就该激活）
- 中文：「这个参数能不能被用户控制」「trace tainted data」「污点分析怎么做」「有静态扫描报告怎么处理」「怎么快速找可利用点」「fuzz 过了没问题还要看代码吗」「为什么代码里有漏洞但扫不出来」「这段代码我推不出来」「desk check 怎么做」「只审入口模块够不够」
- English: "trace tainted data", "back-tracing from dangerous call", "audit every call site", "why does static scan report false positives", "static and dynamic analysis together", "desk-check a function", "custom allocator semantics"

### 与相邻能力的区分
- 与 `security-review-planning` 的区别：那张卡产出组件优先级与工期（评审管理），本卡在选定组件后执行具体的取材与验证。
- 与 `memory-integer-audit` 的区别：本卡找「是否存在破坏、是否连通」，那张卡判「破坏后多严重 / 整型如何被绕过」；ACC 日志在本卡用于发现破坏，六问评级在那张卡。
- 与 `crash-to-exploit` 的区别：本卡起点是静态代码与候选点，那张卡起点是运行时崩溃现场。

## E — 可执行步骤 (Execution)

**必需输入**: 可读源码（或可反编译的二进制）+ 能查全调用点的手段（IDE 交叉引用/ctags）；理想有可运行二进制用于黑盒验证。缺可运行环境时本卡仍可给出可达性推断，但「需特殊状态」的候选无法闭环验证，须标注未验证。

**交付物与完成标准**: ① 输入点清单（含可控程度）；② 端到端数据流图（组件与存储）；③ 候选点清单及逐点判定（可利用/不可利用/待定 + 理由）；④ ACC 日志（内存块）与函数审计日志（接口）；⑤ 边界用例集与 desk-check 表；⑥ 信任闭包与子系统语义差异清单。完成标准：每个候选点都有「谁控制、上限多少、是否可达」的可复核理由。

1. **列输入点与信任闭包**
   - 做什么：列出所有输入点（命令行、网络、文件、环境变量、IPC）并标注可控程度；标出每个组件的信任假设（信任谁/什么数据形态/凭什么），沿链上溯形成信任闭包；把「私有协议太难访问」「只监听回环」等假设标为高风险。
   - 完成标准：输入点清点与信任闭包图齐全。
   - 判停：若信任链最外层不可攻击 → 该分支降权；若需网络拓扑信息而缺失 → 标假设待补。

2. **端到端正向追数据**
   - 做什么：任选一条输入正向追到被消费的每一处，画出经过的组件与存储（含数据库、缓存）；每个消费点判定有无长度/类型/字符集校验及是否覆盖该数据形态；对「几乎有漏洞」的点回溯确认拦截代码是否真在该路径上，记录拦截理由（安全设计 or 巧合）。
   - 完成标准：数据流图覆盖所有消费点，每个拦截点标注设计/巧合。
   - 判停：只在单函数内看安全 → 必须跨函数/跨组件继续追；发现巧合拦截 → 标为高风险（重构即失效）。

3. **反向候选点与指纹搜索**
   - 做什么：产出候选点清单（工具报告、grep、经验）；用指纹按目标漏洞类搜（格式串/SQL→printf/查询拼接函数；符号扩展→movsx；有符号移位→sar；无界拷贝→strcpy/strcat/sprintf/gets）；按模块职能预筛只保留处理外部输入的模块；对每个候选读函数体判危险真实性，找所有调用点逐点检查参数可控性与长度上限，判可利用/不可利用/待定。
   - 完成标准：候选点全集 + 逐点三态判定 + 理由（谁控制、上限多少）。
   - 判停：只看候选点不看调用者 → 判为误报并回退；二进制场景编译器优化令汇编表象不一致 → 以源码语义为准，不凭表象下结论。

4. **黑盒互补验证特殊状态**
   - 做什么：黑盒阶段对每个入口用协议感知 fuzzer 跑一轮收集崩溃；对「需特殊状态才可达」的候选（如 `mode=` 关键字），回到黑盒构造该状态再验；确认拦截在运行时是否真的生效。
   - 完成标准：每个待定候选有「运行时可达/不可达」的实证。
   - 判停：只跑 fuzzer 就宣布「没发现问题」→ 禁止；只读代码不验证可达性 → 报出的假漏洞需回退。

5. **沉淀 ACC / 函数审计日志**
   - 做什么：对每个动态分配写分配公式、所有长度校验、每次拷贝的元素/长度表达式、第四列疑点（分配单位 vs 拷贝单位、拷贝总量能否超分配量、校验是否覆盖乘法溢出）；为每个函数建条目（完整原型、用途、每个返回值含义、错误条件、哪些返回值不可信），每读一个调用点查表判断是否误用返回值。
   - 完成标准：内存块与函数接口都有可查表，不一致处直接标出。
   - 判停：自定义分配器需另查分配器记分卡后再下结论；只记原型不记返回值语义等于没记。

6. **边界用例与 desk-check 验证假设**
   - 做什么：对每个输入取值域分段取边界（小负数、0x80000000、0、0x7FFFFFFF），为人造边界（`+1024`、`&0xFFFFFFF0`）补用例；多输入先做约束消减与无关输入消减；列变量状态表填入怀疑值逐行更新，检查越界/回绕/未初始化读；换一组值重走确认可复现。
   - 完成标准：边界用例集覆盖人造边界，desk-check 能定位到具体语句。
   - 判停：只走正常路径不走错误分支 → 必须补错误分支（缺陷常出在终止符写入与错误处理）；消减过度删掉「不可控但影响处理逻辑」的变量 → 回补。

7. **回归与同类模式全库搜索**
   - 做什么：确认补丁是否回到「值的类型与值域」层（见 `memory-integer-audit` 的反例判据），用 desk-check 取负值逐行推演检查是否仍成立；在同一代码库搜同类模式一并修；复核自定义分配器/封装/系统函数的真实语义。
   - 完成标准：同类模式全库覆盖，修复后原路径与相邻路径均回归通过。
   - 判停：把「代码里有 if 检查」当已修复 → 必须走查；修补后不做回归 → 同类问题会复现（antisniff 三段史）。

## B — 边界 (Boundary)

### 不要用的情况
- 目标是纯运行时崩溃的归因（只有 dump、无源码），转 `crash-to-exploit` / `binary-analysis-toolchain`。
- 想判「溢出后能否拿到 EIP / 写 exploit」，本卡只到连通性与评级，转 `crash-to-exploit` 与 `memory-integer-audit`。
- 目标是恶意样本的行为理解（不关心源码漏洞），转 `malware-behavior-analysis`。
- 只对单个已知注入点做 payload 构造，转 `injection-filter-audit`。

### 已知失败模式
- 只跑 fuzzer 就宣布「没发现问题」；或只读代码不验证可达性，报出一堆不可达的假漏洞（Ch1）。
- 只在单个函数内看数据流，把「本函数内安全」当成「端到端安全」；把巧合的拦截当安全设计（Ch1）。
- 只看候选点本身不看调用者，把「本函数危险」误报成「可利用」；把候选点法当唯一方法，系统性漏掉不符合模式的漏洞（Ch4 CP1）。
- 把指纹命中当漏洞；模式外漏洞零覆盖；编译器优化改写转换后只凭汇编表象下结论（Ch4/Ch6）。
- 把「只监听 127.0.0.1」「私有协议」当安全边界（Ch1 Trust Relationships / Ch2）。
- 默认自定义 `allocate()`/`xmalloc()` 与 `malloc()` 等价、项目字符串封装与 libc 一致（Ch4 Subsystem and Dependency Analysis）。
-  desk-check 只走正常路径、表格过简漏掉中间状态（Ch4 Desk-Checking）。

### 作者与时代的局限
- 候选点法与指纹法覆盖「已知模式」，逻辑/设计类漏洞几乎不产生可搜索候选点，必须靠威胁建模与数据流人工推理补齐。
- 五阶段/四阶段流程与 DREAD 来自 2007 年前后的安全评审实践；现代 CI/CD、SAST/DAST 工具链的集成方式需另行适配。
- desk-check 适合一两个函数的中等规模片段；超长函数或深度递归需借助符号执行/静态分析工具。
- 信任传递闭包示例基于 Solaris/UNIX 的进程与 RPC 模型；Windows 命名对象/句柄的等价问题见 `privilege-windows-audit`。

### 容易混淆的方法
- 「正向数据流」与「反向候选点回溯」方向相反，必须交叉验证，不能只做一种。
- 「ACC 日志」（内存块三列）与「函数审计日志」（函数接口）分别针对内存块与函数，常配合使用；前者找「是否存在破坏」，后者判「返回值是否被误用」。
- 「黑盒补可达性」与「代码补隐藏分支」是同一目标的两种手段，本卡要求两者结合而非二选一。
- 「巧合拦截」与「安全设计拦截」在代码形态上可能相同，区别在重构后是否仍成立，需记录理由。

### 授权与合规边界
> 待补充（用户自行填写）
