# 模糊测试战役工程

## R — 原文 (Reading)

> Some fuzzers are simple input generators. Some consist of an entire framework designed to help with the many stages of fuzzing. Let's take a closer look at all the necessary steps required to conduct fuzzing
> — 《Fuzzing for Software Security Testing and Quality Assurance》Ch8 §8.1 Fuzzing Life Cycle

> It's best to choose something in between.
> — 《Fuzzing for Software Security Testing and Quality Assurance》Ch9 §9.6.1 Select Target

> In fact, running all the fuzzers found, on average, over 50% more bugs than just running the most effective fuzzer by itself.
> — 《Fuzzing for Software Security Testing and Quality Assurance》Ch8 §8.8.1

## I — 方法论骨架 (Interpretation)

这张卡解决「要对一个目标系统性做一轮 fuzz，从选题、定接口、选工具到跑出崩溃的完整战役怎么组织」的问题。核心洞察是：fuzz 的产出瓶颈通常不在生成测试用例，而在「知道哪个输入触发了什么」和「把多个崩溃收敛成几个根因」——但战役级决策（选题、接口、种子、工具组合）决定了后面能走多远，这些决策错了，再好的分诊也救不回来。

完整生命周期六段：识别接口 → 生成输入 → 投递 → 监控目标 → 异常分析 → 报告。每一段都有独立失败点，缺任何一段后面拿到的都是无法归因的噪声；工具的价值差异主要体现在后四段。本卡覆盖前四段的战役组织（接口、目标、种子、工具），异常分析与监控的细节在 `fuzzing-triage-infra`。

选题取「甜区」：期望收益 = 找到概率 × 结果价值。成熟度高的目标（Apache）把找到概率压到接近 0；冷门目标把结果价值压到接近 0，两端都不产出，最优在中间。两条可操作筛选法：选「没被 fuzz 过的」，或选「近期漏洞记录密集的」（QuickTime 2007 年 34+ 个洞）；再用功能面大小做二次排序（支持格式/协议越多攻击面越大）。接口枚举绕过厂商文档，从操作系统文件关联表反查——QuickTime 用 RCDefaultApp 一次拿到近 50 种格式，远超官网宣传；每个入口标「是否跨信任边界」，跨边界的排前面。

工具选型看「效率/成本比」而非「越智能越好」：Charlie Miller 在 DEF CON 2007 实测智能 fuzz 有效性约高 50%，但人力投入 10–100 倍。决策看目标形态——文件解析类上位翻转便宜且出奇有效；有状态网络协议上纯随机会被协议层直接拒掉，才需要抓包回放变异；加密/校验和协议才考虑生成式。落地顺序「先易后难」：先跑最便宜的（位翻转/攻击串库/长度边界表），无产出再逐级加智能（分词→字段识别→校验和修复→完整语法模型）。数据来源四类：固定用例（可回归）、循环（时长确定）、随机（**必须固定种子才能复现**）、攻击串库（已知模式）；先用 library+cyclic 打底、再补 random 扫暗角。取值用倍增序列（1,2,4,8…）与象限采样（观测到当前值 v 就试 v±1 → 0/负/极大 → 异类），承认必然漏掉一部分 bug 是「必要的权衡」。语法测试用 BNF 写接口文法、一次只注入一个异常（语法/定界符/字段值/上下文/状态五类），其余保持正确——可归因性是它与随机 fuzz 的本质差别。模型复杂度决定穿透深度：改字段值测溢出/整数，改报文结构测解析器，只有改**报文序列**才能打到状态机。

两条补盲路径：种子决定变异上限——变异式 fuzzer 只能在种子已走到的路径上扰动，种子是「可达性许可证」，完整抓包比残缺抓包多挖 66%（另两个 fuzzer 从 0 变 3）；选种子按功能覆盖而非数量，用覆盖率验证并列出「罕见但合法」结构的盲区。多 fuzzer 并联优于精选单一最强器——不同 fuzzer 随机性指纹不同、漏检集合不重合，全跑平均多挖 50%+；要跨「知识档位」选（全随机→通用分词→定制分词→完整模型），用同一目标/种子/监控口径并行跑，统计每个器的**独有**发现。最后，关于「跑多久」：带随机成分的 fuzzer 发现曲线是离散跳变+长平台期（前 3 分钟挖 3 个，第 4 个等 76 分钟），不存在「跑够了」的判据，只有「边际期望 vs 成本」的判据。

## A1 — 应用示例 (Application Example)

### 示例 1: 用 RCDefaultApp 枚举 QuickTime 攻击面
- **类型与来源**: 【亲历】《Fuzzing for Software Security Testing and QA》Ch9
- **问题/输入**: 要对 QuickTime 做文件格式 fuzz，选哪个格式作为入口？
- **方法论的使用**: 忽略官网功能页，直接查系统文件关联表（RCDefaultApp）读出注册的全部扩展名（3g2/aac/amc/avi/caf/rtsp 等近 50 种）；对每个入口标「是否跨信任边界」，跨边界排前面；从清单挑 AVI 作为本轮入口，其余留后续轮次；选目标时依据「2007 年单这一款产品就有 34 个以上安全漏洞」。
- **结论**: 覆盖率上限由「你知不知道这个入口存在」决定，文档只列主推功能；只按文档列出的格式做 fuzz 会遗漏「能解析但没宣传」的格式，而漏洞恰恰密集来自功能集极大。
- **结果**: 原书以 AVI 为入口展开后续 fuzz，并明确选择「变异式而非生成式」，理由是「用生成式打 QuickTime 像用大锤打蚂蚁」。

### 示例 2: 完整抓包 vs 残缺抓包的种子对照实验
- **类型与来源**: 【亲历】《Fuzzing for Software Security Testing and QA》Ch8 §8.8.3
- **问题/输入**: 同一批 fuzzer 用不同种子，为什么有人挖到洞有人一个都没有？
- **方法论的使用**: 对同一批 fuzzer 用完整 FTP 抓包 vs 残缺抓包做对照——GPF 用完整抓包多挖 66%，另两个 fuzzer 用残缺抓包 0 个、完整抓包 3 个；DNS 侧更直接——bug 3 只在「SOA 类型且 length>128」触发，而初始种子里根本没有 SOA 记录，所有变异式 fuzzer 全部漏掉。
- **结论**: 变异式 fuzzer 只能在种子已走到的路径上扰动；发现某类漏洞完全挖不到时先查种子而不是先换 fuzzer；完整抓包本身需要协议知识，用它等于把生成式优势偷偷借给变异式。
- **结果**: 原书据此给出种子选择口径（按功能覆盖而非数量，用覆盖率验证并列出盲区）。

## A2 — 触发场景 (Future Trigger)

### 用户会在什么情境下需要它
1. 要启动一次 fuzz 战役，不知道选哪个目标、选哪些输入入口、先上哪种 fuzzer。
2. 一上来就写完整协议模型，数周投入却与位翻转覆盖率相同，需要重新评估成本/收益。
3. 同样的 fuzzer 别人挖到洞自己挖不到，怀疑种子或工具组合有问题。
4. 带随机成分的 fuzzer 出现长平台期，纠结「要不要关掉」。
5. 需要判断目标是「解析器 bug」还是「状态机 bug」，决定要不要建序列级模型。

### 与相邻能力的区分
- 与 `fuzzing-triage-infra` 的区别：本卡覆盖战役级决策（选题、接口、目标、种子、工具组合、运行时长）与生命周期前半段（接口→生成→投递），那张卡覆盖崩溃之后的分诊、最小化、监控health与覆盖率度量；敏感到「崩溃收敛成根因」时切到那张卡。
- 与 `security-review-planning` 的区别：那张卡的目标选择依据是业务损失与威胁分，本卡的可挖性排序依据是「成熟度 × 使用者规模 × 功能面」。
- 与 `protocol-and-race-audit` 的区别：那张卡静态审协议解析器代码，本卡动态生成畸形输入打接口；未知协议差分识别在那张卡，字段 fuzz 取值在本卡。

## E — 可执行步骤 (Execution)

**必需输入**: 一个可运行目标与至少一条可用输入通道；自主选题权或待测系统清单；能抓真实流量/样本作种子；并行算力（多 fuzzer 并联时）。缺真实种子时须先构造覆盖主要功能的最小种子集并标注盲区。

**交付物与完成标准**: ① 目标选择依据（成熟度/使用者规模/功能面/漏洞史）；② 接口清单（标注跨信任边界）；③ fuzzer 档位与数据来源决策；④ 种子集与覆盖率验证结果；⑤ 多 fuzzer 组合及各自独有发现；⑥ 时间—累计独立漏洞数曲线与停机决策。完成标准：每个决策都有「依据 + 排除项」，种子集可通过纯回放覆盖率验证。

1. **选目标取甜区**
   - 做什么：列候选目标，每个标成熟度/被 fuzz 历史与使用者规模；剔除两端极值（大厂主力产品、无人使用的小工具）；在剩余里优先「近期漏洞史密集」或「功能面大但没被系统 fuzz 过」；用功能面大小二次排序，得 1–2 个目标。
   - 完成标准：目标选择依据表 + 排除理由。
   - 判停：受雇审计无选题权时，改为按「暴露程度 + 开发质量」在多个待测系统间排优先级；挑最硬目标投入数周零产出 → 重新评估。

2. **枚举接口（绕过文档）**
   - 做什么：本地程序查命令行参数、环境变量、读取的文件、IPC/本地套接字；网络设备从二层帧、IP 栈到 Web 管理界面逐层列；文件格式类查系统文件关联/注册表/mailcap 映射表拿完整扩展名清单；每个入口标是否跨信任边界，跨边界排前面；从清单挑一个入口开始。
   - 完成标准：接口清单 + 跨边界标注 + 本轮入口。
   - 判停：只按文档列出的格式做 fuzz → 补查系统关联表；只看单一入口就收工 → 列出其余留后续轮次。

3. **定 fuzzer 档位与数据来源**
   - 做什么：判断目标形态——文件/命令行优先位翻转，有状态网络协议优先抓包回放变异，加密/校验和协议才用生成式；用最便宜方案跑一轮，有产出就先不升级复杂度，无产出再逐级加智能（分词→字段识别→长度/校验和修复→完整语法模型）；选数据来源组合（先 library+cyclic 打底、再 random 扫暗角），random 必须固定并记录 seed；按象限采样取长度（1,2,4,8…）与数值（v±1 → 0/负/极大 → 异类）；对有规范接口用 BNF 写文法、一次只注入一个异常（五类），其余保持正确。
   - 完成标准：档位与数据来源决策表 + seed 记录 + 取值序列。
   - 判停：一上来写完整协议模型 → 先退到最便宜方案；对强校验协议只做位翻转（变异全被丢弃）→ 升级；无种子 random 长跑（崩溃无法复现）→ 补固定 seed。

4. **定模型复杂度与穿透目标**
   - 做什么：判断目标风险层——解析器 bug 用结构级够、业务逻辑/状态机 bug 必须序列级；评估现有 fuzzer 处于哪一档并写下「本轮不覆盖状态机」等边界；需要深穿透时升级到能表达序列的模型（状态机/会话模板），而非加大随机量；用「是否触达解析之后的代码」验证穿透深度。
   - 完成标准：穿透目标声明 + 模型档位 + 验证方式。
   - 判停：用无状态 fuzzer 打有状态协议永远停在第一层却误判「目标健壮」→ 升级模型；把「模型完备」等同「fuzzer 聪明」→ 错（协议知识完备但盲目发包不聪明，会看代码路径调整的 dumb fuzzer 反而更聪明）。

5. **准备种子集并验证**
   - 做什么：按功能覆盖挑种子——每种报文类型/可选字段/状态转换至少一条；跑一遍纯回放看命中哪些基本块，未命中功能点补种子；记录种子集缺哪些「罕见但合法」结构（如 SOA 记录、扩展字段）作为已知盲区，单独构造或改用生成式；发现某类漏洞完全挖不到时先查种子。
   - 完成标准：种子集 + 覆盖率验证结果 + 盲区清单。
   - 判停：用「一次正常登录」抓包当种子（分支/错误路径全没覆盖）→ 补；以为增加变异轮数能弥补种子缺陷 → 不能，不在种子里的路径永远走不到。

6. **多 fuzzer 并联**
   - 做什么：按知识档位挑 3–4 个 fuzzer（至少一个全随机、一个通用变异、一个协议感知）；同一目标/种子/监控口径并行跑；分别统计每个器的**独有**发现（其他器都没挖到的）；长期只保留有独有产出的组合，剔除完全被覆盖的。
   - 完成标准：fuzzer 组合清单 + 各自独有发现统计。
   - 判停：用同一款 fuzzer 换不同参数当「多个 fuzzer」（随机性指纹相同、收益≈0）→ 跨档位选；不做统一去重把同一 bug 的多次命中当「多器更强」→ 先按 `fuzzing-triage-infra` 去重。

7. **运行并决定停机**
   - 做什么：记录「时间—累计独立漏洞数」曲线而非只看总数；出现平台期先归因——是随机性没覆盖到（换种子/换 fuzzer）还是真挖完（加覆盖率看是否有未触达分支）；决策用「再加一轮算力的边际期望 vs 成本」，不用「多久没出洞」；长跑配自动化（自动重启、自动收集），否则人力成本先于收益耗尽。
   - 完成标准：发现曲线 + 停机决策依据。
   - 判停：按固定时长（如「跑 24 小时」）收工恰好停在两次发现之间 → 避免；用「最后 N 小时零发现」当收敛证据 → 避免；把「一段时间没新发现」当挖完会丢掉最难的洞（第三个 bug 可能要等 155 分钟）。

## B — 边界 (Boundary)

### 不要用的情况
- 已有可复现崩溃、要做分诊与归因，转 `fuzzing-triage-infra`。
- 目标是「审一处代码是否有漏洞」的静态判断，转 `source-audit-dataflow` / `memory-integer-audit`。
- 目标是恶意样本的行为理解（非找 bug），转 `malware-behavior-analysis`。
- 确定性验收测试追求跨实现可比性（农药效应下的固定测试集），本卡的随机化口径不适用，见 `fuzzing-triage-infra` 的农药效应处理。

### 已知失败模式
- 只做「发生成器」那一段，拿到一堆崩溃但无法归因，人力全耗在人工翻样本（Ch8 §8.1）。
- 挑最硬的目标（Apache）投入数周零产出，或挑最冷门目标挖到洞无人认领（Ch9 §9.6.1）。
- 只按文档列出的格式做 fuzz，遗漏「能解析但没宣传」的格式——QuickTime 的 bug 密集恰来自功能集极大（Ch9）。
- 一上来写完整协议模型，数周投入换来与 dumb fuzz 相同覆盖率；或对带强校验协议只做位翻转，变异全被丢弃（Ch5 §5.1）。
- 用无种子的 random 长跑，崩溃无法复现；只用 library 永远找不到库里没有的 bug 类型（Ch5 §5.1.2）。
- 用「一次正常登录」抓包当种子，所有分支/错误路径都没覆盖；以为增加变异轮数能弥补种子缺陷（Ch8 §8.8.3）。
- 用同一款 fuzzer 换参数当「多个 fuzzer」，收益接近 0；不做统一去重把同一 bug 多次命中当多器更强（Ch8 §8.8.1）。
- 把「一段时间没新发现」当挖完——前 3 分钟 3 个 bug、下一个等 76 分钟、再下一个等 155 分钟（Ch8 §8.8.7）。

### 作者与时代的局限
- 智能 vs dumb 的「50% 有效 / 10–100 倍投入」来自 Charlie Miller 在 DEF CON 2007 的实测，工具与目标的现代化可能改变比值。
- QuickTime 34+ 洞（2007）、PROTOS、SNMP 等案例是历史数据，用于说明选题口径而非现状。
- 语法测试用 BNF/上下文无关文法，对需要语义约束（校验和、跨字段关系、加密）的接口需额外建模。
- 多 fuzzer 并联的收益建立在「有并行算力 + 统一去重口径」前提上；资源受限时须取舍。
- 覆盖率引导（AFL/libFuzzer）的具体工具细节在 `fuzzing-triage-infra`，本卡只做档位决策。

### 容易混淆的方法
- 「智能 vs dumb」（知识投入的成本维度）与「模型层次决定穿透深度」（能测到哪一层）是不同维度，不要混为一谈。
- 「补种子」与「多 fuzzer 并联」是两条不同的补盲路径：前者扩可达性，后者扩算法多样性。
- 「平台期」（随机性运气、可能突然出洞）与「农药效应」（确定性测试集的固定上限，见 `fuzzing-triage-infra`）是两种不同的「没发现」。
- 「语法测试的 BNF 文法」（结构模型）与「攻击启发式库」（内容字典）：一个管结构、一个管内容，轮换使用。

### 授权与合规边界
> 待补充（用户自行填写）
