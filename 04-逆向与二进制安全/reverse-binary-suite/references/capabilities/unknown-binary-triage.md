# 陌生二进制逆向流程

## R — 原文 (Reading)

> 到目前为止，我们已经讨论了一些工具，利用这些工具，可以在对文件的内部结构知之甚少的情况下对文件进行粗略分析，也可以在深入了解文件的结构之后，从文件中提取出特定的信息。
> — 《IDAPro权威指南》第 2 章 逆向与反汇编工具（2.1–2.3）

> 需要记住的是：二进制文件中包含某个字符串，并不表示该文件会以某种方式使用这个字符串。
> — 《IDAPro权威指南》2.3.1 strings

> It is ideal to start with basic static and behavioural analysis and then continue with combined (static and dynamic) code analysis using the knowledge gathered during the first two phases.
> — 《Malware Reverse Engineering Handbook》Ch9 Conclusion

## I — 方法论骨架 (Interpretation)

这张卡解决「拿到一个从未见过的 exe/dll/so/固件镜像，第一小时该怎么花」的问题。核心洞察是：陌生二进制的分析成本几乎全花在「不知道该看哪」上，所以流程必须是广度优先、按成本递增的——先只回答「这是什么」，再回答「它含什么」，最后才回答「它在算什么」。

三级阶梯是这个流程的骨架：① 分类——用 `file` 判定架构、链接方式、是否 strip，这一步决定「要不要处理静态链接库代码」；② 摘要——用 `nm`/`ldd`/`objdump`/`readelf` 取符号、依赖、节表、导入导出，得到结构化元数据；③ 深度检测——用 `strings -a -t x` 抽带偏移的字符串、用 `ndisasm` 对裸 blob 流式反汇编。每上一级都以上一级的结论为前提，避免在一无所知时投入重分析。

第二层闭环是「从界面语义反攻代码」：界面提示语是二进制唯一自带语义的接触点，因此从字符串出发查交叉引用（`X`），落到引用它的函数，再回溯到「决定走成功还是失败」的那条条件跳转，比从入口 `start` 逐条读快一个数量级。这里有几条硬规则：字符串只是候选锚点，必须有 `r`（读取）或 `o`（取地址）交叉引用才算真被使用；优先从失败提示入手而非成功提示（成功提示可能是诱饵或资源）；同一函数内多处引用显示为 `函数名+偏移`，不同函数是不同的 `sub_XXXX`——这一步就把「有几条独立路径」读出来了。

第三层是「压缩分析面」：静态链接/去符号的二进制里库函数占 80% 以上代码量，先跑 FLIRT 签名把库代码整片标记并重命名，导航栏上只剩窄带应用代码，人工投入才有意义；`main` 可通过「启动序列里那个接收三参数、返回值传给 exit 的函数」定位（签名只是自动化了这一步）。对动态链接 ELF，`G` 跳到符号名只会落在 `extern` 条目，必须顺 `extern → .got → .plt` 三级数据交叉引用才能拿到真实调用点全集。数据结构方面，数组看 `[base+reg*N]` 的索引乘法、结构体看堆分配实参给出的总大小与一串递增常量偏移，两者都靠「一个基址上多个不同偏移」来识别。

贯穿全程的纪律是「静态结论必须被动态验证」：命中 `jmp 目标+1`（跳进指令中间）、跳转表、混淆插入的 `EB FF` 都会让线性反汇编整体错位；`call` 到 `目标+1` 会让函数边界错乱。恢复手段是 `U`（取消定义）错误指令、`C`（重新定义为代码）在真实入口重解。对 Android 系统应用则走 Manifest → 入口 Activity → `onCreate` 的 intent 分支 → 真正创建流程的类 → `showDialog()`/`installOthers` 的同类路径。

## A1 — 应用示例 (Application Example)

### 示例 1: 用 RCDefaultApp 枚举 QuickTime 的真实攻击面
- **类型与来源**: 【亲历】《Fuzzing for Software Security Testing and QA》Ch9（接口枚举）
- **问题/输入**: 官网只列出了主推格式，不知道这个软件实际能解析多少种文件。
- **方法论的使用**: 忽略官网功能页，直接查系统文件关联表（macOS 上用 RCDefaultApp），读出该应用注册的全部扩展名；对每个入口标注是否跨信任边界，从清单里挑一个入口（AVI）作为本轮目标，其余留作后续。
- **结论**: 一次拿到近 50 种格式，远超宣传列表；后续漏洞恰恰密集来自「功能集极大」这一被文档掩盖的事实。
- **结果**: 原书以 AVI 为入口展开后续 fuzz，并在 QuickTime 上验证出漏洞。

### 示例 2: 从失败提示定位 crackme 决策点并打补丁
- **类型与来源**: 【亲历】《从零开始学 IDA 逆向（上）》第 8 章
- **问题/输入**: 一个 crackme，字符串窗口里同时有成功与失败提示，需要找到「校验逻辑在哪」。
- **方法论的使用**: 从失败提示 "NO LUCK THERE, MATE!" 出发，按 `X` 看引用，发现引用分属两个不同的 `sub_XXXX`（即两条独立失败路径）；进入函数把它重命名为 `CARTEL_ERROR`、失败块染红/成功块染绿，再对失败函数按 `X` 回溯到唯一调用点，在控制走成功还是失败的条件跳转 `0x401243 JZ` 上打标记 `DECISION_FINAL`；最后把 `JZ` 改 NOP（而非反转成 `JNZ`，否则合法的用户名反而报错），第二处 `JB` 同样 NOP，写回文件验证两类输入。
- **结论**: 失败提示必然挂在「条件不满足」的出口上，天然紧邻决策点；拦截型跳转用等长 NOP 取消检查，比反转条件副作用更小。
- **结果**: 原书完成爆破，两类输入（应通过与应失败）都得到预期行为。

## A2 — 触发场景 (Future Trigger)

### 用户会在什么情境下需要它
1. 拿到一个没有符号、没有文档的可疑可执行文件，需要在几分钟内判断它是什么、有没有壳、值不值得深挖。
2. 想快速定位一个程序的校验/授权逻辑（crackme、授权判断、安全决策分支），而不是从入口读几万行汇编。
3. 静态链接的巨大二进制里几百个 `sub_XXXX`，需要先剥离库代码、找到 `main`，把分析面压缩到应用代码。
4. 反汇编结果与「感觉上」的执行流不一致（`call 目标+1`、跳转表、`EB FF`），需要恢复正确的指令边界。

### 语言信号（出现这些就该激活）
- 中文：「拿到一个 exe 不知道怎么下手」「先看看这是什么文件」「main 函数在哪」「字符串里看到 xxx 说明什么」「反汇编出来一堆乱码」「这个程序是不是加壳了」
- English: "how to start reversing an unknown binary", "triage a sample", "locate main in a stripped binary", "is this string actually used", "find the check with the error string", "disassembly desync fix"

### 与相邻能力的区分
- 与 `malware-behavior-analysis` 的区别：本卡是静态优先的侦察与定位（不执行样本），那张卡是跑起来看行为与环境规避；恶意样本的深度分析在其行为阶段之后才回到本卡的静态定位。
- 与 `binary-analysis-toolchain` 的区别：本卡判断「这是什么、关键逻辑在哪、分析面在哪」，那张卡处理「壳怎么脱、断点怎么下、结构怎么在 IDA 里建」的执行手法。

## E — 可执行步骤 (Execution)

**必需输入**: 一个本地二进制文件（PE/ELF/Mach-O 或裸 blob）；可选：能运行环境（用于验证静态假设）。缺运行环境时本卡仍可跑完静态部分，但「静态结论必须被动态验证」这一步无法完成，须标注置信度。

**交付物与完成标准**: 一份侦察报告，含 ① 文件类型/架构/链接方式/是否 strip；② 符号与依赖清单；③ 带偏移的字符串锚点表并标注哪些有真实交叉引用；④ 加壳/混淆判定；⑤ 关键函数清单与决策跳转位置；⑥ 已恢复的结构体/调用约定（如适用）。完成标准：每个结论都能指回一个具体地址或命令输出。

1. **三级分类侦察**
   - 做什么：`file` 取类型/架构/链接/strip；`nm` 读符号类型字母（U/T/t/D/C，大写全局小写局部）；`ldd`/`dumpbin /dependents`/`otool -L` 列动态依赖；`objdump`/`readelf` 取节表与导入导出。
   - 完成标准：能回答「要不要处理静态库代码」「哪些是程序自己的函数」。
   - 判停：若静态链接且无符号 → 转第 2 步的 FLIRT 路线；若有壳 → 转 `binary-analysis-toolchain`；若是裸 blob → 用 `ndisasm -u` 从指定偏移流式反汇编。

2. **抽字符串并验证使用**
   - 做什么：`strings -a -t x -e l` 抽字符串（含宽字符）带偏移；对每个可疑字符串在反汇编器里 `X` 查交叉引用，只有 `r`/`o` 才算被使用；顺引用回到函数并判断可达性。
   - 完成标准：锚点表里每条都标注「已验证引用 / 死代码存疑」。
   - 判停：若字符串来自库或从不执行 → 整条线索作废，换锚点。

3. **压缩分析面**
   - 做什么：先跑 FLIRT 签名把库代码整片标记重命名，读导航栏只剩窄带应用代码；按四判据定位 `main`（签名 / 三参数唯一性 / `__libc_start_main` 第一参数 / `_p_argc` 引用）；ELF 里沿 `extern → .got → .plt` 找真实调用点；对危险 API 用 `CTRL+X` 穷举调用点（`p` 直接调用 + `o` 取地址间接调用）。
   - 完成标准：得到应用代码范围、main 地址、危险 API 调用点全集。
   - 判停：若无可用签名（自编译 libc）→ 手工判定或自造 FLAIR 签名；若调用点过多 → 用 `flagCalls()` 类脚本打 `*** AUDIT HERE ***` 注释。

4. **从提示语反攻决策点**
   - 做什么：优先选失败提示（成功提示可能是诱饵），`X` 看引用分属几个函数（读 `sub_XXXX` 前缀判断独立路径数）；进入函数确认该字符串如何被消费（如 MessageBox 正文）；`N` 重命名、失败块染红/成功块染绿；回溯到唯一调用点上方的条件跳转，用 `Jump ▶ Mark Position` 打标记。
   - 完成标准：定位到具体的决策跳转地址，并列出所有必须绕开的失败路径。
   - 判停：若成功提示的引用不与同一决策点相连 → 放弃成功提示，只用失败提示。

5. **恢复结构与调用约定（按需）**
   - 做什么：用 `[base+reg*N]` 判定数组并读元素宽度；看堆分配实参得结构体总大小，跨函数累积 `[reg+off]` 偏移得字段表；用 `T`/`Convert to struct *` 在 IDA 里增量补字段，遇到更大偏移就追加；函数入口「未初始化即被读」的寄存器即隐含参数，用 `_usercall` 原型标注。
   - 完成标准：结构体布局自洽（最大偏移+字段宽度 ≤ 已定义结尾），隐含参数在调用点被正确注释。
   - 判停：若参数识别整体错乱 → `U` 取消定义再 `C` 重新识别并 `Create Function`。

6. **静态结论的动态验证（可选项）**
   - 做什么：对决策跳转用 NOP 而非反转条件（拦截型才 NOP，等长 `0x90` 填满）；对 `jmp 目标+1` 类错位用 `U`→`C` 重同步；在调试器中单步确认真实执行流与手工恢复的序列一致。
   - 完成标准：静态恢复的序列与调试器实际执行一致，补丁写回后应通过与应失败的输入都符合预期。
   - 判停：若加壳或反调试导致无法验证 → 转 `binary-analysis-toolchain`，本卡的静态结论标注「未验证」。

## B — 边界 (Boundary)

### 不要用的情况
- 目标是纯算法/密码校验且完全不调用任何外部 API、也没有可见字符串时，锚点法失效，需要靠行为阶段的数据流或纯算法还原，本卡帮不上。
- 样本已加壳/强混淆时，strings 被加密、导入被抹、反汇编被去同步，此时三张索引都不可信——先脱壳（转 `binary-analysis-toolchain`）再回来。
- 只是想确认一个已知格式能否被解析（验收测试），不必走全流程，直接黑盒投递即可。

### 已知失败模式
- 只凭扩展名判断文件类型——原书明确列为「最基本的原则」级错误（IDA 权威指南第 2 章）。
- 把字符串直接映射为功能（见到 "Congratulations" 就认定成功分支、见到 `strcpy` 字符串就认定用了 strcpy 函数）——IDA 权威指南 2.3.1 警告。
- 只处理一条失败路径，改完仍弹另一个失败框——《从零开始学 IDA 逆向（上）》第 8 章亲历。
- 反转条件跳转导致合法输入走进错误分支（把 `JB` 改 `JNB` 后数字用户名报错）——同上。
- 只看 `p` 交叉引用漏掉经寄存器/函数指针的间接调用（`mov esi, ds:strcpy` + `call esi` 只有 `o` 引用）——IDA 权威指南 9.1。
- 只看 Manifest 就下 Android 结论，真正逻辑在 `CertInstaller`/`CredentialHelper` 里——酒仙桥 022（CVE-2020-0015）。

### 作者与时代的局限
- FLIRT 依赖与目标同版本同编译选项的 `.sig`；自编译 libc 或加壳改写的启动例程会让签名匹配率极低（IDA 权威指南第 12 章）。
- `main` 的四条判据基于 32 位 x86 的 cdecl 栈帧与 glibc/MSVC 启动序列；64 位（Windows x64 用寄存器传参、SysV ABI）与 ARM 需调整判据细节。
- Android 弹窗劫持案例（CVE-2020-0015）针对 Android 8–10 的低版本设备，高版本加入 `SYSTEM_FLAG_HIDE_NON_SYSTEM_OVERLAY_WINDOWS` 后形态变化。

### 容易混淆的方法
- 「静态去同步」与「加壳」都表现为大段不可解字节：前者不改字节、只改解析边界（用 `U`/`C` 修），后者是真密文、需先解密。
- 「字符串当线索」与「字符串当结论」是同一数据的两种用法，必须靠交叉引用把后者降级为前者。
- 「 FLIRT 识别库函数名」与「重建 IAT 恢复导入地址」（见 `binary-analysis-toolchain`）方向相反：一个给静态库函数命名，一个在脱壳后恢复导入表。
