## I — 方法论骨架 (Interpretation)

这张卡解决「样本加壳/混淆/反调试，静态看到的是噪声，怎么拿到真实代码」的问题。核心思路是把壳当成一个结构高度一致的处理流程：开头保存寄存器（PUSHAD）、中间解密/解压循环、结束恢复寄存器（POPAD）、然后跳到原始入口点（OEP）。因此不必理解压缩算法——只要在「数据已还原到内存、尚未跳转」的那一刻把进程内存 dump 出来，再修复导入表即可。

判定加壳靠四信号共振：可读字符串极少、导入/函数极少、熵值高、字节直方图从「有 MOV/PUSH/CALL 造成的多峰」变成均匀分布。单看熵会误伤大块加密配置/资源。PE 结构异常是更强的证据：节表里 `RawSize≈0` 而 `VirtualSize` 很大（如 `UPX0` 文件 0/内存 0x8000）是「还原目标区」；入口落在最后一个节尾部而非第一个代码节起始；导入表几乎为空（还原由 stub 自己完成）。

找 OEP 有两条独立判据，互为备份：① 执行断点法——对「被还原的目标节」整段下**执行**断点（必须关掉读写触发，否则解密循环写目标区时就中断在半成品），第一次命中即 OEP；② PUSHAD-POPAD 法——在 `pushad` 下一条指令设临时断点，停下时栈顶是寄存器保存区，在该栈地址下**读写**断点（那里没有代码，执行断点永远不触发），命中时正在 `popad` 恢复，紧接着的跳转就是 OEP。壳作者刻意避免 `pushad` 时第②条失效，回退第①条。

断点选择有一条硬规则：软件断点把目标首字节改成 `0xCC`，任何「往那段内存写数据」的操作（解包器把原始程序写到 00401000）都会抹掉它——此时必须用硬件断点（DR 寄存器比对地址，不改内存，还能表达「写该地址时中断」），但只有 4 个 DR 槽。反汇编去同步则是另一类问题：不加密字节，而是让反汇编器从错误边界解码（`call 目标+1`、`jmp short $+1`、恒真条件跳跨过垃圾、`EB FF` 借字节），表现为用户态出现 `iret`/`out`、大段 `db` 夹在代码中间；修复是 `U`（取消定义）错误指令、`C`（真实入口重定义为代码）。

当样本恶意到不宜执行、或跨架构本机调试器不支持时，走第三条路——静态去模糊：把解密循环当纯计算问题，用 IDC/IDAPython 复现寄存器/内存赋值（`while` 模拟循环体），或用指令模拟器（ida-x86emu，`ALT+F8`）以数据库为后备存储逐条模拟，所有写入落在 IDA 数据库里，模拟结束时数据库本身就是去模糊后的镜像。库调用直接 Skip 并手工补齐副效应（改 EAX、填出参、按 stdcall 手调 ESP）。

dump 之后 IAT 是坏的：磁盘 IAT 存「指向函数名字符串的 RVA」，内存里已被填成本机绝对地址，换机/重启基址变化就全错。重建是把每项从本机地址反查回函数名/RVA，判据是「真正的 API 地址应当有代码引用」——按 `D` 展开后既不是有效地址、`Ctrl+X` 也无引用的项应删除后重新 Autosearch。最后 `dump fixer` 把所有节 `RawSize` 改成与 `VirtualSize` 一致，否则文件偏移与内存偏移错位。崩溃转储分析（无源码/无符号/只有 dmp）也归本卡：读出错指令与寄存器（`call eax` 且 `eax=0` 即调用地址 0，往上找失败的 GetProcAddress），间接调用按「读指针值 + 加基址 + 读字符串」还原 API 名。

## A1 — 应用示例 (Application Example)

### 示例 1: 对 UPX 加壳程序用执行断点找 OEP 并修 IAT
- **类型与来源**: 【亲历】《从零开始学 IDA 逆向（上）》14/15 章
- **问题/输入**: 一个 UPX 加壳的 PE，`UPX0` 节 `RawSize=0`/`VirtualSize=0x8000`，入口从 0x401000 漂到 0x409be0，如何拿到脱壳后的程序？
- **方法论的使用**: 调试器选 Local Win32 在 stub 入口暂停；跳到 0x401000 起的 0x8000 目标节，对整段下执行断点（关掉读写触发），禁用其他断点，F9 一次命中 0x401000 即 OEP；`Reanalyze program` 让 IDA 识别为 `sub_401000`，`Take memory snapshot` 保存镜像；dump 后用 `dump fixer` 对齐节表，attach 停在 OEP 的进程做 `IAT Autosearch` 得起始 0x403184/大小 0x108，`Get Imports` 识别，发现 0x46080c 处「不指向有效地址、Ctrl+X 无引用」的坏项，删除后重新 Autosearch 全部识别，`Fix Dump` 写回。
- **结论**: 执行断点必须限定「执行时」触发，读写触发会在解密阶段反复中断拿到半成品；判 IAT 坏项要看是否有代码引用，不能只看地址是否落在模块范围内。
- **结果**: 原书得到入口为 OEP、调用点显示与原程序一致 API 名的脱壳文件。

### 示例 2: ASPack 软件断点被覆盖，改硬件断点
- **类型与来源**: 【亲历】《有趣的二进制》2.2.6
- **问题/输入**: 对 ASPack 加壳样本，`00401000` 处的软件断点在解包过程中静默消失。
- **方法论的使用**: 判断属于「会被写入覆盖」场景（解包器把原始程序写到 00401000），不用软件断点；右键 → Breakpoint → Hardware, on execution 在 00401000 下硬件执行断点，F9 命中后 Ctrl+A 重新分析，确认数据已还原；计数不超过 4 个硬件断点。
- **结论**: 硬件断点走 DR 寄存器不改内存，不会被解包写入覆盖；第 5 个硬件断点需求必须改用软件/条件断点替代。
- **结果**: 原书一次命中 OEP，后续 dump 成功。

## A2 — 触发场景 (Future Trigger)

### 用户会在什么情境下需要它
1. 样本字符串是乱码、导入极少、熵很高，IDA 提示 packed，需要先确认加壳再脱壳。
2. 脱壳时断点总在解密循环里停，或断点「自己消失」，需要换断点类型与触发条件。
3. 样本恶意到不宜执行、或跨架构（ARM/MIPS）本机调试器不支持，需要不执行就拿到去模糊后的镜像。
4. 反汇编出现 `jmp 目标+1`、用户态 `iret`、大段 `db`，需要恢复正确的指令边界。
5. 手上只有崩溃 dmp 与 Dr. Watson 日志、没有符号，需要黑箱归因到具体 API 调用。

### 语言信号（出现这些就该激活）
- 中文：「这程序是不是加壳了」「OEP 怎么找」「脱壳断点没用」「断点自己消失了」「怎么脱壳」「IDA 反汇编和实际执行不一致」「dump 出来打不开/没图标」「没有符号怎么调试」
- English: "how to tell if a binary is packed", "find original entry point of packed binary", "breakpoint fires during unpacking", "hardware vs software breakpoint", "deobfuscate without executing", "disassembly desync fix", "rebuild import table after unpacking"

### 与相邻能力的区分
- 与 `unknown-binary-triage` 的区别：那张卡判定「这是什么、关键逻辑在哪、分析面在哪」，本卡处理「壳怎么脱、断点怎么下、结构怎么在 IDA 里建」的执行手法；那张卡遇到加壳时把样本转给本卡。
- 与 `malware-behavior-analysis` 的区别：那张卡在环境层面判断「要不要脱壳、有没有反调试」，本卡执行具体脱壳/断点/去混淆；本卡拿到 OEP 后把样本交回那张卡继续行为分析。

## E — 可执行步骤 (Execution)

**必需输入**: 加壳/混淆样本本体；调试器（WinDbg/OllyDbg/Immunity/IDA）与 dump 插件（OllyDump/Scylla）；可选：模拟器（ida-x86emu）用于不执行路线。缺 dump 插件时本卡前 5 步可做，第 6 步 IAT 重建需补工具。

**交付物与完成标准**: ① 加壳判定结论（四信号 + PE 结构证据）；② OEP 地址；③ 脱壳后的内存镜像/dump 文件；④ 重建后的 IAT 与可正常加载的程序；⑤ 去同步修复后的反汇编（如适用）；⑥ 崩溃归因报告（如适用）。完成标准：脱壳文件用 IDA 打开后 0x401000 起是正常函数序言，调用点显示原 API 名。

1. **判定加壳与定位目标区**
   - 做什么：四信号检查（strings 少、导入少、熵高、直方图均匀）；看节表找 `RawSize≈0`/`VirtualSize` 大的节（UPX0/.aspack）——那是还原目标区；看入口是否落在最后节尾部；导入表是否几乎为空；加载时取消「创建导入段」。
   - 完成标准：确定「这是壳」并记下目标节起止地址与还原后代码长度（如 0x8000）。
   - 判停：若只是反汇编错位（字节未加密）→ 转第 5 步去同步；若样本不宜执行 → 转第 4 步静态去模糊。

2. **找 OEP（执行断点 / PUSHAD-POPAD 双判据）**
   - 做什么：① 对目标节整段下执行断点（关读写触发），第一次命中即 OEP；或 ② 确认入口是 `pushad`，在其下一条设临时断点，停下时栈顶为保存区，在该栈地址下读写断点（类型 3），命中即 `popad` 恢复，单步到随后的 `jmp`/`push ret` 得 OEP。
   - 完成标准：拿到 OEP 地址，且命中时目标区数据已还原。
   - 判停：若断点在解密阶段反复中断 → 触发类型设错，改「执行时」；若栈地址下执行断点永不触发 → 那里是数据，改读写；若新式壳无 `pushad` → 只用判据①。

3. **按断点覆盖风险选类型**
   - 做什么：目标区会被写入时（脱壳、自解密、自校验改写代码）不用软件断点，改硬件断点 on execution；软件断点的 `0xCC` 会被写入抹掉；硬件断点最多 4 个。
   - 完成标准：断点能稳定命中且不被覆盖。
   - 判停：第 5 个硬件断点需求 → 用软件/条件断点替代；若需「写该地址时中断」→ 用硬件断点的读写属性而非执行属性。

4. **静态去模糊（不执行路线，可选项）**
   - 做什么：定位「循环读源、算、写目标」的解密例程（如 `ESI` 指密文、`EDI=ESI-0x8000` 指目标）；脚本路线把每个寄存器/内存位置声明为 IDC 变量、循环体翻成 `while`；模拟器路线激活 x86emu（`ALT+F8`），按需创建 `.stack`/`.heap`，必要时把 EIP 处字节强制按代码格式化；抵达「跳向原始入口」的指令后停止，库调用 Skip 并补齐 EAX/出参/ESP 副效应。
   - 完成标准：IDA 数据库里已是明文，回反汇编视图按 `C` 重新识别函数。
   - 判停：若脚本漏掉循环外副作用（`pushf`/`pusha` 保存的状态）导致后续状态错 → 补齐；跳过库函数后必须修正 ESP/EAX。

5. **反汇编去同步修复**
   - 做什么：找症状（`call`/`jmp` 目标带 `+1`、用户态 `iret`/`out`/`hlt`、大段 `db` 夹在代码中）；在错误指令处 `U` 取消定义，在真实目标按 `C` 重定义为代码，重复到整段控制流自洽；对寄存器计算的目标（如 `pop eax` + `lea eax,[eax+0Ah]` + `jmp eax`）手工算出真实地址。
   - 完成标准：跳转目标都落在指令起始处，函数边界完整。
   - 判停：若混淆插 `EB FF` 借字节（`call` 在 IDA 中消失）→ 以跳转目标为起点重新按指令边界解读，并用调试器单步确认真实执行路径。

6. **dump 并重建 IAT**
   - 做什么：从基址到末节末尾逐字节写出 dump；`dump fixer` 把所有节 `RawSize` 改成与 `VirtualSize` 一致；attach 停在 OEP 的进程做 `IAT Autosearch`（得起始/大小）与 `Get Imports`；对无法识别的项按「是否有代码引用」判定——按 `D` 展开既非有效地址、`Ctrl+X` 无引用即删除后重搜；用 `Show suspect` 复核；`Fix Dump` 写回；加载验证入口为 OEP、调用点显示原 API 名。
   - 完成标准：脱壳程序可正常加载运行，API 调用点有名。
   - 判停：若脱壳后仍崩溃 → 检查是否只重建了部分项（首次调用未修 API 即崩），或漏做 `dump fixer` 导致节映射错乱。

7. **崩溃转储归因（可选项）**
   - 做什么：取 dmp（任务管理器创建转储、`drwtsn32 -i` 注册实时调试器）；WinDbg 读错误码/模块基址/出错指令与寄存器（Alt+6/7/4/5）；`call eax` 且 `eax=0` → 找失败的 GetProcAddress；间接调用 `call dword ptr [00402004]` 按「读值 0x2404 + 基址 0x400000 = 0x402404 → 读字符串 GetProcAddress」还原 API 名。
   - 完成标准：定位到根因（如 DLL 名拼错导致 LoadLibrary/GetProcAddress 双双失败后被直接 call）。
   - 判停：EIP=0 时反汇编窗口全是问号 → 从调用栈反推上一层，不依赖符号。

## B — 边界 (Boundary)

### 不要用的情况
- 目标是标准 UPX 等已知壳且有现成解包器时，优先 `upx -d`，不必手工脱壳。
- 未加壳的程序（无四信号、节表正常）套本卡只会浪费时间，转 `unknown-binary-triage`。
- 纯逻辑/算法类二进制的安全决策定位（crackme 授权判断）不涉及壳，转 `unknown-binary-triage`。

### 已知失败模式
- 用软件断点跑带校验和的解压循环，断点写入 `0xCC` 改变校验和或被打包器改写，解密结果错、断点静默消失（《有趣的二进制》2.2.6）。
- 对目标节下读写触发断点而非执行触发，解密写入阶段反复中断拿到半成品（《从零开始学 IDA 逆向（上）》14.8）。
- 跳过 `dump fixer` → 文件能用十六进制打开但节映射错乱、图标资源读不到；把「本机地址恰好落在某模块范围内」当成有效 IAT 项（应看是否有引用）（上 15 章）。
- 脚本只翻译了解密循环却漏掉循环外副作用（`pushf`/`pusha` 保存的状态），导致后续状态错（IDA 权威指南 21.3）。
- 反汇编去同步只改一处就往下读，后面依然是错边界；把 `db` 当数据跳过导致真正代码块被当成数据（21.1.1）。

### 作者与时代的局限
- 硬件断点只有 4 个 DR 槽是 x86/x64 架构限制；ARM 等架构的调试寄存器数量与语义不同。
- PUSHAD-POPAD 法依赖老式壳/未做对抗的壳的 `pushad` 习惯，书内明确指出「壳作者知道这个规律」并会刻意避免；执行断点法不依赖该习惯。
- 静态去模糊示例（Burneye、x86emu）面向 32 位 x86；64 位与跨架构（ARM/MIPS）需不同的模拟器与调用约定补齐。
- ASLR 开启后固定 OEP 候选地址（如 00401000）不再可靠，硬件断点打不中，须回退「自己找 POPAD」（《有趣的二进制》2.2.5）。

### 容易混淆的方法
- 「反汇编去同步」（不改字节、只改解析边界，`U`/`C` 修复）与「加壳」（真密文、需先解密）都表现为大段不可解字节，但处理完全不同。
- 「软件断点被覆盖」与「条件断点命中判断」：前者解决「断点被改写」，后者解决「何时命中」，不要混用。
- 「FLIRT 识别库函数名」（`unknown-binary-triage`）与「重建 IAT 恢复导入地址」（本卡）方向相反，但都属导入/符号知识。

### 授权与合规边界
> 待补充（用户自行填写）
