# 注入与过滤器绕过审计

## R — 原文 (Reading)

> Make a list of every input the filter allows. Make a list of every input that's dangerous if left in the input stream. Check whether there are any results from the intersection of these two lists.
> — 《The Art of Software Security Assessment》Ch8 Metacharacter Filtering

> This algorithm demonstrates a subtle issue common to many multicharacter filters that strip invalid input. By supplying characters around forbidden patterns that combine to make the forbidden pattern, you have the filter itself construct the malicious input by stripping out the bytes in between.
> — 《The Art of Software Security Assessment》Ch8 Character Stripping Vulnerabilities

> escape_string ⽅法并不会转义 % ，所以我们将 Payload 进⾏ URL 编码后并不会被 escape_string ⽅法改变任何内容。⽽当到达 xss_clean 时 Payload 将被 URL 解码，从⽽绕过了对 SQL 注⼊的过滤。
> — 《163酒仙桥六号部队》030 察言观色也能挖到0day（绕过修复方案）

## I — 方法论骨架 (Interpretation)

这张卡解决「一段输入会不会被注入、过滤器/补丁能不能被绕、绕不过时换什么原语」的问题。它把注入判定从「背 payload」变成「找谁在解释数据 + 集合运算 + 处理顺序分析」。

基础判据是集合差：定位数据最终被谁解释（shell、SQL、格式化函数、路径解析、环境变量展开）；枚举该解释器的全部元字符与元序列（含换行、`..`、`%VAR%` 等非常规项）；确认上游过滤覆盖了哪些（注意过滤点与解释点之间是否还有二次变换或解码）；求「危险字符集 − 已过滤字符集」，非空即有漏洞。过滤器强度另用「允许集 ∩ 危险集」判定——安全性只取决于「放行了什么」不取决于「拦住了什么」：黑名单默认放行未知字符，任何遗漏都是漏洞且随解释器版本扩展而失效；白名单默认拒绝，遗漏只造成功能问题。拒绝非法输入也比剥离更安全，因为剥离逻辑本身容易写错。

三类结构性失效是绕过的主要来源：
- **剥离式过滤器**：剥离会修改输入，若实现「删掉命中片段后跳过其后 N 字节」或「不回溯重扫」，攻击者把禁用序列拆开写入（`....//`），让过滤器自己把中间字节删掉后拼回完整序列。这类缺陷只能靠走查剥离循环的指针推进逻辑发现，无法通过「检查过滤规则是否完整」发现。
- **检查与解码顺序**：若 URL/HTML/Unicode/hex 解码发生在检查之后，`%2e%2e` 让检查看到「无点号」的字符串而 `open()` 看到 `../`。两层过滤器叠加也不是「更难绕」：`escape_string` 转义引号/反斜杠/换行但不碰 `%`，后接的 `xss_clean` 见 `%` 就 `rawurldecode` 整串解码——「先转义、后解码」把转义结果还原成原始注入字符，净效果是零防护。安全口径是先完全规范化到唯一表示，再对规范化结果做白名单比对。
- **原语替换**：白名单不是在「减少 payload 数量」而是在「缩小可用原语集合」。禁掉括号 → 所有函数（sleep/substring/mid）失效；禁掉比较符 → 布尔判断失效。此时不要硬凑 payload，而要重算原语：`where` 可接子查询（不需括号）、`regexp '^ad.*'` 可替代 `=`+`substr`、16 进制可替代引号、SQL 执行顺序 `where` 先于 `select` 可把判断放 where 用返回行数作布尔信道。

还有三个高价值入口：① 格式串——唯一判据是 format 参数是否为常量，非常量即回溯，危险等级由 `%n`（任意地址写任意值）决定，易漏点是包装函数（`vsnprintf` 透传）与日志函数（`vsnprintf` 后再 syslog 二次格式化）；② changelog/issue——开源项目 changelog 是「已修漏洞清单」、issue 是「完整施工图」，最高价值信息在修复者与上报者的往返对话，开发者第一次修错、第二次修偏说明他对漏洞类型的理解模型是错的，第二次补丁大概率还能绕；③ 解析差异——用模式匹配去补语义差异只能挡住见过的形状（F5 官方缓解第一版挡 `.*\.\.;.*` 被 `/hsqldb;` 绕、第二版挡 `;` 被 `/hsqldb%0a` 绕）；黑盒异常现象（302 而非 401、Cookie 直接生效）是白盒审计入口，而校验函数绕不过时改「进校验之前的那个参数」（`os.path.join(base,'/')` 直接返回 `/`，绕过 `abspath` 包含 base 检查）。

## A1 — 应用示例 (Application Example)

### 示例 1: PCNFSD 拒绝集漏换行符
- **类型与来源**: 【转述】《The Art of Software Security Assessment》Ch8
- **问题/输入**: `strpbrk(s, ";|&<>`'#!?*()[]^")` 的拒绝集看起来很完整，数据送 `popen()` 还能命令注入吗？
- **方法论的使用**: 读过滤器实现逐字符推导允许集（不是读注释或命名）；按下游解释器（shell）列危险集——换行在 shell 中就是命令分隔符；求交集发现 `\n` 未被拒绝；构造含换行的输入验证。
- **结论**: 凭经验「看一眼觉得够全」不可靠，必须显式列集；黑名单遗漏换行/反引号/`$()`/空白变体是典型失效。
- **结果**: 原书以此例说明拒绝集完整仍可被绕过。

### 示例 2: rev2 双重过滤器经 URL 编码还原注入
- **类型与来源**: 【亲历】《163酒仙桥六号部队》030
- **问题/输入**: 开源 CMS 1.2.3 修了 SQL 盲注（Issue#19）、1.2.4 修了文件上传（Issue#20），rev2 用 `escape_string` + `xss_clean` 两层过滤，原 payload 已失效。
- **方法论的使用**: 读 changelog 列「漏洞类型 × 版本」表；打开 issue 取问题文件、payload、成因、修复建议；读开发者/上报者对话，发现开发者用 `xss_clean`（XSS 过滤函数）修 SQL 注入——修错层次；对修复前后同一文件 diff，看到两层过滤叠加；列出 `escape_string` 处理的字符集（`\x00 \n \r \ ' " \x1a`，不碰 `%`）与 `xss_clean` 的触发条件（见 `%` 调 `rawurldecode`）；对原始时间盲注 payload 整体 URL 编码，使其在第一个过滤器眼里不含危险字符，到达第二个时被解码还原。
- **结论**: 根因是「处理顺序缺陷」而非「过滤不全」——先转义后解码把转义结果又还原了；原 payload 失效恰恰是新绕过的起点。
- **结果**: 原书构造 `**'-( if((1=1), sleep(5), 1) )-''**` 的 URL 编码版，仍触发时间盲注。

## A2 — 触发场景 (Future Trigger)

### 用户会在什么情境下需要它
1. 判定一处输入是否可注入（命令/SQL/路径/格式串），并系统性枚举元字符而不是靠记 payload。
2. 评估一个过滤器/黑名单/白名单是否足够，判断该找遗漏项还是「看似合法实则可组合」的项。
3. 已知一个开源项目修过漏洞，想从 changelog/issue 反推「补丁没补住」的绕过点。
4. 过滤器叠加后原 payload 失效，需要判断净防护是增强还是互相抵消。
5. 白名单禁掉了括号/比较符/引号，经典盲注函数全被过滤，需要重算可用原语。

### 语言信号（出现这些就该激活）
- 中文：「这里能不能注入」「metacharacter 怎么系统查」「命令注入/路径穿越怎么判」「这个过滤够不够」「黑名单还是白名单」「为什么过滤了还能注入」「过滤了 ../ 还能穿越吗」「格式串漏洞怎么找」「开源 CMS 怎么挖 0day」「changelog 能看出什么」「补丁绕过怎么做」「WAF 叠加怎么绕」「双重过滤还能注入吗」「过滤了括号还能注入吗」「打了补丁还能打吗」
- English: "metacharacter filtering", "format string audit", "character stripping bypass", "filter order bypass", "double encoding", "patch bypass", "whitelist primitive reduction", "regexp injection", "official mitigation bypass"

### 与相邻能力的区分
- 与 `source-audit-dataflow` 的区别：那张卡找「数据是否可控、是否连通到危险操作」，本卡接手判「危险操作处注入是否成立、过滤器/补丁是否可绕」。
- 与 `memory-integer-audit` 的区别：本卡处理解释器语义与字符集/编码问题，那张卡处理内存布局与整型语义。
- 与 `protocol-and-race-audit` 的区别：先检查后解码与路径检查顺序属本卡的「表示层不一致」，而文件系统层的检查/使用分离（TOCTOU）属那张卡。

## E — 可执行步骤 (Execution)

**必需输入**: 目标代码或配置（过滤器实现、处理链顺序、补丁 diff）；下游解释器类型（shell/SQL/路径/格式化）；能观察响应差异（页面内容/延时/返回码）。缺源码时只能做黑盒 payload 探测，无法判断顺序根因。

**交付物与完成标准**: ① 元字符危险集与已过滤集的差集；② 过滤器类型与强度判定；③ 处理链顺序图（接收→解码→规范化→检查→使用）；④ 格式串 format 常量性回溯结果；⑤ 补丁绕过的根因分类（顺序缺陷/原语替换/解析差异/修错层次）；⑥ 最小验证输入。完成标准：每个结论都有「谁解释、谁解码、先后如何」的可复核依据。

1. **定位解释器与列元字符集**
   - 做什么：确定数据最终被谁解释（shell/SQL/格式化函数/路径解析/环境变量展开）；枚举该解释器的全部元字符与元序列（含换行、`..`、`%VAR%`、非常规分隔符）；对格式串单独走判据——搜 printf/fprintf/sprintf/snprintf/vsnprintf/syslog/err 家族，标记 format 非字面量的调用，递归检查自定义变参包装函数与日志函数，确认 `%n` 可用时按「任意写」定级。
   - 完成标准：危险集清单 + 格式串 format 常量性结论。
   - 判停：只按常见字符表查易漏组件特有元字符（如 `%` 被 ExpandEnvironmentStrings 解释）→ 必须按实际解释器列全。

2. **求差集判注入**
   - 做什么：逐一确认上游过滤覆盖了哪些字符；注意过滤点与解释点之间是否还有二次变换/解码；求「危险集 − 已过滤集」，非空则构造最小验证输入；对「数据先存储后解释」的场景按二阶注入处理。
   - 完成标准：差集非空/空的结论 + 最小验证输入。
   - 判停：差集为空但怀疑有漏洞 → 转第 3 步查过滤器实现细节与顺序。

3. **判过滤器强度**
   - 做什么：读过滤器实现逐字符推导允许集（不是读注释/命名）；列危险集；求「允许集 ∩ 危险集」；黑名单重点找遗漏项（换行、反引号、`$()`、空白变体），白名单重点找「看似合法实则可组合」的字符；检查过滤点与使用点之间是否还有解码/展开步骤。
   - 完成标准：交集结果 + 过滤器类型（黑名单/白名单/剥离）+ 遗漏项清单。
   - 判停：凭经验「看一眼觉得够全」→ 禁止；剥离式过滤器 → 转第 4 步走查指针推进。

4. **走查剥离循环的顺序缺陷**
   - 做什么：定位剥离循环，确认删除后 `src`/`dst` 指针如何推进；构造「禁用序列 + 插入字节 + 禁用序列后缀」的输入（如 `....//`）用 desk-check 走查；若输出中重新出现完整禁用序列即为绕过；修复方向是删除后不前进读取指针（同位置重扫）或单次替换后再次校验结果。
   - 完成标准：确认「过滤器自己拼回禁用序列」或排除。
   - 判停：只测试正常禁用序列是否被删 → 不够；看代码觉得「已经删掉了 ../」就通过 → 不够（两版实现各有缺陷）。

5. **分析处理链顺序与多层叠加**
   - 做什么：写完整处理链（接收 → 解码 URL/HTML/Unicode/hex → 规范化 → 检查 → 使用）；若「检查」不在最后一次解码之后 → 直接判缺陷；构造等价载荷（`%2e%2e%2f`、`%252e` 双重编码、大小写混合、超长 UTF-8）验证；对多层过滤器列每层处理的字符集与触发解码的条件，判断是「先解码后转义」（安全）还是「先转义后解码」（零防护）。
   - 完成标准：处理链顺序图 + 等价载荷验证结果。
   - 判停：只在业务层加过滤而框架层还会解一次 → 必须计入；把 URL 解码与 HTML 解码混为一谈（顺序不同绕过方式不同）→ 分开分析。

6. **从 changelog/issue 挖补丁绕过**
   - 做什么：读 changelog 列「漏洞类型 × 版本」表；打开 issue 取问题路径、payload、成因、修复建议；拉修复前后同一文件 diff；读对话判断修复者是否理解根因（如用 XSS 过滤函数修 SQL 注入即修错层次）；对补丁叠加检查两过滤器处理顺序与字符集差异；构造穿过第一个又被第二个还原的输入。
   - 完成标准：根因分类 + 可复现的绕过输入。
   - 判停：只验证原 payload 是否失效就收工 → 原 payload 失效恰是新绕过起点；只看 diff 不看讨论 → 漏掉最有价值的「开发者认知偏差」信号。

7. **绕不过时重算原语 / 换参数**
   - 做什么：从过滤函数读白名单字符集，列出「被禁字符 → 失效攻击原语」映射（括号→函数、引号→字符串、比较符→布尔）；为每个失效原语找替代（子查询、regexp、16 进制）；利用 SQL 执行顺序把判断放 `where`，用返回行数/页面内容作布尔信道；校验函数绕不过时改「进校验之前的那个可控参数」（`os.path.join(a,'/')` → `/`），前端限制不可改则回后端接口补字段；判断解析差异类问题（两个组件对同一 URI 解释不一致）时构造仍能通过鉴权组件、却被路由到目标的写法（`;` 参数分隔、`%0a` 编码变体）。
   - 完成标准：重建的可用原语 + 可复现输入 + 根因分类。
   - 判停：反复试 `sleep()`/`substring()` 全被过滤后判「不可利用」→ 错，应重算原语；`regexp` 不加 `^` 锚定 → 逐字符判断失真；应用官方缓解就认为已缓解 → 必须重新验证编码变体。

## B — 边界 (Boundary)

### 不要用的情况
- 纯内存破坏/整型问题（无解释器语义），转 `memory-integer-audit`。
- 文件系统层的检查/使用分离（TOCTOU、symlink 竞态、目录链权限），转 `protocol-and-race-audit`。
- 黑盒异常现象需要反向定位审计起点（如 302 登录异常指向认证逻辑），本卡第 6 步可借力，但完整的白盒定位在 `source-audit-dataflow`。

### 已知失败模式
- PCNFSD 拒绝集很完整却漏了换行符，数据送 popen() 可执行任意命令（Ch8）。
- 剥离式过滤器可被 `....//` 绕过：第一版跳过三字节、第二版（修正版）仍可被 `....//hi` 绕过（Ch8 Listing 8-25/8-26）。
- 先做路径检查再做 URL 解码，`%2E%2E/%2E%2E` 即可穿越（Ch16 open_resource）。
- 只改 payload 语义不做顺序分析：F5 官方缓解第一版挡 `.*\.\.;.*` 被 `/hsqldb;` 绕、第二版挡 `;` 被 `/hsqldb%0a` 绕（酒仙桥 045）。
- 只看 `allow_url_fopen` 忘了 `allow_url_include` 与 `php://input`——PHP 文件包含可经包装器变 RCE（Ch18）。
- 白名单禁括号后反复试 `sleep()`/`substring()` 全部被过滤就判「不可利用」（酒仙桥 093）。
- 只在 `path` 参数上做各种 `..`/编码/截断，被 `abspath` 统一挡回，忽略 `username` 这个可控操作数（酒仙桥 105）。

### 作者与时代的局限
- 元字符表基于 2007 年前后的 shell/SQL/C 格式化函数语义；现代 NoSQL、ORM、模板引擎、GraphQL 的元字符与解释层需重新枚举。
- PCNFSD/`strpbrk`、antisniff、PHPXMLRPC 等案例是历史漏洞，用于说明方法而非现状。
- 格式串 `%n` 任意写在现代编译器/平台上多已默认禁用或缓解，定级时需结合目标实际配置。
- 酒仙桥系列案例抽取文本有空格插入/康熙部首替换，引用按抽取原样保留，比对时忽略空白差异。

### 容易混淆的方法
- 「黑名单遗漏」（元字符不在拒绝集）与「剥离实现缺陷」（规则完整但指针推进错）是两类不同问题，前者看集合、后者看循环。
- 「先转义后解码」（零防护）与「先解码后转义」（安全）是顺序问题，与过滤器数量无关。
- 「原语替换」（字符集缺失导致函数失效，改用 regexp/子查询）与「编码绕过」（顺序缺陷导致转义被还原）作用机制不同。
- 「解析器语义差异」（F5 两组件对 URI 解释不同）与「过滤器顺序」（转义/解码先后）都属「不一致」，但层次不同。

### 授权与合规边界
> 待补充（用户自行填写）
