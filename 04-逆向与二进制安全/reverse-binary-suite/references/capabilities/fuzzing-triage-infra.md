# 崩溃分诊与 fuzz 基础设施

## R — 原文 (Reading)

> Basically, for each crash or error condition discovered, the smallest sequence of inputs that can repeat this fault must be found.
> — 《Fuzzing for Software Security Testing and Quality Assurance》Ch8 §8.1.5

> there is no 100% sure way to say that two errors are from the same root cause, so even with a deduplication system, all test cases triggering an error should always be recorded and retested after a fix has been applied.
> — 《Fuzzing for Software Security Testing and Quality Assurance》Ch6 §6.5

> We had several instances where the system was unreliable, fuzzers wouldn't perform modifications in the intended ways, and results weren't always reproducible.
> — 《Fuzzing for Software Security Testing and Quality Assurance》Foreword to the Second Edition

## I — 方法论骨架 (Interpretation)

这张卡解决「fuzz 跑出一堆崩溃后怎么收敛成几个根因、以及怎么保证 fuzz 系统本身没在悄悄失效」的问题。它覆盖生命周期后半段：监控 → 异常分析（去重/最小化）→ 报告，以及把 fuzz 当生产服务运维的治理机制。

崩溃去重按三级指纹递进，精度与侵入性同时上升：① 生成器信息——记录本次注入了哪些字段/什么异常，靠字段与异常是否重合聚类，零侵入但很粗（长度字段整数溢出与缺边界检查会归到一组）；② OS 日志——Windows 事件日志给异常码+故障模块+fault offset，Linux `dmesg` 给 `segfault at <addr> ip <ip> error <n> in <lib>`，用「最低三字节 IP + 错误码 + 模块」拼指纹；③ 栈回溯——用函数名序列拼指纹（`pcredemo-invalid-write-compile_regex-pcre_compile2`），最准但需调试器/ASan/Valgrind。落地的铁律：去重只用于排序和分配人力，不用于丢弃证据——被折叠样本里可能藏着第二个根因，补丁落地后要对全组样本重测。「10 个崩溃」自动记成「1 个漏洞」、补丁验证只跑最小样本，都是典型误用。

最小化把触发条件收缩到「必要且充分」：原始 fuzz 样本往往几百 KB，绝大多数字节与触发无关，直接分析会误判触发条件。按块删除/缩短（先粗粒度切块、再逐字节），每次删除后重跑，只保留「删了就复现不了」的部分；多报文序列同时收缩报文条数与顺序；用最小样本重跑 3–5 次确认稳定。不稳定崩溃（依赖时序/内存布局）不能最小化，越删越不可复现。

监控层有两类漏检。① 「服务还活着吗」存活探测只能发现灾难级故障：预fork 型服务（Apache）崩的是子进程、主进程立刻补新的，外部看完全正常——故障被架构吞掉。修法是单进程模式（`-X`）、看日志（子进程退出信号）、带符号运行。② 静默越界根本不崩——普通堆里越界几个字节只改相邻对象填充区。Guard Malloc 类分配器护栏把每次分配放独立虚拟页、缓冲区末尾对齐页尾、下一页不映射，任何越界跨页即 bus error；关键开关 `MALLOC_FILL_SPACE`（填 0x55 暴露未初始化读）、`MALLOC_ALLOW_READS`（只抓写不抓读）、`MALLOC_STRICT_SIZE`（取消对齐抓单字节越界）。代价是慢 100 倍以上（作者实测 8192 用例跑近 24 小时、不开则快约 20 倍），且 `MALLOC_STRICT_SIZE` 会让依赖对齐的程序自己崩产生假崩溃。

结论降级有三条：① 资源耗尽型「崩溃」先排除——DoS 常是瞬态、自动重启、或测试机自身资源耗尽；必须证明「攻击者投入极小、目标付出极大」的不对称性，监控 CPU/内存**变化量**找「一个包引发巨大分配」的输入；② 崩溃 ≠ 可利用——生产者（能改码）照「定位→修→回归」走比判可利用性更快（Office 2010 修 1800 个 fuzz bug，多数是顺手修的可靠性问题），外部研究者才需要完整可利用性论证；③ 内存 fuzz 的假阳性——直接改函数参数/寄存器绕过前置校验，会造出「函数崩了但真实流量构造不出这组参数」的不可达状态，识别方法是回推「要什么外部输入才能到这组参数」，推不出即假阳性，改进方向用动态符号执行求路径条件再用 SAT/SMT 生成可行值。

基础设施治理的核心是覆盖率自检闸门：每个 fuzzer 注册时写明应命中的代码位置与「命中率必须达 X%」；每轮结束自动核对，低于阈值即告警并暂停派单，把机器让给正常任务。这一机制同时抓到三类问题——fuzzer 行为异常、基础设施故障、产品改动导致解析代码没被调用。配合把 fuzz 当线上服务运维（设计评审、代码评审、对 fuzzer 自身测试、监控告警，宕机按 service blocker 处理）、结果集中入库用符号文件跨构建去重。覆盖率本身要算对：分母用「攻击面可达块」而非全程序块（1000 块中网络可达 180、命中 90 → 50% 攻击面覆盖率），无源码时用预分析（IDA 定位基本块 + 断点记录）或实时分析（Intel MSR 记录 EIP）。覆盖率引导（AFL 的 fork server、queue/crashes/hangs 三目录；libFuzzer 进程内 `LLVMFuzzerTestOneInput`）本质是「把输入搜索变成对新颖路径的贪心」，高覆盖率只是必要条件（"no bugs will be found in code that hasn't even been executed"），不是「已测比例」。确定性 fuzzer 还有农药效应：测试集有限可枚举，被厂商修完后有效性单调下降（PROTOS 自承「shared knowledge becomes more and more immune」），但它的可比对性价值不能放弃，做法是版本化测试集并观察发现率衰减。

## A1 — 应用示例 (Application Example)

### 示例 1: auplink 与 pcredemo 的三级指纹
- **类型与来源**: 【亲历】《Fuzzing for Software Security Testing and QA》Ch6 §6.5
- **问题/输入**: 几千个崩溃样本，怎么判断哪些同源？
- **方法论的使用**: 先落最便宜的一级（生成器日志）得粗分组压缩待分析量；对每组抽样转第二级——解析 OS 日志拼「模块+异常码+偏移」指纹（`auplink-segfault-ip-578-error-6-libc-2.23.so`）；对剩余可疑组上第三级——取栈回溯函数名序列（`pcredemo-invalid-write-compile_regex-pcre_compile2-pcre_compile`）；跨构建用符号文件对齐；指纹与样本一起入库供多年后查询。
- **结论**: 只用 IP 指纹换构建后全部失效（作者明确警告）；公共代码处崩溃指纹趋同（「所有 memcpy 的非法使用都会得到同一指纹」）而根因在各自调用点，须上三级并保留全部样本。
- **结果**: 原书给出两个指纹实例与三级递进方案。

### 示例 2: Apache 子进程崩溃被存活探测吞掉
- **类型与来源**: 【亲历】《Fuzzing for Software Security Testing and QA》Ch6 §6.2.1
- **问题/输入**: fuzz 跑完「服务一直活着」，真的没崩溃吗？
- **方法论的使用**: 先用合法用例探测建基线（响应内容、时延）；判断目标是预fork 服务，关掉 fork（`-X` 单进程模式）再 fuzz，或改用日志/调试器监控；并行看三层信号——服务可达性、应用日志（子进程退出信号）、系统资源；出现「服务正常但日志有 `child pid 174 exit signal Segmentation fault (11)`」时按崩溃处理而非忽略。
- **结论**: 存活探测只能发现灾难级故障；预fork 架构会吞掉子进程崩溃，必须看日志或改单进程。
- **结果**: 原书以该日志行为例说明监控盲区。

## A2 — 触发场景 (Future Trigger)

### 用户会在什么情境下需要它
1. fuzz 出了几百上千个崩溃，需要按根因分组、排优先级、避免把「10 个崩溃」记成「1 个漏洞」。
2. 崩溃样本很大或来自多报文序列，需要最小化到可分析、可回归的规模。
3. fuzz 跑完「一个崩溃都没有」，怀疑监控口径漏了子进程崩溃或静默越界。
4. 需要判断一个崩溃是不是真的可利用、是不是资源耗尽假象、是不是内存 fuzz 造出的不可达状态。
5. fuzz 跑着但半年没出洞，想判断是目标挖完了还是 fuzzer 在悄悄失效。

### 与相邻能力的区分
- 与 `fuzzing-campaign` 的区别：那张卡覆盖战役级决策（选题、接口、种子、工具组合、跑多久）与生命周期前半段，本卡覆盖崩溃之后的监控/分诊/最小化/基础设施治理；「跑多久」的运行经济学在那张卡，覆盖率作为健康闸门与 search 方向的技术细节在本卡。
- 与 `crash-to-exploit` 的区别：本卡把「一堆崩溃收敛成几个根因并最小化」，那张卡从「一个已确认的崩溃」推进到可控 EIP；本卡的最小样本是那张卡的输入。
- 与 `security-review-planning` 的区别：那张卡把覆盖率当交付质量参考，本卡把它当运行时闸门与搜索方向指标。

## E — 可执行步骤 (Execution)

**必需输入**: 目标可自动重启/脚本化投递；崩溃日志或调试器权限；跨构建比较需符号表；覆盖率闸门需插桩或调试器。缺符号表时只能用一级/二级指纹，三级栈回溯指纹每次构建会失效，须标注。

**交付物与完成标准**: ① 三级指纹与去重分组（标注置信度）；② 每个根因的最小复现样本；③ 监控口径健全性结论（子进程/静默越界是否漏检）；④ 结论降级判定（DoS/可利用性/可达性）；⑤ 覆盖率闸门配置与健康告警；⑥ 农药效应观测与测试集版本。完成标准：全部原始样本入库、补丁落地后全组重测、低于覆盖阈值的 fuzzer 被自动暂停。

1. **三级指纹去重**
   - 做什么：先落生成器日志一级（字段+异常聚类）；对每组抽样解析 OS 日志拼「最低三字节 IP + 错误码 + 模块」二级指纹；对剩余可疑组取栈回溯函数名序列三级指纹；跨构建用符号文件对齐；指纹与样本一起入库。
   - 完成标准：粗→精分组 + 每组置信度标注。
   - 判停：只用 IP 指纹换构建失效 → 加符号对齐；公共代码处指纹趋同 → 上三级并看各自调用点；低置信组不合并。

2. **保留证据并按组重测**
   - 做什么：明确去重产出是「优先级队列」不是「已删除清单」，保留全部原始样本；每组标所用指纹级别与置信度；修复后把该组所有样本重跑，仍有崩溃说明组内存在第二个根因，拆组；对「同组但触发路径差异大」的单独复核。
   - 完成标准：补丁后全组重测通过，无「修完又冒出来」。
   - 判停：按指纹自动关闭整组、把「10 个崩溃」记成「1 个漏洞」→ 禁止；补丁验证只跑最小样本 → 补跑全组。

3. **最小化样本**
   - 做什么：确认崩溃可稳定复现并记录命中率；按块删除/缩短（先粗粒度再逐字节），每次删除后重跑，只保留「删了就复现不了」的部分；多报文序列同时收缩条数与顺序；用最小样本重跑 3–5 次确认稳定，存入崩溃库与指纹绑定；修复后用同一最小样本回归。
   - 完成标准：必要且充分的最小输入序列 + 稳定性确认。
   - 判停：只减少字节数不保持触发 → 得到不再崩溃的小文件（错）；把不稳定崩溃（时序/内存布局依赖）当可最小化对象 → 越删越不可复现，先解决稳定性。

4. **补监控口径盲区**
   - 做什么：用合法用例探测建基线；判断目标是否 fork/多进程，是则关 fork（`-X`）或改日志/调试器监控；并行看服务可达性、应用日志（子进程退出信号）、系统资源三层；对静默越界用 libgmalloc 类护栏（`DYLD_INSERT_LIBRARIES`/LD_PRELOAD），按需要开 `MALLOC_STRICT_SIZE` 抓单字节越界、`MALLOC_ALLOW_READS` 减少噪声；把「加护栏后新增的崩溃」单独标记。
   - 完成标准：子进程崩溃与小幅越界都能被捕获。
   - 判停：预fork 服务只用存活探测 → 误判「目标健壮」；只用调试器监控时忘记排除正常异常（缺页、应用自注册异常处理）→ 把预期行为记成崩溃；护栏慢 100 倍导致单位时间用例数骤降 → 权衡监控与测试时间；`MALLOC_STRICT_SIZE` 产生假崩溃（依赖对齐的程序自崩）→ 复核。

5. **结论降级判定**
   - 做什么：DoS——建资源基线、持续采样（ps//proc/SNMP）、对超阈值用例单发复现排除环境噪声与自动重启，写成「可用性降级」而非「可利用」；可利用性——区分身份（生产者直接修、外部研究者才论证），生产者在同一代码库搜同类模式一并修，把「某模块反复出崩溃」转代码审计/渗透团队；内存 fuzz——回推「要什么外部输入才能到这组参数」，推不出标假阳性，需要时用 DSE 求路径条件 + SAT/SMT 生成可行值。
   - 完成标准：每个崩溃有「DoS / 可靠性 / 可利用 / 不可达假阳性」的分类与依据。
   - 判停：把 fuzzer 自身占满 CPU 造成的超时当目标 DoS → 排除；外部研究者照搬「直接修」把「不可利用」当结论交付 → 错；「寄存器 fuzz 崩了」直接写漏洞被以不可达驳回 → 回推可达性。

6. **配覆盖率闸门并运维基础设施**
   - 做什么：为每个 fuzzer 声明目标代码位置 + 最低命中率（写成配置）；每轮结束自动核对，低于阈值告警 + 暂停派单；定期做「变异是否真的生效」自检；对 fuzzer 与调度器做代码评审与回归；结果集中入库、用符号文件跨机器/跨构建判定是否同一崩溃；覆盖率分母用「攻击面可达块」（合并全部合法用例跑一遍近似上界），对未覆盖块分「不可达（分母误算）/ 可达但没测到（真盲区）」。
   - 完成标准：闸门配置生效，低于阈值自动暂停，覆盖率按攻击面口径计算。
   - 判停：靠「fuzzer 进程还活着」判断健康 → 错（进程活着但变异没生效、目标没被调用）；用全程序块数当分母得「只覆盖 9%」假警报 → 用可达块；把合法用例集合当完备分母忽略只有畸形输入才走的错误处理分支 → 补。

7. **用覆盖率引导并管农药效应**
   - 做什么：用带插桩编译器重建目标（AFL: afl-gcc/afl-clang；libFuzzer: `-fsanitize-coverage=trace-pc-guard` + `-fsanitize=address`）；准备最小种子集启动，监控 queue 增长速率与 exec/s，停滞则换种子/策略/加字典；崩溃取出按第 1–3 步分组最小化；覆盖率只作相对比较（同目标不同 fuzzer/种子集），不作「已测比例」绝对值；用确定性 fuzzer 建基线并观察跨轮发现率，明显衰减即进入农药效应，补随机成分/更新测试集并版本化。
   - 完成标准：搜索方向由新颖路径驱动，覆盖率口径正确，农药效应被识别而非误判为「产品变安全」。
   - 判停：用覆盖率绝对值当质量结论 → 错（分母要先算）；忘记插桩改变时序使竞争型 bug 消失/出现 → 记录；libFuzzer 进程内跑目标有全局状态残留导致用例间互相污染 → 注意隔离；因怕农药效应完全放弃确定性用例 → 丢掉跨实现可比性价值。

## B — 边界 (Boundary)

### 不要用的情况
- 战役级决策（选题、接口、种子、工具组合、跑多久）在 `fuzzing-campaign`；本卡从崩溃/监控问题介入。
- 单个崩溃推进到可控 EIP/利用开发，转 `crash-to-exploit`。
- 静态审计判漏洞是否存在，转 `source-audit-dataflow` / `memory-integer-audit`。
- 目标是恶意样本行为理解，转 `malware-behavior-analysis`。

### 已知失败模式
- 只用 IP 指纹，换构建后全部失效；公共代码处崩溃指纹趋同而根因在各自调用点（Ch6 §6.5）。
- 按指纹自动关闭整组，把「10 个崩溃」记成「1 个漏洞」；补丁验证只跑最小样本漏掉同组其他路径（Ch6 §6.5 开篇）。
- 只做「减少字节数」不保持触发，得到不再崩溃的小文件；把不稳定崩溃当可最小化对象（Ch8 §8.1.5）。
- 预fork 服务只用存活探测，得出「目标没有崩溃」的错误结论；只用调试器监控时把预期异常记成崩溃（Ch6 §6.2.1）。
- 忘记 Guard Malloc 慢 100 倍以上导致用例数骤降；`MALLOC_STRICT_SIZE` 让依赖对齐的程序自崩产生假崩溃（Ch6 §6.3.1）。
- 把 fuzzer 自身占满 CPU 造成的超时当目标 DoS；把「被 watchdog 重启」当「服务未受影响」而漏报，或反过来把正常重启当漏洞（Ch6 §6.1.1）。
- 把「寄存器 fuzz 崩了」写成漏洞被以不可达驳回；忽略分支条件约束把算力浪费在必然被过滤的取值上（Ch5 §5.2.6）。
- 靠「fuzzer 进程还活着」判断健康；分散在个人机器跑结果散落无法归因（Foreword）。
- 用全程序块数当分母得假警报；把覆盖率绝对值当质量结论（Ch7 §7.4）。
- 拿一套确定性用例当长期质量门禁，几年后一个洞都挖不到却以为产品变安全（Ch5 §5.2.3）。

### 作者与时代的局限
- 指纹示例（auplink、pcredemo、libc-2.23.so）与 ClusterFuzz 的早期形态来自 2010 年代前后；现代 ClusterFuzz 的符号化与跨构建去重已产品化。
- Guard Malloc 是 macOS/BSD 的机制；Linux 上等价物（ASan/Valgrind/电路断点的 malloc 钩子）细节不同但原理一致。
- 覆盖率引导示例基于早期 AFL 与 libFuzzer（`-fsanitize-coverage=trace-pc-guard` 是旧接口，现代 libFuzzer 默认集成）；MSR 实时分析路线在虚拟机里不可用。
- 农药效应是结构性限制（确定性测试集有限可枚举），不是工具缺陷；现代 fuzz 的随机化与语料进化缓解但无法消除。
- 「Office 2010 修 1800 个 fuzz bug」的生产者路径经济前提是「能改代码」，外部研究者不适用。

### 容易混淆的方法
- 「去重」（判断是否同源，用于排序）与「保留证据」（全样本入库、补丁后全组重测）是配套的两面，去重不等于丢弃。
- 「覆盖率做健康闸门」（本卡第 6 步，低于阈值暂停派单）与「覆盖率做搜索方向」（第 7 步，对新颖路径贪心）用途不同；与 `fuzzing-campaign` 的「跑多久」决策也不同。
- 「平台期」（随机性运气、可能突然出洞，属 `fuzzing-campaign` 的停机决策）与「农药效应」（确定性测试集固定上限，本卡第 7 步）是两种不同的「没发现」。
- 「存活探测漏检」（架构吞掉子进程崩溃）与「分配器护栏」（静默越界不崩）是两类不同漏检：前者是崩溃被吞，后者是破坏根本没导致崩溃。
- 「DoS 降级」「可利用性降级」「可达性降级」三种结论降级对象不同：可用性类、内存破坏类、内存 fuzz 假阳性类。
