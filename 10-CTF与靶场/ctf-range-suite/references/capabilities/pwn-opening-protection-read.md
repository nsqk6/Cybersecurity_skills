# Pwn 题型起手：可打面与保护组合判读

## R — 原文 (Reading)

> 与我们经常接触的题目不同，这是一个静态链接程序，运行时不需要加载 libc。not stripped 绝对是个好消息。

> — 《ctf-all-in-one》6.1.13 pwn 34C3CTF2017 readme_revenge

> 针对该保护机制的攻击，往往是通过信息泄漏来实现。由于同一模块中的所有代码和数据的相对偏移是固定的，攻击者只要泄漏出某个模块中的任一代码指针或数据指针，即可通过计算得到此模块中任意代码或数据的地址。

> — 《ctf-all-in-one》4.4 GCC 堆栈保护技术 · 地址空间布局随机化

> 对堆利用来说，不用于栈上的溢出能够直接覆盖函数的返回地址从而控制 EIP，只能通过间接手段来劫持程序控制流。

> — 《ctf-all-in-one》3.1.6 Linux 堆利用（上）· Linux 堆简介

## I — 方法论骨架 (Interpretation)

这张卡解决的是 pwn 题最早、也最容易浪费时间的那个决策：**在写第一行 payload 之前，这道题到底能怎么打、该往哪个方向打**。它的核心不是某种利用技巧，而是把「读题」变成一个固定顺序的信息收集过程，让后续所有技巧选择都变成查表而不是试错。

整个过程由四个事实驱动，按依赖顺序读取：

第一，**文件身份**。用 `file` 读位数、链接方式（静态/动态）、是否 stripped。这三项目决定工具链和路线：静态链接意味着 libc 代码在程序内部，可直接当 ROP 目标用，不必找外部 libc；not stripped 意味着函数名可读，定位校验逻辑和 `printf@got` 的成本大幅下降；stripped + 动态链接则必须走「泄漏 libc → 算偏移」的路线。这是解压后一分钟内能拿到的信息，先读它能避免在错误路线上投入几十分钟。

第二，**保护组合**。用 `checksec` 读 RELRO / CANARY / NX / PIE 四列，并把每一列翻译成一句「所以呢」：PIE enabled 表示地址随机，必须先有泄漏点才能谈控制流；Full RELRO 表示 GOT 不可写，「改 GOT 为 system」这条路直接封死，要转 `__malloc_hook` / `__free_hook` / `_IO_FILE` 等仍可写目标；CANARY 表示「覆盖返回地址」这个动作本身会被检测，程序在 ret 之前就 abort；NX 表示栈不可执行，ret2shellcode 不可用。保护不是「难度标签」，而是**对具体动作的具体禁止**，所以读保护必须落到动作层。

第三，**libc 与泄漏条件**。题目附件里有没有 `libc.so` 决定后续是按「已知偏移」算，还是预留 DynELF / dump 分支（见 `format-string-exploitation`、`blind-rop-brop`）。同时要判断「有没有泄漏点」——因为 ASLR/PIE 只随机化基址、不改变模块内偏移，拿到任一指针就能推出整块地址空间，所以泄漏点比溢出点更决定解法。

第四，**目标物位置**。pwn 题的终点不总是 shell。先搜 flag 字样：如果 flag 已以明文编在 `.data` / `.rodata` 里，那么「执行任意代码」是过度目标，正确做法是把利用降级成「让程序本来就会执行的输出函数打印这段内存」。题目名与字符串常量常常直接提示这条路（readme_revenge 的 `34C3_` 串）。

另外还要做一次**栈/堆分道**。菜单式 Create/Show/Edit/Delete 且带 free 的是堆题；堆溢出改的是 chunk 元数据，与当前栈帧无直接关系，不存在「覆盖 ret 就赢」的直线路径，必须找将来会被调用的间接指针（bin 链 fd/bk、hook、vtable、程序回调表）。把栈题的「算偏移到 ret」思路套到堆题上，所有工作都会落空。

还有一条适用于备赛阶段的元判据：作者把各种利用技巧比作「招式」，把编程语言与编译原理、汇编、操作系统与体系结构、数据结构与算法比作「内功」。招式易学但有上限，内功决定遇到新保护机制或非常见架构时能不能迁移。具体表现是：收集大量 exp 模板却讲不出偏移和地址从哪来，换 32/64 位或换 libc 版本就整段失效。因此本卡的每一项判断都要求「能说清所以然」，而不是只记结论——这既是解题纪律，也是学习路径的投入顺序。

这四步加一次分道，产出的不是 payload，而是一份**攻击面摘要**：链接方式、保护组合、缺的信息（libc？基址？canary？）、目标物位置、栈/堆路线。后续所有能力卡都以这份摘要为输入。

最后还有一条关于「用这张卡的方式」的纪律，来自《Handbook for CTFers》Ch6「How to Learn PWN」的反例：作者把各种利用技巧比作「招式」、把编程语言与编译原理、汇编、操作系统与体系结构、数据结构与算法四类基础比作「内功」，明确批评「急着学各种花哨利用技巧、跳过基础」的做法。落到本卡上就是：**读保护、定路线是在用基础做判断，不是在背模板**。如果只会照抄 `checksec` 输出对应的 payload，而不理解「为什么 PIE 需要泄漏、为什么 Canary 挡的是覆盖动作、为什么堆题没有直接 ret 可改」，那么换架构、换 glibc 版本、换保护组合时这份摘要就写不出来。自检标准是能独立解释一段汇编在做什么、能说清每个技巧依赖的系统特性；达不到就先补基础，再回到第 1 步。

## A1 — 应用示例 (Application Example)

### 示例 1: readme_revenge 的「flag 在 .data，不必拿 shell」
- **类型与来源**: 【亲历】《ctf-all-in-one》6.1.13
- **问题/输入**: 静态链接 + 全保护的 pwn 题，附件只有一个 binary。
- **方法论的使用**: 先 `file` 得到 statically linked + not stripped，作者据此判定「not stripped 绝对是个好消息」，直接 `rabin2 -z` 搜赛事前缀而不用硬逆；再由 `rabin2 -z` 找到 `000 0x000b4040 ... (.data) ascii 34C3_XXXX`，结合题名 readme 推断目标是「读取/泄漏 flag」而非控制流；于是不构造完整 ROP，转用「改 canary 让 `__stack_chk_fail` 打印它指向的串」这一最小原语。
- **结论**: 目标物位置决定利用等级，静态链接 + not stripped 直接决定工具选择。
- **结果**: 崩溃输出里出现 `.data` 处的 flag 串（原书给出的路径，具体串值原书未完整说明）。

### 示例 2: brop 题的「无附件黑盒起手」
- **类型与来源**: 【亲历】《ctf-all-in-one》6.1.1 HCTF2016 brop
- **问题/输入**: 只给 ip:port，没有二进制，`file`/`checksec` 全部失效。
- **方法论的使用**: 走到黑盒分支——输入长串看崩不崩（`for i in range(100)` 逐字节加长，得 `buffer size: 72`，即 buf 64 + ebp 8）；确认是栈溢出后，因为连泄漏原语都没有，转 `blind-rop-brop` 的五步流程。作者还专门写了 socat 守护脚本模拟「崩溃即重启」的远程环境。
- **结论**: 「读文件身份」这一步在有附件时做，无附件时就必须用响应探针替代，且必须先确认服务会重启，否则一次崩溃后整条枚举线断掉。
- **结果**: 扫得 `stop address: 0x4005e5`，后续进入 BROP 流程。

### 示例 3: Search-Engine 的「菜单题识别为堆题」
- **类型与来源**: 【亲历】《ctf-all-in-one》6.1.11 pwn 9447CTF2015 Search-Engine
- **问题/输入**: 静态链接、`not stripped` 的菜单式交互程序。
- **方法论的使用**: `file` 后立刻 `checksec`，一句「64 位程序，开启了 NX 和 Canary」定调；随后看到 Create/Show/Edit/Delete 的分配—释放配对，作者只写一句「根据经验，这是一道堆利用的题目」就转入 how2heap，不再找「偏移到 ret」。
- **结论**: 菜单结构 + free 操作是堆题的稳定特征，分道判断先于任何利用细节。
- **结果**: 原书未在本节交代最终利用结果，仅交代方向判定。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要它
1. 刚解压一个 CTF pwn 附件，面对一堆文件不知道先打开哪个、先看什么。
2. 已经有一份能崩的 exp，但换了环境/保护选项后失效，需要判断是哪一项保护在起作用。
3. 题目只给 `nc host port`，没有任何附件，需要先判断有没有可能做、走哪条路线。
4. 面对菜单式交互题，不确定该按栈题还是堆题处理。
5. 想确认「这题到底要不要拿 shell」，还是 flag 本来就在程序里。

### 语言信号（出现这些就该激活）
- 中文：「拿到 pwn 题怎么起手」「附件只有一个 binary 先干什么」「开了 PIE 还能打吗」「Full RELRO 怎么绕」「stack smashing detected 怎么办」「菜单题怎么打」「必须拿 shell 吗」「只有 nc 地址没有附件」
- English: "how do I start a pwn challenge", "what does checksec tell me", "how to tell stack overflow from format string blind", "no leak PIE enabled", "heap exploitation 起手", "how to start a binary exploitation challenge"

### 与相邻能力的区分
- 与 `format-string-exploitation` 的区别：本卡决定「读什么信息、走哪条路线」，那张卡决定「确认是格式化字符串后怎么四步打穿」。本卡的输出（保护组合、有无泄漏、libc 有无）是那张卡的输入。
- 与 `blind-rop-brop` 的区别：本卡在无附件时只做到「判类型、定方向」；BROP 卡负责在连泄漏原语都没有时完成整条利用链。
- 与 `reverse-engineering-workflow` 的区别：两边都从 `file` 开始，但本卡读「能不能打、缺什么信息」，`reverse-engineering-workflow` 读「用什么工具逆、怎么让程序跑起来、校验怎么求解」。
- 与 `misc-forensics-and-encoding` 的区别：那张卡处理的是图片/固件/嵌套容器类附件与编码串，不是可执行程序。

## E — 可执行步骤 (Execution)

**必需输入**: 二进制附件路径；或（无附件时）ip:port 且服务端崩溃后会自动重启；题目附件清单（是否含 `libc.so`）。缺附件又不能确认服务重启时，必须先问清楚赛制环境，再进入第 4 步。
**交付物与完成标准**: 一份「攻击面摘要」，含五项：①位数/链接方式/stripped；②RELRO/CANARY/NX/PIE 四列取值及各自对应的禁止动作；③libc 是否给定、是否存在可用泄漏点；④flag 位置与目标是 shell 还是内存读取；⑤栈/堆路线。五项齐全且每项能一句话说清「所以呢」才算完成。

1. **读文件身份**
   - 做什么：`file <bin>`，记录位数、动态/静态链接、是否 stripped 三项。
   - 完成标准：能一句话说出「有没有符号、要不要外部 libc」。
   - 判停：若没有任何附件，跳到第 4 步（黑盒探针）；若静态链接，后续 libc 相关步骤全部改为「在程序内部找目标」，跳到第 5 步。

2. **读保护组合**
   - 做什么：`checksec -f <bin>`（或 `checksec --file=<bin>`）读 RELRO / CANARY / NX / PIE 四列，逐列翻译成禁止动作。
   - 完成标准：四列全部落定，并写出「能否改 GOT / 能否直接 ret2text / 是否需要泄漏 / 覆盖返回地址会不会被拦」四句结论。
   - 判停：Full RELRO 时划掉所有 GOT 写入方案；CANARY 开启时划掉「直接覆盖返回地址」方案，转第 3 步；PIE 开启时标记「必须先找泄漏点」。

3. **核 libc 与泄漏条件**
   - 做什么：检查附件是否含 `libc.so`；若有，记录版本（`strings libc.so | grep "GNU C Library"`）；若无，标记需要 DynELF 或 dump。同时找已有泄漏原语（格式化串、write/puts 输出、堆残留指针）。
   - 完成标准：确定「按已知偏移算」还是「预留无 libc 分支」，并写下一个可用的泄漏点或明确写「暂无泄漏点」。
   - 判停：PIE enabled 且找不到任何泄漏点时，不要继续构造控制流，转 `format-string-exploitation` 或 `blind-rop-brop` 先拿泄漏；有 libc 时按偏移计算，基址末位应与页对齐（如 `...000`），否则说明泄漏的不是该模块指针。

4. **黑盒探针判类型（无附件分支）**
   - 做什么：先发 `ABCD%7$x` 类探针，看回显是否出现 `44434241` 之类自身字节；若无格式符回显，改发递增长串，记录从哪个长度起连接断开/EOF。
   - 完成标准：判定为「格式化字符串」或「栈溢出」，并记下参数序号或崩溃长度。
   - 判停：命中格式串转 `format-string-exploitation`；命中栈溢出且无泄漏原语转 `blind-rop-brop`；服务不重启则停止枚举，先解决环境（作者用 `while true` 的 socat 守护脚本模拟崩溃即重启），否则一次崩溃后无法继续。

5. **判目标物位置与利用等级**
   - 做什么：`rabin2 -z <bin> | grep <赛事前缀>` 或 `strings -t x` 搜 flag 格式（注意赛事自定义前缀，如 `34C3_`，不要只搜 `flag{`），记下串的地址与所在段；判断该段能否被现有输出函数触达。
   - 完成标准：明确写「目标是拿 shell」还是「让程序打印某段内存」。
   - 判停：flag 已在程序内且输出函数可指过去时，把利用降级为内存读取，不再构造完整 ROP；flag 运行时才生成时，维持 shell 目标。

6. **栈/堆分道**
   - 做什么：看交互是否包含分配/释放/编辑/展示四类操作；有 free/delete 即按堆题处理。若是堆题，判 glibc 版本（是否 2.26+ 有 tcache），列出「未来会被调用」的指针候选（hook、vtable、程序回调表）。
   - 完成标准：写出路线结论，堆题至少列出一个可写且可被控制的间接劫持候选。
   - 判停：堆题时不要计算「偏移到 ret」；栈题时不要去找 bin 链。分道结论写进摘要第 ⑤ 项，结束。

## B — 边界 (Boundary) ★

### 不要用的情况
- 题目是 Web、Crypto、Misc 编码/隐写类：`file`/`checksec` 读出的保护组合对这些题型没有决策价值，本卡的「保护→动作」映射不适用。
- 二进制被加壳或为脚本包装（PyInstaller 等）：`file` 读到的是壳/打包器身份，不是真实程序身份，需先脱壳再回到第 1 步。
- 服务有速率限制或每次连接进程地址都变：黑盒探针第 4 步和 BROP 的前提都不成立。
- 只有 flag 文件格式、没有任何可交互目标：本卡不产出 flag，只能产出路线判断。

### 已知失败模式
- 不读 checksec 直接照抄栈溢出模板：《ctf-all-in-one》6.1.11 反复出现「拿到题先 file 再 checksec」的开场；遇到 Canary 时 payload 在返回地址前被打断，表现是「长度对了却拿不到 shell」，时间全耗在调长度上。
- 把静态链接程序当动态链接处理：会去找根本不存在的 libc 版本（4.4、6.1.13 均警告）。
- 把本地 `echo 0 > /proc/sys/kernel/randomize_va_space` 当成远程也关了 ASLR：4.4 明确这是本地调试手段，exp 拿到远程必炸。
- Full RELRO 下继续写 GOT：写入看似成功但调用仍走原函数，原书 4.4 指出应转 hook / `_IO_FILE`。
- 只看 checksec 不看崩溃输出：会漏掉库函数内部被插桩的情况；Canary 的确认必须结合 `*** stack smashing detected ***` 与函数尾声 `xor gs:0x14` / `fs:0x28`（3.1 节、4.4 节）。
- 默认「必须拿 shell」：6.1.13 表明静态链接 + 全保护程序上构造完整 ROP 是高成本路线，而 flag 可能本来就在 `.data`。
- 只搜 `flag{`：赛事用自定义前缀（本书为 `34C3_`）时会漏掉目标串（6.1.13）。
- 把栈溢出偏移思路套到堆题：3.1.6 明确堆溢出不能直接覆盖返回地址，算偏移到 ret 在堆题里毫无意义。
- 忽略 glibc 版本差异：有无 tcache（2.26+）会让同一份 exp 一机通、一机崩（3.1.6、6.1.11）。
- 黑盒枚举时不 sleep 给守护进程留重启时间：会把「重启中连不上」误判为「地址非法」（6.1.1）。
- 急着收集各种 exp 模板与花哨技巧，跳过编译原理/汇编/OS/数据结构基础：换 32/64 位、换 libc 版本就整段失效（Handbook Ch6「How to Learn PWN」）。

### 作者与时代的局限
- 本书的 checksec 字段与保护解读基于当时的 GCC/glibc（约 2017 年前后），现代发行版默认 Full RELRO + PIE + CET / Shadow Stack 时，本卡的「改 hook / `_IO_FILE`」目标也会被收敛，需要重新评估可写目标。
- 书中大量例子是 32 位程序；x86-64 下前几个参数走寄存器，栈布局与 32 位不同，本卡提到的「数参数序号」需按架构调整（详见格式化字符串卡）。
- 无附件分支默认「崩溃即重启」，这是 CTF 出题环境的便利假设，不是通用服务性质。
- 堆章节只覆盖到 first_fit / 基础 bin 攻击，没有 tcache stashing unlink、largebin attack 等后续手法，本卡只负责识别方向与候选点，不承担具体堆利用。
- 书中没有解题赛的选题与时间分配方法，本卡只做技术起手，不做赛程决策。

### 容易混淆的方法
- **Canary 与 PIE/ASLR**：Canary 不改变地址，只破坏「覆盖返回地址」这个动作；PIE/ASLR 改变地址，不阻止覆盖。二者常同时开启，处置顺序是先泄漏基址、再泄漏 canary。
- **本卡的「读文件身份」与 `reverse-engineering-workflow` 的同名动作**：前者读「能不能打」，后者读「用什么工具逆」，同一个 `file` 输出服务于不同决策。
- **保护判读 vs 背 exp 模板**：《Handbook for CTFers》Ch6 警告「招式易学但有上限」——只会按 checksec 结果套模板、讲不出偏移和地址从哪来，换 32/64 位或换 libc 版本就会整段失效。本卡要求把每项保护翻译成禁止动作，正是在强制使用内功而非招式。
- **堆题与目标物位置**：CU-1-10 管「控制流走哪条间接路径」，CU-1-11 管「要不要控制流」。先判目标物，再决定值不值得找间接劫持点。
- **黑盒探针与 BROP**：黑盒探针只区分漏洞类型与偏移；BROP 是在此之后、连泄漏都没有时的完整利用流程。
- **静态链接 vs 无 libc**：静态链接是 libc 代码在程序内（不需要 libc 文件）；「无 libc」是动态链接但题目没给 libc.so（可能需要 DynELF）。两者路线不同。
