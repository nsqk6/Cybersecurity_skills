## R — 原文 (Reading)

> 模型几乎无条件地相信状态栏
> — 《深入理解AI AGENT-zh-CN》2.6.4 状态更新的两种实现

> 安全机制不可自我修改
> — 《深入理解AI AGENT-zh-CN》9.3.2 持续进化的安全边界

> Agent 修改自身提示以适应和改进很常见
> — 《Agentic Design Patterns》第 8 章 记忆管理（程序记忆）

> LLM 总结只是为了提高可读性…并不是把输入变得无害的净化过程
> — 《深入理解AI AGENT-zh-CN》9.3.2

## I — 方法论骨架 (Interpretation)

这个能力解决"高信任通道被污染后怎么防固化"的问题。它覆盖三条通道：单会话内的状态栏、跨会话的程序记忆、跨版本的自进化闭环。共同点是模型对它们赋予极高信任，一旦被污染，错误不是一次性而是被放大、被持久化。

第一条是状态栏（单会话内信任放大）。状态栏位于上下文末尾、紧邻待生成 token，获得最高注意力权重，模型把它当已核实结论直接使用而不自己重算。这条设计的优点（省 token、纠偏）与风险同源：谁能让状态栏写错，谁就获得了一个高可信度注入点。作者还发现 LLM 做数量统计本身容易出错，"用 LLM 维护状态栏"同时引入错误与投毒两条路径。防御侧一律由代码确定性维护（计数器、时间戳、TODO 状态）；若必须用 LLM，逐条抽取事实再由代码汇总，禁止一次性批量统计；禁止把外部网页片段、工具返回原文直接写进状态栏；每个状态栏写入点列入注入面清单并做"外部内容→状态栏→下一轮行为"端到端注入测试。

第二条是程序记忆自修改（跨会话持久化）。【原文事实】作者把"程序记忆"定义为存于系统提示中的核心指令与行为规则，指出 Agent 修改自身提示很常见，常用技术是"反思"：把当前指令与最近交互一起给模型，要求它产出改进后的指令，再写回存储。【安全推论，依据原文句："Agent 修改自身提示以适应和改进很常见"（第 8 章）与同书"持久记忆是攻击放大器"的立场】若"最近交互"含攻击者可控内容（网页、邮件、被污染的工具返回），反思步骤会把注入文本提炼成**新的常驻指令**，以"Agent 自己学到的经验"身份存在，绕过针对外部输入的检查，并在后续所有会话生效。注意这一步是从架构事实推出的，作者本人在反思章节只讲质量提升、未讨论该风险，落卡不得写成作者结论。防御：把反思输入侧分可信（系统指令、人工反馈）与不可信（对话历史、工具返回、外部内容），不可信内容不得进入指令改写输入；产物进待验证区；保留版本与来源可单条回滚；定期审计指令 diff 中"忽略……""优先发送到……"类祈使句。

第三条是自进化三条边界（跨版本固化）。自我进化会把一次性错误固化成长期能力：注入被总结成"经验"后跨会话反复生效；恶意包被封装成工具后从一次沙盒运行扩散到所有后续任务；有缺陷的验证器会持续批准退化版本。三条边界切断三条固化路径：证据与指令隔离（网页/邮件/工具输出及其 LLM 摘要一律视为不可信证据，按固定 schema 提取主张、原文位置、采集时间，提取出的字符串绝不作为指令执行，模型置信度不作为批准门槛）；待验证与正式隔离（新知识/Prompt/Skill/程序/参数先进不可服务真实流量的待验证区，新代码与外部依赖过沙盒、权限检查、供应链扫描、行为测试）；安全机制不可自我修改（验证器、测试用例、发布门槛、审计日志、稳定版本备份对 Agent 只读，变更以版本化 PR 提交，由独立于生成者的 reviewer 审查，高风险 Skill 需人工批准）。再加结构性检查：任一新版本若修改了只读项，流程直接失败。

三条通道的判据是"信任放大的时间尺度"：状态栏是单会话内，程序记忆是跨会话，自进化是跨版本。防法从"代码维护"升级到"版本化隔离 + 独立审查"。

## A1 — 应用示例 (Application Example)

### 示例 1: 状态栏投毒
- **类型与来源**: 【转述】《深入理解AI AGENT-zh-CN》2.4.7、2.6.4
- **问题/输入**: 一个 Agent 的状态栏由 LLM 汇总对话末尾生成，攻击者把外部网页片段摘要写进状态栏，期望下一轮模型把它当已核实结论执行。
- **方法论的使用**: 状态栏一律改由代码确定性维护（计数器、时间戳、TODO 状态）；若必须用 LLM，逐条抽取事实再由代码汇总，禁止一次性批量统计；禁止外部网页片段、工具返回原文直接写入状态栏；把每个状态栏写入点列入注入面清单，做"外部内容→状态栏→下一轮行为"端到端注入测试。
- **结论**: 状态栏的高注意力位置既是优势也是注入点；用 LLM 维护同时引入统计错误与投毒两条路径。
- **结果**: 原书在 2.4.7 明确点名"状态栏投毒"；未给端到端测试的成功率数据。

### 示例 2: 恶意包被封装成工具后的扩散
- **类型与来源**: 【转述】《深入理解AI AGENT-zh-CN》9.3.2
- **问题/输入**: 一个自进化 Agent 把一次沙盒运行中学到的"新工具"封装进能力库，其中包含恶意依赖，之后所有任务都调用它。
- **方法论的使用**: 按三条边界处理——证据与指令隔离：这次运行的输出及其 LLM 摘要视为不可信证据，按 schema 提取主张与原文位置，不把摘要字符串当指令；待验证与正式隔离：新工具进不可服务真实流量的待验证区，过沙盒、权限检查、供应链扫描、行为测试；安全机制不可自我修改：验证器与发布门槛对 Agent 只读，变更以版本化 PR 交独立 reviewer；加结构性检查，若新版本修改了只读项则流程直接失败。
- **结论**: 一次性沙盒运行不能变成长期能力；固化路径必须被三条边界逐条切断。
- **结果**: 原书以该类扩散说明"自我进化会把一次性错误固化成长期能力"；未给具体事件数据。

### 示例 3: update_instructions 伪代码的反思通道
- **类型与来源**: 【转述】《Agentic Design Patterns》第 8 章（程序记忆）
- **问题/输入**: 作者给出 `update_instructions` 伪代码：读当前指令 → 让 LLM 反思对话 → 存回 store。需要判断这条通道能否被注入利用。
- **方法论的使用**: 【原文事实】作者定义程序记忆并指出 Agent 修改自身提示很常见，反思是把当前指令与最近交互给模型产出改进指令再写回。【安全推论，依据原文句："Agent 修改自身提示以适应和改进很常见"（第 8 章）及同书"持久记忆是攻击放大器"的立场】若"最近交互"含攻击者可控内容，反思会把注入文本提炼成新的常驻指令并以"自己学到的经验"身份绕过输入检查、跨会话生效。防御：把反思输入侧分可信与不可信，不可信不得进入改写输入；产物进待验证区经独立 reviewer 审查；指令存储留版本与来源可单条回滚；定期审计 diff。
- **结论**: 该风险是架构事实推出的推论，不是作者原结论；但防御动作与作者其他章节的"持久记忆放大器"立场一致。
- **结果**: 原书伪代码给出写回流程；未讨论该风险，也未给污染后回滚的实测数据。

## A2 — 触发场景 (Future Trigger)

### 用户会在什么情境下需要它
1. Agent 有状态栏 / `<system-reminder>` / 轨迹摘要机制，想知道能不能让模型自己总结。
2. 系统启用了基于反思的提示自改进或任何写回 system prompt 的机制，担心"学坏"。
3. 有自动更新 Prompt/Skill/知识库/参数的闭环，需要划不可越的边界。
4. 担心一次注入被总结成"经验"后在后续所有会话反复生效。
5. 发现验证器被 Agent 自己改低了测试阈值或删了失败用例。

### 语言信号（出现这些就该激活）
- 中文：「状态栏能不能让模型自己总结」「system-reminder 会不会被注入」「Agent 能不能自己改 prompt」「自进化会不会把注入学进去」「反思会不会学坏」「自改写怎么回滚」「验证器被自己改弱了怎么办」
- English: "status bar poisoning", "agent scratchpad trust", "self-modifying system prompt risk", "prompt self-improvement safety", "self-improving agent guardrails", "prevent agent from weakening its own tests"

### 与相邻能力的区分
- 与 `rag-permission-and-poisoning-defense` 的区别：那张卡处理检索层的越权与投毒，本卡处理"高信任通道被污染后固化"的时间维度问题。
- 与 `defense-in-depth-architecture` 的区别：那张卡处理运行时防线顺序，本卡处理跨会话/跨版本的持久化边界。
- 与 `tool-supply-chain-vetting` 的区别：那张卡审第三方能力准入，本卡的"待验证区"是内部自进化产物的隔离，不是外部工具。

## E — 可执行步骤 (Execution)

**必需输入**: 是否使用状态栏/系统提醒/轨迹摘要机制；是否存在反思或写回 system prompt 的机制；是否启用自动更新 Prompt/Skill/知识库/参数的闭环；版本与审计能力。缺任一项时对应步骤标为不适用，不要硬套。

**交付物与完成标准**: 状态栏写入点清单与端到端注入测试记录；反思输入可信/不可信划分；待验证区配置；只读安全机制清单与结构性检查；指令版本与回滚记录。

1. **把状态栏改为代码维护**
   - 做什么：状态栏由代码确定性维护；若必须用 LLM，逐条抽取事实再由代码汇总，禁止一次性批量统计；禁止把外部网页片段、工具返回原文直接写进状态栏。
   - 完成标准：状态栏值可复现，无外部内容直通路径。
   - 判停：若框架不允许代码维护，标注为高信任注入面，转第 5 步做端到端测试。

2. **做状态栏端到端注入测试**
   - 做什么：把每个状态栏写入点列入注入面清单，做一次"外部内容→状态栏→下一轮行为"的端到端注入测试。
   - 完成标准：每个写入点都有测试记录。
   - 判停：若任一写入点能让外部内容影响下一轮行为，回到第 1 步切断该路径。

3. **划分反思输入的可信/不可信**
   - 做什么：把反思/自改写的输入侧分成可信（系统指令、人工反馈）与不可信（对话历史、工具返回、外部内容）；不可信内容不得进入指令改写输入。
   - 完成标准：有明确的输入分类规则与拦截点。
   - 判停：若不可信内容仍可进入改写输入，判定推论路径成立，暂停自改写上线。

4. **把自改写产物送进待验证区**
   - 做什么：自改写产物一律进不可服务真实流量的待验证区，经独立 reviewer 对照原始证据审查后才生效；指令存储保留版本与来源，可单条回滚。
   - 完成标准：产物不会直接落盘生效，可定位"哪次改写引入"。
   - 判停：若无版本机制，先补版本与来源记录再启用自改写。

5. **划三条不可越边界**
   - 做什么：证据与指令隔离（外部内容及其 LLM 摘要按固定 schema 提取主张、原文位置、采集时间，提取字符串绝不作为指令执行，置信度不作为批准门槛）；待验证与正式隔离（新知识/Prompt/Skill/程序/参数进待验证区，新代码过沙盒、权限检查、供应链扫描、行为测试）；安全机制不可自我修改（验证器、测试用例、发布门槛、审计日志、稳定版本备份对 Agent 只读，变更以版本化 PR 由独立 reviewer 审查，高风险 Skill 需人工批准）。
   - 完成标准：三条边界各有对应配置与责任人。
   - 判停：若 Agent 能修改任一只读项，直接判定结构失败，流程不得推进。

6. **加结构性检查与定期审计**
   - 做什么：任一新版本若修改了只读项，流程直接失败；定期审计指令 diff，重点看"忽略……""优先发送到……"类祈使句。
   - 完成标准：有失败拦截记录与 diff 审计记录。
   - 判停：若只靠 LLM 自评置信度当发布门槛，判定为无效控制，回到第 5 步。

## B — 边界 (Boundary)

### 不要用的情况
- 纯人工维护、无状态栏、无自改写、无自动更新的系统：本卡三条通道都不存在。
- 只需要审外部工具准入：用 `tool-supply-chain-vetting`；本卡的"待验证区"是内部产物隔离。
- 只处理单次检索投毒：用 `rag-permission-and-poisoning-defense`。

### 已知失败模式
- 用 LLM 批量统计状态栏（错且不可审计）；把外部内容摘要写进状态栏（信任放大）；因状态栏"只是元信息"而漏审（《深入理解AI AGENT-zh-CN》2.6.4）。
- 允许 Agent 降低测试阈值或删除失败用例（把退化伪装成进步）；把 LLM 摘要当净化后的安全输入；用模型自评置信度当发布门槛（同书 9.3.2）。
- 把反思当纯收益——作者在反思章节只讲质量提升、未讨论该风险（《Agentic Design Patterns》第 8 章）；自改写直接落盘生效；无版本导致污染后无法回滚。

### 作者与时代的局限
- CU-1-25 的注入固化路径是**安全推论**，不是作者结论；依据原文句为"Agent 修改自身提示以适应和改进很常见"（第 8 章）与同书"持久记忆是攻击放大器"的立场，推理链已在 I/A1 段逐处标注。
- 三条边界给的是原则性要求，未给具体版本化 PR 工具链或 reviewer 配置；只读项清单需按系统实际安全机制枚举。
- 中文译文提取文本，引用按中文逐字引用。

### 容易混淆的方法
- 状态栏投毒 vs 程序记忆自修改：前者是单会话内信任放大，后者是跨会话持久化。
- 程序记忆自修改 vs 自进化边界：前者特指通过反思通道的写入路径，后者覆盖知识/Prompt/Skill/程序/参数更广，且强调"安全机制自身"是保护对象。
- LLM 摘要 vs 净化：作者明确说摘要只是提高可读性，不是把输入变无害的净化过程，不能当信任分界。

### 授权与合规边界
> 待补充（用户自行填写）
