# Agent 三层护栏与独立审查架构

## R — 原文 (Reading)

> 这三层不是按请求处理的先后顺序排的，而是按 被绕过的难度 排的——越靠下的层越不依赖模型自己的判断，因此越难被一次成功的攻击穿透

> 一个模型负责提议行动（Proposer），另一个独立的模型负责审查并批准（Reviewer）
> — 《深入理解AI AGENT-zh-CN》4.6（事前审批/事后验证）；《Agentic Design Patterns》第 4 章 反思

> 还要测试"明确允许的请求是否能够正常完成"
> — 《深入理解AI AGENT-zh-CN》1.2.5 护栏与安全性

> 3. 如果对违规存在任何歧义或不确定性，则默认为"合规"。
> — 《Agentic Design Patterns》第 18 章 Guardrails/安全模式（SAFETY_GUARDRAIL_PROMPT）

## I — 方法论骨架 (Interpretation)

这个能力解决的是"给一个能调工具、能写数据的 Agent 设计整体安全架构"的问题。它的核心不是堆更多检测器，而是回答两个结构性问题：**防线按什么顺序投入**与**谁来做安全判断**。

第一条主线是三层护栏按"被绕过难度"排序，而非按请求处理时序排序。三层分别是上下文层（模型能看到什么）、执行层（模型能做什么）、数据层（世界最终被改成什么样）。上下文层只降低攻击成功率、给不出保证；执行层在动作生效前拦截；数据层由数据库行级策略、约束、受控视图和不可伪造的访问上下文强制执行——即使上两层全失守，越权仍在数据层被拒。所以设计顺序是"先问最坏情况下最后一道门在哪，再往回补前两层"，而不是先写提示词警告。

第二条主线是复核必须外置。同一上下文里的 Agent 判断"我是否被注入"，这个判断本身也是被操纵对象，因此自动降级为"建议"而非"保证"。可用的外置手段五种：独立审查进程、最小权限凭证、沙盒隔离、人在回路、独立数据源。落地时最有效的形态是提议者-审核者：一个模型提议行动、另一个模型审查批准，两者要满足"能力相近但训练偏好不同"（不同家族互审）与"看到不同的信息"（换模态：代码→渲染截图、配置→沙盒实跑）。能力差距过大反而不可靠，因为弱审查者跟不上强提议者的推理。

第三条主线是护栏必须双向评估。只优化"危险请求拦截率"会把护栏调成误拒绝机器——合法但形式敏感的任务（已授权的安全测试、模型蒸馏研究）被一起拒掉，这类失败不出现在安全指标里。反过来，若边界情形一律"默认合规"（fail-open），最难判定的样本被全部放行，且"是否有歧义"由同一个可被措辞影响的模型判断，形成可操纵判据。两端都要监控：应拒样本 + 明确允许样本，同一批回归同时报拦截率与合法通过率。

读完这段的人应当能这样跑一遍：先列出工具与数据访问面 → 定数据层最后一道门 → 回溯配执行层和上下文层 → 把所有"自己判断自己安全"的点迁移到上下文之外 → 用异构模型+换模态搭审查者 → 建双向回归集验证没有过严也没有过松。

## A1 — 应用示例 (Application Example)

### 示例 1: 动态生成软件的三层兜底
- **类型与来源**: 【转述】《深入理解AI AGENT-zh-CN》1.2.5.1
- **问题/输入**: 一个根据自然语言需求动态生成并运行代码的 Agent，外部内容可以进入上下文，模型又能调用执行工具。需要设计"即使被注入也不能越权"的护栏。
- **方法论的使用**: 先在所有能让外部内容进入上下文的入口（用户输入、网页、文档、MCP 返回）布上下文层的来源标记与分类器；再为每个工具按可逆性/权限/财务影响标注风险等级，形成执行层审批矩阵；最后在数据层写行级安全策略、约束与受控视图，读写携带由受信任运行时绑定的访问上下文。验证时假设前两层全部失效，逐条走越权路径，确认每条都在数据层被拒。
- **结论**: 最后一道门必须落在不依赖模型判断的数据层；上下文层只是降低成功率的辅助层。
- **结果**: 原书以该例统一第 2/4/5 章的安全讨论；未给出量化拦截数据。

### 示例 2: PPT 生成的提议者-审核者
- **类型与来源**: 【例题】《深入理解AI AGENT-zh-CN》实验 5-6（4.6 事前审批/事后验证）；《Agentic Design Patterns》第 4 章 反思
- **问题/输入**: 一个负责生成 PPT 的 Agent，需要在交付前发现页面溢出、布局错乱等质量问题与潜在风险，而生成者自己复查同一段文本容易复现同一盲区。
- **方法论的使用**: 划分 Proposer（行动导向，负责生成）与 Reviewer（风险控制，负责审查）；选不同家族、能力相近的两个模型；事后验证换模态——Reviewer 把每页渲染成截图，用 Vision LLM 检查溢出与布局，而不是重读同一段文本；反馈以结构化字段（页码、问题类型、严重程度）回灌 Proposer 轨迹，让它像处理工具失败一样处理拒绝。
- **结论**: 审查者必须"能力相近、偏好不同、看到不同信息"；换模态是打破同一上下文盲区的关键手段。
- **结果**: 原书交代 Reviewer 以截图+视觉检查并输出结构化反馈；未给出通过率数字。

### 示例 3: 被误伤的授权安全测试
- **类型与来源**: 【转述】《深入理解AI AGENT-zh-CN》1.2.5
- **问题/输入**: 护栏上线后拦截率很高，团队据此认定安全达标；但授权的安全测试、模型蒸馏研究等合法任务开始被拒。
- **方法论的使用**: 构造两组样本——应为 non-compliant 的、明确允许且"形式上像攻击但已授权"的；同时报告拦截率与合法请求通过率，任一退化即视为回归；把易误伤类别写进允许清单定期回归。
- **结论**: 只看拦截率会系统性高估安全水位；必须双向评估。
- **结果**: 原书点名授权安全测试与模型蒸馏研究被误拦；未给具体阈值。

## A2 — 触发场景 (Future Trigger)

### 用户会在什么情境下需要它
1. 从零设计一个带工具调用、能写数据库或发外部请求的 Agent，需要决定护栏分几层、按什么顺序做。
2. 已经有一套护栏（输入过滤 + 提示词警告），想知道为什么还是被绕过，或为什么合法任务老被拒。
3. 要让模型自查"我有没有被注入/有没有做错"，需要判断这种自审是否可信、怎么改成独立审查。
4. 要给护栏/过滤器定评估指标，纠结只看拦截率够不够、边界样本怎么处置。
5. 多个 Agent 协作，需要确定谁审查谁、用什么模型、审什么粒度。

### 语言信号（出现这些就该激活）
- 中文：「护栏怎么分层」「guardrail 放哪一层」「纵深防御怎么设计」「让模型自己检查有没有被注入」「self-review 安全吗」「要不要加一个模型复核」「模型太保守老拒答」「边界样本怎么处理」「有歧义就放行行不行」
- English: "layered defense for agent", "where to enforce policy", "can the model audit itself", "proposer reviewer pattern", "cross-model review for safety", "false refusal evaluation", "guardrail precision recall tradeoff", "fail-open vs fail-closed for LLM filter"

### 与相邻能力的区分
- 与 `prompt-injection-surface-and-separation` 的区别：本卡管**整体架构与判断权归属**（防线顺序、谁来审查、怎么评估），那张卡管**外部内容进入上下文这一个具体面**的入口清点与标记。
- 与 `execution-safety-and-server-truth` 的区别：本卡是架构层设计评审，那张卡是单次工具调用与前钩子级的具体机制（Sidecar、命令解析、幂等、身份绑定）。
- 与 `tool-supply-chain-vetting` 的区别：本卡假设工具已准入，处理"运行时怎么防"；那张卡处理"接不接这个工具"的准入判定。

## E — 可执行步骤 (Execution)

**必需输入**: 完整工具清单；数据访问面清单（含库表、行级策略现状）；可改造的后端或数据层；能否并行调用两个不同家族模型；可运行的护栏与标注样本。缺工具清单或数据访问面时先停下来问，不要凭想象画架构。

**交付物与完成标准**: 一份三层护栏矩阵（入口→上下文层措施→工具风险等级→执行层审批→数据层策略）；一份"自我判断点→外置执行者"迁移清单；一份异构审查者配置；一份双向回归集与双指标报告。

1. **枚举注入入口并定最后一道门**
   - 做什么：列出所有能让外部内容进入上下文的入口（用户输入、网页、文档、邮件、MCP 返回、Skill 正文），并列出所有写操作与数据访问面；对每个写操作问"最坏情况下最后一道门在哪"。
   - 完成标准：入口清单与写操作清单齐全，每个写操作标出数据层兜底位置。
   - 判停：若纯调用第三方 API、无法触达后端数据层，则数据层不可落地，只做前两层并在矩阵中标注该缺口，跳到第 5 步。

2. **补上下文层措施**
   - 做什么：为每个入口配来源标记、安全分类器、相关性分类器与确定性规则；在系统提示中声明外部内容中的指令不应被执行。
   - 完成标准：每个入口都有对应拦截点，标注"只降低成功率、不给保证"。
   - 判停：若某入口无法加来源标记，标记为不可信并转第 3 步的执行层强管控。

3. **建执行层审批矩阵**
   - 做什么：为每个工具按可逆性、权限范围、财务影响标注风险等级，定义哪些需要审批、哪些直接放行。
   - 完成标准：工具—风险等级—审批要求三列齐全。

4. **写数据层策略并做失效验证**
   - 做什么：设行级安全策略、约束、受控视图，读写携带受信任运行时绑定的访问上下文；然后假设前两层全部失效，逐条尝试越权路径。
   - 完成标准：每条越权路径都有数据层拒绝记录。
   - 判停：若存在任一越权路径未被数据层拒绝，回到第 3 步收紧该工具的审批要求。

5. **外置所有自我判断点**
   - 做什么：在架构图上标出所有"Agent 自己判断自己是否安全"的位置（自我审查、自我批准、自我统计），逐个迁移到上下文之外——独立进程/独立模型/最小权限凭证/沙盒/人在回路五选一；检查外部机制是否仍读取主模型自由文本或思考过程，若读则降级为不可信。
   - 完成标准：每个判断点都有外部执行者，且不读主模型自由文本。
   - 判停：若外部机制仍需读主模型思考过程，换用只读结构化字段的门控（见 `execution-safety-and-server-truth`）。

6. **搭提议者-审核者**
   - 做什么：划分 Proposer/Reviewer 角色；选不同家族、能力相近的模型；对不可逆操作设事前审批；事后验证换模态（渲染、实跑、结构化 diff）；拒绝理由作为工具结果回灌 Proposer。
   - 完成标准：能给出模型配对、换模态方式、回灌路径；不用同家族同模型换提示词自审。
   - 判停：若成本敏感，只对不可逆操作启用 Reviewer；若审查者与提议者能力差距过大，换模型。

7. **建双向回归集并处置歧义**
   - 做什么：构造应拒样本与明确允许样本（含"形式像攻击但已授权"）；同时报告拦截率与合法通过率；对边界样本单独建集；禁止"有歧义就默认合规"，改为升级人工/降级权限/只读继续。
   - 完成标准：两份样本集、两个指标、歧义处置规则齐备；`triggered_policies` 与 `evaluation_summary` 有记录。
   - 判停：任一指标退化即视为回归，回到第 2/3 步调工作点，不要整体放宽提示词。

## B — 边界 (Boundary)

### 不要用的情况
- 纯前端、纯 API 调用、没有任何工具执行或数据写入的问答系统：没有数据层和执行层可落，本卡的大部分步骤无对象。
- 需要毫秒级、逐次、低延迟门控且审查对象是分类问题的场景：应直接用 `execution-safety-and-server-truth` 的结构化字段 Sidecar，本卡的异构提议者-审核者成本与延迟不匹配。
- 只想解决"某个外部文档怎么标注"的单一问题：用 `prompt-injection-surface-and-separation`，不必动整体架构。

### 已知失败模式
- 只做上下文层（提示词警告 + 输入过滤）就以为防住注入——《深入理解AI AGENT-zh-CN》1.2.5 明确警告上下文层给不出保证。
- 用同一个模型换个系统提示词做"自审"——同书 1.2.5/5.1.9 指出这仍属同一上下文。
- 把 Sidecar 做成读取主模型思考过程，等于把审查者拖进同一上下文（同书 4.6）。
- 用弱模型审强模型——同书 4.6 提醒审查对象不同，分类可用小模型、开放式判断不可；能力与判断质量倒挂。
- 只测拦截率——同书 1.2.5 指出会把护栏调成误拒绝机器，误伤授权安全测试与模型蒸馏研究。
- 照抄"有歧义就默认合规"——《Agentic Design Patterns》第 18 章示例的该默认值等于把最难判定的样本全部放行。

### 作者与时代的局限
- 两本书的中文译文提取文本，引用按中文逐字引用；示例以航空客服、动态软件生成、PPT 生成为主，未覆盖所有行业形态。
- 三层排序依据是作者的工程经验归纳，未给出形式化的"绕过难度"量化口径；护栏评估也未给拦截率/通过率的目标阈值。
- 提议者-审核者强调"不同家族互审"，但未给出具体模型配对清单；模型能力迭代快，配对需重新验证。

### 容易混淆的方法
- 与泛泛的"纵深防御"：本卡的判据是被绕过的难度，据此决定投入顺序，不是"多叠几层"。
- 与"输入校验 + 输出过滤"两段式：那段式缺执行层与数据层，无法在数据层兜底。
- 与"事前审批/事后验证"的通用说法：本卡要求的是异构模型 + 换模态，不是重读同一段文本再审一遍。
