# 远程节点寻址与现场部署

## R — 原文 (Reading)

> "Thus, my suggested workflow for putting your Pi on the Internet is to Configure your Pi with a static IP address... Use a dynamic DNS service. Dynamic DNS services are necessary because DHCP is a lease-based protocol."
>
> — 《Hacking Raspberry Pi》Chapter 15, Putting Your Web Server on the Public Internet

## I — 方法论骨架 (Interpretation)

这个能力解决的是"把一台设备部署到现场之后，怎么让它稳定地可被远程连回来"。它看起来只是"配个地址"，但实际上是一个两级寻址问题，外加一次风险前置评估。把这三件事放在一起，是因为缺任何一件，设备都会变成"放出去就失联"的黑盒。

核心机制有三层：

第一级是局域网内地址不能变。端口转发、SSH known_hosts、监控目标、日志源地址都指向一个固定内网地址。如果设备用 DHCP 自动获取，租约一到期地址就可能变，所有指向它的记录随之失效。做法是把 `iface eth0 inet dhcp` 改成 `static` 并补齐 address/netmask/gateway。

第二级是公网入口名不能变。家庭/现场宽带通常是动态公网 IP，ISP 一换 IP，你记住的地址就失效。DDNS 把易变的公网 IP 绑定到一个固定域名，设备或路由器上运行更新客户端，使域名始终解析到当前公网 IP。作者明确点出"动态 DNS 是必要的，因为 DHCP 是租约式协议"——这句话同时适用于两级：租约带来变化，域名/静态地址消除变化。

第三层是暴露代价的前置评估。把设备放到公网意味着被入侵、误泄私数据、被占用带宽。作者要求"先评估再执行"，只开放必要端口，其余关闭。这一步不是合规话术，而是真实施工判断：设备一旦放在公网，攻击面从"局域网内可达"扩展到"全网可达"，代价清单决定了这台设备该不该以这种方式暴露。

为什么这样做：因为远程节点的失联往往不是"设备坏了"，而是"地址变了"。把寻址固化为"静态内址 + 动态公网域名 + 最小端口"三件套，就把一个动态的、易漂移的环境变成了可写进文档的稳定契约。后续的连接、监控、取证都基于这个契约，而不是基于"上次扫到的那个 IP"。

## A1 — 应用示例 (Application Example)

### 示例 1: 作者建议的上公网工作流

- **类型与来源**: 【转述】《Hacking Raspberry Pi》Chapter 15, Putting Your Web Server on the Public Internet
- **问题/输入**: 作者要把一台 Pi 上的 Web 服务放到公网，需要先让它稳定可寻址。
- **方法论的使用**: 按 E 段：先评估暴露代价（被入侵、误泄数据、占用带宽）；编辑 `/etc/network/interfaces`，把 `iface eth0 inet dhcp` 改为 `static` 并补 address/netmask/gateway；注册 DDNS 服务并在设备上运行更新客户端；只开放必要端口。
- **结论**: 静态地址解决内网级漂移，DDNS 解决公网级漂移，两者缺一不可。
- **结果**: 原书以 No-IP / DynDNS 为例给出流程，未给实测数据。

### 示例 2: 【合成演练】现场节点远端失联的定位

- **类型与来源**: 【合成演练】按本卡 E 段规则推演，非原书案例
- **问题/输入**: 一台部署在外地的采集节点，运维记录里写的内网地址是 192.168.1.50，某天 SSH 连不上了；设备物理上仍在现场、电源正常。
- **方法论的使用**: 按 E 段第 1 步的反向检查，先确认设备是否用了静态地址——查 `/etc/network/interfaces` 发现仍是 `dhcp`，说明地址可能随租约漂移；按第 2 步改为静态并确认网段/网关/广播匹配；按第 3 步确认 DDNS 域名仍解析到当前公网 IP；最后只开放必要端口。
- **结论**: "连不上"优先怀疑地址漂移而非设备故障，静态地址 + DDNS 把漂移变成可写进文档的稳定契约。
- **结果**: 这是按规则推演的处置路径，不代表任何真实现场的结果；原书未给该场景案例。

### 示例 3: 【合成演练】把静态地址配错导致失联

- **类型与来源**: 【合成演练】按本卡 E 段"已知失败模式"推演，非原书案例
- **问题/输入**: 把 `iface eth0 inet static` 的网关写成不同网段地址，重启网络后 SSH 断开。
- **方法论的使用**: 按 E 段第 2 步的判停条件，静态地址需保证网段/网关/广播三者匹配；此处网关错误导致路由不可达，需在现场通过本地控制台（而非远程）回改。
- **结论**: 静态地址配错的代价是"直接失联"，作者提醒需具备网络基础再做。
- **结果**: 这是按规则推演的失败路径，未在任何真实现场验证。

## A2 — 触发场景 (Future Trigger)

### 用户会在什么情境下需要它
1. 把一台单板机/采集器部署到无固定 IP 的现场，需要长期从远端连回来管理。
2. 端口转发或监控配置依赖固定内网地址，但设备当前用 DHCP，地址会漂移。
3. 家庭/现场宽带是动态公网 IP，ISP 换 IP 后远端失联，需要一个固定域名兜底。
4. 准备把一台设备暴露到公网，需要先过一遍"代价清单"再决定是否开放端口。

### 语言信号（出现这些就该激活）
- 中文：「设备放外面怎么远程连回来」「DDNS 固定地址」「remote access to deployed node」「IP 老变连不上」「静态 IP 怎么配」
- English: "static IP on deployed node", "dynamic DNS for home server", "remote access to headless device", "ISP changed my IP lost access"

### 与相邻能力的区分
- 与 `device-discovery-exposure-assessment` 的区别：本能力是让设备"可被稳定寻址"，后者是"在网段里找到它"。寻址关心"地址稳不稳"，发现关心"是哪台"。本能力不负责识别设备身份。
- 与 `covert-remote-access-chain` 的区别：后者解决"连回来之后流量怎么出去、保护什么"，本能力解决"怎么连回来"。前者是出口链路，后者是入口寻址。
- 与 `default-creds-minimal-services` 的区别：后者减少/修补服务入口，本能力只让设备"可达"；可达之后的安全由后者负责。

## E — 可执行步骤 (Execution)

**必需输入**: 设备需长期在线；有公网出口或可做端口映射；具备网络基础知识（作者明确要求）；能现场接触设备以在配错时回改。缺"公网出口或端口映射权限"则只完成内网级静态地址，公网 DDNS 步骤不可用。

**交付物与完成标准**: 一份寻址配置（静态内网地址 + DDNS 域名 + 端口白名单）+ 一份暴露代价评估结论。完成标准为"重启后地址不变"、"域名解析到当前公网 IP"、"非必要端口不可达"。

1. **前置评估暴露代价**
   - 做什么：列出被入侵、误泄私数据、被占用带宽三类代价，判断是否能接受。
   - 完成标准：能接受才继续，否则停止公网暴露方案。
   - 判停：若代价不可接受，转为纯内网方案，不执行第 3 步的公网端口开放。

2. **配置静态私网地址**
   - 做什么：编辑 `/etc/network/interfaces`，把 `iface eth0 inet dhcp` 改为 `static` 并补 address/netmask/gateway。
   - 完成标准：重启后地址不变；网段、网关、广播三者匹配。
   - 判停：若网段/网关/广播不匹配导致失联，立即通过本地控制台回改，不要反复远程重试。

3. **注册 DDNS 并运行更新客户端**
   - 做什么：注册 DDNS 服务（书中举 No-IP / DynDNS 为例），在设备上运行更新客户端。
   - 完成标准：域名解析到当前公网 IP。
   - 判停：若 ISP 使用 CGNAT 导致无公网 IP，本步骤不可达，转内网穿透类方案（本书未涉及，需另选工具）。

4. **收敛端口暴露面**
   - 做什么：只开放必要端口，其余关闭。
   - 完成标准：非必要端口从公网不可达。
   - 判停：若某服务确需公网访问但含默认凭据，先转 `default-creds-minimal-services` 修入口再开放。

5. **验证与留痕**
   - 做什么：从外部网络用域名 + 端口连接验证；把静态地址、域名、端口白名单写入运维文档。
   - 完成标准：可稳定连回；文档可被第三方按图复核。

## B — 边界 (Boundary) ★

### 不要用的情况
- 没有公网出口、且 ISP 使用 CGNAT 时，DDNS 无法提供可用的公网入口。
- 设备不需要远程访问时，配置静态地址和 DDNS 是多余复杂度，还可能引入暴露面。
- 现场网络由他人管理、禁止静态地址或端口映射时，本能力的前两步不适用。
- 需要"隐身出口"而非"被连回"时，本能力方向相反，转 `covert-remote-access-chain`。

### 已知失败模式
- **静态地址配错直接失联**（《Hacking Raspberry Pi》Ch15）：网段/网关/广播不匹配导致路由不可达；作者提醒需具备网络基础。
- **暴露代价被低估**（Ch15）：把服务直接暴露公网会引入"恶意用户或程序可入侵"的风险；作者要求先评估再执行。
- **CGNAT 导致 DDNS 失效**：作者时代家庭宽带多有小公网 IP，今天 CGNAT 普遍，按书照做可能域名解析到的是运营商网关而非设备。
- **与内网穿透混淆**：本书只讲静态地址 + DDNS 两条，未涉及反向代理/内网穿透；把两者混谈会导致方案选型错误。

### 作者与时代的局限
- 书中示例基于 Raspbian Wheezy 的 `/etc/network/interfaces`；现代发行版多用 `netplan`/`NetworkManager`/`dhcpcd`，配置路径已变，但"静态内址 + 动态公网域名"的机制不变。
- DDNS 服务商（No-IP / DynDNS）的免费额度与验证策略已变化；今天还可用 Cloudflare DDNS 等，需按实际服务调整。
- 作者未讨论 IPv6、UPnP 自动映射或防火墙/NAT 穿透的现代实践，这些超出本书范围。

### 容易混淆的方法
- **静态私网地址 vs DDNS**：前者固定内网地址，后者把动态公网 IP 绑到固定域名；解决的是两级不同漂移，不能互相替代。
- **DDNS vs 内网穿透**：DDNS 要求有公网 IP，内网穿透不需要；本书只讲前者。
- **可达 vs 安全**：本能力只让设备可达；认证、最小服务、传输加密分别由 `default-creds-minimal-services` 与 `covert-remote-access-chain` 负责。
- **端口开放 vs 端口转发**：静态地址服务于端口转发/记录的稳定性；不区分两者会导致"配了静态地址却忘了在路由器上做映射"。
